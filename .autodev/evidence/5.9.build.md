# 5.9 build report — Mid-session game transition (new game ID, shared session flag)

**Builder:** task builder subagent. **Date:** 2026-10-06.
**Contract:** `.autodev/evidence/5.9.contract.md`. **Branch:** `autodev/logging-instrumentation`.

## Outcome

Implemented PLAN.md §5.9 per the contract: when a new game is started
before Stop (genuine reset detected by the history tracker during an
ACTIVE session), a new game ID is minted, the boundary is preserved via
the `game_reset` event under the old gameId, and the shared recording
session is flagged via `metadata.gameIds.length > 1` (derivable, no new
flag/key).

## What was built

**`session_controls.js`** (additive):

1. **Control variables** (5.9 section):
   - `activeMetadata` / `activeConditions` — retained from the Start
     success path (the records the session was built from). Cleared by
     `setSlots(null, null)` on Stop.
   - `handleGameReset()` — the 8-step ordered transition:
     1. Phase must be ACTIVE, else `{ok:false, error:'not-active'}`.
     2. Metadata/conditions required, else `{ok:false, error:'no-metadata'}`.
     3. Mint UUID-v4 via `BlindfoldSession.newGameId()` (throws → `{ok:false, error:'mint-failed'}`).
     4. `addGameToSession` appends to `metadata.gameIds`; re-persist via
        `session-save` (failure → `{ok:false, error:'session-save-failed'}`,
        old gameId stays).
     5. Recorder re-set with SAME sessionId + new gameId via `set-session`
        (5.5's guard allows same-session re-set; refusal → `{ok:false}`,
        old gameId stays — fail-closed, no rollback).
     6. Slots + `activeGameId` update on success; returns `{ok:true, newGameId}`.
   - Exposed on the install handle as `handleGameReset`.

2. **Start success path**: retains `activeMetadata = metadata` and
   `activeConditions = conditions` after `setSlots(sessionId, gameId)`.

3. **setSlots**: when called with `(null, null)` (Stop), clears
   `activeMetadata`/`activeConditions`.

**`content.js`** (the `/* §5: mint new game identity + install new tracker */` placeholder):

1. **`createGameHistoryTracker(gameId)` factory** — creates the history
   tracker with the same options shape (gameId, emitEvent via sender,
   onGameReset callback). The original inline creation now uses this factory.

2. **`handleGameResetEvent(info)`** — the tracker's genuine-reset callback:
   - Steps 1–2: existing 3.2.6/3.5.2 handling (orphan attempts, record
     `game_reset` under OLD gameId via `gameLifecycleRecorder`).
   - Steps 3–6: calls `sessionControlsHandle.handleGameReset()`; on
     `{ok:false}` returns early (fail-closed, old tracker stays).
   - Steps 7–8: on success, installs a fresh tracker via
     `createGameHistoryTracker(newGameId)`, updates `game` reference,
     calls `resetEnded()` to re-arm the lifecycle recorder.
   - Failure-isolated throughout (3.2 SF-1): never throws into page code.

3. **Bindings changed**: `historyTracker` and `game` from `const` to `let`
   (reassigned only by the 5.9 transition).
