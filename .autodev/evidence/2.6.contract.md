# Task 2.6 Contract — Restore session metadata and stored sequence state after background-worker restart

## 1. Scope

PLAN.md §2.6 says (quoted verbatim):

> 2.6. Restore session metadata and stored sequence state after background-worker restart.

This task makes post-restart recovery of session state **possible and honest**.
It does not add retry (2.5), lifecycle emission (2.7), status UI (2.8),
retention/export (2.9, §6), or content-script changes.

## 2. Honest design decision: what 2.6 adds vs. what is already restart-safe

The architecture as built makes a large part of 2.6 unnecessary **by
construction**. This contract states that explicitly rather than inventing
ceremony:

### 2.1 Sequence state needs no in-memory restore (verified, not assumed)

`writer.js` keeps **no in-memory counter**. Every `writeEvent` transaction
reads `sequence_state` from IndexedDB (`writer.js` lines ~285–288: the
`seqReq` read inside the single `readwrite` transaction over
`['events','sequence_state']`) and writes back `next + 1` in the same
transaction. After an MV3 worker restart the JS context is fresh, but the
first post-restart write reads the durable counter and continues gaplessly.
There is nothing to "restore" into memory — introducing an in-memory
counter plus a restore step would be strictly worse (a new divergence
hazard). The 2.4 contract's no-lock concurrency argument (§2.6) depends on
exactly this property.

**Therefore 2.6 does NOT add any in-memory sequence-state restore.**
What 2.6 adds for sequence state:
- a read-only peek, `getSequenceState(sessionId)`, for 2.7/§6/2.8
  consumers (the writer remains the sole writer — binding invariant
  2.4-§2.6-i, re-verified here);
- **corruption honesty**: the writer treats a missing/non-numeric counter
  as `0` (writer.js ~286–288; flagged in 2.4 review NOTE-2 as silent
  renumbering). 2.6's restore path must NOT repeat that: a present-but-
  malformed `sequence_state` record is **corruption**, surfaced as an
  error, never silently renumbered.

### 2.2 Session metadata: 2.6 defines the storage-layer save/restore pair

Nothing writes `session_metadata` or `conditions` yet (2.4 §2.9 deferred
them to "2.6/§5"). 2.6 owns the **storage contract** for these stores:

- `saveSessionMetadata(record)` / `saveConditions(record)` — validated
  writes (replace semantics);
- `restoreSessionState(sessionId)` — validated read-back of
  `{metadata, conditions, sequenceState}`.

**Boundary with §5:** 2.6 owns the storage primitives (shapes, validation,
replace semantics, corruption reporting). §5 (session controls) owns
**when** they are called (Start/Stop wiring, 5.1–5.10) and the
content-script → SW message wire-up for those calls. 2.6 adds **no new
`onMessage` kinds** — there are no consumers yet, and inventing wire
protocol without the owning task is speculation.

### 2.3 No eager startup self-check (deliberate)

`sw.js` already re-installs the writer listener synchronously on every
start (importScripts + `installWriterListener()` run top-level). An eager
IndexedDB open at every SW wake would tax the writer's hot path (MV3
workers wake frequently) while duplicating what the first write already
does: `DB.openDatabase()` opens lazily and surfaces failure through the
ack → 2.5-retry → 2.8-status chain. Health checking is 2.8/5.6's domain,
not 2.6's. **Restore is on-demand** via the API below.

### 2.4 What "restore" means, concretely

After a restart, any consumer (2.7, §5, §6, 2.8) calls
`restoreSessionState(sessionId)` and gets the durable triple —
validated — or an honest corruption error, or nulls for "never recorded"
(unknown = unknown). The V2 test proves the full loop: write events →
**real SW restart** → restore returns the triple with the correct
counter → further writes continue gapless.

## 3. Exact deliverables

### 3.1 New file: `session_store.js` (repo root)

Section-1 script pattern: guarded `BlindfoldSession` global, IIFE
`'use strict'`, Node `module.exports` shim. SW-side only (content
scripts cannot see the SW origin's IDB); loaded via `importScripts` in
`sw.js`. Reads `BlindfoldSession.DB` and the 1.1/1.2 validators **at call
time, never cached at load** (load-order independence; loads in Node).
No `chrome.*` at load.

Public API (all return Promises; rejections per §3.3):

| Function | Signature | Behavior |
|---|---|---|
| `saveSessionMetadata` | `(record) => Promise<void>` | Validates with 1.1 `requireValidMetadata`; `DB.put('session_metadata', record)`. Replace semantics. |
| `saveConditions` | `(record) => Promise<void>` | Validates with 1.2 `requireValidConditions`; `DB.put('conditions', record)`. Replace semantics. (Merges are the caller's job via 1.2 `applyConditionChange` + save.) |
| `restoreSessionState` | `(sessionId) => Promise<{metadata, conditions, sequenceState}>` | Reads the three stores; validates each present record (§3.2); absent store → `null` for that field. |
| `getSequenceState` | `(sessionId) => Promise<{sessionId, nextAppendSeq} \| null>` | Read-only counter peek. Absent → `null`. Malformed → corruption error. **Never writes** (writer stays sole writer). |

`session_store.js` **never writes** `sequence_state` or `events`
(binding invariant 2.4-§2.6-i/ii, re-verified). It never touches
`media_chunks`.

### 3.2 Validation rules

- `sessionId` argument: non-empty string, else `TypeError`. (No uuid-v4
  enforcement on the read path — keys are opaque; the 1.1 validator
  enforces ID shape at save time via the record itself.)
- Save path: the 1.1/1.2 validators run **before** any IDB access;
  their `TypeError`/`RangeError` propagate unchanged.
- Restore path: each present record is re-validated.
  - `session_metadata` / `conditions` failing validation → corruption
    error (data was written corrupt or by a foreign writer — honest
    failure, not silent accept).
  - `sequence_state` present but not `{sessionId, nextAppendSeq}` with
    `nextAppendSeq` an integer ≥ 0 → corruption error. **Never
    silently renumber** (contrast the writer's `→ 0` fallback, which is
    a write-path wart documented in 2.4 review NOTE-2, not a restore
    semantic).
- Corruption errors are plain `Error` with stable codes, e.g.
  `session-store: corrupt sequence_state for session <sessionId>`,
  `session-store: invalid stored session_metadata`. Session IDs are
  uuid-v4 (non-sensitive); including them is fine.

### 3.3 Tiny additive change to 1.1/1.2 modules (flagged for reviewer)

`requireValidMetadata` (session_identity.js) and `requireValidConditions`
(session_conditions.js) exist but are **not exported**. `session_store.js`
needs them for save/restore validation. The contract authorizes adding
exactly two export lines (one per module), additive only, no behavior
change. Alternative (duplicating validation in session_store.js) was
considered and rejected — it would drift. The reviewer must confirm this
is acceptable against the "don't weaken reviewed modules" rule.

### 3.4 `sw.js` changes

- `importScripts` gains `'session_identity.js'`,
  `'session_conditions.js'`, `'session_store.js'` (order: after
  `'writer.js'`; all are side-effect-free script evaluations).
- Header: remove the `2.6:` line from the intentionally-absent list;
  update the "Loads ..." paragraph to name the session-state module.
- Nothing else. No startup self-check (§2.3). No new listeners.

- [ ] **AC3 (V1).** `saveConditions` validates via the 1.2 validator

      keys, written around the validator via raw `DB.put`) → restore

## 6. Explicit non-goals (builder must NOT)

- Any `onMessage` intake for save/restore (§5 designs the wire-up when
  it wires the Start/Stop UI).
- Retry policy (2.5), lifecycle event types/emission (2.7), status UI
  (2.8), retention/export (2.9, §6).
- Writes to `sequence_state` or `events` (writer is sole writer —
  binding invariant).
- Writes to `media_chunks`.
- An eager IndexedDB health check at SW startup (§2.3 rationale).
- Any in-memory sequence counter + restore step (§2.1 rationale).
- Content-script changes; `sender.js`/`writer.js`/`db.js` changes;
  `manifest.json` changes; `PLAN.md` changes.

## 7. Downstream needs this contract must serve

- §5 calls `saveSessionMetadata`/`saveConditions` at Start (and
  composes `restoreSessionState` + 1.2 `applyConditionChange` + save
  for mid-session condition edits).
- 2.7 calls `restoreSessionState`/`getSequenceState` to detect
  unclean discontinuity (missing end vs. stored state).
- §6 export reads the triple via `restoreSessionState`.
- 2.8 may call `getSequenceState` for storage-health signals.

## 8. Reviewer notes (stress-test these)

- **The "no in-memory restore" claim**: is it airtight? Find any
  writer/SW state that does NOT survive restart and is NOT re-derived
  (hint: `DB.openDatabase`'s `cachedDb` is re-opened; the sender lives
  in the content script, not the SW — out of 2.6's scope by design).
- **The two validator export lines**: acceptable additive change to
  reviewed 1.1/1.2 modules, or should validation be duplicated/avoided?
- **Save-ownership split**: does leaving the message wire-up + call
  timing to §5 create an integration risk (e.g. §5 saving unvalidated
  via raw `DB.put`)? Is the contract's pinning sufficient?
- **Corruption vs. the writer's `→ 0` fallback**: should 2.6 also fix
  the writer to fail the write on a corrupt counter instead of
  renumbering, or is documenting the asymmetry enough?
- **AC10's two-launch technique**: genuinely a "background-worker
  restart" per PLAN 2.6, or does the idle-timeout restart differ in a
  way that matters? (Idle restart keeps the browser profile; the
  two-launch covers browser restart, a superset.)
