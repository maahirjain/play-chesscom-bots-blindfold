### Per-criterion checks (PLAN.md §2.6 + 2.6.contract.md AC1–AC12)

- **No in-memory restore — airtight.** `writer.js` has exactly one
  module-level `var` (the `BlindfoldSession` namespace guard); zero
  mutable module state. Every `writeEvent` reads `sequence_state` from
  IndexedDB inside the single read/write transaction (`seqReq` read →
  `next+1` write-back, same tx) and the listener is re-installed
  synchronously by `sw.js` on every start. `db.js`'s cached handle is
  re-openable lazily. Nothing survives restart that isn't re-derived.
  Introducing an in-memory counter would be strictly worse — the
  contract's §2.1 reasoning holds.
- **session_store.js API + write boundaries.** Exposes exactly
  `saveSessionMetadata`, `saveConditions`, `restoreSessionState`,
  `getSequenceState`. The only `DB.put` calls in the file target
  `session_metadata` and `conditions`; it never writes `events`,
  `sequence_state`, or `media_chunks` (verified by grep + code read).
  `getSequenceState` calls only `DB.get` — a pure read; a peek on an
  absent session leaves the store absent (asserted in tests).
- **Absent → null; malformed → corruption error.** `restoreSessionState`
  returns `{metadata: null, conditions: null, sequenceState: null}` for
  unknown sessions (unknown = unknown, no throw). Present-but-malformed
  `sequence_state` (non-numeric/negative/fractional `nextAppendSeq`,
  missing/mismatched `sessionId`) → plain `Error`
  `session-store: corrupt sequence_state for session <id>`. Invalid
  stored metadata/conditions → `session-store: invalid stored …`.
  Never a silent renumber or silent accept.
- **No new message kinds.** `writer.js` handles only `kind:'event'`;
  `session_store.js` installs no listeners; `sw.js` adds none. §5 owns
  all future save/restore wire-up, per the contract's boundary.
- **sw.js imports the three modules.** `importScripts('db.js',

### Documented deviation (not a failure)

`saveConditions(sessionId, record)` vs the contract's
`saveConditions(record)`: the conditions store's keyPath is `sessionId`
and the 1.2 record has no sessionId field, so a 1-arg form cannot
store. The 2-arg form is documented in code comments, used
consistently by all tests, and keeps the 1.2 domain record pure.
Independently re-verified: the 1.2 validator tolerates the stored
8-field form on restore (validates the 7 fields, ignores the key);
stripped-field records still throw `TypeError`. The adversarial
reviewer approved this as the least-invasive correct fix; I concur.

### The two-launch technique genuinely proves restart recovery

- **Launch 1:** fresh browser, fixed `--user-data-dir`, fixed
  `--load-extension` path. 6 events via the real sender→writer path
  (5 moves + clock_anchor), all delivered; metadata+conditions saved;
  verified durable: 6 events, appendSeq 0..5, counter = 6. Then the
  browser is **fully closed** (`browser.close()` + 2s settle) — the
  process dies; only the on-disk profile survives.
- **Launch 2:** brand-new browser process, same profile + path. The
  harness asserts the SW origin is byte-identical across launches
  (stable extension ID ⇒ same IndexedDB origin — guards against a
  false-positive from a re-keyed extension). `restoreSessionState`
  returns the triple with `sequenceState.nextAppendSeq === 6`;
  metadata and conditions deep-equal the saved records; 4 more events
  → appendSeq gapless 0..9, counter = 10.
- **Corruption phase (AC11):** launch 3 writes a malformed counter
  (`nextAppendSeq: 'corrupted'`) via raw `DB.put`, bypassing
  validators — the way on-disk corruption presents. Launch 4 (fresh
  browser): both `restoreSessionState` and `getSequenceState` reject
  with a corruption error mentioning `sequence_state`; the
  uncorrupted session still restores (counter = 10) — corruption is
  per-session, not global.

This is a **superset** of the MV3 idle-timeout restart: both destroy
the SW's JS context while the profile persists; the two-launch
additionally destroys the browser process. Any state surviving the
two-launch necessarily survives an idle-timeout restart.
