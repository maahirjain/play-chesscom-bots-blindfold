## 3. Contract verification (read the actual code)

### 6.4 — `assembleSegmentChunks` (exporter.js:773)

- **Byte-concatenation in input order:** chunks are processed in the
  input array's order via a chained promise; the contract's "trusts
  6.6's key-order guarantee" is documented in the function comment and
  pinned by AC1.
- **Zero transcoding:** `parts[idx] = chunk.data` — the *original*
  Blob reference is pushed, not a copy. No bytes are added, removed,
  or transformed. The contract's rationale (MediaRecorder chunks are
  byte-appendable; first chunk carries the init segment) is
  documented.
- **CRC-32:** table-driven ISO 3309 (polynomial `0xEDB88320`),
  incremental per chunk (`crc32Update`), finalized with the standard
  XOR (`crc32Finalize`). O(largest chunk) heap, never O(file).
- **Fail-closed:** non-array args → rejected TypeError; missing or
  non-Blob-like `data` → TypeError naming the chunkIndex;
  duplicate `chunkIndex` → TypeError; negative/non-integer
  `chunkIndex` → TypeError. Validation runs synchronously before any
  Blob read, so malformed input never starts partial work.
- **Gaps honest:** no gap detection, no re-indexing — chunks
  concatenate as-is.
- **Empty input:** `{parts: [], byteLength: 0, crc32: 0,
  chunkCount: 0}` (the initial state `0xFFFFFFFF` finalizes to 0).
- **Async shape:** `async` only because `Blob.arrayBuffer()` is
  asynchronous — documented as data access, not architectural I/O. No
  IndexedDB, no clock, no ID minting.
- **Split-piece limitation:** documented in the function comment (no
  init-data fabrication), per the contract §4.1.

### 6.5 — `nameSegmentFiles` (exporter.js:916)

- **Scheme:** `{streamKind}-{NNN}{ext}`, zero-padded to minimum 3
  digits (`padSegmentNumber`), per streamKind. Verified: 1 →
  `microphone-001.webm`, 12 → `microphone-012.webm`, 1000 →
  `microphone-1000.webm` (no truncation).
- **Numbering:** finalized segments use 4.13's `segmentNumber`
  verbatim; nulls get the smallest unused positive integers in 6.3's
  deterministic sort order (`compareSegments`: kind → segmentNumber
  nulls-last → createdAtUtc → segmentId). All-null → chronological
  1..N; mixed → gap-filling (AC3 pins `{1,3}+null` → `002`).
- **Per-kind independence:** the `usedNumbers` set resets on kind
  change (AC4 pins microphone and screen each numbering from 001).
- **Extension resolution:** manifest `fileExtension` (must start
  with `.`) → `actualMimeType` mapping (mirrors
  format_support.js: `video/webm*`/`audio/webm*` → `.webm`,
  `video/mp4*` → `.mp4`, `audio/mp4*` → `.m4a`) → TypeError naming
  the segmentId when both are unusable.
- **Duplicate finalized numbers:** TypeError (builder judgment,
  documented — 4.13 assigns unique numbers; a silent collision would
  violate "never collides").
- **Return shape:** `{files: [{segmentId, filename, streamKind,
  segmentNumber}], bySegmentId}` — `segmentNumber` is the *effective*
  number used in the filename (real or on-the-fly), feeding 6.3's
  `segmentFiles` and 6.6's ZIP entry names.
- **Pure and synchronous.** No I/O, no clock, no ID minting. Inputs
  not mutated (`records.slice().sort(...)`).
