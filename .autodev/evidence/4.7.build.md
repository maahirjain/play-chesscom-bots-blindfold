## What was built

**4.7 is the audio-content policy layer, not acquisition.** 4.6 already
acquires the screen stream's audio wherever the platform offers it; 4.7
classifies what that audio track *can* contain by construction and
writes the classification into the manifest. It acquires nothing new,
builds no mixer, and performs no content analysis (forbidden by the
raw-collection rule).

### New module: `audio_policy.js`

DOM-free, dependency-free, repo module pattern (guarded
`BlindfoldSession` global → IIFE `'use strict'` → Node shim). Pure
classification functions, fully injected inputs — no media APIs:

- `classifyScreenAudio({captureMode, audioTrackPresent})` →
  `'tab-audio' | 'system-audio' | 'none' | null`. Truth table
  (contract §1.1): tab+track → `'tab-audio'` (tab audio only —
  system/extension audio excluded by platform construction);
  screen+track → `'system-audio'` (whatever the OS mixer delivers —
  MAY include game sounds and extension speech IFF the user shared
  system audio; the checkbox is unobservable); either mode without a
  track → `'none'`; unknown/unrecorded mode with a track → `null`
  (never guessed). Wrong types → `TypeError`.
- `assertMicAudio({audioTrackPresent, audioTrackCount})` →
  `'device-only' | null`. `'device-only'` iff an audio track is
  present — structural, because the policy adds no tracks and 4.6
  wires no mixer. `null` when no audio track. Bad
  `audioTrackCount` → `TypeError` (non-integer) / `RangeError`
  (negative).
- Vocabulary constants frozen and exported; `requireScreenAudioContent`
  / `requireMicAudioContent` validators exported for the manifest
  writer (format_support.js resolves them at call time from the shared
  namespace — sender.js precedent; absence is a wiring defect, plain
  Error).

### Wiring

- `stream_starter.js`: new `audioPolicy` opt (injected for tests;
  lazy document-global fallback). `observeTracks` now also returns
  `audioTrackCount`; the screen acquisition threads `captureMode`
  through the acq object. At the manifest-write stage,
  `classifyStreamAudio(kind, acq)` computes the two classifications —
  wrapped so classification can NEVER fail a stream (a policy throw
  yields nulls, V1-pinned). The record and the
  `recorder-start-streams` per-stream response carry both fields.
- `format_support.js`: `MANIFEST_KEYS` deliberately widened 13 → 15
  (`screenAudioContent`, `micAudioContent`, `// 4.7-owned:` comment);
  `recordSegmentFormat` derives them (nullable; the 4.5 call shape
  still defaults to null); `requireValidManifestRecord` validates the
  vocabularies (RangeError on bad values). Exact-keys discipline
  holds — any future widening (4.10/4.12/4.13) must be equally
  deliberate.
- `recorder.js`: `getAudioPolicy()` (same pattern as
  `getFormatSupport()`; throws on wiring defect) passed into
  `createStreamStarter`; exposed on the recorder surface for tests.
  No new channel message, no new event types — the MSG_* vocabulary
  and the nine event names are V1-pinned unchanged.
- `recorder.html`: loads `audio_policy.js` before `stream_starter.js`.
- `.autodev/DECISIONS.md`: new `## 4.7` section (contract AC6) with the
  mode×content matrix, the speechSynthesis routing fact, the acoustic
  bleed reality, and the loopback-device caveat.

### Honesty boundaries (what 4.7 does NOT do)

- No verification of *which* sounds were captured (unobservable
  without analysis; forbidden). The strongest claim about any
  recording's content is the by-construction classification.
- No routing of `speechSynthesis` into a `MediaStream` (the platform
  offers none to an extension offscreen document — not fabricated).
- No echo-cancellation / noise-suppression policy changes to mic
  constraints. No changes to 3.4 speech instrumentation. No
  mode fallback/retry logic (4.3's domain).
