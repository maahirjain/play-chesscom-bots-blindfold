# Task 2.4 Contract — Transactional event writer: dedup by event ID, durable-write acks

## 1. Scope

PLAN.md §2.4 says (quoted verbatim):

> 2.4. Add a transactional event writer that deduplicates by event ID and acknowledges durable writes.

This task implements the **service-worker side of the 2.3 handoff**: it
receives `{kind: 'event', event}` messages, validates the envelope,
deduplicates by `eventId`, assigns `appendSeq` transactionally with the
write, and acknowledges **only after the transaction commits**. It is the
single writer of the `events` and `sequence_state` stores.

Design inputs this contract consumes (not re-decided here):

- 2.3 handoff contract (`.autodev/evidence/2.3.contract.md` §2.6):
  sender→SW `{kind: 'event', event: <frozen 11-key envelope>}`;
  SW→sender `{ok: true, eventId}` (durable write done) or
  `{ok: false, eventId, error: <string>}` (write failed, keep queued).
  The sender never dequeues without a matching positive ack.
- 1.3 contract §2.8: `appendSeq` is `null` at creation; **assignment is
  §2.4's**, at durable-write time. Setting it creates a **new record** —
  never in-place mutation of the frozen envelope (mirrors 1.1's
  `addGameToSession` pure pattern). An event arriving with non-null
  `appendSeq` indicates double-processing; the writer owns that rule.
  Source times (`clockSegmentId`, `monotonicMs`) are never rewritten.
- `event_envelope.js` exposes `isValidEvent(e)` — documented there as
  "Intake validation for §2.4".
- `db.js` (`BlindfoldSession.DB`): `openDatabase()`, `put`, `get`,
  `getAll`, `closeDatabase`; stores `events` (keyPath `eventId`) and
  `sequence_state` (keyPath `sessionId`, holds `{sessionId,
  nextAppendSeq}`). 2.2 deferred multi-operation transactions to this
  task ("§2.4's multi-operation transactions are that task's design").
- DECISIONS.md #9 (binding): (a) `db.js`'s `withStore` resolves on
  request success, **not** `transaction.oncomplete` — the 2.4 writer
  must implement its own commit-awaiting transaction; `DB.put` alone is
  **not** sufficient for the ack path. (b) A record missing its keyPath
  makes `store.put` throw a raw DOMException (DataError) synchronously —
  the writer must wrap or document this surface.
- DECISIONS.md #10: with no SW listener, `sendMessage` rejects — so the
  2.4 listener must always be installed; the ack protocol is what keeps
  the sender's pump moving.

## 2. Design decisions

### 2.1 Module layout: new `writer.js`, thin `sw.js` wiring

- New file `writer.js` at repo root: plain dependency-free script in the
  Section-1 pattern (guarded `BlindfoldSession` global, IIFE
  `'use strict'`, Node `module.exports` shim). It reads
  `BlindfoldSession.DB` and `event_envelope.js` exports **at call time,
  never at load** (the sender.js/db.js lazy pattern), so it stays
  load-order independent and loads in Node with no `chrome` global.
- `sw.js` gains: `importScripts('db.js', 'event_envelope.js',
  'writer.js');` (replacing the bare `importScripts('db.js');`) plus one
  call `BlindfoldSession.installWriterListener();`, and the `2.4:` line
  is removed from the "Intentionally absent" header. Nothing else.
- Rationale for a separate file over inline-in-sw.js: the writer is the
  most logic-dense piece of §2 so far (validation, dedup comparison,
  transaction protocol); it needs its own V1 test surface and its own
  header documenting the 2.5–2.9 boundary. `sw.js` remains a thin
  registration entry point.

### 2.2 Intake: `chrome.runtime.onMessage` listener

```js
// wire-up (thin adapter; all logic in writeEvent):
chrome.runtime.onMessage.addListener(function (message, sender, sendResponse) {
  if (!isEventMessage(message)) return false;   // not ours: ignore, no response
  writeEvent(message.event).then(function (ack) { sendResponse(ack); });
  return true;                                  // async response follows
});
```

- `isEventMessage(m)`: `m` is an object with `m.kind === 'event'`.
  The discriminator value `'event'` is fixed by the 2.3 contract;
  `writer.js` defines its own `MESSAGE_KIND = 'event'` constant citing
  the 2.3 handoff (it cannot read `SENDER_MESSAGE_KIND` — `sender.js`
  is content-script-only and is never loaded in the SW). The V2
  end-to-end test proves the two sides agree.
- Non-`'event'` messages are **ignored** (`return false`, no
  `sendResponse`): other message kinds belong to future tasks; 2.4 must
  not claim them.
- The listener **returns `true`** for `kind: 'event'` so the message
  channel stays open for the async ack. Every `kind: 'event'` message
  gets **exactly one** `sendResponse` call.
- Installation is explicit: `installWriterListener()` (exported) is
  called by `sw.js`. With no `chrome.runtime.onMessage` available it
  throws a **plain Error** (unavailable platform capability — honest
  failure, per AGENTS.md). V1 tests exercise both paths (fake chrome /
  no chrome).

### 2.3 Validation boundary: envelope-level only

The writer validates with `isValidEvent` / `requireValidEvent` (all 11
keys, types, domains) **plus two writer-owned rules**:

1. `appendSeq === null` (1.3 §2.8: non-null indicates
   double-processing; assignment is the writer's exclusive job).
2. `eventId` is a well-formed uuid-v4 (already covered by
   `requireValidEvent`, restated because it is the dedup key).

The writer does **NOT** perform per-event-type payload validation
(`requireValidMovePayload`, etc.). Rationale, all three required:

- Emitters construct payloads with the `create*Payload` factories,
  which validate at construction; re-validating at the writer would
  duplicate every task's contract in one place.
- New event types (2.7 lifecycle types, §3/§4 emitters) must not require
  writer changes — a type registry in the writer would couple every
  future emitter task to this file.
- The writer's PLAN-mandated job is durability + dedup + ordering, not
  semantic refereeing ("preserve original observations", AGENTS.md).

A malformed `kind: 'event'` message (`event` missing/not an object) →
`{ok: false, eventId: null, error: 'malformed-message'}`. The sender
treats `eventId: null` as a mismatch → `'no-ack'`, keeps the event
queued, stops the pump — honest, since a malformed message is a sender
programming error that 2.5's retry will re-attempt, not silently drop.

### 2.4 Dedup semantics

`eventId` is the `events` store keyPath. On intake the writer reads the
store first, inside the write transaction (§2.5):

- **No existing record** → new event: assign `appendSeq`, write (§2.5).
- **Existing record, same content** → idempotent success:
  `{ok: true, eventId}`. The sequence counter is **not** touched (the
  event was already assigned). This is the 2.5 retry-after-lost-ack
  case; re-acking is honest because the data is already durable.
- **Existing record, different content** → corruption signal:
  `{ok: false, eventId, error: 'event-id-content-mismatch'}`. The
  stored record is **never overwritten** (PLAN §2.9 + "preserve original
  observations"). The error string is the durable signal 2.8 will
  eventually surface.

"Same content" = deep-equal on all keys **except `appendSeq`** (the
stored record has the assigned integer; the incoming has `null`).
`writer.js` carries a small recursive deep-equal helper (no
dependencies). Key order is irrelevant to the comparison.

### 2.5 appendSeq assignment: one transaction, commit-awaited ack

Per session, the counter lives in `sequence_state` as
`{sessionId, nextAppendSeq}` (first write for a session starts at `0`).

Protocol — **one `readwrite` transaction over
`['events', 'sequence_state']`**, executed with raw IndexedDB via
`DB.openDatabase()` (NOT `DB.put`/`DB.get`, per DECISIONS.md #9a):

1. `get('events', eventId)` → dedup decision (§2.4).
2. If new: `get('sequence_state', sessionId)` → `next =
   record ? record.nextAppendSeq : 0`.
3. Build the stored record as a **new object**
   (`Object.assign({}, event, {appendSeq: next})` — never mutate the
   intake object; 1.3 §2.8 pure pattern). The intake object arrives
   structured-cloned (unfrozen) but is treated as read-only regardless.
4. `put('events', stored)`; `put('sequence_state', {sessionId,
   nextAppendSeq: next + 1})`. Both `put` calls are wrapped so a
   synchronous DataError (DECISIONS.md #9b — cannot happen for
   validated input, but defended anyway) becomes a transaction abort →
   `{ok: false, ...}` rather than an uncaught throw.
5. Await **`transaction.oncomplete`** → then `sendResponse({ok: true,
   eventId})`. The ack means *committed*, not *request succeeded*.
6. `transaction.onerror` / `onabort` → `{ok: false, eventId, error:
   'write-failed:<name>'}` where `<name>` is the DOMException name
   (e.g. `QuotaExceededError` — the 2.8 signal travels in the error
   string; there is no status UI yet).

Atomicity: counter increment and event write commit or abort together.
A partial failure leaves no trace → the sender keeps the event queued
→ 2.5 retries → dedup (§2.4) makes the retry safe. This
write-then-ack-on-commit ordering is what makes at-least-once delivery
collapse to exactly-once durable state.

Transaction-body discipline (binding on the implementation): between the
first request and `oncomplete`, the code must **not await any non-IDB
promise** (no timers, no fetches, no message passing) — awaiting a
macrotask while the transaction is open lets the browser auto-commit
it early. Only IDB request promises may be awaited inside the body;
microtask hops between requests are safe.

### 2.6 Concurrency: safe without a JS lock

MV3 service workers run single-threaded JS. `onMessage` handlers
interleave only at `await` points. Safety rests on IndexedDB semantics,
not on application locking:

- Two concurrent `writeEvent` calls open two `readwrite` transactions
  over overlapping scopes (`events` + `sequence_state`). IndexedDB
  **serializes** overlapping readwrite transactions: the second
  transaction does not start until the first commits or aborts.
- Therefore the read-modify-write of `nextAppendSeq` cannot interleave:
  the second writer's counter read observes the first writer's
  committed increment. No two events for one session can receive the
  same `appendSeq`, and none can be skipped.

This holds **iff** (binding invariants, recorded for 2.6/§6):

- (i) the writer is the **sole writer** of `sequence_state` (2.6
  restores by *reading* it after restart; it never writes it);
- (ii) the writer is the sole writer of `events` (no other task
  `put`s there);
- (iii) the transaction-body discipline of §2.5 is honored.

V2 must include a concurrency test (rapid concurrent emits for one
session → unique gapless `appendSeq`) because the V1 fake (§3.3) does
not model transaction serialization.

### 2.7 Ack rules (complete)

| Situation | Ack |
|---|---|
| New event, tx commits | `{ok: true, eventId}` — sent from `tx.oncomplete` |
| Duplicate, same content | `{ok: true, eventId}` — after the confirming read (data already durable) |
| Duplicate, different content | `{ok: false, eventId, error: 'event-id-content-mismatch'}` |
| Envelope fails validation | `{ok: false, eventId, error: 'invalid-envelope'}` |
| `appendSeq !== null` on intake | `{ok: false, eventId, error: 'append-seq-present'}` |
| Malformed `kind:'event'` message | `{ok: false, eventId: null, error: 'malformed-message'}` |
| Transaction/request failure | `{ok: false, eventId, error: 'write-failed:<DOMExceptionName>'}` |

Error strings are short stable codes (2.8 will match on them); never
stack traces, never sensitive data. `eventId` echoes the intake's ID so
the sender's stop-and-wait matching works; it is `null` only when no ID
could be extracted.

### 2.8 Error conventions (AGENTS.md)

- `writeEvent(nonObject)` / `installWriterListener` misuse → `TypeError`
  (programmer-facing shape errors, thrown synchronously where the call
  is synchronous).
- Wire-data domain failures (bad envelope, double-processing,
  content-mismatch, write failures) → `{ok: false, ...}` acks, **never
  throws**. The writer never throws for data that arrived over the
  message channel; the ack is the error channel.
- `installWriterListener()` with no `chrome.runtime.onMessage` →
  plain `Error` (unavailable platform capability).
- Unavailable `indexedDB` at write time → `{ok: false, eventId, error:
  'write-failed:unavailable'}` (via `DB.openDatabase()`'s plain-Error
  rejection, mapped into the ack — the sender keeps the event queued).

### 2.9 Stores the writer does NOT touch

- `session_metadata`, `conditions`: written by later session wiring
  (2.6/§5 own that design — 2.6 restores them, so something must save
  them, but it is not this task). The writer never reads or writes
  them.
- `media_chunks`: §4/§6 own chunk intake and assembly; the event writer
  never touches this store.

## 3. Exact deliverables

### 3.1 New file: `writer.js` (repo root)

- Header comment: what the module is (SW side of the 2.3 handoff),
  the intake/validation/dedup/appendSeq/ack design in brief, what is

  `appendSeq !== null` → `{ok:false, eventId,
  error:'append-seq-present'}`; else the §2.5 transaction
  (dedup → counter → puts → await `oncomplete` → `{ok:true,

### 3.3 New test: `tests/writer.test.js` (`node --test`, no framework)

dependency-free — no `fake-indexeddb`). The fake must support, at
minimum:

- `open(name, version)` consuming the real `DB.SCHEMA` (proves the
  writer works against the actual schema — schema drift breaks here);
- `db.transaction(storeNames, mode)` with `objectStore(name)`,
  `oncomplete`/`onerror`/`onabort`;
- `store.get(key)` / `store.put(record)` as fake requests with
  `onsuccess`/`onerror` and `.result` / `.error`;
- string keyPath extraction (the writer only uses `events` and
  `sequence_state`, both string-keyed);
- failure injection: a flag making the next `put` fail (atomicity
  test), and observability of whether `oncomplete` fired before the
  ack was produced (commit-awaiting test).

Documented fake limits (in the test file header): the fake does **not**
model overlapping-transaction serialization — the concurrency argument
(§2.6) is verified in V2 against real IndexedDB.

Test hygiene: `closeDatabase()` + fresh fake per test (db.js caches
the handle).

Cases (map to AC1–AC11):

- Module loads in Node with no `chrome`; exports `writeEvent`,
  `installWriterListener`; static: no `chrome.*`/`localStorage` at
  load (string checks excluding the header's own mentions).
- `writeEvent` non-object → `TypeError`.
- Malformed `kind:'event'` messages → `{ok:false, eventId:null,
  error:'malformed-message'}`; nothing written.

  `{ok:false, eventId, error:'invalid-envelope'}`; stores untouched.
- `appendSeq: 7` on intake → `{ok:false, error:'append-seq-present'}`.
- New event → stored with `appendSeq: 0`; `sequence_state` =
  `{sessionId, nextAppendSeq: 1}`; ack `{ok:true, eventId}` produced

- Duplicate different-content (flip one payload field) →
  `{ok:false, error:'event-id-content-mismatch'}`; stored record
  unchanged.
- Injected put failure → nothing in `events`, counter not advanced,
  `{ok:false, error:'write-failed:<name>'}`.
- `installWriterListener` with fake `chrome.runtime.onMessage`:
  `kind:'event'` → returns `true`, exactly one `sendResponse` with

## 6. Explicit non-goals (builder must NOT)

- Retry timers/backoff/policy (2.5) — only the ack protocol both sides
  already speak.
- Restart restore (2.6) — the writer only *writes* `sequence_state`;
  2.6 reads it back.
- Lifecycle event types/emission (2.7); status-indicator UI (2.8 —
  only error strings in acks); retention/export (2.9, §6).
- Writes to `session_metadata`, `conditions`, or `media_chunks`
  (owned by 2.6/§5 session wiring and §4/§6 respectively).
- Per-event-type payload semantic validation.
- Any content-script change (`sender.js`, `content.js` untouched);
  any Section-1 module change; `PLAN.md` change.
- Manifest changes beyond none — `manifest.json` is byte-identical
  (the SW file list does not appear in the manifest).

## 7. Downstream needs this contract must serve

- 2.5 consumes the ack protocol: `{ok:true}` → dequeue; `{ok:false}` /
  no-ack → keep queued and retry. The stable error codes
  (`invalid-envelope`, `append-seq-present`,
  `event-id-content-mismatch`, `write-failed:<name>`,
  `malformed-message`) are 2.5/2.8's vocabulary.
- 2.6 reads `sequence_state` (and `session_metadata`) after SW
  restart — the writer's sole-writer invariant (§2.6-i) is what makes
  the restored counter trustworthy.
- 2.7's lifecycle events and §3/§4 emitters flow through this same
  intake unmodified (no per-type registry to update).
- §6.2 reads `events` in `byAppendSeq` order — the writer is what
  makes that order gapless per session.

## 8. Reviewer notes (stress-test these)

- **Validation boundary**: envelope-level only, no per-type payload
  checks (§2.3). Principled scope decision or gap? Consider: could a
  malformed payload corrupt §6 export, and whose job is it to prevent
  that?
- **Metadata exclusion**: `session_metadata`/`conditions` writes are
  deferred to 2.6/§5 (§2.9). Does 2.4 leave a hole (events written for
  sessions with no metadata), or is the boundary correct?
- **Concurrency**: the §2.6 no-lock argument rests on IDB
  serialization + sole-writer invariants. Poke holes: what breaks if
  2.6 or §6 ever writes `sequence_state`? What if a future task adds
  a second writer path?
- **V1 fake fidelity**: the in-memory fake does not model
  transaction serialization — AC13 (V2) is the backstop. Is the
  fake's surface (§3.3) sufficient for AC1–AC11, or does it risk
  testing the fake instead of the writer?
- **install-time failure**: `installWriterListener` throws plain
  `Error` with no chrome — right call, or should `sw.js` tolerate it?
- **Ack-before-commit risk**: trace every code path and confirm no
  path can `sendResponse({ok:true})` before `oncomplete`.
