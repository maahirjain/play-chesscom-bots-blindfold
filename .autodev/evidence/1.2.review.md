## SHOULD_FIX

### SF-1. `playerColor: <non-string>` throws TypeError, contradicting the contract's own 1.1 anchor and AC6's "anything else → RangeError"

**Files:** `session_conditions.js` (`normalizePlayerColor`, ~lines 108–117);
`tests/session_conditions.test.js` (AC6 test, "wrong-typed value is a shape
error" comment); `.autodev/evidence/1.2.build.md` ("One test bug fixed").

**Reasoning.** The contract §3.1 error-convention table states:
`RangeError` = "value outside an allowed domain (bad source, bad color,
unknown field name — **consistent with 1.1's `sessionCategory` →
`RangeError`**)". I verified 1.1's actual behavior in
`session_identity.js`: `isSessionCategory` is a membership predicate
(`typeof s === 'string' && SESSION_CATEGORIES.indexOf(s) !== -1`), and
`requireValidMetadata` throws **RangeError** for `sessionCategory: 1`
(a number). So 1.1 collapses wrong-typed domain values into RangeError —
the exact consistency model the contract cites for "bad color".

The 1.2 implementation routes `playerColor` through
`normalizeConditionString` first, whose type gate throws **TypeError** for
non-strings (verified: `playerColor: 1` → TypeError). This is a *different*
model than 1.1's. The build report's claim — "per the contract's error
conventions a wrong-typed value is a TypeError" — does not survive the
1.1 mirror check the contract itself invokes.

Worse, the original test asserted RangeError (matching AC6's literal "…
anything else (incl. `'White'`, `'w'`) → `RangeError`"), the implementation
disagreed, and the **test was changed to match the implementation** with
the justification "implementation was already correct". That is precisely
the "test mirrors implementation" failure mode the mission warns about,
and the prose justification papers over a genuine ambiguity rather than
resolving it through the contract's stated precedent.

**Fix (small, no ripple):** make `normalizePlayerColor` null-check, trim
strings, then apply membership → RangeError for anything not
`'white'`/`'black'` (including non-strings). This preserves the trimming
behavior (`' white '` → `'white'`) and the 1.1 mirror. Note
`normalizeBotRating` is unaffected: the contract *explicitly* assigns
TypeError to floats/negatives/numeric strings (AC7), so that asymmetry is
contract-mandated, not a defect.

### SF-2. `__proto__` assistance-setting key is silently dropped

**File:** `session_conditions.js` (`normalizeAssistanceSettings`, the
`out[key] = val` assignment loop).

**Reasoning.** Keys are user-controlled (the §3.3 key inventory is
unknown). Verified with Node:

```js
B.normalizeAssistanceSettings({ '__proto__': true, legit: 1 })
// → own keys: ['legit'] — the '__proto__' key silently vanishes
```

The assignment hits the inherited `__proto__` setter instead of creating
an own property. For a data-collection contract whose core ethos is
"never silently drop observations," silent key loss is the wrong failure
mode. Realistic risk is near zero (no DOM audit will produce a literal
`__proto__` setting), but the fix is trivial: build `out` with
`Object.create(null)` (then freeze), or reject `__proto__`/`constructor`/
`prototype` keys explicitly. Also note the output object's prototype was
observably perturbed in the probe — a second reason to use a
null-prototype accumulator.

## NOTES

### N-1. Free-form strings for training approach / verbal scaffolding: faithful, not a dodge

Stress-tested contract §2.3 against PLAN.md text. PLAN §1.2.1 says "Store
the selected training approach and verbal scaffolding level" — "store",
not "classify". §5.2 calls them "**fields**". §3(b) steps 5–6 describe
gradually reducing scaffolding with no numbered scale or named stages
anywhere in the document. An enum (e.g. `['full','reduced','none']`)
would invent a taxonomy the owner never specified and freeze an evolving
personal practice — exactly the silent specification change the mission
forbids. Free-form strings preserve original inputs verbatim, which is the
raw-collection mandate. The decision holds.

### N-2. All-seven-fields-required does not conflict with any realistic §5.4 flow

§5.4 ("show detected game conditions and allow manual completion of
unavailable fields") is fully servable: unknown fields are
`{ value: null, source }`, and the source dichotomy is genuinely
exhaustive — detection attempted and found nothing ⇒ `'observed'`; user
left blank / remembered default (§5.3, origin stays `'manual'`) ⇒
`'manual'`. Composite edge (assistanceSettings partially detected) is
handled per-key with `{ name: null }` for unreadable values. The contract
already flags the theoretical gap in §8 for coordinator judgment; nothing
in §5.2–§5.4 requires a third source state.

### N-3. Rejecting extra input keys is within contract latitude (builder deviation 1)

AC4 requires the *record* to contain exactly the seven keys. For extra
*input* keys the options are reject-loudly or drop-silently; silent
dropping risks real data loss (e.g. a `botname` typo vanishing), which is
worse under this mission's ethos. Rejection is stricter, not weaker, and
is recorded in the build report. Recommend also recording it in
`.autodev/DECISIONS.md` for durability, since it's a behavioral choice
future UI work (§5.2/§5.4) must know about.

### N-4. `undefined` assistance-map values coerce to `null` rather than throwing

Contract §2.7 says values are `boolean | string | number | null` and "a
known setting with an unreadable value is `{ name: null }`". Treating
`undefined` as unreadable → `null` is consistent with AC13's
null-tolerance spirit. Defensible; documenting here so a future strict
reader doesn't mistake it for drift.

### N-5. Test header claims AC19 coverage; no in-suite test performs it

The header says the suite covers "AC1–AC2, AC4–AC17, AC19–AC21", but AC19
(`session_identity.js` byte-identical) is verified only by the build
report's mechanical `git diff --exit-code` step — I re-ran it and it is
clean. Either add a hash/pinned-content check to the suite or correct the
header to say AC19 is covered by mechanical verification, not the suite.

### N-6. "API surface only" test checks presence, not absence

The test named "exports the contract-specified API surface only" asserts
each expected name exists but never asserts no *extra* exports exist.
The implementation does export exactly the 13 contract names (verified by
reading the export block), so this is a test-strength nit, not a code
defect. Suggest `assert.deepEqual(Object.keys(BlindfoldSession).sort(),
expected.sort())`.

### N-7. Whitespace-only assistance keys (e.g. `' '`) are accepted

`' '` passes the non-empty-string key check. Trivial; raw-preservation
ethos tolerates it. Mentioned for completeness.
