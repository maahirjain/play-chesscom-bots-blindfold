# Task 1.1 Contract — Define session and game identity

PLAN.md §1.1 (1.1.1–1.1.3). Read by planner/investigator 2026-10-06.
Source of truth: `PLAN.md` (unchanged). Related: PLAN §1 context, §2–§6 (downstream), §3(a)/(b)/(c).

## 1. Scope

Task 1.1 defines **identity and identity metadata only**: how session IDs and
game IDs are generated, what they look like, and the exact metadata record
that carries schema/extension/protocol versions plus session category.
It defines the *factories and constants*; it does **not** wire the Start
button (§5.1, later), detect games (§3.1/§3.5, later), persist anything
(§2.2, later), or export anything (§6, later).

## 2. Design decisions (investigator-verified)

### 2.1 ID format: UUID v4 via `crypto.randomUUID()`

- `crypto.randomUUID()` returns an RFC 4122 v4 UUID: `8-4-4-4-12` lowercase
  hex, version nibble `4`, variant nibble `8/9/a/b`. Verified in Node 24:
  100,000 generations unique; shape regex passes; `globalThis.crypto.randomUUID`
  is a function.
- 122 bits of entropy ⇒ collision probability negligible across all
  sessions/exports; **no counter or sequence number is persisted** — PLAN §3(a)
  is explicit: "Dates and sequence numbers are illustrative; unique IDs
  establish identity."
- Available in every target context (all secure): content-script isolated
  world (`window.crypto`), extension service worker (`self.crypto`), Node
  test env (`globalThis.crypto`).
- **No silent fallback.** If `crypto.randomUUID` is unavailable the factory
  throws. Fabricating IDs from `Math.random` would silently weaken uniqueness
  and violate the "do not weaken requirements" rule. A throw is honest
  evidence of an environment problem.

### 2.2 Sharing between content scripts and the future MV3 service worker

- Deliverable is one dependency-free plain (non-module) script,
  `session_identity.js` at repo root, exposing a single global namespace
  `BlindfoldSession` (guard: `var BlindfoldSession = BlindfoldSession || {};`).
- Content scripts: loaded via the existing `manifest.json` `content_scripts`
  `js` array (all files in one registration share the global scope).
- MV3 service worker (added by §2.1): loaded via `importScripts('session_identity.js')`
  — supported in extension service workers.
- Node tests: conditional shim at the end —
  `if (typeof module !== 'undefined' && module.exports) module.exports = BlindfoldSession;`
- The module is **chrome\*-independent**: it takes `extensionVersion` as a
  parameter. Call sites (future §2/§5 code) obtain it via
  `chrome.runtime.getManifest().version`. This keeps the contract pure and
  unit-testable in Node (`node --test`), consistent with DECISIONS.md
  (dependency-free, `node --test` for pure logic).
- ES modules were rejected: mixing module/plain registration across content
  scripts and the service worker adds load-order and `"type": "module"`
  registration risk for zero benefit at this stage. Revisit only if a later
  task demonstrates a real need.

### 2.3 Extension version source

`chrome.runtime.getManifest().version` → currently `"1.0.0"` (manifest.json).
The contract accepts the version as an injected string (required, non-empty,
trimmed); it never reads `chrome.*` itself. No version is ever guessed or
hardcoded in the call path.

### 2.4 Session categories

Derived from PLAN.md §1 context ("record three strict blindfold baseline
games… training… periodically repeat standardized blindfold evaluations"),
§3(b) flow (baseline → training → evaluation), §3(a) directory layout
(`baseline/`, `training/`, `evaluation/`), and §5.2 ("baseline/training/
evaluation selection"):

```js
SESSION_CATEGORIES = Object.freeze(['baseline', 'training', 'evaluation']);
```

The category is chosen by the user at session start (§5.2, later); task 1.1
only validates and stores it. Any other value throws `RangeError`.

### 2.5 Protocol version vs schema version (precise definitions)

- **schemaVersion** — version of the *data contract* owned by this codebase:
  the field layout/semantics of `metadata.json`, `events.jsonl`, and
  `media-sync.json` as defined across PLAN §1. Owned by the extension code.
  Initial value: `"1.0.0"` (`SCHEMA_VERSION` constant). Bump when the stored
  format changes.
- **extensionVersion** — the extension build that collected the session,
  from `manifest.json` (`chrome.runtime.getManifest().version`).
- **protocolVersion** — version identifier of the **user-maintained
  experiment protocol document** (PLAN §3(b): "Write down strict
  baseline/evaluation rules… The recorder logs deviations but does not enforce
  these rules"; §3(a) table: metadata.json carries "protocol/schema/extension
  versions"). It is NOT the extension↔storage messaging protocol. It is a
  human-set string (e.g. a date or version of the user's protocol notes) or
  `null` when unknown — never guessed, never `""` (empty normalizes to `null`).
  The UI to set it comes later (§5.2/§5.4); task 1.1 only defines the field.

### 2.6 Session ↔ game relation

- 1.1.1: one session per Start click. 1.1.2: one game ID per *detected* game;
  "use one game per recording session in the normal workflow" (PLAN 1.1.2).
- PLAN §5.9 requires: if a new game starts before Stop, assign a **new**
  game ID, preserve the boundary, and flag the shared recording session.
  Therefore the metadata record holds an **ordered array** `gameIds`; length
  > 1 implicitly marks a shared-recording session — no extra flag (derivable).
- Game *detection* wiring is §3.1/§3.5 (later). Task 1.1 provides
  `newGameId()` and `addGameToSession()`; detection calls them later.
- Duplicate-Start prevention (§5.5) is later lifecycle work; the factories
  are pure so §5 can own the "session in progress" state.

### 2.7 Storage-safety

The metadata record contains only plain JSON values (strings, arrays, null)
so it is structured-clone/IndexedDB-safe when §2.2 stores it.

## 3. Exact deliverables

### 3.1 New file: `session_identity.js` (repo root)

Plain script, no dependencies, global `BlindfoldSession` (+ Node
`module.exports` shim). Contents:

| Export | Type | Behavior |
|---|---|---|
| `SCHEMA_VERSION` | frozen string `"1.0.0"` | Data-contract version |
| `SESSION_CATEGORIES` | frozen array `['baseline','training','evaluation']` | Allowed categories |
| `UUID_V4_RE` | frozen RegExp | `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/` |
| `newSessionId()` | `() => string` | `crypto.randomUUID()`; throws if unavailable |
| `newGameId()` | `() => string` | `crypto.randomUUID()`; throws if unavailable |
| `isUuidV4(s)` | `(any) => boolean` | `typeof s === 'string' && UUID_V4_RE.test(s)` |
| `isSessionCategory(s)` | `(any) => boolean` | membership in `SESSION_CATEGORIES` |
| `normalizeProtocolVersion(v)` | `(any) => string \| null` | trimmed non-empty string → itself; `null`/`undefined`/`""`/whitespace-only → `null`; non-string non-null → `TypeError` |
| `createSessionMetadata({extensionVersion, sessionCategory, protocolVersion})` | `(object) => SessionMetadata` | validates inputs, generates `sessionId`, returns fresh record (see 3.2) |
| `addGameToSession(metadata, gameId?)` | `(SessionMetadata, string?) => SessionMetadata` | validates `metadata` shape and `gameId` (generates one if omitted); returns a **new** record with `gameId` appended to `gameIds`; original untouched |

### 3.2 JSON shape: `SessionMetadata`

Exact keys — no more, no fewer:

```json
{
  "sessionId": "43f267dd-c44d-42ee-b99d-5537c5a4f95e",
  "gameIds": ["9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"],
  "schemaVersion": "1.0.0",
  "extensionVersion": "1.0.0",
  "protocolVersion": null,
  "sessionCategory": "baseline"
}
```

Field types: `sessionId` uuid-v4 string; `gameIds` array of uuid-v4 strings
(possibly empty at construction — a game is *detected* later; the first
`addGameToSession` call populates it); `schemaVersion`/`extensionVersion`
non-empty strings; `protocolVersion` string or `null`; `sessionCategory` one
of the three categories.

Rationale for allowing empty `gameIds` at construction: session identity is
created at Start (§5.1, later) while game detection (§3.1/§3.5, later) may
lag; fabricating a game ID before a game is detected would violate
"do not infer that something happened when only weaker evidence was
observed."

### 3.3 New file: `tests/session_identity.test.js`

`node --test` suite covering every acceptance criterion below that is
V1-verifiable. No test framework dependency (per DECISIONS.md).

## 4. Acceptance criteria

### 1.1.1 — unique session ID at Start

- [ ] **AC1** `newSessionId()` returns strings matching `UUID_V4_RE` (version
      nibble `4`, variant `8/9/a/b`, lowercase). *Verify now (V1): unit test
      asserts shape + bit positions over ≥1,000 samples.*
- [ ] **AC2** 100,000 generated session IDs are all distinct. *Verify now
      (V1): unit test (runs in <2 s in Node 24, measured).*
- [ ] **AC3** Generation uses `crypto.randomUUID`; if `crypto.randomUUID` is
      unavailable the factory throws (no `Math.random` fallback). *Verify
      now (V1): unit test with `globalThis.crypto` stubbed to undefined
      (save/restore); asserts throw.*
- [ ] **AC4** A fresh session ID is created for each new session (at Start
      click). *DEFERRED — depends on §5.1 Start/Stop control. Builder
      delivers `createSessionMetadata` as the pure factory the Start handler
      will call; wiring + duplicate-Start prevention (§5.5) are §5 work.
      Recorded in evidence as deferred with dependency.*

### 1.1.2 — unique game ID per detected game

- [ ] **AC5** `newGameId()` produces UUID v4 with the same guarantees as AC1–
      AC3 (independent function, not an alias, so the streams stay separable
      in review). *Verify now (V1): unit tests.*
- [ ] **AC6** `addGameToSession` appends a new game ID to `gameIds` in order,
      never mutates the input record, never alters existing entries, rejects
      non-uuid game IDs with `TypeError`. *Verify now (V1): unit tests
      incl. immutability (deep-freeze input) and rejection cases.*
- [ ] **AC7** Normal workflow yields exactly one entry in `gameIds`; a second
      detected game appends a second distinct ID (shared-recording session,
      §5.9) rather than replacing or mixing histories. *Verify now (V1) for
      the pure function; the §5.9 boundary flag behavior is deferred to §5.9.*
- [ ] **AC8** Game IDs are assigned on game *detection*. *DEFERRED — depends
      on §3.1/§3.5 game detection. Builder delivers `newGameId`/
      `addGameToSession`; detection wiring is later. Recorded as deferred
      with dependency.*

### 1.1.3 — metadata fields

- [ ] **AC9** `createSessionMetadata` returns exactly the six keys in §3.2 —
      no more, no fewer — with correct types. *Verify now (V1): unit test
      asserts `Object.keys` exact set + per-field type checks.*
- [ ] **AC10** `schemaVersion` equals the frozen `SCHEMA_VERSION` (`"1.0.0"`)
      and cannot be overridden via options. *Verify now (V1): unit test;
      options object has no schemaVersion parameter.*
- [ ] **AC11** `extensionVersion` is the caller-supplied value (future call
      sites: `chrome.runtime.getManifest().version`); missing/empty/non-string
      → `TypeError`. The module itself never touches `chrome.*`. *Verify now
      (V1): unit test with injected values. Live manifest wiring is §5.1
      integration (deferred).*
- [ ] **AC12** `protocolVersion` semantics per §2.5 (user-maintained
      experiment protocol version); `normalizeProtocolVersion` maps
      `null`/`undefined`/`""`/whitespace → `null`, trims real strings,
      rejects non-strings with `TypeError`; the stored value is never `""`.
      *Verify now (V1): unit tests.*
- [ ] **AC13** `sessionCategory` must be one of `SESSION_CATEGORIES`;
      anything else (incl. case variants like `"Baseline"`) → `RangeError`.
      *Verify now (V1): unit tests.*
- [ ] **AC14** No derived/persisted extras: no sequence numbers, dates, SAN,
      PGN, FEN, move numbers, durations, or counts in the record (PLAN §3(a):
      "unique IDs establish identity"; "Do not persist those derived
      products"). *Verify now (V1): key-set test + adversarial review.*
- [ ] **AC15** Unknown stays unknown: `protocolVersion` defaults to `null`;
      nothing is guessed. *Verify now (V1): default-value test.*
- [ ] **AC16** Record is plain-JSON/structured-clone safe (strings, arrays,
      null only). *Verify now (V1): `structuredClone` round-trip test in
      Node 24.*
- [ ] **AC17** Module loads as a plain script (content-script pattern),
      via `importScripts` (future §2.1 service worker), and under Node via
      the `module.exports` shim. *Verify now (V1): Node require test +
      static check that the file declares no `import`/`export` and exactly
      one guarded global. Actual SW `importScripts` loading is deferred to
      §2 integration.*

## 6. Explicit non-goals (builder must NOT)

1. No Start/Stop UI or click wiring (§5.1) — only the factory it will call.
2. No game-detection logic (§3.1/§3.5) — only the ID factories.
3. No session conditions (1.2), event envelope/time (1.3), FEN/moves (1.4).
4. No IndexedDB, service worker, or event sender (§2) — no persistence code.
5. No export/ZIP/metadata.json assembly (§6) — §6.1 consumes this shape later.
6. No sequence numbers, dates-as-identity, or folder-path logic.
7. No analysis, metrics, derived values (SAN/PGN/FEN/move numbers/durations).
8. No changes to `content.js`, `chess_utils.js`, `sounds.js`, `manifest.json`,
   or any existing gameplay behavior (REGRESSIONS.md invariants untouched).
9. No edits to `PLAN.md`.
10. No fallback ID generator weaker than UUID v4; no `Math.random` IDs.
11. No credentials, no network calls, no Chess.com interaction.
12. Do not update `.autodev/STATE.json` (coordinator-owned).

## 7. Downstream needs this contract must serve (from §2–§6 skim)

- §2.2: record stored in IndexedDB → plain-JSON constraint (AC16).
- §2.6: session metadata restored after SW restart → record must be
  self-contained and revalidatable with `isUuidV4`/`isSessionCategory`.
- §3: every event references `sessionId`/`gameId` (1.3.1 envelope, later task).
- §5.1/§5.5: Start creates via `createSessionMetadata({extensionVersion:
  chrome.runtime.getManifest().version, sessionCategory, protocolVersion})`.
- §5.9: second detected game → `addGameToSession(record)`; `gameIds.length>1`
  ⇒ shared recording session.
- §6.1/§6.6: export path uses `sessionCategory` + game ID
  (`<category>/…/…_<gameId>/`); folder dates/sequence numbers stay illustrative.
- Reviewer attention: AC14/AC15 are the likeliest weakening points — watch for
  "helpful" extras (timestamps, counters, normalized categories) creeping into
  the record.
