# Task 4.11 contract — audible and visible sync markers at session start and stop

PLAN.md §4.11: "Add a visible/audible synchronization marker at session
start and stop and save its source timestamps."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.11 is (one paragraph)

4.6 starts each stream at its own actual time (not simultaneous), 4.10
links every segment to its clock anchor, and 4.12 will compute
per-stream offsets — but offsets need a shared observable reference
point. **4.11 inserts one synchronization marker per recording
generation at start AND at stop** (PLAN requires both ends; §7.9
verifies "markers align with event timestamps at both ends of a
recording"). Each marker has two modalities: **audible** (a tone played
through the speakers — captured acoustically by the mic) and **visible**
(a brief fullscreen flash on the Chess.com page — captured by the
screen recording). Each modality emission is timestamped at its source
and saved as a `sync_marker` event sharing one `markerId`, so 4.12 can
align each stream's media against the event log per modality. 4.11
builds the mechanism, wires the START marker into the start-streams
flow, and defines the exact seam 4.13 must call for the STOP marker
(4.13 is not built yet — the section-4 auditor must verify 4.13 wires
it).

## 1. Marker purpose

Post-hoc cross-stream alignment. Each stream has its own recorder,
its own actual start time (4.6), and its own media timeline. The marker
is a single real-world occurrence — a beep you can hear, a flash you
can see — with a precisely recorded emission time. Later (§6/§7, using
4.12's offsets): the beep's onset in the mic recording at media-time
T_mic vs the marker event at event-time T_evt gives the mic offset;
the flash's onset in the screen recording gives the screen offset. One
marker per phase per generation; the two modalities share a `markerId`
but carry their own source timestamps (they occur milliseconds apart —
different message latencies — and 4.12 aligns per modality, which is
more precise than a single blurred timestamp).

"Generation" = one start-streams → stop cycle. A session (§5) may
contain multiple generations (offscreen restart → 4.9's `restart`
discontinuity → new segmentIds). Each generation gets its own start
marker and stop marker with fresh `markerId`s.

## 2. Audible marker mechanics

- **What:** a short sine tone. Start = **one** beep; stop = **two**
  beeps 150 ms apart (human-distinguishable at both ends; the event's
  `phase` disambiguates regardless).
- **Spec:** 880 Hz sine (A5 — distinct from Chess.com's move
  click/pop sounds), 250 ms per beep, 44.1 kHz 16-bit mono WAV, 10 ms
  raised-cosine fade in/out (no clicks). File: `sync_beep.wav` at the
  extension root, generated deterministically by the builder (Python
  `wave` module — no binary blobs committed opaquely; the generation
  command is recorded in the build report).
- **Where it plays:** the **offscreen document**, via
  `new Audio(chrome.runtime.getURL('sync_beep.wav'))` — the same
  pattern as `sounds.js`'s `illegal_move.wav`. Rationale: the offscreen
  document is the dedicated recording context (4.1) that survives page
  refreshes; the tone must survive them too. The 4.1 manifest already
  grants the offscreen document `AUDIO_PLAYBACK`. Extension pages load
  their own packaged resources without `web_accessible_resources`.
- **NOT a mixer (4.7 re-pin):** the tone is played into the room
  through the speakers — acoustic, like 4.7's bleed reality. Nothing
  is routed into any `MediaStream`. Implementation uses
  `HTMLAudioElement` only: **no `AudioContext`, no
  `MediaStreamDestination`, no `AnalyserNode`** — the 4.7 code-scan pin
  over offscreen scripts passes UNMODIFIED. The contract states this
  explicitly so a future reader never confuses playback with mixing.
- **Honest capture matrix:** the mic captures the beep acoustically
  (speaker → mic, same path as 4.7's bleed); the screen stream
  captures it iff system-audio is shared (screen mode) — never in tab
  mode (the tone is not tab audio); the webcam stream is video-only
  and never carries it.

## 3. Visible marker mechanics

- **What:** a brief fullscreen white flash on the Chess.com page:
  fixed overlay, `#fff`, opacity 0→1→0 over ~200 ms,
  `pointer-events: none`, `aria-hidden="true"`, `z-index: 2147483647`,
  removed from the DOM after the flash. Non-interactive by
  construction: it cannot steal focus, cannot receive clicks, cannot
  intercept keyboard input — the 3.2 move-input path and 3.3
  visibility instrumentation are untouched (the flash is 200 ms of
  photons, not UI).
- **Where it runs:** a **new content script `sync_flash.js`**,
  appended to the existing `content_scripts` js list in
  `manifest.json` (deliberate, reviewed manifest delta — `content.js`
  itself stays byte-identical). It listens for
  `chrome.runtime.onMessage` `{kind: 'blindfold-sync-flash',
  markerId, phase}`, shows the flash, and emits the visible
  `sync_marker` event via the existing content-script path
  (`BlindfoldSession.sender.emit({eventType, payload, refs})` — the
  2.3/4.2 precedent), synchronously with the flash display so the
  envelope timestamp IS the flash time.
- **Why the page:** the flash must be ON the captured surface. The
  offscreen document is never visible; SW cannot show UI;
  `chrome.notifications` appear on screen (screen-mode only — tab
  capture would miss them). A page overlay is captured in BOTH modes:
  tab mode records the tab (the overlay is on it), screen mode
  records the screen (the page is on it).
- **Honest capture matrix:** the screen recording always captures the
  flash; the webcam captures it only if the camera sees the monitor
  (physical, NOT promised — §7.9 characterizes this on the real
  device); the mic is unaffected.
- **Webcam sync limitation (documented, not repaired):** the webcam
  stream is video-only by design (4.4/4.6 — the mic already covers
  room audio; duplicating audio into the webcam stream would be the
  intentional mix 4.7 forbids). Its alignment to the marker therefore
  rests on the visible flash when in frame, otherwise on 4.10's clock
  links + 4.6's actual start times + 4.12's offsets. This is the
  honest boundary of what one marker can do.

## 4. Sequencing

- **Start marker:** in `recorder.js`'s `handleStartStreams` final
  `.then` (after 4.8's chunking kickoff and 4.9's monitor attach),
  iff **≥1 stream started successfully**. Fire-and-forget,
  best-effort, never delays or fails the channel response (the 4.8/4.9
  kickoff precedent): play the tone, emit the audible event
  synchronously with the `play()` call (no `await` between — the
  envelope's `monotonicMs` is the beep time), mint the `markerId`
  first and send the flash relay to the SW. If zero streams started:
  no marker at all (the start-streams per-kind response is the
  record — the 4.9 precedent for never-started streams).
- **Stop marker:** at the START of the stop sequence, BEFORE any
  `recorder.stop()` call, so the marker is captured before the final
  flush. 4.11 implements `emitStopMarker()` in the marker module and
  documents the call point; **4.13 wires it** (flagged for the
  section-4 auditor). No waiting for tone completion: alignment uses
  the marker ONSET; a truncated tail does not invalidate it.
- **Per generation:** restart → new start-streams → new `markerId`s.
  The 4.9 `restart` discontinuity and the new generation's markers are
  independent events on the same timeline.

## 5. Recorded fields — the `sync_marker` event

New event type `sync_marker` (1.3 convention: `SYNC_MARKER_EVENT_TYPE`
constant in the new module, flat snake_case, exact-keys payload):

- `payload`: `{markerId, phase, modality, status, error, detail}`
  - `markerId`: uuid-v4, minted by the offscreen document, shared by
    the audible + visible emissions of one phase of one generation.
  - `phase`: `'start' | 'stop'`.
  - `modality`: `'audible' | 'visible'`.
  - `status`: `'played'` (tone) / `'shown'` (flash) /
    `'failed'` / `'skipped'`.
  - `error`: string|null — the platform error name/message verbatim,
    or null.
  - `detail`: string|null — e.g. `'no-target-tab'`,
    `'no-streams-started'`; never a diagnosis.
- `refs`: `{sessionId}` (null only if somehow absent — cannot happen
  at marker time, since the 4.6 no-session guard precedes it).
- **Source timestamps:** the envelope's `monotonicMs` +
  `clockSegmentId` (+ UTC) ARE the saved source timestamps — emission
  is synchronous with the `play()` call / flash display, so no
  separate timestamp field is needed or stored (standing rule: don't
  persist derivable values).
- The audible emission carries the offscreen (recording_context)
  clock; the visible emission carries the content-script (page)
  clock. 4.12 aligns each against its own anchor — no cross-context
  clock confusion.

**No manifest widening.** The marker is per-generation, not
per-segment; the event log is its home (the 4.9 events-not-manifest
precedent). §6.3's `media-sync.json` reads marker events from the log
("synchronization markers" is already in its contracted contents).

## 6. Failure semantics (marker never fails recording)

- Tone `play()` rejects (no audio output, autoplay policy,
  document busy): audible event with `status: 'failed'`,
  `error` verbatim. Streams keep recording.
- Flash relay fails (SW `tabs.sendMessage` throws, no target tab):
  the SW responds `{ok: false, relayed: false, reason}`; the
  offscreen doc emits nothing for the visible modality OR emits
  `status: 'skipped'`, `detail: 'no-target-tab'` — builder's choice,
  V1-pinned either way (honest, exactly one of the two).
- Content script absent (tab closed mid-start): relay fails
  honestly; the screen recording is dead in tab mode anyway.
- Every marker path is try/catch-wrapped: monitoring's
  never-fail-the-pipeline rule (4.9) applies to markers too.

## 7. Channel vocabulary — one deliberate addition

The offscreen document cannot reach `chrome.tabs` (4.3: the SW broker
owns it). New recorder-channel message **`recorder-sync-flash`**
(`MSG_SYNC_FLASH`):

- Offscreen → SW: `{kind: 'recorder', msg: 'recorder-sync-flash',
  v: 1, markerId, phase}`.
- SW: resolve the target tab — the 4.3 broker's currently captured
  tab if known, else the active `https://www.chess.com/*` tab; if
  none, respond `{ok: true, relayed: false, reason:
  'no-target-tab'}`.
- SW → tab: `chrome.tabs.sendMessage(tabId, {kind:
  'blindfold-sync-flash', markerId, phase})`.
- SW → offscreen: `{ok: true, relayed: true}` (relay attempted;
  actual display is the content script's event to report).

The `MSG_*` snapshot gains exactly one value — deliberate vocabulary
evolution, V1-pinned. No other new messages.

## 8. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — audible marker correct.** `sync_beep.wav` exists with the
  §2 spec (builder records the generation command); tone playback
  uses `HTMLAudioElement` only — the 4.7 no-`AudioContext` code-scan
  pin over offscreen scripts passes UNMODIFIED; playback happens in
  the offscreen document (AUDIO_PLAYBACK rationale documented);
  start = 1 beep, stop = 2 beeps 150 ms apart (V1-pinned).
- **AC2 — visible marker correct.** `sync_flash.js` is a new content
  script (manifest `content_scripts` js list gains it — deliberate
  delta; `content.js` byte-identical); flash matches the §3 spec
  (white, ~200 ms, `pointer-events: none`, `aria-hidden`,
  removed after); it cannot steal focus or intercept input
  (V1-pinned: no focus calls, no event listeners on the overlay);
  no interference with 3.2/3.3 (brief, non-interactive).
- **AC3 — event shape exact.** `sync_marker` payload is exactly
  `{markerId, phase, modality, status, error, detail}` with
  `refs: {sessionId}`; `SYNC_MARKER_EVENT_TYPE` defined once in the
  new module (1.3 convention); one `markerId` shared across the two
  modalities of one phase; emission synchronous with play/flash
  (envelope timestamp = source timestamp — V1-pinned by code
  inspection, no `await` between).
- **AC4 — sequencing.** Start marker fires in the start-streams
  final `.then` iff ≥1 stream started; best-effort, never delays or
  fails the channel response; stop marker seam `emitStopMarker()`
  exists, is documented as 4.13's call-before-`recorder.stop()`
  obligation, and is NOT yet wired (auditor check, not a defect);
  per-generation fresh `markerId`s.
- **AC5 — failure honesty.** Tone failure → `status: 'failed'`
  with verbatim error, streams unaffected; flash relay
  failure/no-target-tab → honest `skipped`/`failed` (exactly one
  documented behavior, V1-pinned); zero streams → no marker events.
- **AC6 — vocabulary discipline.** Exactly one new channel message
  (`recorder-sync-flash`); `MSG_*` snapshot gains exactly one value;
  SW relay targets the 4.3-broker tab with the documented fallback;
  no other new messages; content scripts other than the new file
  byte-identical.
- **AC7 — no overreach.** No manifest widening (15→16 stays; the
  4.10 key is the last); no schema change (`DB_VERSION` 2); no
  offset computation (4.12's territory — V1 code-scan: the marker
  module does no timestamp arithmetic); no marker detection in
  recordings (content analysis, forbidden); §6.3 consumption named.
- **AC8 — changed-files discipline.** Working-tree diff touches
  only: `sync_marker.js` (new, offscreen), `sync_flash.js` (new,
  content script), `sync_beep.wav` (new asset),
  `tests/sync_marker.test.js` (new), `recorder.js` (start-marker
  `recorder.js` (start-marker wiring + `MSG_SYNC_FLASH` + relay request),
  `recording_host.js` (SW-leg `onRuntimeMessage` handler for
  `recorder-sync-flash`: resolve the target tab via the 4.3 capture

  `manifest.json` (content_scripts + nothing else),

## 9. Explicit non-goals and boundaries

- No continuous/periodic markers — one per phase per generation.
- No DETECTION of the marker in recordings (audio/video content
  analysis — forbidden by the raw-collection rule). 4.11 emits and
  timestamps; finding the beep in a waveform is §7 human work.
- No §5.8 optional moment markers (user-triggered, §5's feature —
  a separate contract; it may reuse the `sync_marker` shape with a
  new phase value, which would be a deliberate validator widening
  at that time, not now).
- No volume controls, no marker customization, no marker for
  pause/resume (no such feature exists).
- No waiting for tone completion before stop (onset is the
  alignment point).
- No changes to 3.x gameplay instrumentation.

## 10. Honest limitations

- Audibility/visibility in the actual recordings is AC11 (§7) —
  V1/V2 prove emission, timestamping, and honest failure paths, not
  human perception.
- The visible flash depends on the Chess.com tab existing at marker
  time; a tab closed mid-start yields an honest skip.
- The webcam's capture of the flash is physical, not promised
  (§3 limitation).
- `Audio.play()` in the offscreen document is subject to the 4.1
  AUDIO_PLAYBACK idle-close caveat — a failed play is a `failed`
  marker event, not a recording failure.
