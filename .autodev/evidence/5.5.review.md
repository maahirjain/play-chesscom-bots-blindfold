## 1. The atomic guard (recorder.js handleSetSession)

**The code** (sole diff in recorder.js, +16/−0):
```js
if (isSessionActive() && sid !== null && sid !== sessionId) {
  try { sendResponse({ ok: false, error: 'session-active' }); } catch (e) { /* ignore */ }
  return false;
}
sessionId = sid;
gameId = gid;
```

**Atomicity: holds.** The check (`isSessionActive()`, a pure typeof-check function; `sid !== sessionId`, a primitive comparison) and the assignments are in one synchronous block. `sendResponse` (chrome's sync callback) runs only on the refusal path. No `await`, `.then`, `new Promise`, or timer between check and assignment — confirmed both by reading and by the V1 AC2 pin (comment-stripped scan). `handleSetSession` returns `false` on every path (never async), and Chrome dispatches `onMessage` handlers strictly sequentially on the single JS thread, so two racing set-session messages cannot interleave the check-and-set. The V1 pin would not catch a smuggled *synchronous* callback, but there is none — the region is straight-line code.

**Discriminator: correct per the §2.1 matrix.** Verified all four cases against the code:
- No active session → `isSessionActive()` false → allow. ✓
- Active + `null` → `sid !== null` false → allow (Stop-clear). ✓
- Active + same sessionId → `sid !== sessionId` false → allow (idempotent re-set; 5.9's game change). ✓
- Active + different sessionId → refuse `{ok:false, error:'session-active'}`. ✓
- Shape validation above the guard rejects empty-string IDs, so `sid` is a non-empty string or `null` at the guard — no empty-string bypass. ✓

**No state leak on refusal:** the `return false` precedes all four assignments (`sessionId`, `gameId`, `ownerTabId`, `sessionCategory`). Verified `handleSetSession` is the *only* writer to these four variables in recorder.js (declarations at 267–282, assignments only at 1528–1539). A refused tab cannot become `ownerTabId`; its `sessionCategory` cannot be adopted. ✓

**Discretion:** the refusal is exactly `{ok:false, error:'session-active'}` — no sessionId, no tabId, no category. Tab B learns only that *a* session is active. ✓ (Covered by the "refusal carries no session details" V1 test.)

**Bypass search:** no other message handler mutates session identity; `recorder-ensure` does not touch it; boot adoption is local-only (content side). The guard cannot be bypassed through any other channel message. ✓

## 2. The content-side pre-check (session_controls.js)

**Placement: correct.** The chain is now interlock → validate selection → recorder-ensure → pre-check → mint → build records → session-save → set-session → start-streams → slots + emitPageStart + poll, matching contract §3.2. Minting genuinely moved after ensure (the 36 deleted lines are the relocated minting block plus the superseded 5.2 order comment — no functional deletion).

**Pre-check logic: correct and conservative.**
- `ensureResp.created === true` → skip. A freshly created document has `sessionId = null`; no session is possible. (A *lying* SW reporting `created:true` for a live document is out of scope; the atomic guard backstops it.)
- Otherwise `channelCall('recorder-get-status')` with the rejection handler attached **at the call** (`.then(null, () => null)`), not at the chain tail — verified in the diff. A dead document proceeds; the atomic guard arbitrates. ✓
- Verdict aborts only on `{ok:true}` with a non-empty-string `sessionId`. `{ok:false}`, null, or no-response all proceed. A missing `created` field falls through to the query (conservative). ✓
- Refusal uses `localAbortStart('duplicate-start:session-active')` + `throw {handledAbort: true}` — button to idle, fields enabled, slots null, **no minting, no session-save, no further messages, no clearRecorderSession**. The chain tail swallows `handledAbort` without double-reporting (verified at line ~922). ✓

**`localAbortStart` is the right call** (contract §3.3 refinement). I verified the hazard it fixes is real: the old `abortStart` calls `clearRecorderSession()` → `set-session{null,null}` → the 5.5 guard *allows* this as Stop-clear → would wipe the other tab's session. Three paths correctly use the local-only abort: pre-check refusal, set-session `session-active` refusal, and the post-pre-check `id-mint-failed` path (at mint-failure time another tab may have started after our pre-check — clearing would be destructive). The `record-build-failed` path (fields-branch mint failure) still does a manual partial reset (phase + button); it's pre-existing, functionally adequate (slots already null, no recorder state of ours), and out of 5.5's scope — noted, not a defect.

**Set-session refusal mapping: correct.** `err === 'session-active'` → `localAbortStart('duplicate-start:session-active')`; other errors keep the existing `abortStart('set-session-failed:'+err)` path. I checked the other-error path for cross-tab danger: a non-`session-active` error (e.g. `internal-error` from a throwing selector during announce) can only occur *after* the guard allowed the set — i.e. the active session is ours (fresh mint) or the Stop-clear — so `clearRecorderSession` there cannot wipe another tab's session. The guard short-circuits before the announce, so there is no interleaving where we get `internal-error` while another tab's session is active. ✓

**Same-tab double-Start:** the local interlock can't catch a double-click mid-sequence (slots not yet set), but the atomic guard does — the loser gets an honest `duplicate-start:session-active`, exactly as the contract specifies ("refused exactly like a cross-tab one"). ✓

**5.9 / boot adoption / Stop-clear:** 5.9's re-set calls set-session directly (same sessionId → allowed); boot adoption sets local slots so the interlock covers it; Stop-clear (`null`) is allowed and still clears `ownerTabId`. ✓

## 3. The device_selection.test.js evolution — faithful, not a weakening

The 4.2 clock-anchor test's second half previously asserted that a second set-session with a *different* sessionId creates a new session with its own anchor. That behavior is precisely what 5.5's contract §2.1 forbids (active S + different S′ → refuse). The evolution asserts:
- the second set-session returns `{ok:false, error:'session-active'}`,
- no `clock_anchor` is emitted for the refused SID2 (nothing overwritten),
- the subsequent event still carries the original SID (active session unchanged).

This is the contract's specified behavior, pinned as a test. The old expectation was not a "pre-existing failure" — it was a 5.5 behavior change, and evolving it is correct. (See note N1 below about the stale claim in DECISIONS.md.)

## Notes (non-blocking)

**N1 — Stale claim in DECISIONS.md (correct before commit).** The 5.5 entry says: "V1: 1273/1274 … the 1 failure is pre-existing on pristine HEAD — `device_selection.test.js` `clock_anchor`, unrelated." This is factually wrong. The failure was 5.5-caused (the guard correctly refuses the test's second set-session with a different sessionId), and the test has since been evolved to pin the new specified behavior; V1 is now 1274/1274. The entry should be corrected so future work isn't misled.

**N2 — Pre-existing cross-tab wipe hazard in `fields-malformed` path (follow-up, not 5.5's scope).** `session_controls.js` line 642: `abortStart('fields-malformed')` → `clearRecorderSession()` → `set-session{null,null}`. If another tab holds an active session when this tab hits the malformed-fields path, the other tab's session is wiped. This predates 5.5 (5.2's fields path) and is reachable only on a programming error (`resolveFieldsHandle() === false`), but it is the same hazard class that motivated `localAbortStart`, and at that point this tab owns nothing (fix: use `localAbortStart`). Recommend fixing as a small follow-up; not a 5.5 reject since it's outside the contract's change list and 5.5 neither introduced nor worsened it.

**N3 — Minor observations, no action required.**
- The guard's "active" (`isSessionActive()`: sessionId *and* gameId non-empty) is marginally narrower than the contract matrix's wording ("sessionId null/empty"). A hypothetical `(SID, null)` state would be treated as inactive. Unreachable — both fields are always assigned together and no caller sends a null gameId with a string sessionId — but worth knowing.
- The chain-tail `abortStart('start-failed')` on unexpected post-pre-check channel *rejections* could theoretically clear another tab's session, but a rejection implies the offscreen document is unreachable, in which case no session exists to wipe. Theoretical only.
