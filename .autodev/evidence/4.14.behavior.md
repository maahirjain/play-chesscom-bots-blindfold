## Behavioral honesty checks (traced against real code, not claims)

**(a) Lifecycle truth table is mechanical, no 'error' smoothing.**
`buildStatus` in `stream_status.js`: live registry entry → `'recording'`;
else unfinalized>0 → `'stopped'`; else records exist → `'finalized'`;
else `'idle'`. There is no `'error'` branch and no failure-to-state
collapsing. The critical masquerade case: a chunk-stalled stream whose
recorder is still `'recording'` keeps `lifecycle: 'recording'` while the
stall surfaces as `chunk.status === 'chunk-stalled'` + `lastDiscontinuity`
— failures as facts, never smoothed. Confirmed in the real Chrome run
(track-ended case) and in unit tests.

**(b) Read-only.** A direct scan of `stream_status.js` for
`chrome.`/`document.`/`indexedDB`/`sendMessage`/`emitEvent`/`put(`/
`add(`/`delete(`/`.start(`/`.stop(`/`requestData(` hits only the header
comment describing the V1 pin itself. Zero write/emit/control vocabulary in
executable code.

**(c) getStreamHealth generation scoping.** `attachStream` calls
`detachStream(kind)` (which `clearHealth`s → deletes the entry), then ends
with a fresh `healthEntry(kind)`. A new generation's attach therefore
clears the old generation's retained error/discontinuity. `detachStream`
alone also clears. Traced at `track_monitor.js` lines 495–554.

**(d) createdAtUtc-primary manifest ordering.** `compareRecords` orders by
`createdAtUtc` ascending (most recent wins via `pickLatest`), then
`segmentNumber`, then `segmentId` lexicographic tie-break. The contract's
"latest segment" row (AC truth table, line 80) is satisfied; the deliberate
deviation (a newer in-progress generation with null `segmentNumber` wins
over an older finalized segment) is documented in `4.14.build.md` and is the
only sane reading of "latest". Deterministic.

**(e) Channel handler never throws.** `handleStatusCommand`
(`recorder.js` ~line 1338): no session → `{ok:false, error:'no-session'}`;
synchronously-throwing factory → `{ok:false, error:'unavailable'}`; rejected
status read → `respondAsync` → `{ok:false}` (the 3.2 SF-1 precedent); every
`sendResponse` is wrapped in try/catch. Nothing is thrown across the channel.

**(f) In-memory loss honestly documented.** The contract (§2, §7), the
`track_monitor.js` health-mirror comment, and the `stream_status.js` header
all state that `lastRecorderError`/`lastDiscontinuity` are this document
generation only and empty by construction after a document restart, with the
manifest (`unfinalizedSegments`, `finalizedAtUtc`) as the cross-generation
source. No overclaim.

**(g) unfinalizedSegments semantics.** Counts manifest records per kind with
falsy `finalizedAtUtc`. Before crash recovery runs, a dead document leaves
`'stopped'` + `unfinalizedSegments > 0` — the contract's "honestly abnormal"
row. After 4.13's `finalizeOrphans` sets real `finalizedAtUtc` on orphans,
the status correctly reports `'finalized'` + 0. Both states are honest.

**(h) Message vocabulary.** Exactly 24 distinct `var MSG_*` declarations in
`recorder.js` (the same regex the V1 pin uses), 23→24 deliberate with
`recorder-get-status`. No other files declare channel messages.

**(i) Manifest/DB discipline.** `MANIFEST_KEYS` is exactly 18 (no 4.14
widening); `DB_VERSION` is 2 (no schema change). Independently counted.

**(j) No "required streams" policy in 4.14.** No required/readiness
vocabulary in `stream_status.js` (V1-pinned) or in the `recorder-get-status`
wiring. The only "required" hit in `track_monitor.js` is a pre-existing,
unrelated opts comment (`emitEvent — Required.`). Required-set policy stays
§5's job per the contract.
