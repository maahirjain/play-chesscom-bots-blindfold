# 5.9 contract — If a new game is started before Stop, assign a new game ID and preserve its boundary; flag the shared recording session rather than mixing move histories

## 1. Scope

PLAN.md §5.9: "If a new game is started before Stop, assign a new game ID and preserve its boundary; flag the shared recording session rather than mixing move histories."

**PLAN evidence:** §(c) step 4's normal flow is one game per session ("use one game per recording session in the normal workflow," 1.1.2), but the Flow section's export table is explicit about the accident case: "If multiple games share a recording session accidentally, retain the media once and map all game boundaries to it; do not duplicate the same recording into multiple bundles."

**Current state (verified by the planner):** When the history tracker (`createHistoryTracker`, chess_utils.js) detects a genuine reset — 3.1.5's suspect-threshold mechanism distinguishing a temporarily missing move-list element from a genuine reset/new game — it calls `onGameReset({confirmedMoveCount})` in content.js. That callback currently:
1. Orphans in-flight attempts (`attemptTracker.handleGameReset()`),
2. Records the reset (`gameLifecycleRecorder.recordGameReset(...)` → `game_reset` event under the current gameId),
3. Hits the placeholder: `/* §5: mint new game identity + install new tracker */` — **not implemented**.

Additionally, when `gameId !== null` (a session is active), the tracker sets its internal `ended = true` and **halts** — `observe()` returns `{reset: true}` without processing — "halt until §5 creates a tracker for the new game" (chess_utils.js). With `gameId === null` (no session), it restarts tracking in place (existing 3.1 behavior, unchanged by 5.9).

**What 5.9 does:** Implement the placeholder. When a genuine game reset is detected during an ACTIVE session, mint a new gameId, append it to the session metadata's `gameIds` array (the 1.1-designed shared-session flag), re-set the recorder session with the same sessionId + new gameId (5.5's guard explicitly allows this), update the content-side game slots, install a fresh history tracker for the new game, and re-arm the lifecycle recorder. The `game_reset` event already recorded under the old gameId is the boundary; subsequent events carry the new gameId, so move histories never mix.

**What 5.9 does NOT do:** It does not stop or restart recording (5.7's invariant holds — the session stays ACTIVE throughout). It does not change the media streams, the readiness badge (5.6, latched per session), or the Stop sequence. It does not interpret or analyze the games.

## 2. Detection — how "a new game before Stop" is observed

The sole detection signal is the existing `onGameReset` callback (content.js), fired by the history tracker's genuine-reset detection (3.1.5). No new detection mechanism is added.

5.9 acts **only when a session is ACTIVE** (phase `ACTIVE` in session_controls.js, i.e. `activeSessionId` is a non-empty string). In all other states the existing behavior is preserved:
- **Idle / no session** (`gameId === null`): the tracker restarts in place (3.1's existing path). 5.9 does nothing — there is no session identity to protect.
- **STARTING phase**: the session is not yet established (slots not set, recorder session not confirmed). A reset here is a pre-session observation; 5.9 does nothing. The Start sequence mints its own gameId when it completes. (Rationale: minting a mid-START game identity would race the Start chain's own minting.)
- **STOPPING phase**: the session is ending. 5.9 does nothing; the Stop sequence owns teardown.

The phase check must be honest: if the phase cannot be determined, 5.9 does nothing (fail-closed — a missed game boundary is honest raw data; a fabricated gameId is not).

## 3. The 5.9 transition — what happens, in order

When `onGameReset` fires during an ACTIVE session, the following happens **in this exact order** (order matters for the boundary):

1. **Existing:** `attemptTracker.handleGameReset()` — orphans in-flight attempts (unchanged).
2. **Existing:** `gameLifecycleRecorder.recordGameReset(confirmedMoveCount)` — emits the `game_reset` event **under the OLD gameId**. This is the boundary marker in the event stream: everything before it belongs to the old game, everything after to the new one. (Unchanged.)
3. **NEW — mint:** `newGameId = BS.newGameId()` (UUID v4 via `crypto.randomUUID`; no fallback — the 1.1 rule).
4. **NEW — metadata:** `updatedMetadata = BS.addGameToSession(currentMetadata, newGameId)` — appends to the ordered `gameIds` array. Then re-persist via the existing `session-save` channel message (idempotent by sessionId; the SW upserts). The 1.2 conditions record is unchanged (conditions describe the session, not the game).
   - **The "flag":** `metadata.gameIds.length > 1` implicitly marks a shared-recording session. This is the 1.1 design decision, already documented in session_identity.js: "Length > 1 implicitly marks a shared-recording session — no extra flag, it is derivable." 5.9 implements exactly this — no new flag field, no new metadata key.
   - If `session-save` fails or is unavailable, the transition **aborts honestly**: the new gameId is discarded, the old gameId stays active, and the failure is surfaced (the session continues under the old gameId — a missed boundary is honest; a half-applied identity change is not). The tracker remains halted; subsequent observations return `{reset: true}` until the next successful transition or Stop. This is the fail-closed rule.
5. **NEW — recorder:** `recorder-set-session` with `{sessionId: <unchanged>, gameId: newGameId}` (plus the existing `sessionCategory` echo). 5.5's guard explicitly allows this (same sessionId → allow; the 5.5 contract's AC5 pins it). On refusal (`{ok:false, error:'session-active'}` — another tab's session, the TOCTOU race) or no-response, the transition aborts honestly per the rule in step 4 (old gameId stays).
6. **NEW — slots:** `sessionControlsHandle` updates its slots (`setSlots(sessionId, newGameId)`) and `BlindfoldSession.activeGameId = newGameId`. All subsequent emissions (moves, markers, lifecycle events) carry the new gameId via the existing `activeGameId` reads. The `activeSessionId` is unchanged.
7. **NEW — tracker:** install a fresh `createHistoryTracker` for the new game (same options shape as the original, with the new gameId). The old tracker stays halted and is discarded. `content.js`'s `historyTracker` binding becomes reassignable (`const` → `let`, or a holder) and the derived `game` reference is refreshed.
8. **NEW — lifecycle re-arm:** `gameLifecycleRecorder.resetEnded()` — clears per-source idempotency so the new game's ending can be observed (the seam 5.1's Start already uses; 5.7's contract explicitly names it as 5.9's input).

Steps 3–8 are **all-or-nothing per step**: each step validates before mutating; a failure at any step leaves the earlier steps' effects in place but stops the transition (the session continues under the old gameId — see the fail-closed rule in step 4). There is no rollback of already-persisted metadata: a persisted-but-unadopted gameId is honest raw data (the metadata records a detected game; §6 exports what was observed).

## 4. How move histories don't mix

- **Partition key:** every event carries `gameId`. The old game's events (moves, attempts, speech, markers, lifecycle) keep the old gameId; the new game's events carry the new gameId. No event is ever rewritten or reassigned.
- **Boundary marker:** the `game_reset` event (emitted in step 2 under the old gameId, before the new identity exists) marks the exact boundary in append order. A consumer reconstructing games splits on `game_reset` + the gameId change.
- **No retroactive reassignment:** 5.8's contract already specifies this for markers ("a marker always attaches to whatever game is active when pressed — no retroactive reassignment"); 5.9 generalizes it to all event types.
- **Media:** the streams are never restarted (5.7). The Flow section's rule applies: "retain the media once and map all game boundaries to it." The gameId change in the event stream is the mapping; §6's export uses `metadata.gameIds` to enumerate the games sharing the media.

## 5. Interactions with neighboring tasks

- **5.5 (duplicate-Start guard):** the re-set in step 5 uses the *same* sessionId, which the guard explicitly allows (5.5 contract §2.1 matrix: "active + same sessionId → allow"; AC5 pins "5.9's re-set (same sessionId, new gameId) is allowed"). 5.9 must NOT mint a new sessionId — that would be a duplicate session, exactly what 5.5 forbids.
- **5.7 (no auto-stop):** the session never stops during the transition. Phase stays ACTIVE; the button stays "Stop"; streams keep recording; the 5.6 badge stays latched. 5.7's pins (no path from game-end to stop) are unaffected — 5.9 adds no stop path.
- **5.6 (readiness):** the badge is latched per *session*, not per game. A game change does not reset it (the streams' health is unchanged). The poll loop continues uninterrupted.
- **5.8 (marker):** markers emitted after the transition carry the new gameId automatically (they read `activeGameId` at press time).
- **5.10 (finalization):** the Stop sequence is unchanged — it finalizes the *session* (all games). The 3.5.4 termination-reason seam (`getLastObservedEnd` + `recordStopTermination`) applies to whichever game is active at Stop; earlier games' endings were already recorded as `game_ended` events under their own gameIds. 5.10's export-complete presentation covers the whole session.
- **§6 (export):** `metadata.json` includes the full `gameIds` array (already in the 1.1 schema); `events.jsonl` is partitioned by gameId with `game_reset` boundaries; media is retained once. No 5.9-specific export code — §6 consumes what 5.9 records.

## 7. Explicit non-goals

- Any UI change (no new buttons, badges, or prompts for the game transition — it is automatic and silent by design; the user didn't ask for a second game, it just happened).
- Any new event type (the `game_reset` event already exists and is the boundary marker), channel message, store, or permission.
- Stopping, restarting, or reconfiguring media streams on game change.
- Interpreting which game is "the" game, or analyzing/comparing the games.
- Retroactive reassignment of already-emitted events to the new gameId.
- Rollback of persisted metadata on partial transition failure (honest raw data, not silent correction).
- 5.10's finalization gating, §6's export assembly.
