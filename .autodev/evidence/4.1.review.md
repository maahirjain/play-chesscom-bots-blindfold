# Task 4.1 adversarial review — dedicated extension recording context

PLAN.md §4.1: "Create a dedicated extension recording context that remains
alive across Chess.com page refreshes; do not host recording solely in the
content script or a transient popup."

Reviewer: independent (did not implement). PLAN.md verified unmodified
(`git diff HEAD -- PLAN.md` empty; the AC6 test pins it). Code and STATE.json
untouched by this review.

**Verdict: APPROVE_WITH_DEFECTS — 0 BLOCKER, 2 SHOULD_FIX, 6 NOTEs.**

The 4.1 surface is sound: the offscreen-document architecture is the
sanctioned MV3 pattern, the supervisor's concurrency and failure handling
are correct, the message channel cannot collide with the writer's intake,
the 4.1 boundary holds (zero capture code, pin-tested), and the manifest
change is exactly the `"offscreen"` permission. The two SHOULD_FIX items
are real but non-blocking for the mission target (owner device, Chrome 154).

---

## SHOULD_FIX

### SF-1: `chrome.offscreen.hasDocument()` is Chrome 150+, not 109+ — the documented floor is wrong

- `recording_host.js:116` gates everything on
  `typeof off.hasDocument === 'function'`. Per the official API reference
  (https://developer.chrome.com/docs/extensions/reference/api/offscreen,
  fetched 2026-10-06), `hasDocument()` is marked **"Chrome 150+"**.
  `chrome.offscreen` itself exists since 109, but the *detection primitive
  this task depends on* does not.
- Consequence: on Chrome 109–149, `offscreenAvailable()` returns false and
  `ensureRecordingContext()` reports `{ok:false, reason:'offscreen-unavailable'}`
  — a misleading reason string (offscreen IS available) — and the whole of
  §4 silently never functions. The contract (§1) and DECISIONS.md document a
  "Chrome 109+ requirement" with honest degradation "on older Chrome"; the
  effective floor is 150, and the degradation mislabels the cause.
- The established pre-150 detection primitive is
  `chrome.runtime.getContexts({contextTypes:['OFFSCREEN_DOCUMENT']})`
  (Chrome 116+, same official docs page). Fix options (either is fine):
  (a) fall back to `getContexts()` when `hasDocument` is unavailable, or
  (b) correct the documented floor to Chrome 150+ and keep the degradation.
- Not a blocker for this mission: the owner device runs Chrome 154
  (V2 environment), where `hasDocument()` exists and is proven.

### SF-2: `start()` swallows failures with no diagnostic trace

- `recording_host.js` `start()`: both the listener install and the lazy
  `ensureRecordingContext()` have their rejections swallowed with empty
  catch blocks. The never-throw-at-startup behavior is contract-mandated
  (§2.4) and correct — but a broken recording context then fails *silently*:
  no console output, no event, nothing for 4.9/4.14 to observe later.
- Fix: keep the never-throw guarantee, but add a `console.warn` (or route
  through the existing status/lifecycle surface when §5 exists) on the
  swallowed paths so a dead recording context is diagnosable. One-line,
  mechanical.

## Adversarial checks — verified sound

1. **Offscreen choice is correct, not over-engineered.** The SW cannot host
   media APIs and is killable; content scripts and popups are explicitly
   forbidden by PLAN 4.1; a persistent extension tab is user-visible and
   user-closable. Offscreen is the documented Chrome pattern for exactly
   this (getUserMedia/getDisplayMedia + MediaRecorder in MV3). The full
   reason set up front (`USER_MEDIA`+`DISPLAY_MEDIA`+`AUDIO_PLAYBACK`) is
   justified: exactly one offscreen document may exist per extension, it
   hosts all of §4, and declaring the set once avoids a later recreate.
   Reasons are declared purposes, not permission grants — nothing is
   over-requested.
2. **AUDIO_PLAYBACK 30-second rule — probed empirically, not a problem.**
   The official docs state "The AUDIO_PLAYBACK reason sets the document to
   close after 30 seconds without audio playing." I built a minimal probe
   extension (`/tmp/oc-probe`, not in the repo) creating a document with the
   identical full reason set and no audio: `hasDocument()` stayed `true` at
   10/20/35/50/70/100/130/160s idle in headless Chrome 154. The multi-reason
   document is NOT subject to the 30s close in this environment. Caveat: a
   DevTools-driven browser may suppress lifetime enforcement, so §7's AC12
   (real idle on the owner device) should specifically watch for this —
   the contract already defers exactly that observation.
3. **Create race is handled correctly.** `inflightEnsure` collapses
   concurrent ensures onto one in-flight creation (unit-proven: 3 concurrent
   → 1 `createDocument`); a create-race loser re-checks `hasDocument()` and
   adopts the winner instead of failing. `runEnsure()` never throws
   synchronously (pure promise chain), so the guard cannot stick on a sync
   throw.
4. **No create→ping race.** The official docs state `createDocument()`
   "resolves when the document is created and has completed its initial page
   load" — the document's auto-boot (announce + listener install) has run by
   the time `ensure` pings. The best-effort `recorder-ready` plus the
   ping-based re-sync cover the announcement being missed.
5. **Channel cannot collide.** Writer intake is `kind:'event'`
   (`writer.js:10-12`, `sender.js:67`); recorder channel is
   `kind:'recorder'`. Both receivers validate the envelope and ignore
   unknown kinds/msgs without responding. Unknown protocol versions get
   `{ok:false}` — never thrown — on both sides.
6. **`recorder-ready` is idempotent and loop-free.** `runtime.sendMessage`
   from the offscreen document does not deliver to the sender; the SW
   listener only records `bootId`. No ack is sent, so no response loop.
7. **4.1 boundary holds.** `recorder.js` and `recording_host.js` contain zero
   `MediaRecorder`/`getUserMedia`/`getDisplayMedia` references outside
   comments (pin-tested with comments stripped). No device selection,
   formats, streams, chunks, manifests, sync marker, timecode, Stop
   finalization, or per-stream status. `sw.js` stays a thin entry point
   (import + two startup lines).
8. **bootId sound.** `newUuidV4()` via `crypto.randomUUID`, no weak fallback
   (throws plain `Error` when unavailable — the repo's unavailable-capability
   convention). Fresh uuid per document boot; V2 proved recreation mints a
   *new* bootId while re-discovery preserves the old one.
9. **Manifest diff is exactly the permission.** `git diff HEAD --
   manifest.json` shows only `"permissions": ["offscreen"]`. No host
   permissions, no other changes. Content scripts byte-identical (AC6 test).
10. **Deviations acceptable.** AC10's fresh-host-vs-true-process-death
    substitution is the deterministic equivalent of a restarted SW (blank
    in-memory state + identical `start()`→`ensure()` code path); the true
    process boundary is honestly deferred to §7. AC9's localhost-vs-chess.com
    substitution is mechanism-identical (offscreen documents are independent
    of every content tab by construction).

## NOTEs

- **N-1:** `ensureRecordingContext` has no timeout on the `hasDocument()` /
    `createDocument()` legs (only the ping leg has one). If `hasDocument()`
    hung forever, `inflightEnsure` would never clear and all future ensures
    would hang on the same promise. Consider bounding the whole ensure with
    a timeout in a later task.
- **N-2:** `pingRecorder` broadcasts with no `target` field; the first
    responder wins. Only the offscreen document answers `recorder-ping`
    today, but a future extension context that naively responds to unknown
    messages could poison pongs. Consider `target:'offscreen'` (the official
    sample uses a target field).
- **N-3:** `start()` ensures (and thereby *creates*) the document on every
    SW boot, even if the user never records. Contract-sanctioned (§2.4), but
    it means the offscreen document is a permanent resident — worth a
    resource-consciousness note for §5's Start/Stop design.
- **N-4:** `bootTime` is a client-generated ISO string, trusted, never
    verified against anything. Fine for 4.1's identity purposes; 4.10/4.12
    must not treat it as a clock anchor (they own the monotonic hook).
- **N-5:** The AC6 git-status allowlist does not yet include
    `.autodev/evidence/4.1.review.md` / `4.1.behavior.md` (expected —
    workflow ordering). Coordinator: add both with the standard
    honest-evolution comment (2.x/3.x precedent).
- **N-6:** `chrome.offscreen` in split-incognito mode allows one document
    per profile; the supervisor does not distinguish profiles. Out of scope
    for 4.1 (no incognito requirement in PLAN), noted for completeness.
