# 6.6 contract — Package the files into one ZIP with a category/date/game-ID path; streaming export

**Planner:** 6.6 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §6.6. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. Scope

PLAN.md §6.6: "Package the files into one ZIP with a category/date/game-ID
path; use export that does not require loading an entire long recording into
memory at once."

**What 6.6 does:** The orchestration that ties 6.1–6.5 together. It adds:
(a) a hand-rolled STORE-method ZIP writer in `exporter.js` (pure, Node-testable);
(b) the SW-side async `exportSession({sessionId, stopVerdict})` orchestration
(readonly store reads → 6.1–6.5 builders → ZIP assembly → download);
(c) the `export-request` SW channel message; (d) the `"downloads"` manifest
permission; (e) a Download affordance in the content-script session controls.

**What 6.6 does NOT do:** transcoding (never), progress UI (default: none —
the download shelf shows native progress), selective/partial export (whole
session or nothing), upload/cloud sync, deletion on export (2.9 owns it).

## 2. Definitions

### 2.1 The bundle contents

One ZIP per session, containing exactly:

| ZIP internal path | Source | Task |
|---|---|---|
| `<dir>/metadata.json` | `buildMetadataJson` | 6.1 |
| `<dir>/events.jsonl` | `buildEventsJsonl` | 6.2 |
| `<dir>/media-sync.json` | `buildMediaSyncJson` | 6.3 |
| `<dir>/microphone-001.webm` … | `assembleSegmentChunks` + `nameSegmentFiles` | 6.4+6.5 |
| `<dir>/screen-001.webm` … | (same) | 6.4+6.5 |
| `<dir>/webcam-001.webm` … | (same) | 6.4+6.5 |

`<dir>` is the category/date/identity path (§2.2). Media filenames are
6.5's `{streamKind}-{NNN}{ext}`; JSON filenames are fixed.

### 2.2 The directory path

PLAN §6.6: "category/date/game-ID path". Exact scheme:

- **Single-game session:** `<category>/<YYYY-MM-DD>_<gameId>/`
  where `<gameId>` is the full UUID-v4 gameId (not truncated — truncation
  risks collision and the gameId is already in metadata.json).
- **Multi-game session** (5.9, `gameIds.length > 1`): `<category>/<YYYY-MM-DD>_session-<sessionId>/`
  (the architecture's scheme; media is retained once per the Flow rule,
  never duplicated per game).

`<category>` is the session's `sessionCategory` verbatim (it is a short
controlled string from 5.2; the builder MUST sanitize it for ZIP-path
safety — see §4.3). `<YYYY-MM-DD>` is the UTC date of the session start
(from `session_metadata.createdAtUtc`, not the export clock — the bundle
documents the recording, not the download).

The **download filename** (outside the ZIP) is
`<category>-<YYYY-MM-DD>-<shortId>.zip` where `<shortId>` is the first 8
hex chars of the gameId (single-game) or sessionId (multi-game). `saveAs:
false` (architecture §4 — respects the user's configured location; the
planner confirms the section-planner's judgment: a save dialog is a
one-line 6.6 change if the owner later wants it).

### 2.3 STORE-method ZIP (no compression)

The ZIP writer is hand-rolled, STORE (method 0) only:

- **Rationale** (architecture §4): dependency-free repo; media already
  compressed; STORE needs no compression code.
- **Structure per file:** local file header → raw file data → (repeat);
  then central directory (one entry per file) → end-of-central-directory
  record.
- **Checksums:** CRC-32 (ISO 3309) per file. For media files, 6.4's
  `assembleSegmentChunks` already returns the incremental CRC — the ZIP
  writer consumes it directly (no re-read). For JSON files, the writer
  computes CRC-32 over the UTF-8 bytes using the existing in-module
  `crc32Update`/`crc32Finalize` (same IIFE scope; no new CRC code).
- **No data descriptors** (flag bit 3 NOT set): all sizes and CRCs are
  known before the local header is written (6.4 precomputes per-segment
  `{byteLength, crc32}`; JSON strings are fully materialized). This keeps
  the writer simpler and the output maximally compatible.

### 2.4 Streaming (the "not loading into memory" requirement)

The ZIP is assembled as an **ordered array of Blob parts**, never as one
ArrayBuffer (architecture §4):

```
parts = [localHeader(json1), jsonBlob1,
         localHeader(json2), jsonBlob2,
         localHeader(json3), jsonBlob3,
         localHeader(media1), ...chunkBlobs(media1)...,
         localHeader(media2), ...chunkBlobs(media2)...,
         ...,
         centralDirectoryBlob, endRecordBlob]
final = new Blob(parts, {type: 'application/zip'})
```

- Media bytes flow IDB → Blob (one chunk at a time, in key order) →
  parts array. The SW's JS heap holds only headers and Blob
  *references*; bytes live in the browser's blob storage (disk-backed).
- The central directory needs each file's offset: the orchestrator
  tracks a running byte offset as parts are appended (local header
  sizes are fixed/known; chunk Blob sizes via `blob.size`; JSON Blob
  sizes via `blob.size`).
- JSON files (metadata/events/media-sync) ARE fully materialized as
  strings/Blobs — they are small (kilobytes). Only media streams
  through the chunked path. This is the honest reading of "does not
  require loading an entire long recording into memory at once": the
  *recording* (media) streams; the *manifests* (JSON) do not need to.

### 2.5 Filenames inside the ZIP

- Forward slashes only. No leading `/`. No `..` segments (the builder
  validates this — a corrupt category must not escape the directory).
- ZIP filename encoding: UTF-8 with the UTF-8 flag bit set (bit 11) in
  both local and central headers (standard practice; category strings
  are ASCII in practice but the flag is correct regardless).
- DOS timestamps in headers: the session start time (from metadata),
  not the export time — the bundle documents the recording. If the
  session start time is unusable, use the MSDOS epoch (1980-01-01);
  never the wall clock silently.

## 3. The ZIP writer (pure, in exporter.js)

### 3.1 `buildZipParts({files})`

Pure function (sync; Blob construction is sync):

**Input:** `{files: [{path, dataParts, byteLength, crc32}]}` where:
- `path` is the ZIP-internal path (e.g. `blitz/2026-10-06_<gameId>/metadata.json`)
- `dataParts` is an array of `Blob` (for media: 6.4's chunk Blobs; for JSON: single-element `[new Blob([string])]`)
- `byteLength` and `crc32` are precomputed (6.4 provides them for media; the writer computes them for JSON via the in-module CRC)

**Output:** `{parts: Blob[], byteLength, fileCount}` where `parts` is the
ordered array for `new Blob(parts, {type:'application/zip'})`.

**Behavior:**
1. For each file in order: emit local file header Blob (30 bytes fixed +
   path bytes), then the `dataParts` verbatim. Record `{path, crc32,
   byteLength, offset}` for the central directory; advance `offset` by
   `30 + pathByteLength + byteLength`.
2. After all files: emit central directory (one 46-byte-fixed +
   path entry per file, with the recorded offset/CRC/sizes), then the
   22-byte end record (with central directory offset/size and file count).
3. Path validation: non-empty string, forward slashes only, no `..`,
   no leading `/`, UTF-8 encodable. Violation → `TypeError` naming the path.
4. Empty `files` array → `TypeError` (a bundle with zero files is a
   programmer error, never a valid export).

**Header details** (the builder implements exactly; V1 pins byte-exact):
- Local header signature `0x04034b50`, version-needed `20`, flags bit 11
  (UTF-8), method `0` (STORE), DOS time/date from §2.5, CRC-32, compressed
  size = uncompressed size = `byteLength`, path length, extra length `0`.
- Central header signature `0x02014b50`, version-made-by `63` (Unix),
  same fields plus external attributes `0`, local header offset.
- End record signature `0x06054b50`, disk numbers `0`, entry counts,
  central directory size/offset, comment length `0`.

### 3.2 Path helpers (pure, in exporter.js)

- `buildBundleDir({sessionCategory, createdAtUtc, gameIds, sessionId})`
  → the `<dir>` string per §2.2. Sanitizes `sessionCategory` for
  ZIP-path safety: allow `[A-Za-z0-9_-]` only; anything else →
  `TypeError` (fail-closed; a corrupt category must not produce a
  corrupt path). Derives `YYYY-MM-DD` from `createdAtUtc` (must be a
  valid ISO string → `TypeError` if not).
- `buildDownloadFilename({sessionCategory, createdAtUtc, gameIds, sessionId})`
  → the `<category>-<YYYY-MM-DD>-<shortId>.zip` string (same sanitization).

## 4. The orchestration: `exportSession`

### 4.1 Location and signature

**New async function in `exporter.js`:**
`exportSession({sessionId, stopVerdict, deps})` → 
`{ok:true, filename, bytes, fileCount} | {ok:false, error}`.

**Why in exporter.js:** it is the SW-side module that already owns the
pure builders; the orchestration is the thin async shell around them.
It takes `deps` (dependency injection) for testability:
`{db, downloads, createObjectURL, nowUtcIso}` — the builder decides the
exact shape, but V1 MUST test the orchestration with fake deps (no real
IndexedDB, no real `chrome.downloads`).

**`stopVerdict`** is the 5.10 retained verdict passed through from the
`export-request` message (architecture §1). May be `null` (re-export
after SW restart) — the builders degrade honestly per their contracts.

### 4.2 The export flow (exact order)

1. **Validate input:** `sessionId` must be UUID-v4 → `TypeError`
   otherwise. `stopVerdict` validated per 6.1's `requireValidStopVerdict`
   (null allowed).
2. **Snapshot counts** (readonly proof, architecture §3): count rows in
   `events`, `media_chunks`, `recording_manifest` for `sessionId`
   (via `DB.getAll({index:'bySessionId', lower:sessionId, upper:sessionId})`
   and `.length`). Store as `before`.
3. **Read `session_metadata`** via `DB.get('session_metadata', sessionId)`.
   Absent → `{ok:false, error:'session-not-found'}` (honest; not a throw —
   this is an expected user-facing condition).
4. **Read `conditions`** via `DB.get('conditions', sessionId)`.
   Absent → `null` (6.1 handles null conditions honestly).
5. **Read events** via `bySessionId`; **read manifest** via `bySessionId`.
6. **Extract `clockAnchors`** from the events: filter
   `type === 'clock_anchor'` payloads → `[{segmentId, utcEpochMs,
   monotonicMs}]` (6.3's contract: 6.6 extracts these from the event
   stream, following 6.1's `gameStartingFens` precedent).
7. **Extract `gameStartingFens`** from the events: filter
   `type === 'game_started'` → `{gameId: fen|null}` per game_records.js's
   denormalization rule (6.1's contract).
8. **Name the segment files** via `nameSegmentFiles({manifestRecords})`
   → `{files, bySegmentId}` (6.5).
9. **For each segment** (in 6.3's deterministic order — reuse the sorted
   order from `nameSegmentFiles`'s `files` array): read its chunks via
   `DB.getAll('media_chunks', {index:'bySegmentId', lower:segmentId,
   upper:segmentId})` — **verify** the DB has a `bySegmentId` index on
   `media_chunks`; if the index is named differently (e.g. compound
   `[segmentId, chunkIndex]`), use the correct index/key-range per the
   4.13 `readSegmentChunks` precedent. Then `assembleSegmentChunks({chunks})`
   → `{parts, byteLength, crc32, chunkCount}` (6.4). Accumulate
   `chunkStats[segmentId] = {chunkCount, chunksAfterFinalize}` —
   `chunksAfterFinalize` is computed by comparing chunk `createdAtUtc`
   against the manifest record's `finalizedAtUtc` (architecture §5:
   "the chunk set is append-only; §6 reads the store, not the finalize
   tally").
10. **Build the three JSON files** via 6.1–6.3 (passing `bySegmentId` as
    6.3's `segmentFiles`, `chunkStats`, `clockAnchors`, `gameStartingFens`).
11. **Build the bundle directory and download filename** via §3.2 helpers.
12. **Assemble the ZIP parts** via `buildZipParts({files})` where `files`
    is `[{path: <dir>/metadata.json, dataParts:[jsonBlob], ...}, ...media...]`
    in the order: metadata.json, events.jsonl, media-sync.json, then media
    files in 6.5's `files` order.
13. **Re-count stores** (the after-proof): recount `events`,
    `media_chunks`, `recording_manifest` for `sessionId`. Any mismatch vs
    `before` → `{ok:false, error:'store-changed-during-export'}` — do NOT
    proceed to download (never deliver a possibly-inconsistent bundle).
14. **Create the Blob:** `new Blob(parts, {type:'application/zip'})` →
    `URL.createObjectURL(blob)` → `chrome.downloads.download({url,
    filename, saveAs:false})`.
15. **Revoke the object URL** after the download call settles (success or
    failure — do not leak).
16. **Respond** `{ok:true, filename, bytes: <total byteLength>, fileCount}`.
    `bytes` is the summed `byteLength` (tracked during assembly, not
    `blob.size` — though they must agree; the builder may assert).

### 4.3 Failure handling (all honest, none silent)

| Condition | Response |
|---|---|
| `sessionId` malformed | `TypeError` (programmer error) |
| Session not in `session_metadata` | `{ok:false, error:'session-not-found'}` |
| `stopVerdict.verdict === 'failed'` | `{ok:false, error:'session-not-complete'}` (6.1's builders throw; the orchestration catches and maps — reviewer N1 from 6.1) |
| Store counts change mid-export | `{ok:false, error:'store-changed-during-export'}` (no download attempted) |
| Corrupt record (bad appendSeq, bad manifest, etc.) | `{ok:false, error:'corrupt-<store>-record:<detail>'}` naming the store and key (2.6 precedent; the pure builders throw `TypeError`, the orchestration catches and maps) |
| `chrome.downloads.download` rejects/fails | `{ok:false, error:'download-failed:<reason>'}` (sources untouched; 6.7 retry works) |
| `chrome.downloads` unavailable | `{ok:false, error:'downloads-unavailable'}` (plain `Error` per convention — unavailable platform capability) |

**Critical:** on ANY failure, the stores are untouched (readonly throughout).
The user can retry; 6.7 proves byte-identity.

### 4.4 Readonly proof (static pin)

V1 MUST include a static test scanning `exporter.js` for `DB.put`,
`DB.delete`, `indexedDB` write patterns, `sendMessage` — asserting none
appear in the orchestration path. (The 6.1–6.5 precedent: pure builders
have no I/O at all; the orchestration has reads only.)

## 5. The channel message: `export-request`

### 5.1 SW-side handler

**In `sw.js`:** add `exporter.js` to the `importScripts()` list, then
install a `chrome.runtime.onMessage` listener (the first in sw.js —
currently sw.js has NO message listener; the offscreen document owns the
recorder channel).

**Message shape** (following the `recorderEnvelope` precedent but
SW-side, not offscreen):
- Request: `{kind:'export', v:1, msg:'export-request', sessionId, stopVerdict}`
- Response: `{ok:true, filename, bytes, fileCount} | {ok:false, error}`

**Handler behavior:**
1. Validate envelope: `kind === 'export'` and `msg === 'export-request'`;
   ignore (return `false`) anything else — do NOT interfere with the
   recorder channel (which uses `kind:'recorder'`).
2. Call `BlindfoldSession.exportSession({sessionId, stopVerdict, deps})`
   with real deps (`{db: BlindfoldSession.DB, downloads: chrome.downloads,
   createObjectURL: URL.createObjectURL.bind(URL)}`).
3. Return `true` (async response) and `sendResponse` the result.

**Diff discipline:** sw.js gains the importScripts entry + the listener.
No other sw.js behavior changes. The offscreen MSG_* vocabulary is
untouched (this is SW-side, architecture §6).

### 5.2 Content-side send

`session_controls.js` already has `channelCall` → `opts.sendRecorderMessage`
→ `chrome.runtime.sendMessage`. The Download affordance (§6) sends:
```js
opts.sendRecorderMessage({kind:'export', v:1, msg:'export-request',
  sessionId: <id>, stopVerdict: getLastStopResponse()})
```
No new content-side permission. No new content-side channel infrastructure.

## 6. The content affordance: Download button

### 6.1 Placement and enablement

- **Where:** in the session-controls cluster (the in-page Start/Stop UI
  from 5.1), adjacent to the Start/Stop button. The builder decides exact
  DOM (following the existing cluster conventions).
- **When enabled:** ONLY when the control is in idle phase AND
  `getLastStopResponse()` is non-null (i.e., a session has completed
  Stop with a retained verdict — 5.10's state). Disabled otherwise
  (never during ACTIVE/STARTING/STOPPING/FINALIZING).
- **What it sends:** `export-request` with `{sessionId, stopVerdict}` —
  `sessionId` from the retained verdict's `stopResp` (or the last
  session's metadata — the builder resolves the exact source, but it
  MUST be the session the verdict belongs to, never a guessed ID).
  `stopVerdict` is `getLastStopResponse()` verbatim (may be null only
  if the button were enabled without a verdict — which §6.1 forbids).
- **What it shows:** while the export is in flight, the button shows a
  transitional state (e.g. "Exporting…", disabled). On `{ok:true}`: brief
  success indication (the builder's choice, following the "Finalizing…"
  precedent — must not claim more than "download started"). On
  `{ok:false}`: the error in the button detail (following the
  `stop-failed:<err>` / `finalize-warnings:` precedent, e.g.
  `export-failed:<error>`).
- **No auto-export:** the user clicks Download explicitly. 5.10's Stop
  does NOT trigger export (that would be a new requirement).

### 6.2 Phase-machine interaction

The Download button is **presentation-only**: it does not touch the
phase machine, the session slots, the readiness badge, or the marker
input. Clicking Download during idle does not start a session, does
not alter `lastStopResponse`, and does not interfere with a subsequent
Start (5.5's guard is unaffected — export holds no session).

## 7. The `"downloads"` permission

**In `manifest.json`:** add `"downloads"` to the `permissions` array
(current: `["offscreen", "tabCapture", "storage"]`).

**Justification** (for the permission rationale doc / review):
`chrome.downloads.download()` is the only MV3 API that delivers a file
to the user's download location from a service worker. Content scripts
and offscreen documents cannot trigger downloads. The permission is used
in exactly one place (the `exportSession` orchestration, §4.2 step 14).

**V1 pin:** `"downloads"` is the ONLY manifest permission delta vs the
committed manifest (static test).

## 9. Explicit non-goals

- Transcoding (never — 6.4's byte-concatenation is the media path).
- Progress UI (the download shelf's native progress suffices; a progress
  channel would be a new message).
- Selective/partial export, bundle preview, playback UI.
- Upload, cloud sync, automatic backup.
- Deletion on export (2.9 owns retention).
- Auto-export on Stop (user clicks Download explicitly).
- `saveAs: true` (one-line change if the owner wants a save dialog).
