# Task 4.5 contract — recording format verification and the recording manifest

PLAN.md §4.5: "Verify supported recording formats at runtime and save the actual
MIME type/file extension in the recording manifest."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope boundary — what 4.5 is and is not

**4.5 builds the format-verification machinery and defines the recording
manifest; it starts no recording.** The "actual MIME type" of a segment only
exists once a `MediaRecorder` is constructed, which is 4.6's job ("Start
separate microphone, screen, and webcam recording streams"). So 4.5 delivers:

1. Runtime format verification (`MediaRecorder.isTypeSupported` probing in the
   offscreen document, per stream kind, with frozen prioritized candidate
   lists).
2. The recording manifest: a new extension-owned IndexedDB store
   (`recording_manifest`) holding one record per recording segment, including
   the actual negotiated MIME type and derived file extension.
3. The manifest write API that 4.6 calls at stream start (V1-pinned with a
   fake recorder exposing `.mimeType`; the real-recorder call is 4.6's V2).

**Not 4.5:**
- No `MediaRecorder` construction, no stream acquisition, no retained streams
  (4.6 owns all of it).
- No chunk writing (4.8), no segment IDs/clock anchors (4.10 assigns them),
  no timecode/offsets (4.12), no Stop finalization (4.13), no per-stream
  status events (4.14).
- No new event types. Format support is queryable state, not an event.
- No UI of any kind (§5 owns it).
- No changes to existing event types, validators, or content scripts.

## 2. The recording manifest

### Why a store, not events

The manifest is **mutable**: 4.5 writes the format identity at stream start,
4.10 adds the clock anchor, 4.12 adds timecode/offsets, 4.13 marks it
finalized. Events are append-only and immutable by design (2.4) — the wrong
home. §6.3 ("Export media-sync.json with media filenames, formats, clock
anchors, segment offsets, and known gaps") reads this store; the manifest is
the single source of truth for media-sync.json.

### Store spec (db.js)

- Store name: `recording_manifest`
- keyPath: `segmentId` (uuid-v4 string, assigned by 4.10 — 4.5 defines the
  key, not the assignment)
- Indexes: `bySessionId` (keyPath `sessionId`, unique false) — for §6 export
  and 4.13 finalization sweeps
- `DB_VERSION` 1 → 2. The existing `applySchema` upgrade path already creates
  missing stores on version bump, so pre-4.5 databases upgrade cleanly. The
  builder must confirm the 2.9 retention tests still pass with the new store.

### Segment record — field ownership

One record per recording segment. 4.5 owns and writes the format-identity
fields; later tasks own their fields and extend the validator when they add
them (the repo's exact-keys convention: validators reject extra keys, so each
field-adding task must widen the validator it touches — documented here to
prevent silent breakage).

| Field | Type | Owner | Notes |
|---|---|---|---|
| `segmentId` | uuid-v4 string | 4.10 assigns; 4.5 defines the key | Primary key |
| `sessionId` | uuid-v4 string | 4.5 (write API requires it) | Session scope |
| `gameId` | uuid-v4 string | 4.5 (write API requires it) | Game scope |
| `streamKind` | `'microphone'`\|`'screen'`\|`'webcam'` (frozen) | 4.5 | Which stream this segment belongs to |
| `requestedMimeType` | string \| null | 4.5 | What 4.6 asked `MediaRecorder` for (may differ from actual) |
| `actualMimeType` | string \| null | 4.5 | The negotiated type from `recorder.mimeType` at construction; null until a recorder exists |
| `fileExtension` | `'.webm'`\|`'.mp4'`\|`'.m4a'`\| null | 4.5 (derived) | Derived from `actualMimeType` via `extensionForMimeType`; null = unknown, never fabricated |
| `createdAtUtc` | ISO-8601 string | 4.5 | Manifest write time (not a media timestamp) |
| `clockAnchor` | (4.10's shape) | **4.10** | Reserved; 4.5 must not write or require it |
| timecode/offset fields | (4.12's shape) | **4.12** | Reserved; 4.5 must not write or require it |
| `status`, `finalizedAtUtc` | (4.13's shape) | **4.13** | Reserved; 4.5 must not write or require it |

4.5's exact-keys validator covers exactly the eight 4.5-owned fields.
Pre-session inertness (2.x/3.x/4.2 precedent): the manifest write API requires
non-null sessionId/gameId; without them it refuses (plain data `{ok:false}`,
never throws across the channel — the channel-error vocabulary precedent).

### Manifest write API

`recordSegmentFormat({segmentId, sessionId, gameId, streamKind,
requestedMimeType, actualMimeType})` → validates (exact keys, uuid-v4 ids,
frozen streamKind, MIME-type strings), derives `fileExtension` from
**`actualMimeType`** (never from the requested type), stamps `createdAtUtc`,
and `put`s the record. Returns `{ok:true, segmentId, fileExtension}`.

Rationale for deriving from actual: `new MediaRecorder(stream,
{mimeType: chosen})` may negotiate a different type than requested
(Chrome normalizes the string); `recorder.mimeType` is ground truth. 4.6
reads it immediately after construction and passes it in.

## 3. Format verification

### Module

New DOM-free `format_support.js` (repo module pattern: guarded
`BlindfoldSession` global → IIFE `'use strict'` → Node shim), loaded only by
`recorder.html`. **Recording platform APIs live only in the offscreen
document** (4.1's rule) — `MediaRecorder.isTypeSupported` is injected for
tests, read lazily from the real global in the document.

### Candidate lists (frozen, prioritized)

Probed in order; first `isTypeSupported() === true` wins per stream kind.
Priority rationale: VP9 (best quality/size, Chrome-native) → VP8 (universal
WebM) → H.264 (hardware acceleration, broader player compatibility) → bare
container. Audio: Opus in WebM (Chrome-native) → MP4 fallback.

- **microphone** (audio-only):
  `audio/webm;codecs=opus`, `audio/webm`, `audio/mp4`
- **screen** (video + tab audio, 4.7's feed):
  `video/webm;codecs=vp9,opus`, `video/webm;codecs=vp8,opus`,
  `video/webm;codecs=h264,opus`, `video/webm`
- **webcam** (video-only, face separate from screen):
  `video/webm;codecs=vp9`, `video/webm;codecs=vp8`,
  `video/webm;codecs=h264`, `video/webm`

`verifyFormats()` returns `{ microphone: [...], screen: [...], webcam: [...]
}` — the supported subset of each list, order preserved. Empty list for a
kind is an honest "nothing supported" (4.6 must refuse to start that stream;
4.14 reports it) — never a silent fallback to an unverified type.

If `MediaRecorder` or `isTypeSupported` is unavailable → plain `Error`
(unavailable platform capability per AGENTS.md — never a weak fallback, never
a fabricated list).

### File extension mapping

`extensionForMimeType(mimeType)` — pure function:

| actualMimeType | fileExtension |
|---|---|
| starts with `video/webm` or `audio/webm` | `.webm` |
| `video/mp4...` | `.mp4` |
| `audio/mp4...` | `.m4a` |
| anything else / non-string | `null` |

`null` means "unknown — §6 must not assume"; the manifest records it honestly
and media-sync.json carries the MIME type regardless.

## 4. Message channel

On 4.1's envelope `{kind:'recorder', msg, v:1}`:

| msg | Request | Response |
|---|---|---|
| `recorder-get-formats` | — | `{ok, formats: {microphone:[...], screen:[...], webcam:[...]}, verifiedAtUtc}` |

The probe **always re-runs** `isTypeSupported` (synchronous, cheap) — no
cache, no staleness. No session gating: this is device capability, not
session data, and it emits nothing. Failure isolation per the 3.2 SF-1
precedent (a throwing verifier never breaks the message listener).

  kind — headless Chrome's exact codec set is observed, not assumed);
  `recording_manifest` store exists in the extension IDB with keyPath

  stream start is **4.6's V2**, not 4.5's — documented, no fabricated green.
- **/tmp hygiene:** 2.x/3.x/4.x precedent.

- AC2 (V1): priority order preserved — first supported candidate wins; order
  matches the frozen lists in §3.
- AC3 (V1): `MediaRecorder`/`isTypeSupported` unavailable → plain Error

- AC6 (V1): `recordSegmentFormat` derives `fileExtension` from

  `segmentId`, `bySessionId` index); `DB_VERSION` bump documented with the
  upgrade path.
- AC8 (V1): changed-files discipline — no `MediaRecorder` **construction**
  in 4.5 product code (only `isTypeSupported` probing); content scripts
  byte-identical; no new event types; `event_envelope.js` untouched.
- AC9 (V2): real headless Chrome — `recorder-get-formats` through the real
  channel returns real codec lists (shape asserted; exact codecs observed).
- AC10 (V2): `recording_manifest` store exists in the extension IDB with

- AC11 (V2): kill + recreate the offscreen document → formats still

## 7. Non-goals

- No `MediaRecorder` construction, stream acquisition, or retained streams.
- No chunk writing, segment IDs, clock anchors, timecode, finalization.
- No events emitted by 4.5; no UI; no manifest-permission changes
  (`isTypeSupported` needs none).
- No changes to the 1.2 session-conditions schema.

## 8. Known seams and honest limitations

1. **Actual-type capture is 4.6's call.** 4.5 provides the writer; if 4.6
   passes a wrong `actualMimeType`, the manifest is wrong. V1 pins the
   derivation; 4.6's V2 must prove the real `recorder.mimeType` read.
2. **Codec support can change** (browser updates, platform differences) —
   hence always-re-probe, never cache.
3. **Empty candidate list** for a kind means that stream cannot start; 4.5
   reports it honestly and stops there. 4.6/4.14/5.6 own the UX.
4. **Headless Chrome's codec set differs from headed** (e.g. H.264 may be
   absent) — V2 asserts shape, not specific codecs; the real-device list is
   AC12/§7.
5. **4.10/4.12/4.13 field additions** must widen the exact-keys validator;
   this contract documents their reserved fields so the widening is
   deliberate, not a silent break.
