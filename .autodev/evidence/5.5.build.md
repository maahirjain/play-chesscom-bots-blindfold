# 5.5 build evidence — Prevent a duplicate Start from creating overlapping recording sessions

## What was built

Implemented PLAN.md §5.5 per `.autodev/evidence/5.5.contract.md` (11 ACs:
AC1–AC7 V1, AC8–AC10 V2, AC11 V3-deferred to §7), on branch
`autodev/logging-instrumentation`. Nothing committed; STATE.json untouched.

**Offscreen guard (`recorder.js`, purely additive, +22 lines):** in
`handleSetSession`, immediately after the request-shape validation and
before the `sessionId = sid` assignment, the duplicate-Start guard:

```js
// 5.5: duplicate-Start guard. Refuse a *new* session while one is
// active; allow idempotent re-set (same sessionId — 5.9's game
// change) and the Stop-clear (null). ...
if (isSessionActive() && sid !== null && sid !== sessionId) {
  try {
    sendResponse({ ok: false, error: 'session-active' });
  } catch (e) { /* ignore */ }
  return false;
}
```

The discriminator is sessionId equality, not tab identity (contract
§2.1): no active session → allow; active + null → allow (Stop-clear);
active + same sessionId → allow (idempotent re-set); active +
different sessionId → refuse `{ok:false, error:'session-active'}`.
The check-and-set is synchronous — no await/promise/callback between
the check and the assignments (V1 code-review pin). On refusal nothing
is overwritten (sessionId/gameId/ownerTabId/sessionCategory keep
active values), the refused tab never becomes owner, and the response
carries no session details (discretion).

**Content-side pre-check (`session_controls.js`):** the Start sequence
is reordered to interlock → validate selection → recorder-ensure →
pre-check → mint → build records → session-save → set-session →
start-streams → slots + emitPageStart + poll (contract §3.2). After
`recorder-ensure`, unless ensure reported `created:true` (a fresh
document cannot hold a session), the control queries
`recorder-get-status`. `{ok:true}` with a sessionId while this tab
passed the local interlock means another tab holds the session →
abort honestly **before minting**: button back to idle Start, detail
`duplicate-start:session-active`, fields stay enabled, nothing
persisted, no further recorder messages. `{ok:false}` or no-response
proceeds — the atomic guard remains the correctness arbiter (it
closes the pre-check's TOCTOU race). A get-status rejection is
caught at the pre-check itself (`.then(null, onRejected)`), not at
the chain tail, so a dead document proceeds instead of aborting.

**Refusal handling on the set-session leg:** the existing
`{ok:false}` abort path maps `session-active` to the honest detail
`duplicate-start:session-active`. Critically, it uses a new
`localAbortStart(detailText)` helper — a local-only reset that does
NOT call `clearRecorderSession()`. The old `abortStart` would send
`set-session{null,null}`, which the new guard allows as the
Stop-clear — wiping the *other* tab's session. Other set-session
errors keep the existing `abortStart('set-session-failed:'+err)`
path. The 5.1 no-fields `id-mint-failed` path was also moved from
`abortStart` to `localAbortStart` (same reasoning: post-pre-check,
the recorder may hold another tab's session).

**No new channel messages** (offscreen MSG_* stays 24, SW envelope
stays 7), no new events/stores/permissions. 4.6's stream guard
remains as backstop. Race-loser metadata is kept as honest raw data
(contract §4).

## Deviations from the contract

1. **`localAbortStart` helper (contract §3.3 refinement).** The
   contract says "the existing set-session `{ok:false}` abort path
   already handles the guard's refusal." During implementation this
   proved unsafe: the existing path calls `clearRecorderSession()`,
   which sends `set-session{null,null}` — now a legal Stop-clear
   that would wipe the *other* tab's active session. The refusal
   path (and the post-pre-check mint-failure path) therefore use a
   new local-only abort that never touches recorder-side state.
   Same button/tooltip surface, no new UI.
2. **Test-only rejection-handler placement.** The pre-check's
   no-response proceed is implemented as `.then(null, onRejected)`
   attached to the get-status call itself (a first version attached
   it at the chain tail, which let the rejection skip the verdict
   handler and abort — caught by the new V1 test, fixed).
3. **V2 mint-counting instead of IDB-record assertion.** AC8's "no
   new session_metadata record for B" is verified via
   `window.__minted` counters (B's minters never called) rather
   than an IDB read: the V2 harness drives the 5.1 no-fields path
   (no `session-save`), so no record could exist; the counters
   prove the pre-check aborted before minting.
