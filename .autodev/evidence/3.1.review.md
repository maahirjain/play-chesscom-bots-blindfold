## SHOULD_FIX

### SF-1 — Interim `onGameReset` stub permanently halts gameplay after an in-page genuine reset

**Location:** `chess_utils.js` `handleSuspect()` (ended=true branch);
`content.js` `onGameReset: () => { /* §5 ... */ }`.

**The problem.** When `suspectCount >= suspectThreshold`, the tracker sets
`ended = true` and `observe()` ignores everything thereafter. The host is
supposed to "install a new tracker" — but the content.js stub is empty, and
§5 (which owns game identities) is at least two sections away (§3.2–3.5,
§4 first). Until then, after a genuine in-page reset/new-game that does
**not** reload the page:

- the tracker's internal `game` stays `reset()` to the initial position;
- `result.confirmed` is always empty → `sayMove` never fires;
- `announceResultIfOver()` (sounds.js:44, bare global `game`) reads the
  initial position → never announces.

The old `updateGame` reset-and-continued on shorter lists, so this is a
**gameplay regression** for the new-game-without-reload flow: the
blindfold player gets silence and a frozen position readout. The
DECISIONS.md entry ("Gameplay (board, speech) works without §5") is
false in this scenario.

**Why not a blocker.** Normal single-game flow is unaffected; a page
reload (the common chess.com new-game path, covered by 2.7 lifecycle)
discards the ended tracker; §5.9 will wire proper game boundaries. The
contract explicitly designed the halt.

**Recommended repair (minimal, interim-safe).** In `handleSuspect`'s
threshold branch, when `gameId === null` there is no game identity to
protect and nothing is emitted — restart tracking in place instead of
halting:

```js
if (suspectCount >= suspectThreshold) {
  game.reset();
  confirmed = [];
  suspectCount = 0;
  desyncCount = 0;
  if (gameId === null) {
    // Interim (pre-§5): no identity to preserve, nothing emitted —
    // keep gameplay alive. §5 installs per-game trackers and uses
    // the halt path for real gameIds.
  } else {
    ended = true;
    onGameReset();
  }
  result.reset = true;
}
```

Alternatively, correct the DECISIONS.md claim to document the interim
gap explicitly. Either way, do not ship the claim "gameplay works"
unqualified.

## NOTEs

### NOTE-1 — `internal_desync` is likely unreachable via mission code paths (defensive, fine)

The bridge test replays the full observed list from initial with the
same deterministic `tryApplyMove` (raw-then-normalize) the incremental
path uses. I could not construct a case where incremental validation
fails but the full replay succeeds while the internal board is
"actually right": the confirmed SAN prefix uniquely determines the
internal position (chess.js parsing is deterministic given the
position), so a bridge success implies the internal board had already
diverted from the confirmed sequence — unreachable, since every
confirmed move was validated and every rewind uses canonical
from/to/promotion replays. Keeping the branch as defense-in-depth is
correct; observation-wins is the right policy per "preserve original
observations". No action.

### NOTE-2 — Checkpoint gate overclaims the "from the last checkpoint" leg

Contract §2.7 describes a three-leg gate including a "from the last
checkpoint" check against `lastCheckpointFen`. The implementation has
no `lastCheckpointFen` variable — the leg is vacuous because only one
checkpoint ever fires (`checkpointEmitted` guard). Harmless, but the
contract text should be corrected when §3.1 is next touched.

### NOTE-3 — `malformed_observation` / `unobservable_promotion` feed the checkpoint counter without a bridge test

`onDesyncFailure()` is called for all four sync-failure reasons, so
five consecutive malformed observations (or unobservable promotions)
emit `position_checkpoint` with `reason: 'unreconciled_history'`
although no bridge test ever ran on those paths. The FEN is genuinely
last-known-good (the game is never advanced on failure — `validateBatch`
rolls back, `handleCorrection` restores), so the checkpoint is honest,
but the reason label is slightly imprecise for those paths. Consider a
distinct reason or a bridge-only counter if §5/§6 consumers key on the
reason. Not wrong today.

### NOTE-4 — Transient-prefix takeback is honest but noisy (documented trade-off, accepted)

A transiently-missing last move element is exactly the takeback shape
(strict non-empty prefix) and fires `history_revised('takeback')`
immediately; the self-correcting follow-up emits a correction/append.
The stream stays truthful about what the DOM showed (contract §2.4
rationale), at the cost of marker pairs on glitches. This satisfies
3.1.5's letter (transient vs *genuine reset* are distinguished — the
latter goes through the suspect window to `onGameReset`), but anyone
consuming the stream should expect takeback+correction pairs and not
treat every takeback as user intent. The contract documents this;
no code change.

### NOTE-5 — `sayMove` on normalize-fallback moves spells the raw SAN (pre-existing, unchanged)

`m.san` is the raw observed string; when validation succeeded only via
the `normalizeMove` fallback, `sanToSpeech`'s `game.move(rawSan)` fails
and falls back to letter-spelling. Identical to pre-3.1 behavior
(old code spoke the same raw string). Not a regression; a future
improvement could speak the normalized form.

### NOTE-6 — `emitEvent` host contract is load-bearing but degrades gracefully

The tracker requires `emitEvent` to synchronously return the envelope
(or `{eventId}`) so `history_revised.retractedMoveEventIds` can
reference confirmed moves. content.js's wrapper returns
`sender.emit(...)`, which synchronously returns the queued envelope
(sender.js: ~line 386) — verified. If a future host violates the
contract (returns undefined), `retractedMoveEventIds` silently becomes
empty and the revision marker is skipped (guarded by
`retractedIds.length > 0`) while truncation still proceeds — a
graceful but silent degradation. Worth a one-line comment at the
`confirmMove` site.

### NOTE-7 — `sharedBS()` depends on classic-script load order (pinned by tests, fine)

`game_records.js` must execute before `chess_utils.js` so the 1.4
factories exist on the shared global; the manifest order pins this and
`tests/sender.test.js` AC7 asserts the exact js list. If anyone reorders
the manifest, the tracker throws at factory-call time (loud, not
silent). Acceptable.

### NOTE-8 — `updateGame` removal is the one planned main-origin deletion

`git diff main` (worktree) shows the removal (~15 lines) from
`chess_utils.js`, a main-origin file. This is the explicitly flagged
exception (contract §2.10, DECISIONS.md): the function's contract is
exactly what 3.1 replaces, a wrapper is impossible (tracker owns the
instance), and dead code is worse. Verified: zero remaining callers
outside the test asserting removal. Additive-substance convention holds
everywhere else.

## SF-1 repair re-review (2026-10-06, targeted re-reviewer)

**What was checked:**

1. **Repair matches the recommendation.** `git diff HEAD -- chess_utils.js`
   shows the SF-1 change confined to `handleSuspect`'s threshold branch:
   `game.reset(); confirmed = []; suspectCount = 0; desyncCount = 0;
