# 7.6 contract — Verify reveal/hide events and every existing help shortcut are captured

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.6. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.6 requires demonstrating that two categories of user-observable
behavior produce their contracted event records:

1. **Reveal/hide events:** toggling the blindfold piece visibility (the `v`
   hotkey, or the UI toggle) emits `visibility_changed` events (3.3) with the
   correct before/after state. Every toggle — not just the first — is
   captured.

2. **Every existing help shortcut:** each keyboard shortcut in the extension's
   help surface produces its contracted observable:
   | Shortcut | Action | Expected capture |
   |---|---|---|
   | `j` | focus move input | (focus event — check contract) |
   | `Enter` | submit move | `move_attempt` (via attempt tracker) |
   | `v` | toggle blindfold pieces | `visibility_changed` |
   | `w` | speak whose turn | speech `utterance_started` (help speech) |
   | `z` | speak last move | speech `utterance_started` |
   | `i` | speak full move list | speech `utterance_started` |
   | `s` | speak current position | speech `utterance_started` |
   | `m` | speak game result | speech `utterance_started` |
   | `Esc` | stop all speech | speech cancellation event |

   "Captured" means the event appears in the tracker's emitted stream when the
   shortcut's action runs — the acceptance test drives each shortcut handler
   and asserts the corresponding event.

## 2. What already exists

- `tests/visibility.test.js`: AC1 (3.3 event vocabulary + validators), AC2/3/4
  (transitions + initial state), AC5 (emission gating pre-§5), AC6
  (`help_requested` with `hadUsableContent`), AC7/8 (content.js wiring via
  source inspection).
- `tests/speech.test.js`: utterance lifecycle (started/done/cancel).
- `content.js`: hotkey handlers for each shortcut.
- README.md: documents all shortcuts (the "every existing" list).

**Gaps identified:**
1. No single test drives **every** shortcut and asserts its capture — the
   coverage is per-module (visibility, speech) but not per-shortcut.
2. The `j` (focus) shortcut's capture contract needs checking — does focusing
   the input emit an event, or is it intentionally silent? (Either is fine;
   the contract must pin the actual behavior.)
3. Repeated toggles (`v`, `v`, `v`) — each must emit; no dedup.

## 3. Verification plan

### V1 — static/unit (Node)

- [ ] **AC1.** Reveal/hide: toggle visibility 3 times; assert 3
  `visibility_changed` events with alternating states, in order.
- [ ] **AC2.** Shortcut sweep: for each shortcut in the README list
  (`j`, `Enter`, `v`, `w`, `z`, `i`, `s`, `m`, `Esc`), invoke the handler
  and assert the contracted event is emitted (or document as intentionally
  silent with the reason).
- [ ] **AC3.** `Enter` end-to-end: submit a move via the Enter handler;
  assert `move_attempt` with the input's text (links 7.6 to 7.1).
- [ ] **AC4.** `Esc` end-to-end: start speech, press Esc; assert the
  cancellation event (links 7.6 to 7.7).

### V2 — integration (headless Chrome, optional)

- [ ] **AC5.** Real keyboard events dispatched to the page; assert the
  handlers fire and events emit through the real content-script path.

### V3 — deferred to owner device

- [ ] **AC6.** On the real device: press each shortcut during a bot game;
  confirm the exported `events.jsonl` contains the corresponding records.

## 4. Non-goals

- Adding new shortcuts or changing handler behavior (verification-only).
- Testing Chess.com's own keyboard handling (out of scope).

## 5. Diff discipline

Expected: new tests (acceptance file or additions to `visibility` /
`speech` suites — builder's choice), evidence files, DECISIONS.md entry.
No product-code changes (verification-only). If a shortcut is found
unwired, that's a defect to report, not to fix silently — the builder
reports it and the coordinator decides.
