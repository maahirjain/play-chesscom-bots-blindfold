## 6.7 — Repeatable export — APPROVE

### The exportedAtUtc resolution is honest

The builder's central claim: two exports differ ONLY in the two
`exportedAtUtc` fields. I verified this by probing for
non-determinism in the export pipeline:

1. **Clock reads:** `grep -n "Date.now\|new Date()\|Math.random\|performance.now"
   exporter.js` returns exactly ONE hit — line 54,
   `defaultNowUtcIso()` returning `new Date().toISOString()`. This
   function is called ONLY for `exportedAtUtc` in `buildMetadataJson`
   (line 308) and `buildMediaSyncJson` (line 644), and passed through
   `exportSession` via the injectable `nowUtcIso` dep (lines
   1408–1409, 1542, 1552). There is no other clock read in the
   pipeline. The timestamp cannot be derived from stored data (no
   stored "export time" exists), so the wall clock is the only honest
   source. The builder's resolution is correct, not a dodge.

2. **DOS timestamps:** `dosDateTimeFromIso` (line 1020) takes its
   input from the earliest manifest `createdAtUtc` (line 1074,
   "stored-data proxy"), never the wall clock. Deterministic.

3. **Ordering:** 6.1–6.3 builders use fixed key insertion order
   (pinned by golden tests); 6.3's `compareSegments` is a total order;
   6.5's numbering is deterministic; ZIP central directory follows the
   same order. No iteration over unordered Maps/Sets in the
   serialization path.

4. **Media bytes:** 6.4 pushes original Blob references; CRC-32 is a
   pure function of bytes. Deterministic.

The "labeled exception" framing is accurate: `exportedAtUtc` is
explicitly documented as the one clock read (exporter.js line 7
header comment), injected for testability, and the 6.7 tests pin both
the exception (AC1: different clocks → differ only in the timestamp)
and the rule (AC2: same clock → fully byte-identical).

### The tests are substantive, not theater

- **AC1** runs the REAL `exportSession` (not a mock) with fake DB
  deps, captures both ZIP Blobs, writes them to disk, unzips via the
  SYSTEM `unzip` binary (6.6 AC1 precedent — not a JS ZIP parser that
  could share bugs with the writer), and diffs per-file contents. For
  JSON files it parses and asserts deep-equality modulo
  `exportedAtUtc`; for media it asserts `Buffer.equals`. This is a
  genuine end-to-end repeatability proof.
- **AC2** asserts `a.equals(b)` on the raw ZIP buffers with a fixed
  clock — the strongest possible byte-identity claim.
- **AC3** is a static pin, but I independently verified its premises:
  `setDownloadEnabled(false)` appears exactly ONCE in
  session_controls.js (line 1290, comment "not exportable while
  starting"); the success-path comment "Keep the button enabled for
  re-export" exists (line 905); `refreshDownloadButton()` enables the
  button when `phase === CONTROL_PHASE_IDLE && lastStopResponse !==
  null`, which holds after a successful export. The guarantee is real,
  not aspirational.
- **AC4** asserts zero product-file diffs — I confirmed via `git diff
  HEAD --stat`: 0 lines for exporter.js, sw.js, manifest.json,
  session_controls.js, content.js, recorder.js.

### Non-blocking notes

- **N1:** AC1's fake DB returns chunks via `(seed.chunksBySegment || {})[seg]`,
  which bypasses the real 4.13 compound-key-range read. The ordering
  guarantee (chunks in key order) is therefore assumed, not proven, by
  this test. The 6.4 contract explicitly documents this trust
  ("trusts 6.6's key-order guarantee"). Acceptable — the unit under
  test is repeatability, not chunk ordering.
- **N2:** The `exportedAtUtc` values in the two AC1 exports are
  asserted to equal the injected clock strings exactly. This pins the
  injection seam, which is good, but means a future change to timestamp
  format would break the test rather than the implementation. Not a
  defect.

no filesystem writes. All true. It does not overclaim: "the extension
does not do this for you" (extraction), "cannot choose where the ZIP
lands" (saveAs:false), "analysis happens in your own tools."
