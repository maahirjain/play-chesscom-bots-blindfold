# 7.3 contract — Verify accepted mouse moves are captured even without a keyboard attempt

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.3. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.3 requires demonstrating that when the player makes a move with the
**mouse** (clicking/dragging pieces on the Chess.com board, not typing in the
extension's move input), the move is still captured in the event stream.

The collection architecture makes this possible by design: `observeMoves`
(`chess_utils.js`) watches the Chess.com DOM move list (`.play-controller-moveList
.node.main-line-ply .node-highlight-content`) via MutationObserver. Any move
that Chess.com accepts — whether typed through the extension, clicked with the
mouse, or dragged — appears in that DOM list, and the history tracker emits
`move_confirmed` for it. The attempt tracker (keyboard path) is bypassed
entirely; there is simply no `move_attempt` for a mouse move, which is itself
an honest record (the move was not attempted via keyboard).

"Verified" means: a DOM mutation adding a move to the move list (simulating
what Chess.com does when a mouse move is accepted) produces a `move_confirmed`
event with no preceding `move_attempt` — and the event stream remains
unambiguous about the move's provenance.

## 2. What already exists

- `chess_utils.js` `observeMoves` + `getMoveList`: DOM move-list observation
  (MutationObserver on `document.body`, content comparison not just length —
  3.1.1).
- `tests/history_tracker.test.js` AC1 (observeMoves content comparison):
  covers the observer firing on DOM changes.
- The attempt tracker is only wired to the keyboard input path (`content.js`
  move-input submit handler).

**Gaps identified:**
1. No test demonstrates the **mouse path specifically**: a move appearing in
   the DOM with no keyboard attempt must yield `move_confirmed` and must NOT
   yield a spurious `move_attempt`.
2. The provenance distinction (mouse move = confirmed without attempt) is
   architectural but unpinned.

## 3. Verification plan

### V1 — static/unit (Node with DOM fake)

- [ ] **AC1.** Simulate a DOM move-list mutation (add `e4` to the observed
  list) with no keyboard submission; assert the history tracker emits
  `move_confirmed` for `e4`.
- [ ] **AC2.** Assert no `move_attempt` is emitted for the DOM-observed move
  (the attempt tracker's emit spy stays empty).
- [ ] **AC3.** Mixed sequence: keyboard move (`d4`, with attempt) → mouse move
  (`d5`, DOM-only) → keyboard move (`c4`, with attempt); assert the event
  stream is `[move_attempt(d4), move_confirmed(d4), move_confirmed(d5),
  move_attempt(c4), move_confirmed(c4)]` — each confirmed move is present,
  attempts exist only for keyboard moves.

### V2 — integration (headless Chrome)

- [ ] **AC4.** Drive the real `observeMoves` against a synthetic Chess.com
  move-list DOM in headless Chrome; mutate the DOM as Chess.com would on a
  mouse move; assert `move_confirmed` fires via the real MutationObserver
  path.

### V3 — deferred to owner device

- [ ] **AC5.** On the real device: play a mouse move in a bot game; confirm
  `events.jsonl` contains `move_confirmed` without a preceding
  `move_attempt` for that move.

## 4. Non-goals

- Simulating actual mouse events (clicks/drags) — the collection observes the
  DOM consequence, not the input device; the DOM mutation IS the faithful
  simulation of "Chess.com accepted a mouse move."
- Changing the observation path (verification-only).
