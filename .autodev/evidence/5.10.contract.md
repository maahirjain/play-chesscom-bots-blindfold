# 5.10 contract — After Stop, await final storage acknowledgments and media finalization before presenting export as complete

## 1. Scope

PLAN.md §5.10: "After Stop, await final storage acknowledgments and media finalization before presenting export as complete."

**PLAN evidence:** §(c) "Each game", step 8: "Wait for media finalization and download the game ZIP. Check whether the bundle reports complete or interrupted recording." The user must not be told the recording is complete before it actually is — a premature "done" would lose the post-game reflection audio or the final media segments.

**Current state (verified by the planner):** The Stop sequence (`onStopClick`, session_controls.js) does:
1. `recordStopTermination()` (3.5.4 seam — emits the final lifecycle event),
2. `channelCall(MSG_STOP_STREAMS)` → 4.13's 11-step finalizer (stops recorders, **bounded** final-flush await with per-stream `flushTimedOut`, monitor detach, track release, segment finalization),
3. one final `pollOnce()` (lights to `finalized`),
4. hands the **full** stop response (including `flushTimedOut`) to `onStopComplete` → `BlindfoldSession.onSessionStopComplete` (5.10's seam, currently a no-op passthrough),
5. goes idle ("Start" button) immediately.

**The gap 5.10 closes:** Step 4→5 presents "done" (idle button) **without awaiting the event pipeline's final acknowledgments**. `sender.flush()` — the pump-to-completion that reports `{delivered, pending}` — is never called in the Stop path (verified: zero references in session_controls.js/content.js). Events emitted late in the session (the `recordStopTermination` event itself, final `moment_marker`s, late lifecycle events) may still be queued or unacknowledged when the UI declares the session over. Additionally, nothing surfaces `flushTimedOut` — the Section 4 audit carry-forward explicitly assigns this to §5.10: "`flushTimedOut` is response-only, not persisted, and 4.14's status does NOT surface it — §5's Stop flow must surface it."

**What 5.10 does:** Insert a bounded final-acknowledgment await into the Stop sequence (event-queue drain via `sender.flush()`), compute an honest completion verdict from the stop response + flush result, surface `flushTimedOut` and any undelivered events in the completion presentation, and retain the verdict for §6's export assembly. The button must not present a clean idle state before the acknowledgments are awaited.

**What 5.10 does NOT do:** It does not generate the export bundle (§6's job — 6.1–6.8). It does not re-run or extend the media finalizer (4.13's bounded flush is the media finalization; 5.10 consumes its result). It does not add retry loops beyond the sender's existing 2.5 discipline.

## 2. Definitions

### 2.1 "Final storage acknowledgments" (event pipeline)

The content-script sender's queue must be drained through the acknowledged-delivery discipline:

- Call `opts.sender.flush()` after the stop-streams response arrives (so every session event, including the `recordStopTermination` event emitted at Stop start, is in the queue).
- `flush()` resolves (never rejects) with `{delivered, pending}` when the pump stops: queue drained, no transport, or an attempt failed (2.5 schedules one retry; the flush does not wait for it).
- **Acknowledged** = `pending === 0` after flush. **Undelivered** = `pending > 0` (transport dead, writer rejecting, or no ack). Both are honest outcomes; only the presentation differs.

The flush is inherently bounded (the pump stops on first failure); 5.10 adds no extra timeout. If the transport is unavailable, flush resolves immediately with the queue intact — the verdict reports undelivered events honestly rather than hanging the UI.

### 2.2 "Media finalization" (media pipeline)

4.13's finalizer, already executed inside `MSG_STOP_STREAMS`. 5.10 does not re-run it. The stop response carries:

```js
{
  ok: true,
  markerId: <string|null>,       // sync-marker id; null on marker failure (never a Stop failure)
  finalizedAtUtc: <string>,      // when the finalize pass ran
  streams: {
    microphone: { ok: true, segments: [...], flushTimedOut?: true },
    screen:     { ok: true, segments: [...], flushTimedOut?: true },
    webcam:     { ok: true, segments: [...], flushTimedOut?: true }
    // failed kinds: { ok: false, segments: [], <failure detail> }
  }
}
```

"Media finalization" for 5.10's purpose = this response has arrived with `ok: true`. Per-stream `flushTimedOut: true` means that stream's final MediaRecorder data was not flushed within the bound — the last seconds of that stream may be missing. This is the response-only fact §5.10 must surface (audit carry-forward).

### 2.3 "Presenting export as complete"

§6 (export bundle generation) is not implemented. 5.10 therefore defines the **completion state** and its **presentation**, which §6 will consume:

- **Completion verdict** (pure function of stop response + flush result), one of:
  - `'complete'` — all streams `ok`, no `flushTimedOut`, event queue drained (`pending === 0`).
  - `'complete-with-warnings'` — the session finalized, but: any stream has `flushTimedOut: true`, any stream `ok: false`, or `pending > 0` events undelivered. Each warning names the specific fact (which stream, how many events).
  - `'failed'` — the stop itself failed (existing path: stays in "Stopping…" with `stop-failed:<err>`; 5.10 does not change this).
- **Presentation:** the control must not show a clean idle ("Start", no detail) before the flush completes. During the flush await, the button shows a transitional "Finalizing…" state (following the "Stopping…" precedent). On verdict:
  - `'complete'` → idle, button "Start", no warning detail. (The session is over; §6 will later add the download.)
  - `'complete-with-warnings'` → idle, button "Start", **with the warnings as the button detail text** (honest, following the existing `stop-failed:<err>` detail pattern) — e.g. `finalize-warnings:webcam-flush-timed-out;3-events-undelivered`. The user sees that the bundle (§6, step 8: "check whether the bundle reports complete or interrupted") will be incomplete.
  - The full verdict (stop response + flush result + computed warnings) is retained via the existing `getLastStopResponse` seam (extended to include the flush result) for §6's `media-sync.json` "known gaps" and export completeness reporting.
- **What must NOT be shown prematurely:** the button must not return to plain idle ("Start" with null detail) while the flush is still in flight, and must never present `'complete'` when warnings exist. A premature clean idle is the masquerade 5.10 exists to prevent.

### 2.4 flushTimedOut surfacing (audit carry-forward)

`flushTimedOut` is response-only (not persisted, not in 4.14's status). 5.10 surfaces it in two places:
1. **Immediately:** in the completion presentation's warning detail (per-stream naming, e.g. `webcam-flush-timed-out`).
2. **Durably:** in the retained stop verdict (for §6 — `media-sync.json` lists "known gaps"; the flush timeout is a known gap in the media).

5.10 does not persist it to a store itself (no new stores); retention is in-memory via the existing `lastStopResponse` mechanism, extended.

## 3. Stop-sequence ordering (5.10's changes)

Current (5.1): `recordStopTermination` → `MSG_STOP_STREAMS` → `pollOnce` → `onStopComplete(stopResp)` → idle + `clearRecorderSession()`.

5.10 inserts the acknowledgment await between the stop response and the idle transition:

1. `recordStopTermination(reason, result)` — unchanged (emits the final lifecycle event into the sender queue).
2. `channelCall(MSG_STOP_STREAMS)` — unchanged (4.13 finalizes media; bounded flush with `flushTimedOut`).
3. On `{ok:true}`: `pollOnce()` — unchanged (lights to `finalized`).
4. **NEW — transitional UI:** button shows "Finalizing…" (enabled, so a hung flush never traps the user; the existing retry philosophy) while the flush runs. Phase stays `STOPPING`.
5. **NEW — `opts.sender.flush()`:** await the single flush promise. It resolves with `{delivered, pending}`; it never rejects (sender contract). No additional timeout — the pump is self-bounding. On flush completion (regardless of `pending`):
6. **NEW — `computeCompletion(stopResp, flushResult)`:** pure function → `{verdict, warnings[]}` per §2.3.
7. `lastStopResponse = {stopResp, flushResult, verdict, warnings}` — extended retention for §6 (the existing `getLastStopResponse` handle method returns the enriched object; still null before any Stop).
8. `opts.onStopComplete(...)` — called with the enriched verdict object (backward compatible: it still carries the full stop response; the 5.1 test pins the handoff, which 5.10 extends, not breaks).
9. Idle transition — unchanged mechanics (`stopPolling`, `setSlots(null,null)`, `resetReadiness`, `setMarkerEnabled(false)`, form re-enable), except the button detail carries warnings on `'complete-with-warnings'`.
10. `clearRecorderSession()` — unchanged (best-effort, after successful finalization).

**Failure paths (unchanged):** if `MSG_STOP_STREAMS` fails (`{ok:false}` / no-response), the control stays in "Stopping…" with `stop-failed:<err>` — the flush is not attempted (there is no finalized media to acknowledge against; the session is retained for retry per 5.1). 5.10 does not alter this.

**Ordering rationale:** the flush runs after the stop response (not before) because the finalizer's media flush and the event queue are independent pipelines; running the event flush after media finalization means the `finalizedAtUtc` and segment list are already known when the verdict is computed. The `recordStopTermination` event is queued before the flush by construction (step 1 precedes step 5).

## 4. Acceptance criteria

### V1 — static/unit

- [ ] **AC1.** `computeCompletion(stopResp, flushResult)` truth table: all-ok + drained → `'complete'`; any `flushTimedOut: true` → `'complete-with-warnings'` naming the stream; any stream `ok: false` → warnings naming it; `pending > 0` → warnings with the count; combinations accumulate all warnings. Malformed inputs → honest `'complete-with-warnings'` (fail-closed toward warning, never silent `'complete'`).
- [ ] **AC2.** Stop sequence awaits `sender.flush()` before the idle transition: with a queued event at Stop, the flush is called exactly once and the idle transition happens after the flush promise resolves (not before).
- [ ] **AC3.** `flushTimedOut` surfacing: a stop response with `streams.webcam.flushTimedOut: true` produces a warning naming `webcam`; the warning appears in the button detail text and in the retained verdict.
- [ ] **AC4.** Undelivered events: `flushResult.pending > 0` produces a warning with the count; the verdict is never `'complete'`.
- [ ] **AC5.** Button never shows clean idle during the flush: between stop-response arrival and flush resolution, the button shows the transitional "Finalizing…" state (not "Start" with null detail).
- [ ] **AC6.** Failure paths unchanged: `MSG_STOP_STREAMS` `{ok:false}` → stays "Stopping…" with `stop-failed:<err>`, no flush attempted, session retained for retry.
- [ ] **AC7.** Diff discipline: changed files exactly the §7 list; no new channel messages (offscreen MSG_* stays 24; SW envelope stays 7); no new event types, stores, or permissions; PLAN.md unmodified.

## 5. Explicit non-goals

- Generating the export bundle or download UI (§6 owns 6.1–6.8; 5.10 only produces the verdict §6 consumes).
- Re-running, extending, or re-tuning the media finalizer (4.13's bounded flush is final; 5.10 surfaces its result).
- Additional sender retry loops beyond the existing 2.5 discipline (one flush await, then honest reporting).
- Persisting `flushTimedOut` or the verdict to a new store (in-memory retention via the existing seam; §6 reads it at export time).
- Changing the stop-failure path (stays in "Stopping…" for retry).
- 5.9's game-boundary handling (untouched), 5.8's marker (untouched).

## 7. Open questions for the builder

1. **Wording:** the exact transitional label ("Finalizing…") and warning-detail format — builder's choice, subject to "must not claim complete prematurely" and the existing detail-text conventions (`stop-failed:<err>` precedent suggests `finalize-warnings:<w1>;<w2>`).
2. **`onStopComplete` payload shape:** whether to pass the enriched `{stopResp, flushResult, verdict, warnings}` object or keep the raw stop response and expose the verdict via `getLastStopResponse` — builder's choice, but the 5.1 handoff test (`onStopComplete` receives the full stop response) must keep passing.
3. **Flush failure isolation:** `sender.flush()` never rejects per its contract, but the builder should still guard the await (defensive try/catch → treat as `{delivered: 0, pending: <unknown>}` → warning, never a hung Stop).
