## What was built

### 1. Pure `computeReadiness()` policy function (session_controls.js)

`computeReadiness(streamStatuses, senderStatus, startResults, initialEmitObserved)` — pure, no DOM/timers/chrome.*, follows the `classifyStreamStatus` precedent.

**Signature note (contract open question #1 resolution):** the contract specified three params; I added a fourth, `initialEmitObserved` (boolean). Rationale: the storage-ack mechanism ("≥1 event acknowledged since Start") requires knowing that an event was emitted in this context. The sender's `getStatus()` alone cannot distinguish "queue drained because all events were acked" from "queue was always empty." The boolean is set true after the Start chain's `emitPageStart` succeeds (so ≥1 event was definitely emitted) and false on boot adoption (the emission happened in a previous context — ambiguous, never ready). This is the honest mechanism the contract asked for: it reflects actual writer acknowledgments, not the mere act of sending.

**Storage-ack mechanism (honest):**
- The sender dequeues exclusively on positive ack (`isPositiveAck` in sender.js), so `pendingCount === 0 && lastError === null` with an observed initial emission PROVES all emitted events were durably acknowledged.
- `lastError` taxonomy mirrors 2.8's `classifySenderStatus`: transient (`send-timeout`, `no-ack`, `transport-error:*`) → not-ready but not blocked (retrying); persistent (`write-failed:*` or unrecognized — fail-closed) → not-ready and blocked.
- No `sender.js` changes were needed — `getStatus()` already exposes everything required.

**Verdicts:**
- `'ready'` — all three streams `recording-healthy` AND storage confirmed.
- `'not-ready'` — with raw-fact reasons; `blocked` flag distinguishes confirmed failures (failed-not-started, degraded, write-failed, unconfirmed) from mere pending.
- `'unknown'` — streamStatuses null/malformed (query failed). Never defaults to ready.

### 2. Readiness badge presentation

- New `span.blindfold-readiness` in the control cluster (after the three lights), with `data-readiness` attribute (`hidden`|`waiting`|`ready`|`not-ready`|`unknown`).
- Text: "Waiting for recording…" (pending), "Ready — recording" (ready, latched), "Not ready: <reasons>" (blocked), "Recording status unknown" (query failed). Hidden while idle.
- **Latched per session:** once `'ready'`, stays ready (no flapping on later degradation; lights still show the truth).
- **Change-detected:** no DOM churn per poll (same pattern as lights).
- **Does not gate:** session becomes active on start-streams (5.1 behavior preserved); Stop always available.

### 3. Poll-loop wiring

- `pollOnce()` now reads `sender.getStatus()` defensively (missing `getStatus` or throwing → storage unconfirmed, never premature ready) and feeds `computeReadiness`.
- Query failures render "Recording status unknown" (unless latched).
- `pageStartEmitted` set true after successful `emitPageStart`; cleared on abort/Stop/new Start.
- `resetReadiness()` helper called on all idle transitions (abortStart, localAbortStart, manual abort paths, Stop completion).

### 4. No overlay.css changes

Per contract §7 diff discipline (changed files: session_controls.js + tests + evidence + DECISIONS.md only), the badge uses text content and `data-readiness` attributes without new CSS. The badge is functional and honest without styling; visual polish is out of scope.
