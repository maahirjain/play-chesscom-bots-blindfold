# 2.8 contract — Surface write failures and storage-capacity problems in the session status indicator

## 1. Scope

PLAN.md §2.8: "Surface write failures and storage-capacity problems in the
session status indicator."

This task builds the status-indicator UI that sender.js anticipated
("2.8: status-indicator UI (only getStatus() is provided)") and the
failure classification that 2.5/2.6 deferred to it:

- 2.5 carry-forward: "2.8 should visibly distinguish persistent writer
  rejections from transient transport stalls using pendingCount,
  lastError, and retryScheduled."
- 2.6/SF-1 carry-forward: 2.8's status surface should distinguish
  persistent `CorruptSequenceState` from transient stalls.

## 2. Definitions

**Session status indicator.** A minimal in-page DOM element (new module
`status_indicator.js`, instantiated by content.js) that renders the
content-script sender's recorder health as one of three visual states.
It is a health light, not a dashboard: it shows a state and the raw
failure code as a tooltip/title. It shows no counts, no history, no
metrics, and has no user interaction. (PLAN forbids dashboards; raw-data
collection scope only.)

**Health states** (closed set, derived from `sender.getStatus()`):

| state | meaning | visual |
|---|---|---|
| `healthy` | no recorded failure (`lastError === null`) | green |
| `degraded-retrying` | transient stall, recovery scheduled | amber |
| `failed-persistent` | writer rejected the write or unknown failure; will not self-recover | red |
| `failed-storage-full` | storage capacity exhausted | red (distinct title text) |

**Failure taxonomy** (closed — the sender only produces these
`lastError` shapes; see sender.js `recordAckFailure` and the pump):

- Transient family: `send-timeout`, `no-ack`, `transport-error:<name>`.
- Persistent family: any `write-failed:<code>`, including
  `write-failed:unavailable`, `write-failed:CorruptSequenceState`,
  `write-failed:DataError`, and any future writer code.
- Storage-capacity: `write-failed:QuotaExceededError`. The writer's
  `toWriteFailed` already propagates the DOMException name via
  `errorName`, so quota failures arrive at the sender with this exact
  code today. No writer.js change is needed.

**Fail-closed rule.** Any non-null `lastError` not in the transient
family is classified persistent. A failure we do not understand must
never be presented as "will recover."

## 3. Design

### 3.1 Classification is a pure function, separate from rendering

New module `status_indicator.js` (BlindfoldSession convention:
dependency-free classic script → guarded global → IIFE `'use strict'`
→ Node shim) exports:

- `classifySenderStatus(status)` — pure. Input: the object returned by
  `sender.getStatus()` (`{pendingCount, lastError, transportAvailable,
  retryScheduled}`). Output: a frozen
  `{state, detail}` where `state` is one of the four health states and
  `detail` is the raw `lastError` string (or `null` when healthy).
  Throws `TypeError` on malformed input (per AGENTS.md error
  conventions). No DOM, no timers — independently unit-testable.
- `installStatusIndicator(sender, options)` — creates the DOM element,
  polls `sender.getStatus()` on an injectable interval, re-renders only
  on state/detail change. Never throws into the caller (indicator
  failures must not break gameplay); invalid sender → `TypeError` at
  install time, before any timer starts.

`sender.js` is **unchanged**: `getStatus()` already exposes
`pendingCount`, `lastError`, `transportAvailable`, `retryScheduled` —
everything the classifier needs. No additive fields, no behavior
change.

### 3.2 Classification rules

1. `lastError === null` → `healthy` (detail null), regardless of
   `pendingCount`. A non-empty queue with no failure is normal draining
   (including the pre-transport "waiting for SW" state).
2. `lastError` in the transient family → `degraded-retrying`, detail =
   lastError. (Whether or not a retry is currently scheduled: a
   transport failure with no retry scheduled and no transport available
   is still transient in nature — recovery is possible when the SW
   wakes. The `retryScheduled` flag remains available in the raw status
   for debugging but does not change the state.)
3. `lastError === 'write-failed:QuotaExceededError'` →
   `failed-storage-full`, detail = lastError.
4. `lastError` starts with `'write-failed:'` (any other code) →
   `failed-persistent`, detail = lastError. This covers
   `CorruptSequenceState`: the writer will reject every subsequent
   write for the session, so the indicator latches red — honest, and
   distinct from a transient stall.
5. Any other non-null `lastError` → `failed-persistent` (fail-closed).

### 3.3 Storage-capacity problems: reactive surfacing only

"Storage-capacity problems" are surfaced reactively via
`write-failed:QuotaExceededError` on the write path. Deliberately NOT
included:

- No `navigator.storage.estimate()` polling. Rationale: a new timer, new
  failure modes, and cross-browser estimate unreliability, for a signal
  that is strictly weaker than the ground truth (an actual quota failure
  on write). The quota error is the honest capacity signal; the
  indicator shows it the moment it occurs.
- No proactive warnings, no usage bars (dashboard territory).

### 3.4 Status lifecycle

The indicator is a pure function of `getStatus()`: the sender already
clears `lastError` to `null` on the next positive ack, so transient
failures clear when the pump recovers. Persistent writer rejections
latch: the head event never dequeues, so the indicator stays red until
the context ends. There is no dismiss interaction — the indicator
reflects the truth; hiding a persistent failure would falsify the
record.

### 3.5 UI constraints

- One small element adjacent to the extension's existing move-input UI
  (the extension's own DOM anchor; falls back to a fixed corner only if
  the anchor is absent). Must not alter chess.com layout or gameplay.
- Three colors (green/amber/red); the element's `title` carries the raw
  `detail` code (e.g. `write-failed:QuotaExceededError`).
- Re-renders only on state/detail change (no DOM churn per poll).
- Styles in overlay.css (additive classes only).
- The indicator never throws into page code; a broken indicator degrades
  to absent, never to a gameplay break.

### 3.6 content.js wiring

content.js gains the install call (a few lines, next to the existing
sender/lifecycle wiring), passing `BlindfoldSession.sender`. No other
content.js changes.

### 3.7 Explicitly out of scope

- Browser-action badge/popup (would need manifest `action`, SW-side
  status aggregation, and a new content→SW status message path — all
  unneeded machinery; the in-page indicator is where the user already
  looks during play).
- SW-side status surface (the SW has no UI; the sender owns the queue).
- New message kinds; writer.js, db.js, session_store.js, lifecycle.js,
  event_envelope.js changes (all byte-identical to HEAD).
- Manifest changes; new permissions.
- 2.7 discontinuity markers in the indicator (they are stream events,
  not recorder health); §6 export status; 2.9 retention.
- Alert sounds, auto-recovery, failure dismissal.

  `installStatusIndicator`.
- [ ] **AC2.** `classifySenderStatus`: `lastError: null` → healthy with

## 5. Notes for the builder

- The `''` empty-string edge in AC6: the sender never produces it
  (`lastError` is null or a non-empty string). Specify the behavior
  explicitly in code and test it; recommended: treat falsy-but-not-null
  as healthy is WRONG (it would hide a bug) — treat any non-null value
  via the classification table, with `''` → `failed-persistent`
  (fail-closed). Document the choice.
- `transportAvailable: false` with `lastError: null` and queued events
  (SW not yet awake) is `healthy` per rule 1 — the indicator must not
  cry wolf before the first attempt.
- Keep the DOM footprint tiny: one element, one text node (or none —
  color + title may suffice; the builder may include a minimal glyph
  like "●" but no text metrics).
- Cumulative test-pin precedent: earlier tasks' diff-discipline tests
  pin byte-identical files and git-status allowlists; evolve them
  honestly (exact-diff assertions for legitimately changed files,
  allowlist extensions with justification comments), never weaken
  silently.
