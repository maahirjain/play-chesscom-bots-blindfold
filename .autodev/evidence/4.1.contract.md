# Task 4.1 contract — dedicated extension recording context

PLAN.md §4.1: "Create a dedicated extension recording context that remains alive
across Chess.com page refreshes; do not host recording solely in the content
script or a transient popup."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Architecture decision

**The recording context is an MV3 offscreen document** (`recorder.html` +
`recorder.js`), created and supervised by the service worker. This is the
sanctioned MV3 pattern for the whole of Section 4:

| Candidate | Verdict |
|---|---|
| Offscreen document (`chrome.offscreen`) | **Chosen.** Independent of content tabs (survives page refresh by construction); not subject to the SW 30-second idle termination; the documented Chrome pattern for `getUserMedia`/`getDisplayMedia` + `MediaRecorder` in MV3 extensions. |
| Service worker itself | Rejected. Event-driven, killable at any time; `getUserMedia`/`getDisplayMedia`/`MediaRecorder` are unavailable or unreliable there. |
| Content script on chess.com | Rejected by PLAN 4.1 explicitly: dies on page refresh/navigation, taking in-flight recordings with it. |
| Transient popup / action page | Rejected by PLAN 4.1 explicitly: closes when focus leaves. |
| Persistent extension tab (`chrome-extension://` page) | Rejected. User-visible, user-closable, and redundant given offscreen documents exist for exactly this purpose. |

Supporting evidence: Chrome extension recorder patterns (e.g. the offscreen +
`getDisplayMedia` + `MediaRecorder` capture pattern with the SW owning one
session and `chrome.storage.session` state surviving SW restarts) are the
established community approach; Chrome keeps offscreen documents alive for
active media reasons rather than terminating them like service workers.

### Files owned by 4.1

- `recorder.html` — offscreen document shell. Loads `recorder.js` only. (No
  manifest listing needed: offscreen documents are loaded by URL from the
  extension package via `chrome.offscreen.createDocument`.)
- `recorder.js` — the recording-context module. Follows repo house
  conventions: dependency-free classic script → guarded `BlindfoldSession`
  global → IIFE `'use strict'` → Node `module.exports` shim for tests.
  **Recording platform APIs (`MediaRecorder`, `getUserMedia`,
  `getDisplayMedia`) live ONLY here — never in content scripts, never in the
  SW.** (Existing test pins in attempt_tracker/visibility/speech/
  game_lifecycle suites assert these tokens are absent from content scripts;
  4.1 must not trip them.)
- `manifest.json` — gains the `"offscreen"` permission. No other new
  permissions in 4.1 (device permissions belong to 4.2–4.4).
- SW side: a new module `recording_host.js`, loaded via `importScripts` in
  `sw.js`, owning offscreen-document supervision. `sw.js` itself stays a thin
  registration entry point (2.1 precedent: no behavior beyond imports).

### chrome.offscreen reasons

`createDocument` is called once with the full Section-4 reason set —
`USER_MEDIA` (4.2 mic, 4.4 webcam), `DISPLAY_MEDIA` (4.3 screen/tab),
`AUDIO_PLAYBACK` (4.7 game/extension audio, 4.11 audible sync marker) — and a
justification string citing synchronized session recording for blindfold
chess research. Rationale: there is exactly one offscreen document per
extension; it exists to host all of Section 4, so declaring the full reason
set up front is honest, and avoids a later task having to recreate the
document to widen reasons. The document performs no capture in 4.1 itself.

Constraint (documented, not solved here): `chrome.offscreen` requires
Chrome 109+. The repo declares no `minimum_chrome_version` today; 4.1
documents the requirement in DECISIONS.md and degrades honestly —
`ensureRecordingContext()` reports `{ok:false, reason:'offscreen-unavailable'}`
on older Chrome rather than throwing.

## 2. Lifecycle guarantees

1. **Survives Chess.com page refresh/navigation.** The offscreen document is
   extension-owned and independent of every content tab. A refresh of
   `chess.com/play/computer` cannot touch it. (V2 proves this.)
2. **Survives SW restart.** The offscreen document is a separate document
   process; when the SW is killed and restarted, the document keeps running.
   On every SW startup, `recording_host.js` runs `ensureRecordingContext()`:
   `chrome.offscreen.hasDocument()` → if present, no-op + status ping to
   re-sync in-memory state; if absent, recreate. Recording in progress (later
   tasks) continues in the document uninterrupted by the SW restart.
3. **Recreatable when lost.** If the browser kills the document (memory
   pressure) or the extension reloads/updates (which closes it), the next
   `ensureRecordingContext()` / status ping recreates it. The gap is
   observable — later task 4.9 logs it as an explicit discontinuity; 4.1
   only guarantees the loss is *detectable* (last-known state vs fresh boot).
4. **SW-may-die-during-create hazard.** `createDocument` is async and the SW
   can be terminated mid-call. `ensureRecordingContext()` is idempotent and
   retry-safe: concurrent/overlapping calls collapse onto a single in-flight
   creation (guard flag), and every call re-checks `hasDocument()` first.
   It is invoked lazily — at SW startup AND on demand before any recording
   command (later tasks) — never assumed to have completed from a previous
   SW lifetime.

## 3. SW ↔ recording-context message contract

4.1 owns the channel; later tasks add recording commands on it. Envelope:

```js
{ kind: 'recorder', msg: '<name>', v: 1, ...fields }
```

- `kind:'recorder'` is namespaced so it can never collide with the writer's
  `kind:'event'` intake (writer.js) on the same `chrome.runtime.onMessage`
  bus. Both directions validate the envelope and ignore unknown `msg`
  values (lenient-on-input).
- `v: 1` versions the protocol; receivers reject (with `{ok:false}` ack,
  never throw) unknown major versions.

Messages defined in 4.1:

| Direction | msg | Purpose |
|---|---|---|
| offscreen → SW | `recorder-ready` | Sent once on document load. Includes `bootId` (uuid-v4 per document boot) and `bootTime` (UTC ISO). Lets the SW distinguish a fresh document from a surviving one. |
| SW → offscreen | `recorder-ping` | Liveness probe. |
| offscreen → SW | `recorder-pong` | Reply: `{ ok, bootId, state, nowMonotonicMs }`. `nowMonotonicMs` is a `performance.now()` reading — the hook later tasks (4.10/4.12) use for clock-anchor alignment. |

Timeout: the SW's ping helper rejects after an injectable timeout
(default 5 s) with a plain `Error('recorder-unreachable')` — the
unavailable-platform convention — so callers can treat "document gone" as
a normal branch, not an exception storm.

### Relationship to the existing event pipeline (2.3/2.4)

Recording-*lifecycle* events (segment started/stopped, discontinuities —
built in 4.8–4.13) travel the **existing** path: the offscreen document
sends `{kind:'event', ...}` directly via `chrome.runtime.sendMessage` to
the SW's transactional writer (writer.js), which accepts messages from any
extension context. 4.1 builds **no relay**: the writer stays the single
intake, preserving append-sequence and transactional guarantees.
4.1 documents this reuse; the events themselves are later tasks.

### Relationship to chunk storage (2.2/4.8)

Media chunk *bytes* (Blobs, potentially hundreds of MB) must NOT travel
through SW messaging. The offscreen document writes them **directly to the
extension-owned IndexedDB** (2.2) — same extension origin, shared storage
partition. 4.8 defines the chunk schema; 4.1 only establishes that the
document has direct IDB access and that the SW never sees chunk bytes.

## 4. What 4.1 builds vs later tasks

4.1 (this task):
- `recorder.html`, `recorder.js` (context skeleton: boot, ready
  announcement, ping/pong responder, message-envelope validation —
  **no capture code**).
- `recording_host.js` (ensure/create supervision, ping with timeout,
  SW-startup wiring).
- Manifest `"offscreen"` permission.
- Message-envelope contract (above).
- DECISIONS.md entry: offscreen choice, reason set, Chrome 109+ note,
  direct-IDB chunk-write decision, writer-intake reuse decision.

Explicitly NOT 4.1 (later tasks own these; 4.1 must not stub them):
- 4.2/4.3/4.4 device selection and permission flows.
- 4.5 format verification and manifest.
- 4.6 starting streams; 4.7 audio routing.
- 4.8 chunk schema and incremental writes.
- 4.9 track mute/end/error/discontinuity logging.
- 4.10 segment IDs and clock anchors (beyond the pong hook).
- 4.11 sync marker; 4.12 timecode/offsets; 4.13 Stop finalization;
  4.14 per-stream status.

## 5. Acceptance criteria

- AC1 (V1): `recorder.js` loads in Node via the shim; `ensure`-side pure
  logic (envelope validation, version check, idempotent-create guard) is
  unit-tested with an injected `chrome` mock.
- AC2 (V1): `manifest.json` contains the `"offscreen"` permission and no
  other permission changes vs 4.1's parent commit.
- AC3 (V1): Concurrent `ensureRecordingContext()` calls collapse to one
  `createDocument` call (unit-proven with mock).
- AC4 (V1): Unknown `msg` values and unknown protocol versions are ignored /
  rejected with `{ok:false}` — never throw, never crash the SW listener.
- AC5 (V1): On a platform without `chrome.offscreen`, ensure reports
  `{ok:false, reason:'offscreen-unavailable'}` (plain data, no throw).
- AC6 (V1): New/changed files only: `recorder.html`, `recorder.js`,
  `recording_host.js`, `manifest.json` (permission), `sw.js` (import line),
  tests, evidence. Content scripts byte-identical (the media-API pins stay
  green).
- AC7 (V1): `recorder.js` contains no `MediaRecorder`, `getUserMedia`, or
  `getDisplayMedia` references (4.1 hosts no capture; pin-test it).
- AC8 (V2): In real Chrome, after SW startup the offscreen document
  exists (`hasDocument()` true) and answers `recorder-ping` with a matching
  `bootId`.
- AC9 (V2): Reloading the Chess.com content page leaves the document alive:
  same `bootId` before and after reload.
- AC10 (V2): After a forced SW restart (terminate + wake), the SW
  re-discovers the surviving document (same `bootId`, no duplicate
  document — `createDocument` is not called twice; only one document ever
  exists).
- AC11 (V2): Killing the offscreen document is detected: the next ping
  fails with `recorder-unreachable` and the following ensure recreates it
  with a *new* `bootId`.
- AC12 (V3, deferred to §7/owner device): offscreen document stays alive
  across a real multi-minute idle gap on the owner's machine with no
  recording running (documents Chrome's actual keep-alive behavior on the
  target device; a failure here becomes a 4.9 discontinuity case, not a
  4.1 defect).

## 6. Non-goals

- No actual media capture, no device enumeration, no permission prompts.
- No recording UI of any kind (5.1 owns Start/Stop controls).
- No chunk storage schema (4.8), no segment/manifest records (4.10),
  no sync marker (4.11), no timecode (4.12).
- No `minimum_chrome_version` manifest change (documented constraint only).
- No changes to the 2.x event pipeline semantics; the writer intake is
  reused as-is.
