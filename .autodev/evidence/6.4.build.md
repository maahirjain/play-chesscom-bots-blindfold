## What was built

**`assembleSegmentChunks({chunks})`** (async, pure) in `exporter.js`:

- Takes one segment's `media_chunks` rows (in `[segmentId, chunkIndex]` key
  order, read by 6.6's orchestration) and returns
  `{parts: Blob[], byteLength, crc32, chunkCount}`.
- **Byte-concatenation, zero transcoding:** processes chunks in input order
  (trusts 6.6's key-order guarantee; documented in code and contract §3).
  No bytes added, removed, or transformed.
- **Streaming:** one Blob per chunk (original references pushed to `parts`,
  not copies); CRC-32 updated incrementally per chunk. JS-heap is
  O(largest chunk), never O(file). The precomputed CRC feeds 6.6's ZIP
  data descriptors (general-purpose flag bit 3 — standard streaming-ZIP).
- **Gaps are honest:** chunkIndex gaps (e.g. `[0, 2, 5]`) concatenate as-is;
  no invention, interpolation, or re-indexing. Empty input → zeroed result.
- **Fail-closed:** non-array, missing/non-Blob `data`, duplicate or negative
  `chunkIndex` → `TypeError` naming the chunk.

**CRC-32 helper:** table-driven ISO 3309 implementation, generated once at
module load. Exported as `BlindfoldSession.EXPORTER_CRC32_TABLE` for 6.6's
use and test cross-checking.
