## Findings

### Timeout-vs-late-ack race (contract §7's stress-test question) — CORRECT

I verified the implementation genuinely races rather than misattributing:

- Each `step()` mints its own `timeoutError` (closure-private per attempt)
  and its own `timeoutPromise`; the rejection handler discriminates by
  **identity** (`err === timeoutError`), not message text. A transport
  cannot forge the token — it never escapes the closure.
- The loser is discarded because the loser's `.then` handlers belong to
  that attempt's already-settled race: a late ack from attempt N can only
  invoke attempt N's handlers, which already ran. My P1 probe
  (timeout → retry in flight → original late ack with matching eventId →
  attempt-2 ack) confirmed: no double-dequeue, no state corruption,
  exactly-once dequeue of the retried head (`sender.js:283-322`).
- 50 rapid ack/timeout race ties: all drained exactly once (P2).
- Post-timeout transport rejection: zero `unhandledRejection` — the race
  subscribes both promises, so the loser always has handlers (P3).
- Fast ack clears the timeout handle; no stray timer survives (P5).

### Retry-timer discipline — CORRECT

- At-most-one invariant holds: all `retryTimerId` mutations are synchronous
  in one thread; `scheduleRetry()` no-ops when one is pending, when the
  queue is empty, or when no transport resolves; `onRetryTimer()` nulls
  the handle *before* kicking; every new pump run calls `clearRetry()`
  first (`sender.js:159-186, 229`).
- Hammering probe (interleaved `emit()`/`flush()` under continuous
  failure): retries stayed bounded at ~1 per interval, no stacking (P4);
  recovery drained fully with no phantom sends afterwards.
- Drain and no-transport paths call `finish()` directly, never
  `failAttempt()` — no retry is scheduled in either case
  (`sender.js:262-266`; AC6 test pins the no-transport case).

### Uniform retry / head-of-line blocking — ACCEPTED (contracted)

AC9 pins the behavior: even a deterministic `event-id-content-mismatch`
reschedules a retry, and the queue blocks behind the poison head to
preserve order. I stress-tested whether this can *silently* wedge a
session: it cannot be silent — `lastError` carries the writer's exact
error string, `retryScheduled: true`, and `pendingCount` grows. The
mission's prime directive is never-silently-drop, and the resends are
byte-identical and idempotent via 2.4's dedup. The realistic poison
(`QuotaExceededError`) recovers by draining in order once quota is freed.
This is the right call for raw-data collection. See NOTE-1 for the 2.8
consequence.

### No pagehide flush — AGREE with the contract's rejection

A fire-and-forget send at unload cannot be acked, so durability would be
unknown — exactly the uncertainty the mission forbids. The honest
mechanism is `sourceSeq` gaps plus 2.7's discontinuity marking, as the
contract states. No change requested.

### Fixed 5 s interval, no backoff — ACCEPTED

One sender per context means no herd; each retry is one `sendMessage` +
one timer per 5 s (negligible even in persistent failure); backoff would
only delay recovery from the transient case. Background-tab throttling
(~1 s observed) slows but does not break the cadence — documented in
DECISIONS.md #11.

## NOTEs

- **NOTE-1 (for 2.8):** under uniform retry, a permanently-rejected head
  (e.g. quota exhaustion) wedges the queue *loudly* but indefinitely.
  2.8's status surfacing should distinguish persistent `{ok:false}`
  (`lastError` writer string, retrying forever) from transient transport
  failure, so the owner can see a poisoned head vs. a recovering stall.
  `getStatus()` already provides all three signals
  (`pendingCount`, `lastError`, `retryScheduled`).
- **NOTE-2:** `mock.timers.tick()` runs timer callbacks synchronously
  without interleaving microtasks — each chained retry needs its own
  `advance()` (documented in the AC4 test NOTE). Future test authors
  extending the 2.5 block should read that NOTE first.
- **NOTE-3:** `err === timeoutError` identity discrimination is safe only
  because `timeoutError` is per-attempt closure-private. If the timeout
  mechanism is ever refactored (e.g. shared error instance), this must
  become a generation token — noted here so a future refactor doesn't
  silently break it.
- **NOTE-4:** the no-timer fallback (`setTimeout` unavailable → fail fast
  as timeout, `scheduleRetry` silently returns) leaves the queue stalled
  with `retryScheduled: false`, which 2.8 would read as "stalled with
  nothing scheduled (a bug)". Documented in the contract; unreachable in
  production (timers always exist). No change, just recorded.
- **NOTE-5:** diff-discipline allowlists are now mutually cumulative
  across tasks (2.4's allowlist admits 2.5's files and vice versa). The
  pattern works but each task must extend the previous task's allowlist —
  a small cumulative maintenance cost, accepted.
- **NOTE-6:** DECISIONS.md #11 accurately records the timeout race
  semantics, the pagehide rejection rationale, and the throttling
  observation. No correction needed.
