# 5.8 contract — Add an optional timestamped note/moment marker without requiring its use during play

## 1. Scope

PLAN.md §5.8: "Add an optional timestamped note/moment marker without requiring its use during play."

**PLAN evidence:** §(c) "Each game", step 5: "Play normally. … No manual counts or per-move notes are required." The marker is the sanctioned exception — a lightweight, voluntary way to flag a moment (or attach a short note) without breaking concentration or adding required work. The §6 export table confirms the intent: `events.jsonl` retains "optional notes" among the raw data. 5.7's contract explicitly assigns markers to 5.8 ("The optional timestamped marker is 5.8's work"; "no new event type (5.8 owns the timestamped marker — adding one here would duplicate it)").

**What 5.8 does:** Add a small, optional UI affordance (button + optional text input) in the session-controls cluster that emits a single timestamped `moment_marker` event through the existing content-script sender pipeline. Using it is never required; the core Start → play → Stop flow is untouched.

**What 5.8 does NOT do:** It does not analyze, transcribe, or display markers back to the user; it does not require or prompt for markers; it does not change the Start/Stop sequences, the phase machine, readiness, lights, or any §5.1–5.7 behavior.

## 2. The marker event

### 2.1 Event type and constant

- Event type string: `'moment_marker'` (flat snake_case, ≤64 chars, per the `requireEventType` rule in event_envelope.js).
- Exported constant: `BlindfoldSession.MOMENT_MARKER_EVENT_TYPE = 'moment_marker'`, following the existing convention (`BS.MOVE_ATTEMPT_EVENT_TYPE`, `BS.GAME_ENDED_EVENT_TYPE`, `BS.PAGE_START`, etc.).
- **Justification for the new event type:** 5.5–5.7 held a "no new event types" discipline because none of those tasks needed one. 5.8 is the task PLAN charges with markers, and 5.7's contract explicitly reserves marker ownership to 5.8. One new event type is the specified deliverable, not scope creep. No other new types.

### 2.2 Payload

`{ note: <string | null> }` — the user's optional note text, trimmed; `null` when the input is empty (a bare moment marker). Strict validator `requireValidMomentMarkerPayload(payload, eventTypeName)` following the `requireValidPermissionChangedPayload` precedent (TypeError on wrong shape; the record itself rejects extra keys — factories are lenient-on-input/strict-on-record per repo convention). A sane maximum note length (builder chooses, e.g. 500 chars; over-length is a RangeError, not silent truncation — never silently alter user input).

Rationale for nullable-not-absent: a bare marker (no text) is the primary low-friction use — flag the moment mid-game, add context later from the audio. `null` keeps the shape stable for §6 export.

### 2.3 Emission path and semantics

- Emitted through the content-script sender: `opts.sender.emit({ eventType: 'moment_marker', sessionId: <active sessionId>, gameId: <active gameId>, payload })` — the same call pattern as `emitPageStart` (lifecycle.js).
- Timestamping is the sender's existing job (1.3.3): monotonic `monotonicMs` at emission + `clockSegmentId` anchor reference + UTC anchor on the segment. 5.8 adds no timing code; the "timestamped" requirement is satisfied by the pipeline.
- Session/game reference: the marker belongs to the **currently active game** (`activeGameId` slot). Under 5.9's future mid-session game changes, a marker always attaches to whatever game is active when pressed — no retroactive reassignment.
- Storage: the SW transactional writer stores it like any other event (dedup by eventId, appendSeq on write). No new store, no new channel message, no new SW code.
- Failure honesty: if `sender.emit` throws (e.g., malformed session state), the click handler must not break the page (3.2 SF-1: failure-isolated try/catch) and must surface the failure honestly on the button affordance (e.g., title/detail text), never silently drop.

### 2.4 Idle behavior

When no session is active (phase idle), the marker affordance is **disabled** (button disabled, input disabled). Clicking/typing does nothing and emits nothing. Rationale: a marker with no sessionId is meaningless raw data; disabled-not-hidden keeps the cluster layout stable and communicates availability honestly. This is not "requiring use" — it is refusing to record a dangling marker.

## 3. UI presentation

### 3.1 Affordance

In the session-controls cluster (session_controls.js DOM section), after the readiness badge:

- A compact text `<input>` (placeholder e.g. "Note (optional)", `aria-label` set) for the optional note text.
- A "Mark" `<button type="button">` (aria-label e.g. "Record moment marker").
- Both disabled unless phase is ACTIVE. On successful Start they enable; on Stop/abort/boot-idle they disable and the input clears.
- Clicking Mark: read input value, trim, emit `moment_marker` with `{note}` (null when empty), clear the input on success. The input clearing is the success signal; on emit failure the text is preserved and the failure is surfaced honestly.
- No `overlay.css` changes required (follow the 5.6 precedent — diff discipline; builder may add minimal classes only if needed for the disabled state, but the existing button/input patterns suffice).

### 3.2 "Without requiring its use"

- The marker UI adds zero steps to Start → play → Stop. It is never focused automatically, never blocks, never prompts.
- No confirmation dialog, no `prompt()`.
- Hotkey: optional, builder's choice. If added, it must not conflict with existing hotkeys (content.js: `j`, `Enter`, `v`, `w`/`W`, `m`/`M`, `z`/`Z`, `i`/`I`, `s`/`S`, `Escape`) and must be inert when idle. Not required by this contract.

### 3.3 What does NOT change

- Start/Stop button, phase machine, per-stream lights, 5.6 readiness badge, 2.8 saving indicator: all untouched.
- The 5.5 duplicate-Start guard, 5.7 no-auto-stop invariant: untouched.
- No new channel messages (offscreen MSG_* stays 24; SW envelope stays 7), no new stores, no new permissions.

## 5. Explicit non-goals

- Displaying markers back to the user (no marker list, count, or timeline — that is analysis UI, out of scope per §1 "no dashboards").
- Transcription or interpretation of note text.
- Requiring, reminding, or prompting marker use.
- Editing or deleting markers after emission (raw data is append-only; a correction is a new marker).
- Retroactive game reassignment of markers.
- 5.9's game-boundary handling, 5.10's finalization gating.
- Any timeout, rate limit, or quota on markers (PLAN sets none; abuse is not a collection concern).
