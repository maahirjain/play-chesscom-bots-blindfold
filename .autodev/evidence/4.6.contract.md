# Task 4.6 contract — start separate microphone, screen, and webcam recording streams

PLAN.md §4.6: "Start separate microphone, screen, and webcam recording
streams, saving actual start times rather than assuming simultaneous
starts."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. Contract amendment to 4.5 §2 (segmentId assignment)

4.5's contract says "segmentId: 4.10 assigns; 4.5 defines the key." That
cannot hold: the manifest record must be written **at stream start** (it
carries the real negotiated `recorder.mimeType` and the actual start
times), and `recording_manifest`'s keyPath **is** `segmentId` — so 4.6
must supply one. **Amendment: 4.6 mints the segmentId** (uuid-v4 via
`crypto.randomUUID`, no weak fallback — the repo's `newEventId`
precedent) at each stream start. 4.10 does **not** mint new IDs; it links
clock anchors to 4.6's IDs (updating the existing records; the exact-keys
validator widens deliberately per the 4.5 field-ownership table). 4.13
mints additional segmentIds only for post-discontinuity / restarted
segments. Invariant: every segment has exactly one uuid-v4 ID, minted at
the moment its recording starts. The section-4 auditor must confirm this
amendment is consistently applied in 4.10/4.13.

## 1. Scope boundary — what 4.6 is and is not

**4.6 acquires the three MediaStreams, constructs the three
MediaRecorders, starts them, and writes the manifest records with the
real negotiated MIME types and per-stream actual start times.** Each
stream starts when it starts — mic acquisition, tab streamId resolution,
and camera acquisition take different amounts of time — and 4.6 saves
each one's own start timestamp rather than stamping one shared time.

**4.6's per-stream pipeline** (each stream independent; a failure in one
never blocks the others):
1. Verify formats fresh via 4.5's `verifyFormats()`; empty candidate
   list for a kind → that stream reports `{ok:false,
   error:'no-supported-format'}` honestly, never a silent fallback.
2. Acquire the `MediaStream`:
   - **microphone:** `getUserMedia({ audio: { deviceId: { exact:
     <selection> } } })`, or `{ audio: true }` (system default) when no
     selection exists. An actually-used-but-unselected device is recorded
     as `source:'default'` through the selector's selection-recording
     path — never mislabeled `'user'` (builder: use the existing
     vocabulary; add a minimal method to `device_selection.js` if none
     exists; the honesty requirement is the point, not the method name).
   - **webcam:** `getUserMedia({ video: { deviceId: { exact: <selection>
     } } })`, or `{ video: true }` when none (same defaulting rule).
   - **screen/tab:** tab mode (primary): SW broker re-resolves the target
     tab **fresh at Start** (tab ids are unstable — 4.3 §6 seam #2), then
     `getStreamId(tabId)`, then `getUserMedia` with the
     `chromeMediaSource` constraints (video + audio, mirroring the 4.3
     probe). Screen mode (fallback): `getDisplayMedia({ video: true,
     audio: true })` in the offscreen document — see §6.2 for the honest
     gesture uncertainty.
3. Construct `new MediaRecorder(stream, { mimeType: <first verified
   candidate> })`. No bitrate policy in 4.6 — recorder defaults; file-size
   tuning is §7/4.8 territory, documented not decided.
4. Read the **real** `recorder.mimeType` immediately after construction
   (4.5's V2 deferred this proof to 4.6 — 4.6's V2 must show a real
   negotiated type landing in the manifest).
5. Call `recorder.start()` **with no timeslice**; capture
   `streamStartedAtUtc` (`new Date().toISOString()`) and
   `streamStartedAtMonotonicMs` (`performance.now()`) at that moment.
   `ondataavailable` is left explicitly unset — 4.8 owns chunk extraction
   (recommended: `requestData()` interval polling; 4.8's planner decides —
   see §5 seam).
6. Write the manifest record via 4.5's `recordSegmentFormat`, widened
   with 4.6's fields (see §3).

**Failure semantics (per-stream independence — 4.14's raison d'être):**
a failed stream never blocks the others. On failure: stop any partially
acquired tracks (no orphaned live tracks), do **not** write a manifest
record (no segment exists), and report `{ok:false, error, errorName,
stage}` for that stream (`stage` ∈ `{'verify-formats','acquire-stream',
'construct-recorder','start-recorder','write-manifest'}` — honest
staging, not a stack trace). The channel response carries all three
per-stream outcomes. 4.14 will formalize durable status events; 4.6
itself emits **no new event types** — the manifest records plus the
channel response are the durable trace, and 4.9/4.10/4.14 own the event
timeline.

**Mechanical guards** (4.6's own; 5.5 owns the UX-level Start dedup):
- No active session (`recorder-set-session` never set) →
  `{ok:false, error:'no-session'}` (4.5's manifest write requires
  sessionId/gameId — same precedent).
- Streams already running → `{ok:false, error:'already-started'}`.
- A start already in flight → `{ok:false, error:'start-in-progress'}`
  (error, not collapse — the first caller's per-stream results are not
  safely shareable mid-flight).

**Not 4.6:**
- No chunk wiring (`ondataavailable` unset; 4.8 owns it).
- No track mute/end/error listeners (4.9 owns them; 4.6 keeps the
  streams/recorders in a module registry so 4.9 can attach).
- No clock anchors (4.10 links them to 4.6's segmentIds).
- No sync marker (4.11), no timecode/offsets beyond the two start-time
  fields (4.12), no Stop/finalization (4.13 — but 4.6 must keep
  streams/recorders referenced in the registry so Stop is possible and
  nothing is GC'd).
- No per-stream status events (4.14), no UI (§5), no audio-content policy
  (4.7 — see §4).
- No new event types. No manifest-permission changes.

## 2. Separateness guarantee (the 4.4 boundary, now implemented)

Three separate `MediaStream` objects, three separate `MediaRecorder`
instances, no `AudioContext`, no track merging, no stream combination:
- microphone → audio-only stream from the mic device (game audio cannot
  enter except via physical acoustic bleed — 4.7 documents it);
- screen/tab → video + tab-audio stream (4.7's feed);
- webcam → video-only stream (the camera probe uses `{video:...}`
  constraints with no audio key — 4.4's kind-branch).
4.6 records `audioTrackPresent` / `videoTrackPresent` per stream
(observed from `stream.getTracks()`) so 4.7 and 4.14 can see what was
actually acquired. V1 pins: the three recorders receive three distinct
stream objects.

## 3. Manifest record — 4.6's fields

4.6 widens 4.5's exact-keys validator **deliberately** (4.5 §2 table
anticipated this) to add:

| Field | Type | Notes |
|---|---|---|
| `segmentId` | uuid-v4 string | **Minted by 4.6** at stream start (§0 amendment) |
| `streamStartedAtUtc` | ISO-8601 string | Captured at `recorder.start()` — the media-relevant start |
| `streamStartedAtMonotonicMs` | number | `performance.now()` at `recorder.start()` — the hook 4.10/4.12 align against (4.1's pong hook is the SW↔doc clock relation) |
| `effectiveDeviceId` | string \| null | From the acquired track's `getSettings().deviceId`; `null` for screen/tab (no deviceId; tabId deliberately not persisted — 4.3) |
| `audioTrackPresent` | boolean | Observed track presence |
| `videoTrackPresent` | boolean | Observed track presence |

Plus 4.5's eight fields (`sessionId`, `gameId`, `streamKind`,
`requestedMimeType`, `actualMimeType` ← the real `recorder.mimeType`,
`fileExtension` ← derived from actual, `createdAtUtc` ← manifest-write
time). 4.10/4.12/4.13 fields remain reserved.

## 4. Boundary with 4.7 (audio)

Precise line: **4.6 = plumbing, 4.7 = audio-content policy.**
4.6 acquires the screen/tab stream with audio whenever the capture path
yields it (tab-mode constraints include audio per the 4.3 probe;
screen-mode `getDisplayMedia({audio:true})` yields whatever the user
shares) and records `audioTrackPresent` honestly — it never mixes,
excludes, or reroutes audio. 4.7 owns: verifying the tab-audio track
actually carries game audio (vs. silence), the "keep game audio out of
the microphone stream" verification, acoustic-bleed documentation, and
any include/exclude/mix decisions. If 4.7 later needs acquisition
changes, it amends this contract's §2 — 4.6 does not pre-build audio
policy.

## 6. Architecture

### Where the code lives

- **`stream_starter.js`** (new, DOM-free, repo module pattern, Node
  shim), loaded by `recorder.html` after `format_support.js`.
  `createStreamStarter(opts)` with injected: `mediaDevices`,
  `getDisplayMedia` (injected for tests; real global in the document),
  `MediaRecorder` (injected; 4.5's format support reads it lazily —
  coordinate the injection), mic/camera selectors, SW broker client
  (`resolveTargetTab`, `getStreamId` — both already exist on the
  recorder's broker client per recorder.js), 4.5's
  `{verifyFormats, recordSegmentFormat}`, session thunks
  (`getSessionId`, `getGameId`), clock (`nowUtcIso`, `perfNowMs`),
  `newUuidV4`.
- **`recorder.js`** — instantiates the starter, routes the new
  `recorder-start-streams` message with the 3.2 SF-1 failure isolation
  (a throwing starter never breaks the message listener or drops a
  liveness pong).
- **Recording platform APIs live only in the offscreen document**
  (4.1's rule): `getUserMedia`, `getDisplayMedia`, `new MediaRecorder`
  never appear in the SW, content scripts, or `capture_broker.js`.

### Message channel

On 4.1's envelope `{kind:'recorder', msg, v:1}`:

| msg | Request | Response |
|---|---|---|
| `recorder-start-streams` | — (session comes from `recorder-set-session`) | `{ok:true, streams:{microphone:{ok,segmentId,streamStartedAtUtc,...}, screen:{...}, webcam:{...}}}` or per-stream `{ok:false, error, errorName, stage}`; top-level guards `no-session` / `already-started` / `start-in-progress` |

### The streams registry

Module-internal `Map<streamKind, {stream, recorder, segmentId,
startedAtUtc, startedAtMonotonicMs}>`. In-memory only (streams cannot
survive document death — honest; 4.9 logs the discontinuity, 4.13
re-segments on restart). Later tasks (4.8/4.9/4.13) access it through
documented accessors 4.6 exposes; the contract names them so 4.8's
planner can rely on them: `getActiveStreams()`,
`getStreamRecord(streamKind)`.

### 6.2 Screen-mode picker honesty (explicit probe item)

`getDisplayMedia` in an offscreen (hidden, user-invisible) document is
the one acquisition path 4.6 cannot assert from prior contracts. The
builder must probe empirically in V2 (headed/headless with
`--auto-select-desktop-capture-source` + fake devices if workable):
- If the picker resolves → screen stream starts like the others.
- If it requires transient user activation unavailable to the offscreen
  document → 4.6 reports `screen:{ok:false,
  error:'picker-unavailable', errorName, stage:'acquire-stream'}`
  honestly. Screen mode is then a documented limitation; tab mode is the
  supported path; §5 must not present screen mode as working until §7
  proves otherwise. **No workaround is fabricated** (no hidden-tab
  capture, no silent tab-mode substitution — the mode the user selected
  is the mode attempted).

## 10. Known seams and honest limitations

1. **Probe-then-start race** (4.2 §6 / 4.3 §6 seam): a grant at probe
   time can be revoked before Start. 4.6 treats every stream-start
   failure as its own per-stream case — this is the seam working as
   designed, not a defect.
2. **Screen-mode picker uncertainty** (§6.2): if `getDisplayMedia`
   needs transient activation the offscreen document cannot provide,
   screen mode degrades honestly and tab mode is the supported path.
3. **Streams die with the document.** The registry is in-memory;
   kill+recreate loses live streams (manifest records survive — they're
   durable). 4.9 logs the discontinuity; 4.13 re-segments on restart.
4. **Tab closed/navigated between resolve and acquire** → honest
   per-stream failure (`stage:'acquire-stream'`).
5. **Headless codec/MIME set differs from headed** (4.5 §8.4) — V2
   asserts the *mechanism* (real `recorder.mimeType` lands in the
   manifest), not specific codecs; real-device types are AC12/§7.
6. **No timeslice in 4.6** means chunks only arrive via 4.8's
   `requestData()` (or on stop). If 4.8's planner prefers a timeslice,
   it amends §1 step 5 — the seam is documented, not locked.
