# Task 4.4 contract — webcam selection and permission handling

PLAN.md §4.4: "Add webcam selection and permission handling so the
player's face is saved separately from the screen."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope boundary — what 4.4 is and is not

**4.4 is a near-mechanical reuse of 4.2's `createDeviceSelector` factory
for `kind: 'videoinput'`, plus one genuine factory gap fix.** The 4.2
build deliberately pre-designed this: `device_selection.js` already
contains `STORAGE_KEYS.videoinput = 'blindfold.cameraDeviceId.v1'`,
`EVENT_TYPES.videoinput = { camera_permission_changed,
camera_device_selected }`, and `CAMERA_PERMISSION_QUERY_NAME = 'camera'`.
4.4 instantiates a second selector in the offscreen recorder and routes
a `cam-*` message family to it.

**The one genuine gap (not pure reuse):** `runPermissionProbe` in
`device_selection.js` hardcodes `{ audio: ... }` constraints. For
`videoinput` the probe must use `{ video: { deviceId: { exact:
<selection> } } }` (or `{ video: true }` with no selection). The fix is
a kind-branch on the constraints key — small, and V1-pinned.

**"Saved separately from the screen"** is 4.6's boundary, not 4.4's: 4.6
("Start separate microphone, screen, and webcam recording streams") owns
wiring the camera stream into its own `MediaRecorder`/chunk stream,
separate from the screen capture stream. 4.4 delivers a selected,
permitted camera and stops there — the separateness guarantee lives in
the stream wiring, which does not exist yet. 4.4 must not build any
stream-retention or recording machinery.

**Not 4.4:**
- No UI of any kind (§5 owns it).
- No retained streams, no `MediaRecorder`, no chunks (4.5/4.6/4.8).
- No resolution/framerate policy: the probe uses `{ video: true }` or an
  exact deviceId only. Recording-quality constraints are 4.6's decision.
  (No `facingMode` request: the mission's device is a laptop webcam; the
  default facing is user-facing. If 4.6 wants explicit facing, it says so.)
- No manifest changes: Chrome requires no manifest permission for
  `getUserMedia` video in extensions, same as audio (4.2 precedent).
- No changes to the 1.2 session-conditions schema.

## 2. Architecture

### Where the code lives

- `device_selection.js` — the kind-branch on probe constraints (the gap
  fix). Nothing else in the factory needs to change: enumeration filters
  by `kind`, the storage key, event types, and permission query name are
  already kind-parameterized.
- `recorder.js` — a `getCameraSelector()` beside `getMicSelector()`,
  instantiated with `kind: 'videoinput'` and the same injected surfaces
  (mediaDevices, storage adapter, permissions, emitEvent, session
  thunks). Routes the `cam-*` family with the same failure isolation
  (3.2 SF-1 precedent). `restoreDevices()` also restores the camera
  selector (best-effort, never throws).
- No `recording_host.js` changes (no new SW behavior; §5 drives via the
  channel).

### Message channel additions

On 4.1's envelope `{ kind: 'recorder', msg, v: 1, ... }`, mirroring the
`mic-*` family exactly:

| msg | Request fields | Response |
|---|---|---|
| `cam-list-devices` | — | `{ ok, devices: [{ deviceId, label, kind:'videoinput' }] }`. Labels `null` pre-grant (honest, never fabricated). |
| `cam-select` | `{ deviceId }` | `{ ok, selection }` or `{ ok:false, error }`. Unknown deviceId → `{ ok:false, error:'unknown-device' }`; never throws across the channel. Persist-before-live (4.2 SF-1 precedent). Emits `camera_device_selected`. |
| `cam-request-permission` | — | `{ ok:true, permissionState:'granted' }` or `{ ok:false, permissionState, errorName }`. Emits `camera_permission_changed`. Probe tracks always stopped before responding — **no open camera stream is ever retained**. |
| `cam-get-state` | — | `{ ok, selection, permissionState, devicesEnumeratedAt }`. The queryable state 4.14 and 5.6 read. |

`recorder-set-session` is shared: one message arms/disarms session
scoping for both selectors (4.2's seam, reused as-is).

### Permission flow

Identical honesty to 4.2, with the `camera` permission name:
1. Advisory `permissions.query({ name:'camera' })`; ground truth is the
   `getUserMedia({ video: ... })` outcome.
2. Denial → persisted queryable `'denied'` state, never an exception.
3. `NotFoundError`/`OverconstrainedError` → stale selection invalidated
   (cleared to null, `camera_device_selected` with `source:'invalidated'`).
4. Permission state is never persisted (revocable in browser UI).
5. Concurrent probes share the in-flight request (4.2 §6.5 precedent).

### Selection state and persistence

- `selection`: deviceId string or `null`; starts `null` per boot.
- Restore: read `blindfold.cameraDeviceId.v1`; present in a fresh
  enumeration → `source:'restored'`; absent → `null`, no event, no silent
  default.
- 4.4 never silently defaults a camera; defaulting is 4.6/§5's decision
  at Start (recorded then with `source:'default'`).

### Events (4.4-owned event types)

Already reserved in the factory defaults; 4.4 activates them:

- `camera_permission_changed`
  `{ permissionState: 'granted'|'denied'|'prompt'|'unknown', source: 'query'|'request', errorName: string|null }`
- `camera_device_selected`
  `{ deviceId: string|null, label: string|null, source: 'user'|'restored'|'default'|'invalidated' }`

Exact-keys validators, via the existing writer intake with
`sourceContext: 'recording_context'`, session-gated (inert pre-session).

**Builder note:** `requireValidPermissionChangedPayload` /
`requireValidDeviceSelectedPayload` hardcode `'microphone_*'` in their
error-message strings. Parameterize the messages by the actual event-type
names so 4.4 failures don't mislabel themselves (small, mechanical).

### Failure isolation

Same as 4.2: every `cam-*` handler failure-isolated; a throwing selector
never breaks the recorder's message listener or drops a liveness pong.

## 4. Acceptance criteria

- AC1 (V1): `createDeviceSelector({ kind:'videoinput' })` constructs;
  storage key is `blindfold.cameraDeviceId.v1`; event types are the
  `camera_*` pair.
- AC2 (V1): `runPermissionProbe` builds `{ video: ... }` constraints —
  `{ video: { deviceId: { exact } } }` with a selection, `{ video: true }`
  without; **no `audio` key** in the video probe (spy on getUserMedia).
- AC3 (V1): probe success → `'granted'`; every probe track stopped; no
  stream retained; permission query name is `'camera'`.
- AC4 (V1): scripted `NotAllowedError` → `{ ok:false,
  permissionState:'denied', errorName:'NotAllowedError' }` +
  `camera_permission_changed` event with the raw error name.
- AC5 (V1): stale selection (`OverconstrainedError`) → selection null,
  stored key dropped, `camera_device_selected` with
  `source:'invalidated'`.
- AC6 (V1): validator error messages use the `camera_*` event-type names
  (no `microphone_*` mislabeling).
- AC7 (V1): recorder routes `cam-list-devices`, `cam-select`,
  `cam-request-permission`, `cam-get-state` with envelope validation and
  failure isolation; unknown `msg` still ignored; boot restore covers the
  camera selector.
- AC8 (V1): changed files only: `device_selection.js` (kind-branch +
  validator messages), `recorder.js`, tests, evidence, DECISIONS.md
  entry. No manifest changes. Content scripts byte-identical. No
  `MediaRecorder` token in product code.
- AC9 (V2): real headless Chrome with fake devices: list shows ≥1
  `videoinput`; select + request-permission → granted; tracks stopped.
- AC10 (V2): CDP-denied camera → denied state + `camera_permission_changed`
  in extension IDB via the writer intake (append-sequence gapless).
- AC11 (V2): kill+recreate of the offscreen document restores the camera
  selection (`source:'restored'`) without user action.
- AC12 (V3, deferred to §7/owner device): real webcam — true labels after
  grant; selection survives browser restart; browser-UI denial → explicit
  `'denied'`.

## 5. Non-goals

- No UI; no retained streams; no `MediaRecorder`/chunks.
- No resolution/framerate/facingMode policy (4.6's).
- No "separate from screen" wiring (4.6's stream wiring).
- No manifest changes.

## 6. Known seams and honest limitations

1. **Probe-then-start race** (same as 4.2 §6.1): a grant at probe time can
   be revoked before 4.6 starts the stream; 4.6 owns the failure case.
2. **Labels empty pre-grant** (Chrome privacy) — §5's UI problem, flagged.
3. **Stored id staleness** — handled via the `'invalidated'` path.
4. **Mic/camera independence:** the two selectors are fully independent
   instances; a combined "all devices ready" judgment is 5.6/4.14's, not
   4.4's.
