# 5.3 contract — Remember previous selections without silently changing a game's recorded conditions

## 1. Scope

PLAN.md §5.3: "Remember previous selections without silently changing a game's recorded conditions."

This is the third task of Section 5 ("Add minimal session controls"). 5.2 built the
selection fields (category + training approach + verbal scaffolding) and exposed the
5.3 seam: the install handle `{getSelection, setSelection, setEnabled}` plus the
write-once/disabled-while-active rule ("setSelection while disabled is a no-op —
restoring defaults can never rewrite an active session's record"). The 5.2 build
evidence hands off: "5.3 owns remembered-defaults persistence (chrome.storage.local);
the seam is the install handle + write-once rule + the 'last selection stays in
place' comment in the Stop path."

PLAN's constraint has two halves, and the contract treats them asymmetrically:

1. **Remember** — persist the user's last-used selection durably so the next
   session's setup is pre-filled. This is a UI-preference convenience, not
   experimental data.
2. **Without silently changing a game's recorded conditions** — the remembered
   values may only ever flow *into the pre-session form*. They must never flow
   into the stored `session_metadata` / `conditions` records of any session
   except through the normal, explicit Start path (which records exactly what the
   form shows at Start).

## 2. Remembered-fields set: all three 5.2 fields

5.3 remembers exactly the three fields 5.2 owns, as one selection record:

- `sessionCategory` (`'baseline' | 'training' | 'evaluation' | null`)
- `trainingApproach` (string, raw form value)
- `verbalScaffolding` (string, raw form value)

Rationale: PLAN §5.3 says "previous selections" with no qualification. The
counter-argument (free-text fields may be session-specific) is answered by
editability: remembered values are pre-filled but always editable before Start,
and the category placeholder remains re-selectable, so the user is never trapped
in a stale default. A training block typically reuses the same approach text
across sessions (e.g. "shadowing aloud"), which is precisely the re-entry burden
5.3 removes. Remembering a subset would require 5.3 to decide which of the user's
inputs "count" — a judgment PLAN does not authorize.

The remembered value shape is exactly `getSelection()`'s shape. No envelope, no
timestamps, no version field inside the value — the storage key is versioned
instead (§4).

## 3. Capture timing: at successful Start, and only there

- **Capture** happens once per session, at the Start-success point in
  `session_controls.js` (where `phase` becomes `'active'`, after `session-save`
  has persisted the records built from the same form values). The captured value
  is the selection that was just recorded — `getSelection()` at Start.
- **Aborted Start captures nothing.** Any abort path (no-category, ensure
  failure, channel failure, page-start failure) leaves the stored remembered
  value untouched. Only a selection the user actually recorded with becomes the
  default.
- **No capture on field change.** Debounced capture-on-edit would persist
  half-typed text and selections the user never committed to. Start is the
  commitment point.
- **No capture at Stop.** After Stop the form already holds the last session's
  values in place (5.2's "last selection stays in place"); re-capturing would be
  a no-op write.
- **Adopted sessions:** a session adopted after page reload (5.1/5.2 boot
  adoption) was not started in this tab, so 5.3 does not capture it. Known edge
  (NOTE, not defect): after an adopted session stops and the page reloads, the
  restored defaults may lag by one session. The in-place form values are always
  correct; only the cold-boot restore can be stale in this path.

## 4. Storage decision: chrome.storage.local

**Decision: `chrome.storage.local`, key `'blindfold.sessionSelection.v1'`,**
accessed through an injected promise-shaped `{get, set, remove}` adapter (the
established 4.2/4.3/4.4 selector pattern — `createCaptureSelector`'s `storage`
opt, `createLocalStorageAdapter` precedent). The new module never touches the
`chrome` global directly; production wires `chrome.storage.local`, tests inject
fakes.

Evidence for the choice:

- The 5.2 build evidence explicitly hands 5.3 "remembered-defaults persistence
  (chrome.storage.local)".
- It is extension-scoped: not visible to chess.com page JavaScript, not cleared
  with site data, survives browser restarts. The remembered selection is a UI
  preference, not experimental raw data — IDB (§2's raw-data store) is the wrong
  home, and reusing `session_metadata`/`conditions` would conflate defaults with
  records (the exact confusion §5.3 forbids).
- The page-localStorage alternative (piece-set precedent, `content.js:72`) needs
  no manifest change but lives in chess.com's origin store, readable and
  clobberable by the page. For a preference this is tolerable but strictly worse.
- Cost: one additive manifest change — `"storage"` appended to `permissions`.
  This is a benign, standard permission; it does not touch content-script
  matches, host permissions, or the SW.

**Exclusion pins (architectural):**

- 5.3's module runs in the content-script context only. It is never imported into
  the service worker (`manifest_sw.test.js` already pins `chrome.storage` out of
  SW functional code — that pin must stay green) and never into the offscreen
  document (`recorder.js` documents that `chrome.storage` is undefined there
  even with the permission; 5.3 must not depend on it there).
- V1 pins: the new module contains no `session-save`, `saveSessionMetadata`,
  `saveConditions`, `indexedDB`, or `chrome.runtime.sendMessage` token
  (comment-stripped scan); it is listed in `content_scripts` js and nowhere else.

## 5. What 5.3 builds

### 5.1 New module `selection_memory.js` (content-script side)

Repo convention (dependency-free classic script → guarded `BlindfoldSession`
global → IIFE `'use strict'` → Node shim). Fully injected:

```
createSelectionMemory({ storage, nowUtcIso? }) → { restore, capture, STORAGE_KEY }
```

- `storage` — required, promise-shaped `{get, set, remove}` (production: a
  thin `chrome.storage.local` adapter; the 4.2 `createLocalStorageAdapter`
  pattern). Missing/malformed → `TypeError` at construction.
- `restore(fieldsHandle)` — async, never throws into page code (3.2 SF-1):
  reads the key; validates with `validateRememberedSelection` (§5.2); on valid,
  calls `fieldsHandle.setSelection(selection)`; on missing/corrupt/unreadable,
  does nothing (fields stay blank). **No enabled-check is needed**: the 5.2
  write-once rule makes `setSelection` a no-op while the form is disabled, so
  `restore` is safe to call unconditionally at install — if boot adoption has
  already disabled the form, the restore is a harmless no-op; if adoption lands
  later, `showAdoptedCategory` overrides. Both orders are safe; the adopted
  truth always wins and remembered values never masquerade as the adopted
  session's category.
- `capture(selection)` — async, never throws: validates, then
  `storage.set({[STORAGE_KEY]: selection})`. A write failure is swallowed — the
  session already started successfully; a preference write must never affect it.
- `validateRememberedSelection(value)` — pure: returns a clean
  `{sessionCategory, trainingApproach, verbalScaffolding}` or `null`.
  `sessionCategory` must be `'baseline' | 'training' | 'evaluation' | null`
  (anything else → whole value corrupt → `null`); the two text fields must be
  strings (coerced via `String()`, never `null`-dropped — an empty string is a
  legitimate remembered value). Unknown extra keys are ignored
  (lenient-on-input convention). Wrong top-level shape → `null`, never throw
  (restore/capture swallow; the pure validator itself throws `TypeError` only on
  a non-object? — no: it returns `null` for anything invalid. Total function,
  no throws, so the page can never break on a corrupt stored value).

### 5.2 Wiring (all additive)

- `session_controls.js`: new optional install option `onSessionStarted`.
  Called exactly once per successful Start, at the `phase → 'active'` point,
  with the selection object that was recorded (`getSelection()` at Start, the
  same values `session-save` persisted). Guarded in try/catch — a throwing
  callback must never break Start (3.2 SF-1). Not required by `validateOptions`
  (5.1/5.2-era callers stay compatible).
- `content.js`: after installing fields, create the memory
  (`BlindfoldSession.createSelectionMemory({storage: chromeStorageLocalAdapter})`)
  and call `restore(sessionFieldsHandle)` (fire-and-forget inside the existing
  try/catch — install never throws into page code); pass
  `onSessionStarted: (sel) => memory.capture(sel)` into `installSessionControls`.
- `manifest.json`: `"storage"` appended to `permissions`. Nothing else.
- No new channel messages. No new event types. No new IDB stores. No SW
  changes. No offscreen changes.

## 6. The no-silent-change invariant (exact)

Four independent mechanisms; all four are pinned in V1:

1. **Write-once (5.2, existing).** `setSelection` while the form is disabled
   (session active or adopted) is a no-op. Restoring defaults can never rewrite
   an active session's record — including the boot-adoption race (§5.1).
2. **No record-write path (5.3, new).** The memory module's only external
   surface is the injected storage adapter pointed at `chrome.storage.local`.
   It cannot reach `session-save`, the IDB stores, or the recorder channel —
   architecturally, not just by convention. V1 comment-stripped scan pins the
   absence of `session-save`, `saveSessionMetadata`, `saveConditions`,
   `indexedDB`, `chrome.runtime.sendMessage`.
3. **Capture reads the live form at Start.** `capture` receives the selection
   the control recorded; it writes only to the prefs key. The record path
   (`session-save` → IDB) is untouched by 5.3 — `git diff` on the record path
   is empty.
4. **No load-past-session path exists.** 5.3 provides no API to load a recorded
   session back into the form. There is simply nothing that could write a past
   record back.

Consequence for review: the dangerous direction is *defaults → record*. Every
defaults→record flow in the system goes through Start, which records exactly
what the form shows — and the form, pre-Start, is the user's explicit, editable
setup. That is "remembering", not "silently changing".

## 7. Failure honesty

- Storage unreadable at boot (permission revoked, corrupt JSON, throwing
  adapter): `restore` no-ops; fields stay blank; install continues. The user
  re-enters selections manually — degraded convenience, never broken recording.
- Storage unwritable at capture: swallowed; the session is unaffected.
- `chrome.storage.local` itself unavailable (adapter construction finds no
  `chrome.storage`): `createSelectionMemory` throws `TypeError` at construction;
  `content.js` catches it in the existing install try/catch and continues
  without remembered defaults (same degradation as 4.2's selector when
  localStorage is unavailable — honest plain-Error capability path, documented
  in DECISIONS.md).

## 9. Explicit non-goals

- A "clear remembered selections" UI affordance. The fields are always editable
  pre-session and the category placeholder is re-selectable; a dedicated reset
  is scope creep under PLAN §5's "minimal session controls". (If the owner
  wants it, it is a one-line `storage.remove` — recorded as a §5 follow-up, not
  a 5.3 defect.)
- Remembering anything beyond the three 5.2 fields (no device selections —
  those are 4.2/4.3/4.4's selectors with their own persistence; no 5.4 detected
  conditions; no note markers).
- Syncing preferences across devices (`chrome.storage.sync` — not requested;
  local-only is the privacy posture).
- Including remembered preferences in §6 export (they are not experimental
  data; export reads the recorded session stores only).
- Any change to the Start/Stop sequences beyond the single guarded
  `onSessionStarted` call.
- Manual termination-reason UI (still unassigned — §5 follow-up from 5.1).

## 10. Privacy

Remembered selections live in `chrome.storage.local`: on-device, per-extension,
never transmitted. They contain only what the user typed/selected into the
setup form. Nothing in 5.3 sends them anywhere.
