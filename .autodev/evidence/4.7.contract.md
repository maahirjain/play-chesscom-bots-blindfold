# Task 4.7 contract — record game and extension audio with the screen capture where supported

PLAN.md §4.7: "Capture game/extension audio with the screen where
supported, keeping it out of the microphone stream's intentional mix;
document device-specific limitations and possible acoustic bleed."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.7 is (one paragraph)

4.6 built the capture machinery: the screen stream is acquired *with*
audio wherever the platform offers it (tab mode requests tab audio via
the SW broker; screen mode requests `{audio:true}` via getDisplayMedia),
and the three streams/recorders are strictly separate (no AudioContext,
no track merging — V1-pinned in 4.6). **4.7 is the audio-content policy
layer on top of that machinery.** It does not acquire anything new. At
each stream start it classifies, honestly and by construction, what the
screen stream's audio track *can* contain given the capture mode, and it
asserts structurally that the microphone stream contains only what the
mic device captured (no intentional mix of game/extension audio). The
classification is written into the manifest record; the device-specific
limitations and the acoustic-bleed reality are documented durably. 4.7
never inspects audio content — the mission is raw data collection, and
content analysis is out of scope by standing rule.

## 1. Audio-content model (by construction, not by measurement)

### 1.1 Screen stream audio — what each mode can contain

| captureMode | audioTrackPresent | classification (`screenAudioContent`) | what it can contain (by construction) |
|---|---|---|---|
| `tab` | true | `'tab-audio'` | The tab's own audio pipeline: game sounds (move sounds, alerts). **Cannot** contain system audio or extension speech output — tab audio is the tab's rendered audio only. |
| `tab` | false | `'none'` | Video-only tab capture. Downstream (4.14/§5/§6) must treat the screen recording as silent. |
| `screen` | true | `'system-audio'` | Whatever the OS mixer delivers to the shared system audio — **may** include game sounds *and* extension speech output, **iff** the user ticked "Share system audio" in the picker. That checkbox is outside our observation boundary: we cannot verify whether it was ticked. |
| `screen` | false | `'none'` | Video-only screen capture. Same downstream consequence. |

Key honesty point: `'system-audio'` is a *possibility* classification,
not a content claim. We record that the track exists and that the mode
permits system audio; we do **not** claim any particular sound was
captured. The reverse is firm: `'tab-audio'` *excludes* system/extension
audio by platform construction, and `'none'` excludes all audio.

### 1.2 "Where supported" — operational definition

"Where supported" resolves to the classification table above:

- Supported and present → `'tab-audio'` / `'system-audio'` (track exists).
- Not supported or not granted → `'none'` (no track; recorded honestly).
- `screenAudioContent` is `null` only when the classification could not
  run (manifest write path never reached — the same conditions under
  which 4.6 writes no record at all).

There is no third state. 4.7 does not retry, re-prompt, or fall back
between modes — mode selection is 4.3's domain and the user's choice.

### 1.3 Extension audio (speechSynthesis) — the sharp honest line

Task 3.4's speech instrumentation produces audio via `speechSynthesis`
(blindfold announcements). Platform fact, documented not measured:

- `speechSynthesis` renders through the platform TTS engine to the
  **system audio output** — it does not travel through any tab's audio
  pipeline and is not a `MediaStream` we own.
- Therefore tab-mode capture **cannot** contain extension speech audio
  (by platform construction). Screen mode **can**, iff the user shares
  system audio.

What 4.7 CAN observe: whether the screen stream has an audio track, and
the capture mode. What 4.7 CANNOT observe: whether any particular
utterance is audible in the recording — that would require audio content
analysis, which the mission's raw-collection rule forbids. The contract
between 3.4 and 4.7 is therefore: 3.4's event log says *what was spoken
and when* (timestamps); 4.7's classification says *which recordings could
possibly contain the sound*. Correlation of the two is §6/§7 analysis
territory, not 4.7's.

4.7 must not fabricate an audio pipeline (no routing of speechSynthesis
into a MediaStream, no `AudioContext` capture of system output — the
platform does not offer one to an extension offscreen document).

### 1.4 Microphone stream — "keeping it out of the intentional mix"

The PLAN's second clause is a **negative requirement**: game/extension
audio must not be *intentionally* mixed into the microphone stream. 4.6
already enforces this structurally — one audio track from the mic device,
no `AudioContext`, no track merging (V1-pinned). 4.7's job:

1. **Re-pin the structural guarantee** with a code-scan test over the
   offscreen scripts: no `AudioContext` / `webkitAudioContext` /
   `AudioDestinationNode` / `createMediaStreamDestination` in executable
   code (comments excepted, per the 4.6 precedent). This is the
   "intentional mix" prohibition made testable.
2. **Record the assertion** in the manifest: `micAudioContent:
   'device-only'` — the mic recorder's audio is exactly what the mic
   device captured, nothing added by us. `null` when the mic stream did
   not start (no record exists anyway) or when the track observation is
   inconclusive.
3. **Document acoustic bleed as a physical reality, not a defect.** The
   microphone transduces whatever sound reaches it, including speaker
   output (game sounds, spoken announcements). Bleed is *acoustic*, not
   *electronic*: it cannot be eliminated in software, only mitigated by
   the owner (headphones, mic placement). 4.7 documents this; it does not
   attempt suppression, filtering, or echo-cancellation policy (no
   constraint changes to the mic acquisition — `echoCancellation` policy
   is a device/owner matter, out of scope).

Device-specific caveat (documented): if the owner's selected "mic"
device is itself a loopback / stereo-mix / virtual-cable device, the mic
stream may contain game/extension audio **by device configuration**, not
by our mixing. We record `effectiveDeviceId` (4.6) so the provenance is
traceable; we do not second-guess the owner's device choice.

## 2. Manifest change — deliberate widening 13 → 15

Two new nullable fields, 4.7-owned, appended to `MANIFEST_KEYS` with the
`// 4.7-owned:` comment convention:

- `screenAudioContent`: `'tab-audio' | 'system-audio' | 'none' | null`
  — written on the **screen** stream's record only; `null` on mic/webcam
  records (field present, value null — the record shape stays uniform,
  per the 4.6 precedent).
- `micAudioContent`: `'device-only' | null` — written on the
  **microphone** stream's record only; `null` elsewhere.

The exact-keys discipline holds: this widening is deliberate and
documented here; any future widening (4.10/4.12/4.13) must be equally
deliberate. `null` means "not applicable / not observed," never a guess.

## 3. Runtime design

### 3.1 New module: `audio_policy.js`

DOM-free, dependency-free, following the repo module pattern
(`BlindfoldSession` guarded global, IIFE, `'use strict'`, Node shim).
Pure classification functions, fully injected inputs — no media APIs:

- `classifyScreenAudio({captureMode, audioTrackPresent})` →
  `'tab-audio' | 'system-audio' | 'none' | null`. `null` on malformed
  input (unknown captureMode with a track present is *not* guessed —
  returns `null`; the honest answer when the mode is unrecorded).
- `assertMicAudio({audioTrackPresent, audioTrackCount})` →
  `'device-only' | null`. `'device-only'` iff an audio track is present
  and every audio track originates from the device acquisition (the
  caller passes what 4.6 observed; the policy module adds no tracks, so
  "device-only" is structural). `null` when no audio track.

Type discipline per repo convention: `TypeError` on wrong type/shape,
`RangeError` on bad domain value (e.g. an unknown classification string
passed *in*), plain `Error` never (no platform capability involved).

### 3.2 Wiring into the 4.6 pipeline

`stream_starter.js` calls the policy functions during the manifest-write
stage (the same stage 4.6 owns), passing `captureMode` (already read for
acquisition) and the `observeTracks` result. No new pipeline stage, no
new failure mode: classification is pure and cannot fail the stream
(malformed input → `null`, recorded honestly). The per-stream response
of `recorder-start-streams` carries the two classifications alongside
the 4.6 fields.

### 3.3 No new event types, no new channel message

The classifications ride the existing `recorder-start-streams` response
and the manifest record — the durable trace. 4.14 owns per-stream status
reporting and reads the manifest; §6.3's media-sync.json reads it too.
No mixer, no analyzer, no new permissions, no manifest-permission
changes. `recorder.html` loads `audio_policy.js` (same pattern as
`stream_starter.js`).

## 4. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — screen classification correct.** `classifyScreenAudio`
  returns `'tab-audio'` for `{captureMode:'tab',
  audioTrackPresent:true}`, `'system-audio'` for `{captureMode:'screen',
  audioTrackPresent:true}`, `'none'` for either mode with
  `audioTrackPresent:false`, and `null` for malformed/unknown input
  (never a guess). V1-pinned with a truth table.
- **AC2 — mic assertion correct.** `assertMicAudio` returns
  `'device-only'` iff an audio track is present from device acquisition;
  `null` when no audio track. The "intentional mix" prohibition is
  V1-pinned by a code-scan test: no `AudioContext`,
  `webkitAudioContext`, `AudioDestinationNode`, or
  `createMediaStreamDestination` in executable code of the offscreen
  scripts (`stream_starter.js`, `audio_policy.js`, `recorder.js`,
  `device_selection.js`, `capture_selection.js`, `format_support.js`,
  `recording_host.js`) — comments excepted, per the 4.6 precedent.
- **AC3 — manifest widening is deliberate.** `MANIFEST_KEYS` is exactly
  the 15-key shape (13 prior + 2 new, `// 4.7-owned:` comment);
  `requireValidManifestRecord` still rejects extra keys; new fields
  nullable; 4.5/4.6 field-ownership comments updated. `screenAudioContent`
  is non-null only on screen records; `micAudioContent` non-null only on
  mic records (cross-stream nulls V1-pinned).
- **AC4 — wired into the start pipeline.** `stream_starter.js` populates
  both fields at manifest-write time from the real acquisition
  observations; `recorder-start-streams` responses carry them; failure
  isolation across the five 4.6 stages is unchanged (classification
  cannot fail a stream).
- **AC5 — no new event types; no new channel message.** Verified by
  code-scan pin (no new `BlindfoldSession` event-name string for audio;
  no new `msg` value on the recorder channel).
- **AC6 — documentation is durable.** The mode×content matrix (§1.1),
  the speechSynthesis routing fact (§1.3), the acoustic-bleed reality
  and the loopback-device caveat (§1.4) are recorded in
  `.autodev/DECISIONS.md` under `## 4.7` (not only in this contract —
  contracts are per-task, DECISIONS.md is the durable log).
- **AC7 — changed-files discipline.** Working-tree diff vs HEAD touches
  only: `audio_policy.js` (new), `tests/audio_policy.test.js` (new),
  `stream_starter.js`, `format_support.js`, `recorder.html`,
  cumulative pin evolutions in existing test allowlists (with
  justification comments), `.autodev/evidence/4.7.*`,
  `.autodev/DECISIONS.md`. Content scripts byte-identical; no gameplay
  change; PLAN.md unmodified.
- **AC8 — no content inference.** No `AnalyserNode`, no audio-level
  metering, no speech-content detection, no "utterance X was recorded"
  claim anywhere in code, tests, or evidence. The strongest claim 4.7
  makes about any recording's *content* is the by-construction
  classification of §1.1.

### V2 — integration (AC9–AC10)

- **AC9 — `sw-audio.js` harness (new, in `~/workspace/tools/ext-verify/`,
  repo path argv REQUIRED).** Real headless Chrome: start streams via
  the real `recorder-start-streams` channel with fake devices; read the

  audio track is actually yielded, else `'none'` — the harness reports
  what the platform yielded, honestly); assert the mic stream carries
  exactly the device audio track and no second/foreign audio track.
  Headless-Chrome audio-track availability for getDisplayMedia is
  genuinely unknown — the harness records the observation, whatever it
  is, and does not simulate a track.
- **AC10 — regression.** `sw-streams.js`, `sw-recorder.js`,

### V3 — deferred (AC11)

- **AC11 — real-device audio reality (§7 / owner device).** On the
  owner's device: tab-mode screen recording contains game sounds but not
  spoken announcements; screen-mode with "share system audio" ticked
  contains both; the mic recording contains only mic input (plus whatever
  acoustic bleed the room produces); bleed characterized honestly. This
  is the only AC that can verify *audible content*, and it needs human
  ears — explicitly out of reach for V1/V2.

## 5. Explicit non-goals

- No Web Audio graph, no `AnalyserNode`, no level metering, no VAD.
- No routing of `speechSynthesis` into a `MediaStream` (platform does
  not offer it; do not fabricate).
- No verification of *which* sounds were captured (unobservable without
  analysis; forbidden by the raw-collection rule).
- No echo-cancellation / noise-suppression policy changes to mic
  constraints.
- No changes to 3.4 speech instrumentation or its event log.
- No mode fallback/retry logic (4.3's domain).
- No new event types, no new channel messages, no new permissions.
