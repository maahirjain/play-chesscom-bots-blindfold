## What was stress-tested

### 1. Writer hook — cannot break the ack path (verified)

- `fireAfterEventStored` (writer.js:396-405) runs **after**
  `sendResponse(ack)` / `sendResponse(failAck)`, inside try/catch. The ack
  is already on the wire before the hook runs.
- `afterEventStored` (lifecycle.js:228-238) never throws synchronously:
  all property accesses are guarded (`!ack`, `!event`).
- **Failure path is safe**: `afterEventStored(event, failAck)` returns
  `undefined` via the `ack.ok !== true` filter. `message.event`
  undefined → `!event` guard. `message` null → TypeError caught by the
  hook's try/catch.
- **No double-fire**: the hook sits in the promise `.then(onOk, onErr)`
  callbacks — exactly one fires per produced ack.
- **No added latency**: fire-and-forget; the returned promise is
  discarded. Background IDB work only.
- **Suspected unhandled-rejection leak — PROVEN FALSE empirically**:
  `notePageStartStored` returns `next`, and `sessionChains[sid] =
  next.catch(()=>{})` attaches a rejection handler to that same promise
  object, so Node's unhandled-rejection tracking marks it handled even
  though `fireAfterEventStored` discards the return. Verified with a
  forced `DB.getAll` rejection: no `unhandledRejection` fired. The
  chain-keepalive catch doubles as leak protection. (AC13's "rejects"
  contract is preserved for direct callers/tests.)
- Type-agnosticism holds: writer.js never inspects `eventType`
  (asserted by the evolved pin in session_store.test.js).

### 2. Detection correctness — temporal guard is sound; one narrow race (NOTE-1)

- **Out-of-order case verified by logic**: B's start (anchor 200) stored
  before A's delayed start (anchor 100). A's detection: newTime=100,
  B orphanTime=200, `200 < 100` false → B not flagged. Correct.
  (Also covered by AC11 test.)
- **`newTime === undefined` (new segment's anchor missing)**: then an
  orphan with a present anchor is NOT flagged (`t < undefined` false).
  Unreachable via mission code paths — the sender's stop-and-wait
  discipline guarantees the anchor commits before page_start is sent —
  so this is defensive dead code, not a live hole.
- **Same-millisecond anchors**: strict `<` means two segments anchored
  in the same `Date.now()` ms would not flag. Requires two full
  content-script init cycles within 1 ms; consequence is a single
  false-negative marker. Astronomically unlikely; documented
  conservative bias is toward false positives anyway.
- **Cross-instance double-marking (NOTE-1)**: per-session serialization
  is airtight *within* an SW instance, but `sessionChains` is
  in-memory. If the SW restarts mid-detection and a second page_start
  lands in the new instance before the first instance's discontinuity
  writes commit, both instances flag the same orphan → duplicate
  `page_discontinuity` rows. Narrow race window; consequence is
  semantically idempotent (the marker's meaning asserted twice, keyed
  by the same orphaned start eventId); the `marked` set self-limits a
  third start. Acceptable for raw collection; no silent corruption.

### 3. False-positive surface — honest, correctly scoped (NOTE-2, NOTE-3)

- **Concurrent tabs**: two live tabs in one session WILL mark each
  other (A alive, B starts → A flagged). The marker's documented
  meaning — "no clean end on record when newer started" — is literally
  true here; it does not claim "crashed". Honest, not wrong. Whether
  the noise level is acceptable depends on §5's session scoping across
  tabs (NOTE-3 for §5: if §5 shares one sessionId across tabs, expect
  routine markers; per-tab sessions avoid them).
- **Lost pagehide race → spurious marker on clean reload**: the
  designed-for trigger case, explicitly conservative. The empirical
  rate is deferred to AC18/V3 (§7, owner device) — correct scoping,
  since only a real browser measures the unload race. For raw data the
  bias direction is right (spurious flag > hidden gap).
- Markers are never retracted; late ends don't rewrite history.
  Append-only honesty preserved.

## Findings

### NOTE-1 — Cross-SW-instance double-marking race (narrow, self-limiting)
`sessionChains` serialization is per-instance. An SW restart
mid-detection plus a second page_start in the new instance before the
first instance's writes commit can emit a duplicate `page_discontinuity`
for one orphan. Semantically idempotent, `marked`-set self-limits.
No action required; documented here for §6 consumers (dedupe on
`refs.orphanedStartEventId` if exact-once markers matter downstream).

### NOTE-2 — Marker noise on clean reloads is unmeasured until V3
The pagehide delivery race determines the spurious-marker rate; AC18
defers measurement to §7/owner device. If the rate proves high, a
future task (not 2.7) could add a grace heuristic — 2.7's raw,
conservative markers are the correct primitive to build on.

### NOTE-3 — For §5: session scoping across tabs controls marker noise
If §5 assigns one sessionId across concurrent tabs, routine
cross-tab markers are expected (honest, per the marker's defined
meaning). Per-tab/per-window sessions avoid them. §5 should decide
explicitly and document the choice.

### NOTE-4 — `detectOrphans` is O(session events) per page_start
Full `bySessionId` scan on every committed start. Fine for bot-game
session sizes (hundreds of events); revisit if sessions grow orders
of magnitude.

### NOTE-5 — Unhandled-rejection protection is incidental, not explicit
The chain-keepalive `.catch()` happens to shield the discarded
`afterEventStored` promise (verified empirically). If
`notePageStartStored`'s chaining is ever refactored, add an explicit
`.catch(()=>{})` in `fireAfterEventStored` to preserve the
fire-and-forget guarantee.
