# Task 4.9 contract — log recording track mute/end, recorder errors, and explicit recording discontinuities

PLAN.md §4.9: "Log recording track mute/end, recorder errors, and explicit recording discontinuities."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.9 is (one paragraph)

4.6 starts the streams, 4.8 extracts the chunks, and both expose their
health through narrow seams (`getActiveStreams()` /
`getStreamRecord()`; `getChunkState()` with terminal states
`chunk-stalled`, `chunk-quota-exceeded`, `chunk-write-error`). **4.9 is
the observation layer on top of that machinery**: it attaches
`track.onmute` / `onunmute` / `onended` and `recorder.onerror` listeners
to every successfully started stream, watches chunk-writer terminal
transitions, detects restarts, and writes all of it to the **event log**
as three new event types. 4.9 interprets nothing (no diagnosis of *why*
a track muted), recovers nothing (no stream restarts — §5/4.13's
decision), and never lets monitoring fail recording: every listener is
guarded, malformed tracks are skipped, and a failed event emission is
tolerated, never thrown into the pipeline (the 4.8 "can never fail the
streams" precedent).

Note on wording: PLAN.md says "mute/end". "Mute" here is the observed
mute *state*: logging a mute transition without its unmute leaves the
raw record ambiguous, so both transitions are logged as state
observations. This is faithful recording of the mute observation, not an
expansion of the requirement.

## 1. The log-shape decision: events, not the manifest

The 4.8 contract deferred this explicitly ("4.9 decides the log shape").
**Decision: all 4.9 observations go to the append-only event log (2.4);
the manifest gains nothing.**

Justification:

1. **Observations are timestamped occurrences.** Track muted at T,
   recorder errored at T — this is exactly what the event system is
   for. The manifest is the recording's identity/format/clock state,
   mutable and keyed by `segmentId` — a stream-health timeline does not
   belong there (the 4.5 "events are the wrong home for mutable state"
   decision, in reverse).
2. **The time model already exists.** `emitRecorderEvent` stamps every
   event with `clockSegmentId` + `monotonicMs` at the source
   (`recording_context`). 4.10 needs exactly this to anchor around
   discontinuities; 4.12 needs the verbatim monotonic timestamps. No
   new clock machinery.
3. **Consumption is uniform.** §6.3 exports events via the 2.x
   surfaces; 4.14's per-stream status reads the event log (latest health
   per `streamKind`), the same way it will read everything else. One
   timeline, not two stores to reconcile.
4. **The transport already exists.** `emitRecorderEvent(eventType,
   payload, refs)` → `{kind:'event'}` → SW writer intake (2.4). The
   4.2/4.3/4.4 selector events prove the path. No new channel message;
   the `MSG_*` vocabulary snapshot stays unchanged.

Known limitation (documented, not repaired here): `sendEventMessage`
is best-effort — a failed send warns and drops the event. The
chunk/manifest records are the backstop: §7/4.14 can compare the event
log against manifest + chunks to detect emission gaps. No retry queue
in 4.9 (out of scope).

## 2. The three new event types

Defined in the new module `track_monitor.js`, following the
event_envelope.js convention ("each task defines its own *_EVENT_TYPE
constant(s) in its own module"). Flat snake_case, passing
`EVENT_TYPE_RE`. `sourceContext` is `'recording_context'`; `refs` carries
`{segmentId}` — the 4.6-minted segmentId of the affected (or new)
segment — so 4.10/4.13 can join discontinuities to segments.

### 2.1 `recorder_track_state_changed`

Track mute/unmute/end observations.

- `payload`: `{streamKind, trackKind, muted, ended, baseline}`
  - `streamKind`: `'microphone'|'screen'|'webcam'` (4.6 vocabulary).
  - `trackKind`: `'audio'|'video'`. (4.6's acquisition yields at most
    one track per kind per stream, so `(streamKind, trackKind)`
    uniquely identifies the track.)
  - `muted`: boolean — `track.muted` observed at event time.
  - `ended`: boolean — `track.readyState === 'ended'` observed at
    event time. Recorded on every event (a mute event on a live track
    carries `ended:false`; an end event carries the muted value as
    observed).
  - `baseline`: boolean — `true` for the single attach-time
    observation per track (so 4.14 knows the starting state),
    `false` for transitions.
- `refs`: `{segmentId}`.
- Emitted: once per track at attach (baseline), then on every
  `onmute` (`muted:true`), `onunmute` (`muted:false`), `onended`
  (`ended:true`) transition. **No debouncing** — every observed
  transition is logged (raw collection; a debounce policy would be
  lossy and the mission defines none). After `onended`, the monitor
  detaches that track's listeners: a dead track produces no further
  events.

### 2.2 `recorder_error`

MediaRecorder platform errors. No interpretation.

- `payload`: `{streamKind, errorName, errorMessage, recorderState}`
  - `errorName`: string|null (e.g. `'InvalidStateError'`).
  - `errorMessage`: string|null — the platform message verbatim,
    never paraphrased or diagnosed.
  - `recorderState`: string|null — `recorder.state` observed at
    event time (`'inactive'` etc.).
- `refs`: `{segmentId}`.
- Emitted: on `recorder.onerror`. Listeners stay attached afterwards
  (no assumption that the recorder is dead — the observation is the
  error, nothing more).

### 2.3 `stream_discontinuity`

The explicit discontinuity flags PLAN.md requires. A discontinuity =
the segment's media timeline has (or will have) a gap.

- `payload`: `{streamKind, reason, lastChunkIndex, supersededSegmentIds, detail}`
  - `reason`: `'track-ended' | 'recorder-error' | 'chunk-stalled' |
    'chunk-quota-exceeded' | 'chunk-write-error' | 'restart'`.
  - `lastChunkIndex`: number|null — from `getChunkState()` at flag
    time (null when chunking never started for the stream).
  - `supersededSegmentIds`: string[]|null — non-null only for
    `reason:'restart'` (the prior generation's segmentIds, §3.3).
  - `detail`: string|null — short context (e.g. the chunk error's
    name/message for `'chunk-write-error'`); never a diagnosis.
- `refs`: `{segmentId}` — the affected segment for live reasons; the
  **new** segment for `'restart'`; null only when the stream never
  started (restart with a failed start — the discontinuity is still
  real).
- Emission rules (§3):
  - `'track-ended'`: after the `recorder_track_state_changed`
    `{ended:true}` event, same tick.
  - `'recorder-error'`: after the `recorder_error` event, same tick.
  - `'chunk-stalled'` / `'chunk-quota-exceeded'` /
    `'chunk-write-error'`: on the chunk-writer terminal transition
    (§3.2), exactly once per stream.
  - `'restart'`: §3.3.

The chained emission (state/error event *then* discontinuity event) is
deliberate: the first is the observation, the second is the explicit
flag for the media timeline. Different consumers (4.14 status vs 4.13
re-segmentation) read different events; deriving discontinuities
instead of logging them would violate "explicit".

## 3. Runtime design

### 3.1 New module: `track_monitor.js`

DOM-free, dependency-free, repo module pattern (`BlindfoldSession`
guarded global, IIFE, `'use strict'`, Node shim). Fully injected
platform surface (no direct `chrome.*`, no media APIs at module scope):

- `createTrackMonitor({emitEvent, getChunkState})` →
  `{attachStream({streamKind, stream, recorder, segmentId}), detachStream(streamKind), getMonitoredKinds()}`.
- `attachStream` reads each track's initial `{muted, ended}`,
  emits the baseline events, and installs `onmute`/`onunmute`/
  `onended`/`onerror` handlers. Every handler body is
  try/catch-guarded; a throwing `emitEvent` is tolerated. A track
  that fails shape validation (not an object, missing `kind`) is
  skipped — monitoring never fails the stream.
- Owns the three `*_EVENT_TYPE` constants and the payload
  constructors (validators per repo convention: `TypeError` on wrong
  type/shape, `RangeError` on bad domain).
- `recorder.html` loads it after `stream_starter.js`/`chunk_writer.js`.

### 3.2 Chunk-writer terminal seam

`chunk_writer.js` gains an **optional** injected
`onTerminalState({streamKind, terminalState})`, invoked exactly once
per stream when a poll loop reaches a terminal state
(`chunk-stalled`, `chunk-quota-exceeded`, `chunk-write-error`).
The monitor's handler maps the terminal state to the discontinuity
reason and emits `stream_discontinuity` with `lastChunkIndex` from
`getChunkState()`. Rationale for a callback over monitor-side
polling: exact-once, no second timer, no timing ambiguity. The
parameter is optional — 4.8's existing behavior is unchanged when
absent.

### 3.3 Restart detection

Wired in `recorder.js`'s `MSG_START_STREAMS` handler, **before**
delegating to `starter.startStreams()`:

1. Read the manifest for this `sessionId` via a new
   `format_support.js` factory method
   `getManifestRecordsBySession(sessionId)` → array of records
   (additive; format_support already owns the manifest store and db
   access). Records carrying 4.13's finalized marker are excluded —
   the marker name is 4.13's to define (db.js already anticipates
   "4.13 marks it finalized"); until defined, the exclusion matches
   nothing.
2. If unfinalized records exist, remember
   `{streamKind: [segmentIds]}` as the superseded generation. (First
   start: no records → no event. §5 mints fresh sessionIds per
   recording session, so a false positive requires out-of-contract
   sessionId reuse.)
3. After `startStreams()` resolves, for each affected `streamKind`
   emit `stream_discontinuity` with `reason:'restart'`,
   `supersededSegmentIds`, and `refs.segmentId` = the new segmentId
   (null if that kind failed to start — the old generation is dead
   either way).

Why the new document can detect this: the manifest lives in
extension-owned IDB and survives document death; the dead document's
recorders do not. The start of a new generation *is* the observable
restart. 4.9 does not resurrect anything.

### 3.4 Wiring summary (all in `recorder.js`'s start-streams handler)

1. Restart check (§3.3) → superseded map.
2. `starter.startStreams(...)` (unchanged).
3. Chunking auto-start (4.8, unchanged) — now passing the monitor's
   `onTerminalState` into the chunk writer.
4. For each successfully started kind:
   `monitor.attachStream({streamKind, stream, recorder, segmentId,
   ...})` from `starter.getActiveStreams()`.
5. Emit pending `'restart'` discontinuity events.
6. `recorder.html` loads `track_monitor.js`.

Steps 3–5 are best-effort and try/catch-wrapped like 4.8's
chunking kickoff: monitoring can never fail the streams or the
channel response.

### 3.5 Streams that never start

4.9 logs nothing for 4.6's failure stages (verify-formats,
acquire-stream, construct-recorder, start-recorder, write-manifest).
The `recorder-start-streams` per-kind response (with stage + error
codes) is the durable record. 4.9 monitors only successfully started
streams. Explicit.

## 4. Discontinuity taxonomy (complete)

| # | Source | Detected by | Event(s) |
|---|---|---|---|
| 1 | track muted/unmuted (not a gap) | `onmute`/`onunmute` | `recorder_track_state_changed` only |
| 2 | track ended mid-session | `onended` | `recorder_track_state_changed{ended:true}` → `stream_discontinuity{reason:'track-ended'}` |
| 3 | recorder platform error | `recorder.onerror` | `recorder_error` → `stream_discontinuity{reason:'recorder-error'}` |
| 4 | chunk poll stalled (3 misses) | chunk_writer terminal | `stream_discontinuity{reason:'chunk-stalled'}` |
| 5 | IDB quota exceeded | chunk_writer terminal | `stream_discontinuity{reason:'chunk-quota-exceeded'}` |
| 6 | chunk write failed | chunk_writer terminal | `stream_discontinuity{reason:'chunk-write-error'}` |
| 7 | offscreen-document restart (recorders died, chunks persisted) | manifest pre-check at next start | `stream_discontinuity{reason:'restart', supersededSegmentIds}` |

Not discontinuities (no event): `recorder.onstop` at Stop (the
expected end — 4.13's territory), mute flaps beyond logging (logged,
not flagged), streams that never started (4.6's response is the
record).

## 5. Honesty rules (no analysis)

- **muted ≠ silent.** `track.muted` is a platform flag; a muted track
  may still yield data. 4.9 logs the flag, never claims silence —
  the 4.7 no-content-inference rule, applied to track state.
- **No why.** The monitor records `errorName`/`recorderState` and
  moves on. No device diagnostics, no "the user unplugged the mic"
  claims. What the platform reports is what gets logged.
- **Error messages verbatim.** `errorMessage` is the platform string
  or null; never paraphrased, never truncated-with-meaning-changed.
- **Unknown is null.** `lastChunkIndex` null when chunking never
  started; `detail` null when there is nothing to add. Never
  fabricated.

## 6. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — track mute/end logged.** `recorder_track_state_changed`
  carries exactly `{streamKind, trackKind, muted, ended, baseline}`
  with `refs:{segmentId}`; baseline emitted once per track at attach;
  every `onmute`/`onunmute`/`onended` transition emits (no debounce —
  V1-pinned); listeners detached after `onended`.
- **AC2 — recorder errors logged.** `recorder_error` carries exactly
  `{streamKind, errorName, errorMessage, recorderState}` on
  `recorder.onerror`; monitoring never throws into the pipeline
  (V1: throwing `emitEvent`, malformed tracks, missing APIs — the
  stream still starts and records).
- **AC3 — discontinuities flagged.** `stream_discontinuity` carries
  exactly `{streamKind, reason, lastChunkIndex,
  supersededSegmentIds, detail}`; the six reason codes; chaining
  order (state/error event *then* discontinuity) V1-pinned;
  `lastChunkIndex` sourced from `getChunkState()`; chunk-terminal
  reasons fire exactly once per stream via the `onTerminalState`
  seam.
- **AC4 — restart detected.** Pre-existing unfinalized manifest
  records for the sessionId at start time → one
  `stream_discontinuity{reason:'restart'}` per affected kind with
  `supersededSegmentIds` and `refs.segmentId` = the new segmentId
  (null when that kind failed); first start emits nothing; new
  segmentIds minted normally through the 4.6 path.
- **AC5 — vocabulary discipline.** The three event types are defined
  as constants in `track_monitor.js` (1.3 convention); **no new
  channel message** (`MSG_*` snapshot unchanged); events flow through
  the existing `{kind:'event'}` writer path; content scripts
  byte-identical.
- **AC6 — log-shape decision documented.** This contract §1 records
  the events-not-manifest decision with justification; the
  consumption points are named (4.10 anchors via
  `refs.segmentId`+`monotonicMs`, 4.12 verbatim timestamps, 4.13
  re-segmentation, 4.14 status, §6.3 export).
- **AC7 — no analysis.** No `AnalyserNode`/metering/VAD; no
  why-claims; muted≠silent documented; error strings verbatim;
  V1 code-scan pin over `track_monitor.js` (no media-capture APIs
  at module scope — everything injected).
- **AC8 — changed-files discipline.** Working-tree diff touches
  only: `track_monitor.js` (new), `tests/track_monitor.test.js`
  (new), `recorder.js` (wiring), `recorder.html` (script tag),
  `chunk_writer.js` (optional `onTerminalState` seam),
  `format_support.js` (`getManifestRecordsBySession` read),
  cumulative pin evolutions with justification comments,
  `.autodev/evidence/4.9.*`, `.autodev/DECISIONS.md`. No new event
  types beyond the three; no gameplay change; PLAN.md unmodified;
  no 4.10+ bleed; no auto-recovery.

## 7. Explicit non-goals and boundaries

- **No auto-recovery.** 4.9 flags dead streams; it never restarts
  them. Restart policy is §5's decision, re-segmentation is 4.13's.
- **No `onstop` handling.** `recorder.onstop` at Stop is the expected
  end of recording — 4.13's territory. 4.9 listens to tracks and
  errors, not to the expected stop.
- **No device diagnostics.** `errorName`/`errorMessage` verbatim;
  no "why" claims, no remediation suggestions.
- **No manifest widening, no schema change, no new channel message.**
  (§8 would call these scope leaks; the contract forbids them by
  naming them.)
- **No debounce on mute transitions.** (Raw-collection rule.)
- **No retry queue for event emission.** (§1 known limitation.)

| Concern | 4.9 owns | Someone else owns |
|---|---|---|
| stream acquisition | nothing new (4.6) | — |
| chunk extraction | nothing new (4.8; consumes `onTerminalState` seam) | — |
| track/error/discontinuity observation + events | the three event types, wiring, restart check | — |
| final flush at Stop (`onstop`) | — | 4.13 |
| re-segmentation after discontinuity | — | 4.13 |
| timecode/offsets around gaps | — | 4.12 (reads 4.9's verbatim timestamps) |
| per-stream status reporting | — | 4.14 (reads the event log) |
| media-sync.json export | — | §6.3 (reads events + manifest + chunks) |
| restart *policy* (should we restart streams?) | — | §5 |

## 8. Honest limitations

- `sendEventMessage` is best-effort; dropped events leave a gap
  only §7/4.14 can detect (compare event log vs manifest vs chunks).
- `track.stop()` does not dispatch `'ended'` in headless Chrome 154
  with fake devices (verified in isolation) — V2's end-path proof is
  synthetic-dispatch-against-the-real-handler, labeled as such.
- Mute transitions on fake devices are not physically forceable
  headless — the no-debounce-every-transition logic is V1-pinned; the
  physical behavior awaits AC11/§7.
- A platform `recorder.onerror` cannot be forced headless — the
  handler attachment and payload shape are V1-pinned; the real error
  path awaits AC11/§7.
- The `'restart'` reason fires only when the new generation starts
  (the observable moment). A restart with no subsequent start leaves
  no discontinuity event — the manifest's unfinalized records are the
  backstop.
