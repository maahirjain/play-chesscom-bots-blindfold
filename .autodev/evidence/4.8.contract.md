# Task 4.8 contract — save recorder chunks incrementally in extension-owned storage

PLAN.md §4.8: "Save recorder chunks incrementally in extension-owned
storage."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.8 is (one paragraph)

4.6 starts each stream's `MediaRecorder` with **no timeslice** and
`ondataavailable` **unset** — until 4.8, the only data path is the
implicit final flush on `stop()`, so a crash or document death mid-game
loses everything. 4.8 wires chunk extraction: a per-stream
`requestData()` poll loop feeds `ondataavailable`, and each non-empty
Blob is appended to the **extension-owned IndexedDB** `media_chunks`
store (compound key `[segmentId, chunkIndex]`, created for exactly this
purpose in task 2.2) keyed to 4.6's segmentIds. Chunks are written
durably as they arrive — not only at Stop — so already-written chunks
survive offscreen-document or SW restarts. 4.8 appends and indexes; it
does **not** concatenate, finalize, or interpret chunk timing (4.13 /
4.12 own those).

## 1. Storage choice — IDB `media_chunks` (ratified, not new)

Task 2.2 created the `media_chunks` store (compound keyPath
`[segmentId, chunkIndex]`, no indexes) with the comment "§4.8
incremental chunks; §6.4 ordered assembly". 4.8 ratifies that choice:

- **Why IDB, not OPFS.** The extension's durable state is already
  IDB-only (standing §2.9 retention discipline; §6 export reads IDB with
  readonly proof). Adding OPFS would introduce a second storage
  mechanism, a second quota surface, and a second retention story for no
  functional gain: chunk Blobs are stored and later read back in order —
  IDB structured-clones Blobs natively in Chrome, and §6.6's
  streaming export (never loading a whole recording into memory) works
  over an IDB cursor just as well as over OPFS files.
- **Why IDB, not in-memory.** The entire point of 4.8 is surviving
  restarts; in-memory chunks die with the offscreen document.
- **No schema change.** The store exists; `DB_VERSION` stays 2. Chunk
  export scoping (§6) needs no new index: the manifest's `bySessionId`
  index yields the session's segmentIds, and chunks are read by the
  `[segmentId, chunkIndex]` compound key prefix — full ordered scans per
  segment. Deliberate: keep the schema frozen.
- **Quota (§2.9 carry-forward).** Blob chunks are the largest thing this
  extension stores. Quota exhaustion is handled honestly per §5 below;
  4.14 reports per-stream status so a quota-stalled stream cannot
  masquerade as a healthy recording.

## 2. Chunk identity and record shape

One chunk record per non-empty `dataavailable` event:

```
{
  segmentId,              // 4.6's segmentId — the compound key's first half
  chunkIndex,             // integer, 0-based, per segmentId; incremented
                          // per stored chunk for that segment
  receivedAtUtc,          // ISO string — when ondataavailable fired
  receivedAtMonotonicMs,  // performance.now() at fire time — ARRIVAL time,
                          // not frame time (4.12's explicit warning)
  timecodeMs,             // raw event.timecode if present, else null —
                          // stored RAW for 4.12 to interpret, never analyzed here
  data                    // Blob — the chunk bytes
}
```

Key: `[segmentId, chunkIndex]`. Notes:

- `streamKind`/`sessionId`/`gameId` are **not** stored on the chunk —
  they are derivable from the manifest via `segmentId` (standing rule:
  don't persist derivable values).
- `byteLength` is **not** stored — `data.size` is the source of truth.
- `chunkIndex` counts **stored** chunks only: 0-byte Blobs are dropped
  (documented §3.3) and do not consume an index.
- 4.13 re-segments on restart → new segmentId → `chunkIndex` restarts
  at 0. Numbered export files (`microphone-001.webm`, …) are 4.13's
  mapping, not 4.8's.

## 3. Extraction design — `requestData()` polling

Per the 4.6 recommendation (4.6.contract.md §5), 4.8 uses
**`requestData()` interval polling**, not a timeslice:

- **Why polling over timeslice.** A timeslice fires on the recorder's
  clock whether or not data exists, cannot be aligned with write
  backpressure, and needs a recorder restart to retune. Polling gives
  4.8 control: skip ticks when `recorder.state !== 'recording'`, back
  off on write failures, and stop cleanly per stream.
- **One poll loop per active stream** (`setInterval`, constant
  `CHUNK_POLL_MS = 5000`, jitter ±10% to avoid lockstep IDB contention
  across three streams). 5 s balances incremental durability against IDB
  write volume; the value is a named, V1-pinned constant — tuning it is
  §7 territory, not 4.8's.
- **Tick semantics.**
  1. If the stream is no longer in the registry or
     `recorder.state !== 'recording'` → stop this stream's loop (no
     error; 4.13's Stop owns the final flush).
  2. Call `recorder.requestData()`. If it throws (e.g. recorder died
     between the state check and the call) → treat as a missed tick.
  3. Await `ondataavailable` up to `CHUNK_REQUEST_TIMEOUT_MS = 2000`.
     - Non-empty Blob → write the chunk record (§2), reset miss counter.
     - 0-byte Blob → dropped (documented; not stored, index not
       consumed, `emptyPolls` counter incremented in state).
     - No event within the timeout → missed tick; increment
       `consecutiveMisses`.
  4. `consecutiveMisses >= 3` → mark the stream `chunk-stalled`, stop
     its loop, surface state for 4.9/4.14 (a stalled chunker is a
     recording anomaly; 4.9 decides the log shape). This is fail-loud,
     not fail-silent.
- **Polling never fails the stream.** Chunk-writing is best-effort
  durability around a recording that continues regardless; a broken
  chunker is reported, never thrown into the stream pipeline.

## 4. Durability across restarts (the honest line)

- **Already-written chunks persist.** `media_chunks` lives in the
  extension-owned IDB, same origin/partition as the manifest (4.5's V2
  proved the offscreen document and SW share it). Offscreen-document
  death, SW restart, or browser crash cannot unwrite them.
- **In-flight data is honestly lost.** Anything the encoder holds but
  4.8 has not yet requested via `requestData()` dies with the
  document — there is no API to recover it. 4.8 documents this; it does
  not fabricate recovery.
- **Poll timers die with the document.** 4.8 does not resurrect
  recorders or restart chunking after a document recreate — the
  recorders are dead too. 4.9 logs the discontinuity; 4.13 re-segments
  on restart; §5 decides whether to restart streams at all. 4.8's job
  ends at "what was written stays written."

## 5. Quota and write-failure handling

- A chunk write that rejects with `QuotaExceededError` (name check, not
  string match) → **stop that stream's poll loop immediately**
  (fail-closed; retrying would spin against a full quota), mark the
  stream state `chunk-quota-exceeded`, and surface it via
  `getChunkState()` for 4.9/4.14. The recording itself keeps running —
  later data is not silently discarded into a void; the failure is
  visible.
- Other write rejections (IDB errors) → same treatment with state
  `chunk-write-error`; the rejection reason is preserved in state
  (name + message, in-memory only).
- **No new event type in 4.8.** Whether a quota/write failure becomes a
  durable event is 4.9's decision ("recorder errors" is 4.9's PLAN
  language); 4.8's contract is to detect, stop, and expose the state.
  4.14 reports it per stream so it cannot masquerade as complete.

## 6. Module and wiring

- **New module `chunk_writer.js`**, DOM-free, repo module pattern
  (`BlindfoldSession` guarded global, IIFE, `'use strict'`, Node shim).
  `createChunkWriter({db, nowUtcIso, performanceNow, setInterval,
  clearInterval})` — fully injected platform surface for V1.
  API: `startForStream({streamKind, segmentId, recorder})`,
  `stopForStream(streamKind)`, `stopAll()`, `getChunkState(streamKind)`
  → `{status, lastChunkIndex, lastWriteAtUtc, consecutiveMisses,
  emptyPolls, lastErrorName, lastErrorMessage}` (all in-memory; the
  durable trace is the chunks themselves), `hasActivePoll(streamKind)`.
- **Wiring into the 4.6 pipeline.** `recorder.js` gains a lazy
  `getChunkWriter()` (same pattern as `getFormatSupport()` /
  `getStreamStarter()` / `getAudioPolicy()`). After a successful
  `recorder-start-streams`, chunking starts automatically for every
  stream that started — **no new channel message** (§5 surface stays
  minimal; Start implies record). `recorder.html` loads
  `chunk_writer.js`.
- **Seam for 4.13.** 4.13's Stop flow will need a final flush: 4.8
  exposes the poll lifecycle (`stopForStream` stops the loop; the
  final `dataavailable` from `recorder.stop()` is itself a chunk and is
  stored like any other — 4.8 documents that 4.13 must await it before
  declaring a segment finalized). 4.8 does not implement Stop.

## 7. Boundaries

| Concern | 4.8 owns | Someone else owns |
|---|---|---|
| chunk extraction + durable append | `ondataavailable` wiring, poll loop, `media_chunks` writes | — |
| concatenation into final files | — | 4.13 (reads chunks in key order) |
| chunk timing interpretation | raw `timecodeMs` + arrival timestamps stored, never analyzed | 4.12 (offsets/timecode) |
| track mute/end, recorder errors, discontinuities | exposes `getChunkState()` (stalled/quota) | 4.9 (log shape: event vs manifest) |
| clock anchors per segment | chunks keyed to 4.6's segmentIds | 4.10 (anchor linking) |
| per-stream status reporting | feeds state | 4.14 (reads `getChunkState()`) |
| export assembly / ZIP streaming | ordered chunk reads | §6.4/§6.6 (reads `media_chunks` by key prefix) |
| chunk deletion / retention | — | §2.9 (retention owns deletion) |
| sync marker | — | 4.11 |

## 8. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — chunk record shape and identity.** `media_chunks` writes use
  exactly the §2 shape; compound key `[segmentId, chunkIndex]`;
  `chunkIndex` is 0-based per segment and increments only for stored
  (non-empty) chunks; no `streamKind`/`sessionId`/`byteLength` persisted
  (derivable rule). V1-pinned against injected fakes.
- **AC2 — polling, not timeslice.** No timeslice argument is passed to
  any `recorder.start()` (code-scan pin); one `setInterval` loop per
  stream at `CHUNK_POLL_MS` (named constant, 5000 ± 10% jitter);
  ticks skip when `recorder.state !== 'recording'`; `requestData()`
  throw → missed tick, never a stream failure.
- **AC3 — empty-chunk and miss handling.** 0-byte Blobs are dropped
  (not stored, index not consumed, counted in state); missing
  `dataavailable` within `CHUNK_REQUEST_TIMEOUT_MS` (2000) counts a
  miss; 3 consecutive misses → `chunk-stalled`, loop stopped, state
  surfaced.
- **AC4 — quota/write-failure fail-closed.** `QuotaExceededError` on
  write → loop stopped, state `chunk-quota-exceeded`, no retry spin;
  other rejections → `chunk-write-error` with name/message preserved;
  the stream's recorder is untouched (recording continues; failure is
  visible, not silent).
- **AC5 — restart honesty.** In-flight (unrequested) data loss on
  document death is documented in code comments and DECISIONS.md;
  no resurrection logic; `stopAll()` is idempotent.
- **AC6 — wiring and seams.** `recorder.js` lazy `getChunkWriter()`;
  chunking starts automatically for every successfully started stream
  (no new channel message — `MSG_*` snapshot unchanged); `recorder.html`
  loads `chunk_writer.js`; `getChunkState()` exposes exactly the §6
  shape for 4.9/4.13/4.14.
- **AC7 — changed-files discipline.** Diff touches only:
  `chunk_writer.js` (new), `tests/chunk_writer.test.js` (new),
  `recorder.js`, `recorder.html`, cumulative pin evolutions in existing
  test allowlists (justified), `.autodev/evidence/4.8.*`,
  `.autodev/DECISIONS.md`. No new event types; no manifest widening
  (counts are derivable — no new fields); no DB schema change
  (`media_chunks` already exists); content scripts byte-identical;
  no gameplay change; PLAN.md unmodified.
- **AC8 — no overreach.** No concatenation, no Blob assembly, no
  playback UI, no transcoding, no chunk deletion, no timing analysis
  of `timecodeMs` (stored raw), no 4.9/4.10/4.12/4.13 field pre-claims.

### V2 — integration (AC9–AC11)

- **AC9 — `sw-chunks.js` harness (new, in `~/workspace/tools/ext-verify/`,
  repo path argv REQUIRED).** Real headless Chrome: start streams via
  the real `recorder-start-streams` channel with fake devices; assert
  `media_chunks` accumulates records while recording (not only at
  Stop); chunk records carry non-empty Blobs with sequential
  `chunkIndex` per segment; per-stream isolation (mic chunks under the
  mic segmentId only). Kill the offscreen document mid-recording:
  already-written chunks remain readable from the SW; document the
  honest in-flight loss.
- **AC10 — quota path (best-effort in harness).** If the harness can
  force a write rejection (e.g. injected failing IDB), assert the
  loop stops and state reports `chunk-write-error`; if not forcible
  in headless, V1 pins it and the harness notes the gap honestly.
- **AC11 — regression.** `sw-streams.js`, `sw-audio.js`,
  `sw-recorder.js`, `sw-formats.js` still pass with the repo path.

### V3 — deferred (AC12)

- **AC12 — real-device chunk reality (§7 / owner device).** On the
  owner's device: chunk cadence under real load, chunk sizes sane,
  multi-minute session survives with chunks accumulating, export
  reads them back in order. Long-session quota behavior is observed,
  not simulated.

## 9. Explicit non-goals

- No concatenation/finalization (4.13); no `new Blob([...])` assembly.
- No playback, preview, or download UI.
- No transcoding or re-encoding of any kind.
- No chunk deletion, compaction, or retention policy (§2.9).
- No timeslice mode (deliberate: polling, §3).
- No new event types, no new channel messages, no new permissions.
- No manifest widening (chunk counts are derivable via key-prefix
  count; standing rule).
- No DB schema change and no `DB_VERSION` bump.
- No interpretation of `timecodeMs` or arrival timestamps (4.12).
