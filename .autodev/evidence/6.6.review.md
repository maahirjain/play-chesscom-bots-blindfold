## 1. ZIP correctness — PASS

- **Structure valid:** Generated ZIPs pass `unzip -t` with correct filenames,
  CRCs, sizes, and byte-identical extracted data (verified with real CRCs).
- **Path traversal rejected:** `../../../evil.txt` → `TypeError` (P1).
- **Empty files rejected:** `files: []` → `TypeError` (P2).
- **Category sanitization:** `../evil` → `TypeError` (P3). The
  `[A-Za-z0-9_-]` allowlist is enforced in `sanitizeCategoryForPath`.
- **Header details:** Local signature `0x04034b50`, central `0x02014b50`,
  end `0x06054b50`; method `0` (STORE) in all headers; UTF-8 flag (bit 11)
  set; no data descriptors (flag bit 3 NOT set); DOS timestamps from session
  start (not wall clock).
- **Directory scheme:** Single-game `<category>/<YYYY-MM-DD>_<gameId>/`;
  multi-game `<category>/<YYYY-MM-DD>_session-<sessionId>/` (Flow rule).
  Download filename `<category>-<YYYY-MM-DD>-<shortId>.zip`.

## 2. Streaming — PASS

- **Blob parts, not buffers:** `buildZipParts` returns `{parts: Blob[]}`.
  Media flows as one Blob per chunk (6.4's `assembleSegmentChunks` pushes
  the *original* Blob references, not copies — verified by source).
- **Heap bounded:** The SW heap holds only local headers (30B each),
  central directory entries (46B each), and Blob *references*. The bytes
  live in the browser's blob storage (disk-backed). No `arrayBuffer()`
  concatenation of full files before Blob creation.
- **JSON materialized:** The three JSON manifests ARE fully materialized
  as strings (kilobytes) — the honest reading of "does not require loading
  an entire long recording into memory": the *recording* (media) streams;
  the *manifests* do not need to.

## 3. Readonly discipline — PASS

- **Snapshot proof:** `exportSession` counts `events` + `recording_manifest`
  + `media_chunks` before (step 2) and after (step 13). Mismatch →

## Contract deviation (non-blocking)

**D1 — Offset tracking uses declared byteLength, not blob.size:**
`buildZipParts` computes central directory offsets via
`offset = dataOffset + f.byteLength` (the declared value) rather than
summing actual `blob.size` values. The contract §2.4 says "chunk Blob
sizes via `blob.size`".

**Impact:** None in practice. The orchestration always passes matching
values:
- JSON: `new Blob([jbytes])` with `byteLength: jbytes.length` (exact).
- Media: 6.4's `byteLength` from `arrayBuffer.byteLength` with the original
  Blobs (size matches for well-formed Blobs).

The V1 tests validate with real `unzip` and pass. However, this is a
latent risk: a future caller passing mismatched `byteLength`/`blob.size`
would produce a silently corrupt ZIP. The robust fix (for a future task,
not 6.6) is to sum `blob.size` in `buildZipParts` or validate they match
(fail-closed).

**Not a defect in 6.6's code** — the deviation is from the contract's
letter, not a functional bug. The implementation is correct for all
inputs the orchestration produces.
