## 1. The 8-step transition ordering — correct

**Boundary before identity.** In `content.js`, `handleGameResetEvent` runs steps 1–2 synchronously: `attemptTracker.handleGameReset()` then `gameLifecycleRecorder.recordGameReset(...)`. The lifecycle recorder was wired with `getGameId: () => BlindfoldSession.activeGameId` (content.js:178) — read at emission time. At the synchronous call point, `activeGameId` is still the OLD gameId: `handle.handleGameReset()` (which mints the new one) is deferred to a microtask via `Promise.resolve().then(...)`. Single-threaded dispatch guarantees no interleaving between the sync emission and the microtask. The `game_reset` event therefore goes out under the old gameId before the new identity exists. ✓

**No wrong-gameId interleaving during the async gap.** The old tracker halts on genuine reset when `gameId !== null` (chess_utils.js:835, `ended = true`; `observe()` returns `{reset:true}` without processing at line 864). It cannot emit moves during the transition. The lifecycle recorder's other emitters (visibility, chess-rules-ended) would carry the OLD gameId during the gap — which is correct, since the old game is still active until the transition succeeds. After `setSlots(sid, newGameId)`, the new tracker is installed synchronously in the same microtask chain — no interleaving. ✓

**SessionId byte-identical.** `var sid = activeSessionId` is captured before the async chain; both the `set-session` call and `setSlots(sid, newGameId)` use it. No other writer to `activeSessionId` runs during an ACTIVE session except Stop's `setSlots(null, null)` (see N1). ✓

**Double-reset cannot corrupt.** A second reset cannot fire while the first is in flight: the old tracker is halted, and the new tracker is only installed after success. A failed transition leaves the old tracker halted (contract-specified: "subsequent observations return `{reset: true}` until the next successful transition or Stop"). No `gameIds` array corruption via concurrent appends. ✓

## 2. Fail-closed behavior — correct

Every failure path leaves the old gameId active:
- `phase !== ACTIVE` → `{ok:false, error:'not-active'}` (no channel traffic; V1 AC5 pins zero calls).
- Missing metadata/conditions → `{ok:false, error:'no-metadata'}` (5.1 no-fields path and boot-adopted sessions fail closed rather than fabricating identity — the honest choice).
- Mint throw → `'mint-failed'`; `addGameToSession` throw → `'metadata-invalid'`.
- `session-save` failure/rejection → `'session-save-failed'`; the `set-session` call is never sent (V1 AC4 pins `setSessionCalls.length` unchanged).
- `set-session` refusal (`'session-active'` — the 5.5 TOCTOU case) or no-response → `'set-session-failed:<err>'`; slots untouched (V1 AC4b).
- `activeMetadata` is only reassigned on the success path (`activeMetadata = updatedMetadata` inside the final `.then`, synchronous with `setSlots` — no async gap between them).

**Persisted-but-unadopted metadata** (session-save succeeds, set-session fails) is left in place — the contract explicitly specifies no rollback ("honest raw data"). The metadata records a detected game; §6 exports what was observed. This is a deliberate design choice, not a leak. ✓

## 3. 5.5 guard interaction — real

The re-set sends `{sessionId: sid, gameId: newGameId}` where `sid === activeSessionId`. 5.5's guard (`isSessionActive() && sid !== null && sid !== sessionId → refuse`) allows same-sessionId re-sets. I verified the V2 pin is genuine: `sw-duplicate-start.js` AC9 sends `recorder-set-session` with `{sessionId: SID_A, gameId: GID_A2}` (a NEW gameId, not just the same one) and asserts `{ok:true}` plus `gameId === GID_A2, sessionId === SID_A` afterward. This is exactly 5.9's pattern, tested in real headless Chrome. ✓

The TOCTOU case (another tab's session won the race → `'session-active'` refusal) is handled as fail-closed, not as an error to retry. Correct — retrying would be wrong. ✓

## 5. Detection gating — honest

`handleGameReset` gates on `phase !== CONTROL_PHASE_ACTIVE` → `'not-active'`. STARTING (session not established — minting here would race the Start chain) and STOPPING (session ending — Stop owns teardown) both no-op. A spurious reset cannot fabricate a gameId: it additionally requires `activeMetadata`/`activeConditions` (fail-closed `'no-metadata'` for the 5.1 no-fields path and boot-adopted sessions, whose persisted records live SW-side). Content.js calls the handle unconditionally but the handle is the authority, and content.js no-ops on `{ok:false}`. ✓

## Notes (non-blocking)

**N1 — Stop-during-transition race (narrow, visible).** `handleGameReset` checks phase once at entry but does not re-check before `setSlots(sid, newGameId)` on the success path. If the user clicks Stop in the millisecond window between the phase check and the chain completing (two channel round-trips), the sequence is: Stop clears the recorder (`set-session{null,null}`, slots null, phase IDLE) → then handleGameReset's `set-session(sid, G2)` re-sets the recorder and `setSlots(sid, G2)` repopulates slots on an IDLE phase. Result: a zombie session — the recorder holds `(sid, G2)` while the UI shows idle. A subsequent Start would hit 5.5's pre-check (`{ok:true, sessionId}` → `duplicate-start:session-active`) and refuse, leaving the user stuck until page reload. The window is tiny (requires human timing within ~10–50ms of a game reset), the failure is visible rather than silent corruption, and the contract doesn't specify this interleaving. A phase re-check before the final `setSlots` would harden it. Not a reject — but worth a follow-up.

**N2 — V2 success-path gap.** `sw-new-game.js` (5/5) covers only the fail-closed paths (`no-metadata`, phase preservation, Stop undisturbed). The success path (mint → save → re-set → slots → new tracker) is V1-covered and the recorder re-set is V2-covered via `sw-duplicate-start` AC9, but no single V2 test drives the full transition in real Chrome. Acceptable given the V1 depth, but a future harness could close it.

The boundary (`game_reset` under old gameId) is structurally guaranteed by synchronous-before-async ordering, and the 5.5 guard interaction is genuinely tested. **APPROVE** — proceed to commit.
