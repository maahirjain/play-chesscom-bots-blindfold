## SHOULD_FIX

### SF-1 — Instrumentation is not failure-isolated from move dispatch (content.js Enter handler)

**Location:** `content.js` async Enter handler (the 3.2 wiring block).

The handler awaits instrumentation calls with no `try/catch`:

```js
const attempt = attemptTracker.submitAttempt({...});   // may throw
if (attempt !== null && legal) {
    const dispatch = attemptTracker.noteDispatchStarted(attempt.attemptEventId); // may throw
    const outcome = await makeMoveOnBoard(game, move);  // may throw/reject
    ...
}
```

`sender.emit` (reached via the tracker's `emitEvent`) **can throw**:
it runs `createEvent`, which validates against the envelope —
`requireUuidV4(value, 'sessionId')` (`event_envelope.js:177`),
eventType regex, payload/refs shapes. Any disagreement between the 3.2
validators and the envelope (or a non-uuid `activeSessionId`, which the
tracker's `isActive()` gate permits since it only checks non-empty
string) makes `submitAttempt` throw.

Consequences of a throw here are **gameplay-breaking**, not just noisy:

1. The async listener's promise rejects → unhandled promise rejection.
2. `makeMoveOnBoard` is never reached for a legal move → **the user's
   move is silently dropped**. Pre-3.2, dispatch was unconditional for
   legal moves. Instrumentation must never be able to veto gameplay.

The same applies to `noteDispatchStarted` (throws `TypeError` on
non-string attemptEventId) and to a synchronous throw inside
`makeMoveOnBoard` itself (DOM ops: `getBoardElement`,
`squareToXY`, `clickElementAt`, `waitForVisiblePromotionWindow` —
the `await` turns it into an unhandled rejection; the clicks already
issued stay issued, so this half is less severe, but the rejection
noise remains).

**Why not a blocker:** every 3.2 payload passes both validator layers
today (41/41 V1, SW-ATTEMPTS 12/12 V2 drove the real input element);
the throw paths are latent, reachable only via validator disagreement
or a malformed `activeSessionId` that §5 controls. No live bug.

**Recommended repair:** isolate instrumentation from dispatch — e.g.
wrap the tracker calls so a throw is swallowed (optionally recorded
nowhere; there is no honest failure-reason for "instrumentation
threw"), and ensure `makeMoveOnBoard` is always invoked for legal
moves and its promise never rejects unhandled:

```js
// instrumentation must never prevent dispatch or reject unhandled
var attempt = null, dispatch = null;
try {
  attempt = attemptTracker.submitAttempt({...});
  if (attempt !== null && legal) {
    dispatch = attemptTracker.noteDispatchStarted(attempt.attemptEventId);
  }
} catch (instrErr) { /* record nothing; dispatch proceeds */ }
if (legal) {
  var outcome;
  try {
    outcome = await makeMoveOnBoard(game, move);
  } catch (dispatchErr) {
    outcome = 'dispatch_threw_unexpectedly'; // or simply true; do not invent a reason
  }
  ...
}
```

(Careful: do not invent a `DISPATCH_FAILURE_REASONS` member for the
throw case unless the contract is amended — the honest record is "no
dispatch outcome recorded".)

## NOTEs

### NOTE-1 — `isActive()` gate is weaker than the envelope's sessionId requirement

`createAttemptTracker`'s `isActive()` (`chess_utils.js`) accepts any
non-empty string for sessionId/gameId; the envelope requires uuid-v4
(`event_envelope.js:177`). A non-uuid non-empty `activeSessionId`
would pass the gate and then make `sender.emit` throw — which is
exactly the SF-1 trigger. In practice §5 will set 1.1-factory uuids,
so this is latent. Options: tighten the gate to uuid-v4 (consistent
with 1.1) or leave it (thunks may legitimately carry §5's future
formats). Flagged for §5, not for 3.2.

### NOTE-2 — 30s unconfirmed timeout is a heuristic

`unconfirmedTimeoutMs` defaults to 30000 (injectable, tested). A
confirmation delayed beyond 30s (backgrounded tab, slow DOM update)
is recorded `unconfirmed {reason:'timeout'}` even though the move may
later confirm and match — the attempt is already out of `pending`, so
the late confirmation matches nothing. This is honest (it *was*
unconfirmed at the deadline) but can be noisy. No change recommended;
§7 can tune with real-timing data.

### NOTE-3 — `dispatchStartedEventId: null` allowance is defensive-only

`requireValidDispatchFailedRefs` permits null `dispatchStartedEventId`
(build-report deviation 2). In the `content.js` wiring the start event
is always emitted before dispatch is attempted (synchronous section),
so the null branch is unreachable there — it exists only for direct
tracker-API use. The exact-keys requirement is preserved (the key must
be present), so the link shape is not weakened. Acceptable.

### NOTE-4 — `parseMoveSquares` runs twice per submit

`content.js` parses for the attempt's from/to/promotion, then
`makeMoveOnBoard` parses again internally. Both run synchronously
back-to-back on the same game state, so they agree; the redundancy is
minor compute, not a correctness issue. (Deduplicating would couple
the attempt record to dispatch internals — the current separation is
cleaner.)

### NOTE-5 — `markPendingUnconfirmed` aborts on mid-loop emit throw

In `markPendingUnconfirmed` (`chess_utils.js`), `pending.shift()`
removes the attempt *before* `emitEvent`; if `emitEvent` throws
mid-loop, remaining pendings stay queued and only surface at their
individual timer expiries (whose `onAttemptTimeout` emit can then
throw inside a timer callback). Same latent class as SF-1, confined
to the validator-disagreement scenario. No separate action beyond
SF-1's isolation.

### NOTE-6 — Pre-§5 inertness is the right call, thunks verified

Emission gated on both IDs via call-time thunks
(`() => BlindfoldSession.activeSessionId`), and both slots exist
(`chess_utils.js:13`, `lifecycle.js:401`, default null). §5 can set
them after tracker creation without recreating anything. The
"dangling records" rationale holds: 3.1's `move_confirmed` events are
themselves game-gated, so pre-§5 attempt events could never be
linked. No interim data is lost that §5 could use (there is no
session to attribute it to).

### 2. markPendingUnconfirmed try/catch (NOTE-5) — APPROVE

The emit call inside the drain loop is now wrapped in try/catch.
Marking semantics preserved:

- `marked.push(p.attemptEventId)` happens **before** the emit, so an
  attempt whose emit throws is still counted as marked and removed
  from pending — coherent with the best-effort philosophy (the
  alternative, re-queueing, risks unbounded loops; excluding it from
  `marked` would misreport `pendingCount()`).
- The loop continues to remaining pendings; `pendingCount()` is 0
  after. ✓

### 3. NOTE-5 test is genuine — APPROVE

`tests/attempt_tracker.test.js:534` ("emit throw during

### 4. `outcome = true` on dispatch throw — APPROVE

On an unexpected `makeMoveOnBoard` throw, `outcome` is set to `true`,
which skips `noteDispatchFailed`. Per the review's explicit guidance
("do not invent a DISPATCH_FAILURE_REASONS member"), recording no
dispatch outcome is the honest choice — a throw mid-dispatch leaves
the actual board state unknown, and any fabricated reason would be
dishonest. The inline comment states this plainly, so the dual use
of the `outcome` flag is not a readability trap. The attempt remains
in `pending` (its timer live): a later confirmation still matches it,
otherwise it goes `unconfirmed` on timeout — coherent, not limbo.
