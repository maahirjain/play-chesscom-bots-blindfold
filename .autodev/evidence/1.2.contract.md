# Task 1.2 Contract — Define session conditions

PLAN.md §1.2 (1.2.1–1.2.4). Read by planner/investigator 2026-10-06.
Source of truth: `PLAN.md` (unchanged). Related: PLAN §1 context, §3(a)/(b)/(c),
§5.2–§5.4, §6.1; `.autodev/evidence/1.1.contract.md` and `1.1.md` (identity
contract — 1.2 builds on it and must NOT redefine it); `session_identity.js`
(existing deliverable, extended alongside but not modified).

## 1. Scope

Task 1.2 defines the **session-conditions data contract only**: the exact
condition field set, value domains, per-field observed/manual source marking,
the unknown representation, the initial-conditions record factory, and the
condition-change event payload for later changes. It defines *factories,
validators, and constants*; it does **not** observe the Chess.com DOM (§3.3,
§5.4 — later), build the manual-entry UI (§5.2, §5.4 — later), wire the Start
button (§5.1 — later), persist anything (§2.2 — later), define the event
envelope (1.3 — next task), or export anything (§6 — later).

## 2. Design decisions (investigator-verified)

### 2.1 Separate record; `session_identity.js` untouched

Conditions live in a **new file `session_conditions.js`** (repo root), not
in `SessionMetadata`. Rationale:

- The 1.1 contract specifies `SessionMetadata` as *exactly six keys* and
  `requireValidMetadata`/`addGameToSession` validate that shape. The 1.1
  evidence file records an explicit reviewer note: "if §1.2 later extends
  the record, the contract needs an amendment."
- Nesting conditions into `SessionMetadata` now would invalidate the
  verified 1.1 contract and force re-verification of 1.1. A separate
  `SessionConditions` record needs no amendment to 1.1 and keeps the
  "do not redefine identity" requirement literal.
- The join point is documented, not implemented here: §6.1 assembles
  `metadata.json` from the identity record plus the conditions record
  (proposed merge key `initialConditions`; see §7). Change events carry
  session/game references via the 1.3 envelope, so the conditions record
  itself needs no session ID — identity stays single-sourced in 1.1.

### 2.2 Same module pattern as 1.1

Dependency-free plain (non-module) script exposing the **existing**
`BlindfoldSession` global (guard `var BlindfoldSession = BlindfoldSession ||
{};` — the guard exists precisely so multiple files contribute to one
namespace), IIFE-wrapped `'use strict'`, Node `module.exports` shim at the
end. chrome\*-independent, node-testable via `node --test`, frozen records,
plain-JSON values only. Zero changes to `session_identity.js`; the two files
share no code, only the namespace object. (Pattern verified in
`session_identity.js` and `manifest.json` content-script loading.)

### 2.3 Training approach / verbal scaffolding: free-form strings, no taxonomy

PLAN.md does **not** enumerate training approaches or scaffolding levels.
Evidence from the full read:

- §1 context describes journey *phases*, not a code list: "record three
  strict blindfold baseline games, develop square associations/stories,
  practice relational think-aloud mapping with occasional peeks, gradually
  reduce verbal scaffolding, and periodically repeat standardized blindfold
  evaluations." These are examples of an evolving personal practice.
- §3(b) step 5: "Select Training and the current scaffolding level."
  Step 6: "Gradually reduce verbal scaffolding, recording each condition
  change." No scale (no numbered levels, no named stages) is defined.
- §5.2 calls them "**fields**" (inputs), not dropdowns or option lists.

An enum (e.g. `['full','reduced','none']`) would be an **invented taxonomy**
freezing the owner's future approaches — exactly the kind of silent
specification change the mission forbids. Decision: both are validated
non-empty free-form strings; empty/whitespace-only normalizes to `null`
(unknown). A user who wants nuance writes it in the string itself
(e.g. `"reduced — square names only"`); no separate note field (that would
be scope creep beyond 1.2.1's "approach and level").

### 2.4 Source marking: wrapped `{ value, source }` per field

1.2.2 requires each of bot identity/displayed rating, player color, time
control, and assistance settings to carry its source ("observed or manually
supplied"). Design: every condition field is `{ value, source }` with
`source ∈ {'observed','manual'}`. Rejected alternative: a parallel
`conditionSources` map — it can drift out of sync with values, and 1.2.4
change payloads are then not direct subsets of the record. Wrapped fields
are self-describing in JSON and make change events (`{ field: {value,
source} }`) a clean subset.

`source` is **required on all seven fields**, including the two user-selected
ones (1.2.1's "selected" ⇒ source `'manual'`). Rationale: provenance is a
first-class 1.2.2 requirement; a silent default source would weaken it, and
the dichotomy is exhaustive by construction — a value either came from DOM
detection (`observed`) or from the user, remembered defaults included
(`manual`; §5.3 "remember previous selections" does not change origin).

When a value is `null` (unknown), `source` still records *how the unknown
was determined* (detection attempted and found nothing ⇒ `observed`; user
left the field blank ⇒ `manual`).

### 2.5 Unknown = `null`, consistent with 1.1

`normalizeProtocolVersion` maps `null`/`undefined`/`""`/whitespace-only →
`null` ("unknown stays unknown, never guessed, never `""`"). The same rule
applies to every condition value: no sentinel strings (`"n/a"`,
`"unknown"`), no guessed defaults. A condition that is inapplicable (e.g.
training approach for a baseline session) is also `null` — its inapplicability
is derivable from `sessionCategory` (1.1), so no third state is needed.

### 2.6 Time control: single label string

`timeControl.value` is a nullable trimmed string preserving the **original
observed/manual label text** (whatever Chess.com or the user provides).
Rejected: a structured `{label, base_seconds, increment_seconds}` object.
Seconds are *derivable* from the label at analysis time, and PLAN §3(a) is
explicit — "Do not persist those derived products." If a later task (§3.3
DOM audit) demonstrates the label genuinely cannot represent an observed
time control, that is a spec-level finding to raise then, not a structure
to pre-invent now. The contract is deliberately DOM-agnostic: no
assumptions about Chess.com's label formats are baked in.

### 2.7 Assistance settings: extensible map, keys defined by §3.3

`assistanceSettings.value` is `null` (unknown) or a **flat map** of setting
name → primitive (`boolean | string | number | null`). Rationale:

- PLAN 1.2.2 names "assistance settings" without enumerating them; §3.3.4
  requires recording "reliably observable Chess.com hints and
  assistance-setting changes" and §3.3.5 requires a DOM audit of "what the
  current DOM can expose." The key inventory is genuinely unknown until
  that audit — a fixed field set now would be invented.
- The contract defines only the container shape and value-type constraints
  (flat primitives; nested objects/arrays rejected — keeps records
  plain-JSON and prevents smuggling structured observations past review).
- `{}` (empty map) vs `null` is a meaningful, preserved distinction: `{}`
  = observed, no assistance settings to report; `null` = unknown.
  A known setting with an unreadable value is `{ "name": null }`.
- This covers **Chess.com-side** assistance settings only. The extension's
  own piece-visibility state is recorded as visibility events (§3.3.1/§3.3.2),
  not as a session condition — do not conflate them.

### 2.8 Change events carry new values only (1.2.4)

A later condition change is a `conditions_changed` event whose payload is
`{ changes: { <field>: { value, source }, … } }` containing **only the
changed fields**. Previous values are derivable by folding the stream
(initial conditions + prior changes), so persisting `from` values would
violate "do not persist derivable values." A pure `applyConditionChange`
fold helper is provided so §6.1/tests can compute current conditions
without duplicating logic. A change that returns a field to unknown is
`{ value: null, source }` with source per §2.4.

The **event envelope** (event ID, type placement, session/game refs,
timestamps, append sequence) is task 1.3's job — 1.2 defines only the
event-type constant and the payload shape, and marks the wiring deferred.

### 2.9 No timestamps on the conditions record

"Stored once at session start" (1.2.1) is a lifecycle semantic, not a
record field. Occurrence time comes from the 1.3 envelope on the change
events and from session-start lifecycle events (§2.7/§3.5) for the initial
record — never a `recordedAt` inside the record itself (that would be
fabricated timing at the contract layer).

## 3. Exact deliverables

### 3.1 New file: `session_conditions.js` (repo root)

Plain script, no dependencies, contributes to the `BlindfoldSession` global
(+ Node `module.exports` shim). Contents:

| Export | Type | Behavior |
|---|---|---|
| `CONDITION_FIELDS` | frozen array | `['trainingApproach','verbalScaffolding','botName','botDisplayedRating','playerColor','timeControl','assistanceSettings']` — exact key set, no more, no fewer |
| `CONDITION_SOURCES` | frozen array | `['observed','manual']` |
| `PLAYER_COLORS` | frozen array | `['white','black']` |
| `CONDITION_CHANGE_EVENT_TYPE` | frozen string | `'conditions_changed'` |
| `isConditionField(s)` | `(any) => boolean` | membership in `CONDITION_FIELDS` |
| `isConditionSource(s)` | `(any) => boolean` | membership in `CONDITION_SOURCES` |
| `isPlayerColor(s)` | `(any) => boolean` | membership in `PLAYER_COLORS` |
| `normalizeConditionString(v)` | `(any) => string \| null` | `null`/`undefined` → `null`; non-string → `TypeError`; trim; `""`/whitespace-only → `null` |
| `normalizeBotRating(v)` | `(any) => number \| null` | `null`/`undefined` → `null`; must be a finite integer ≥ 0 → else `TypeError` (displayed ratings are non-negative integers; no invented upper cap) |
| `normalizeAssistanceSettings(v)` | `(any) => object \| null` | `null`/`undefined` → `null`; must be a plain object (not array) → else `TypeError`; keys must be non-empty strings; values `boolean`/`string`/`number`/`null` only (strings trimmed, `""` → `null`; nested objects/arrays → `TypeError`); unknown keys impossible by construction (extensible map) |
| `createInitialConditions(input)` | `(object) => SessionConditions` | requires all seven fields present, each `{ value, source }` with valid source (`RangeError` otherwise); normalizes each value per-field; returns fresh frozen record (see 3.2). Called exactly once per session at Start (§5.1 wiring, deferred). |
| `createConditionChange(changes)` | `(object) => ConditionChangePayload` | non-empty map of known field names → `{ value, source }`; unknown field name → `RangeError`; empty map → `Error`; each change validated per-field; returns frozen `{ changes }` containing only the changed fields (see 3.3) |
| `applyConditionChange(conditions, change)` | `(SessionConditions, ConditionChangePayload) => SessionConditions` | validates both inputs; returns a **new** frozen record with changed fields replaced; original untouched |

Error conventions mirror 1.1: `TypeError` = wrong type/shape (including a
missing field or malformed `{value,source}` wrapper); `RangeError` = value
outside an allowed domain (bad source, bad color, unknown field name —
consistent with 1.1's `sessionCategory` → `RangeError`); plain `Error` =
logic error (empty change map, mirroring 1.1's duplicate-gameId `Error`).

### 3.2 JSON shape: `SessionConditions` (initial, at session start)

Exact keys — the seven in `CONDITION_FIELDS`, no more, no fewer. Each value
is a frozen `{ value, source }`:

```json
{
  "trainingApproach":  { "value": "relational think-aloud mapping with occasional peeks", "source": "manual" },
  "verbalScaffolding": { "value": "full think-aloud", "source": "manual" },
  "botName":           { "value": "Nelson", "source": "observed" },
  "botDisplayedRating": { "value": 1000, "source": "observed" },
  "playerColor":       { "value": "white", "source": "observed" },
  "timeControl":       { "value": "10 min", "source": "manual" },
  "assistanceSettings":{ "value": { "hints": false }, "source": "observed" }
}
```

(Example values illustrative, not claims about Chess.com.) Field semantics:

- `trainingApproach` — free-form non-empty string; `null` = unspecified/
  inapplicable (e.g. baseline session; inapplicability derivable from
  `sessionCategory`). Never an enum.
- `verbalScaffolding` — free-form non-empty string; `null` = unspecified.
  May hold for evaluation sessions too (§3(b) step 7: keep evaluation
  verbalization stable) — no category-conditional logic in the contract.
- `botName` — bot identity as observed/shown; free-form non-empty string.
- `botDisplayedRating` — the **displayed** rating (PLAN's word), integer ≥ 0.
- `playerColor` — `'white'` | `'black'` | `null`.
- `timeControl` — original label text; `null` = unknown.
- `assistanceSettings` — flat map per §2.7; `null` = unknown, `{}`
  = observed-none.

All-unknown initial record is legal: every field `{ value: null, source }`
with honest per-field sources (§2.4).

### 3.3 JSON shape: `ConditionChangePayload`

```json
{
  "changes": {
    "verbalScaffolding": { "value": "reduced — square names only", "source": "manual" },
    "assistanceSettings": { "value": { "hints": true }, "source": "observed" }
  }
}
```

Only changed fields appear. Envelope (event ID, `sessionId`/`gameId` refs,
timestamps, sequence) is 1.3's — this payload is the `payload` the envelope
will carry.

### 3.4 New file: `tests/session_conditions.test.js`

`node --test` suite covering every V1-verifiable acceptance criterion
below. No test framework dependency (per DECISIONS.md).

## 4. Acceptance criteria

### 1.2.1 — training approach + verbal scaffolding stored once at session start

- [ ] **AC1** `createInitialConditions` accepts arbitrary non-empty strings
  for `trainingApproach`/`verbalScaffolding` (no enum, no allowlist) and
  stores them verbatim after trimming. *Verify now (V1): unit tests with
  multi-word, punctuation-heavy, and numeric-as-text inputs; assert exact
  round-trip.*
- [ ] **AC2** Empty/whitespace-only/omitted-via-null inputs normalize to
  `{ value: null, source }`, never `""`. *Verify now (V1): unit tests.*
- [ ] **AC3** The initial record is created once per session; later changes
  never rewrite it — they go through `createConditionChange`/
  `applyConditionChange`. *Verify now (V1): `createInitialConditions`
  returns a fresh frozen record each call; no in-place update API exists
  (static check). The §5.1 "exactly once at Start" wiring is DEFERRED →
  §5.1.*

### 1.2.2 — bot/rating/color/time-control/assistance with observed/manual source

- [ ] **AC4** Record contains exactly the seven `CONDITION_FIELDS` keys, no
  more, no fewer; each is a frozen `{ value, source }`. *Verify now (V1):
  `Object.keys` exact-set test + frozenness checks.*
- [ ] **AC5** Every field carries an explicit `source ∈ {'observed',
  'manual'}`; missing/invalid source → `RangeError`; a missing field
  entirely → `TypeError`. No defaulted sources. *Verify now (V1): unit
  tests incl. per-field source matrix.*
- [ ] **AC6** `playerColor` accepts only `'white'`/`'black'`/`null`;
  anything else (incl. `'White'`, `'w'`) → `RangeError`. *Verify now (V1).*
- [ ] **AC7** `botDisplayedRating` accepts only finite integers ≥ 0 or
  `null`; floats, negatives, `NaN`/`Infinity`, numeric strings →
  `TypeError`. *Verify now (V1).*
- [ ] **AC8** `timeControl.value` is a trimmed non-empty string or `null`
  (original label text preserved verbatim); no seconds parsed or stored.
  *Verify now (V1).*
- [ ] **AC9** `assistanceSettings.value` is `null`, `{}`, or a flat
  primitive map; nested objects/arrays → `TypeError`; `{}` ≠ `null`
  preserved. *Verify now (V1), incl. `{hints: null}` (known setting,
  unknown value).*
- [ ] **AC10** Sources are honest by construction: the contract cannot
  produce a record without per-field provenance. *Verify now (V1): AC5
  tests + adversarial review.*

### 1.2.3 — unavailable conditions as unknown, never guessed

- [ ] **AC11** Any condition may be `{ value: null, source }`; `null` is the
  only unknown representation — no `"n/a"`, `"unknown"`, or invented
  defaults anywhere. *Verify now (V1): all-null record test + static
  search for sentinel strings.*
- [ ] **AC12** No derived values are persisted: no seconds parsed from
  labels, no counts, no durations, no inferred categories. *Verify now
  (V1): key-set/purity tests + adversarial review.*
- [ ] **AC13** `normalizeConditionString`/`normalizeBotRating`/
  `normalizeAssistanceSettings` never throw on `null`/`undefined` input
  (they yield `null`); they throw `TypeError` only on wrong-typed
  non-null input. *Verify now (V1).*

### 1.2.4 — later changes as events, not repeated conditions

- [ ] **AC14** `createConditionChange` payload contains **only** the supplied
  changed fields; unchanged conditions are absent, never repeated.
  *Verify now (V1): payload key-set test.*
- [ ] **AC15** `applyConditionChange` is pure: input record never mutated,
  returns a new frozen record with exactly the changed fields replaced and
  all else identical. *Verify now (V1): deep-freeze input, assert
  untouched; assert output frozen and correct.*
- [ ] **AC16** Multi-field changes are one payload; a field changed twice
  is two separate change payloads (append-only, never merged). A change to
  unknown is `{ value: null, source }`. *Verify now (V1).*
- [ ] **AC17** `CONDITION_CHANGE_EVENT_TYPE === 'conditions_changed'`
  (frozen). *Verify now (V1): constant test.*
- [ ] **AC18** Envelope wiring (event ID, session/game refs, timestamps,
  append sequence) is **DEFERRED → 1.3**. The builder delivers the payload
  shape and type constant only; 1.3 owns the envelope. Recorded as
  deferred with dependency; never claimed as verified before then.

   (§3.3, §5.4) — representation only.

4. No event envelope, timestamps, session/game refs, or append sequences
   (1.3) — payload + type constant only.

6. No export/ZIP/metadata.json assembly (§6).
7. No changes to `session_identity.js`, `content.js`, `chess_utils.js`,

## 7. Downstream needs this contract must serve (from §1.3–§6 skim)

- **1.3 (next task):** consumes `CONDITION_CHANGE_EVENT_TYPE` and the
  §3.3 payload shape as the event `payload`; owns envelope (ID, type
  placement, `sessionId`/`gameId` refs, UTC+monotonic timestamps, source
  sequence, append sequence). If 1.3 namespaces event types, this
  constant's value needs a contract amendment — flagged, not decided here.
- **§2.2:** `SessionConditions` stored in IndexedDB → plain-JSON constraint
  (AC21); frozen records are storage-safe (1.1 verified the same property).
- **§3.3:** defines the `assistanceSettings` key inventory from the DOM
  audit (this contract only constrains the container); records
  assistance-setting *changes* via `createConditionChange`.
- **§5.1:** Start handler calls `createInitialConditions` exactly once per
  session with per-field sources; owns "once at session start" enforcement.
- **§5.2/§5.4:** UI supplies `trainingApproach`/`verbalScaffolding` text
  fields and manual completions; must pass explicit per-field sources
  (`observed` for detected, `manual` for user-supplied — including
  remembered defaults per §5.3, whose origin stays `manual`).
- **§6.1:** `metadata.json` merges the identity record with the initial
  conditions (proposed key `initialConditions`) plus their
  observed/manual sources — directly serving the §3(a) table row
  ("initial conditions; observed/manual sources"). Later changes are
  already in `events.jsonl` via 1.3 envelopes; §6.1 must not duplicate
  them into metadata.json.
- Reviewer attention: §2.3 (taxonomy creep — "helpful" enums/dropdowns),
  AC12 (derived seconds/counts), §2.6 (structured time-control objects),
  and envelope creep (timestamps/IDs in the conditions module) are the
  likeliest weakening points.
