## NOTEs

### NOTE-1 — Manifest deviation (contract AC10) was the right call
The contract said `manifest.json` byte-identical to HEAD, which is
unachievable: MV3 content scripts load *only* via the manifest
`content_scripts[].js` list (no `importScripts` in content-script
worlds; inlining into content.js would violate module conventions).
The builder's one-entry addition + exact-diff pin is the minimal honest
fix. **Contract correction approved.**

### NOTE-2 — `recordAckFailure` fail-open corner: not reachable, deferral honest
The builder's note is accurate (`sender.js:200–210`): a writer ack with a
dropped/mismatched `eventId` yields `no-ack` → amber forever. But I
verified the writer echoes `eventId` in *every* ack path (`writer.js`
lines 180–392, including `eventId: null` for malformed intake — which the
sender can never produce since it builds its own validated envelopes).
The corner requires a writer bug, not a reachable state; even then the
event stays queued and retries (no data loss), only the color is wrong.
Deferring the "no-ack after N attempts → persistent" idea to §5/2.9 is
honest. Not a 2.8 defect.

### NOTE-3 — `transportAvailable: false` + queued events → healthy green
`sender.js:259–263`: no transport → `finish()` with no `lastError`, no
retry. `resolveTransport` (`sender.js:97–106`) returns null only when
`chrome.runtime.sendMessage` is not a function — i.e. extension-context
invalidation, where the content script (and indicator) is dying anyway.
The contract's "waiting for SW" rationale is slightly imprecise (a
sleeping SW still has a working sendMessage), but the behavior is
correct and the contracted table is implemented faithfully.

### NOTE-4 — `setTimeout` resolved outside the try in `tick()`
`status_indicator.js` `tick()`: `globalThis.setTimeout` is dereferenced
*after* the try/catch. A missing `setTimeout` would throw into page
code, violating the module's "never throws after install" contract.
Unreachable in content-script/Node targets; suggest the 2.5-style
`typeof st === 'function'` guard if this module is ever touched again.

### NOTE-5 — First-tick `getStatus` throw keeps the initial green class
The element is created with `blindfold-status-healthy` before the first
(swallowed) tick. A throwing `getStatus` would leave a green light on a
broken sender. `sender.js` `getStatus` (lines 396–404) has no throw
paths (`Object.freeze`, property reads), so this is unreachable;
noted for completeness.

### NOTE-6 — `installStatusIndicator` is not idempotent
A second content-script execution in the same document would insert a
second indicator + poll loop (the move-input block at `content.js:24`
is guarded; the install at line 58 is not). MV3 injects once per
document load, so this is not demonstrated reachable; a
`querySelector('.blindfold-status-indicator')` guard would be cheap
defense-in-depth.

### NOTE-7 — Quota on metadata/conditions saves won't reach the indicator
`session_store.saveSessionMetadata/saveConditions` go through `DB.put`
directly, not the writer. When §5 wires those calls, a `QuotaExceededError`
there rejects the §5 promise — it will NOT surface in this indicator
(which watches the sender's event pipeline only). §5 should decide how
to surface those failures.

### NOTE-8 — Fallback placement vs. V3
The fixed-corner fallback uses `z-index: 2147483647`. It only triggers
when the extension's own move input is absent (abnormal). AC15
(owner-device visual check, §7) is the right place to judge it.

### NOTE-9 — `stop()` is never called by content.js
The 2s poll runs for the content-script (page) lifetime. Correct —
no leak beyond page lifetime, and SPA route changes don't re-inject
content scripts.
