## V2 — integration (real headless Chrome 154, repo path passed as argv[2])

### sw-conditions-panel.js: 62/64 on the shipped harness → 64/64 after fixing a harness defect

The shipped harness failed 2 checks on my independent run:

1. `FAIL: AC8: session 2 conditions recorded {"value":"black","source":"observed"}` — expected `{white, observed}`.
2. `FAIL: AC8: session 2 manual-only fields stay {null, manual} with no entries {"botName":{"value":"TestBot","source":"manual"}}` — expected null.
3. (also) `FAIL: AC8: session 3 records manual playerColor {white, manual} {"value":"black","source":"observed"}` — expected `{white, manual}`.

**Root cause (harness defect, not a product defect):** the harness matches
conditions records by array index (`all[1]`, `all[2]`), assuming insertion
order. The `conditions` store has `keyPath: 'sessionId'` (db.js:80), and
sessionIds are UUID-v4 strings — IDB `getAll` on a keyPath store returns
records in **key order, not insertion order**. The failing checks' actual
values (`playerColor {black,observed}`, `botName {TestBot,manual}`) are
exactly **session 1's** values, proving the harness compared the wrong
record. The builder's reported 64/64 was luck of UUID sort order in their
run.

**Proof:** I ran a patched copy of the harness (scratch file, deleted
afterwards — the shipped harness was not modified) that matches records by
distinguishing content instead of index (session 1: `botName==='TestBot'`;
session 2: `playerColor {white,observed}` + null botName; session 3:
`playerColor {white,manual}`). Result: **64/64 checks passed**. The product
wrote the correct record for every session; only the harness's indexing was
wrong.

**Recommendation for the parent:** fix the shipped
`sw-conditions-panel.js` to match records by `sessionId`/content rather
than index (same latent defect pattern could affect other harnesses that
index into keyPath stores). I did not modify the harness per my
do-not-modify instructions.
