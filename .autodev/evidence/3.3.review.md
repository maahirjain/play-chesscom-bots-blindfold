## NOTEs (no action required for 3.3)

### NOTE-1 — `s` usable-content proxy vs the speech path's selectors
`content.js:295` tests `BlindfoldSession.getBoardElement() !== null`
(`wc-chess-board`), but `speakPosition()` → `positionToSpeechText()` →
`readPiecesFromBoardDOM()` (`sounds.js:250-253`) reads `#board-primary` /
`#board-play-computer`. These are different selectors. In the narrow
transient where the `wc-chess-board` component exists but the inner
board element has not rendered, `hadUsableContent: true` would misreport
while speech says "Board not found." The contract explicitly specified
the `getBoardElement()` proxy, the builder implemented it faithfully,
and `wc-chess-board` is the codebase-standard board proxy (3.2's
dispatch uses it) — so this is a documented proxy limitation, not a
defect. Recommendation: 3.4 (or a future pass) should either align the
test with the speech path's readability check or keep the proxy with
this limitation noted.

### NOTE-2 — Cross-tab piece-set changes are unobserved
There is no `storage` event listener; if another tab writes
`blindfold_chess_piece_set`, this tab's `piece_set` variable goes stale
and no transition is recorded. Out of 3.3's contracted scope (the
source vocabulary has no cross-tab member), but §5's session model
should decide whether cross-tab state is in or out.

### NOTE-3 — `w: true` is honest per shortcut behavior, not per session meaning
`w` always speaks a turn announcement (`game.turn()` always defined in
chess.js), so `hadUsableContent: true` accurately reflects that the
shortcut produced its content. Whether the announced turn is
*meaningful* (e.g., no game loaded) is session context, not shortcut
content — the contract's §2.2 table defines it this way explicitly.
Recorded as designed.

### NOTE-4 — `recordTransition` validates before the `isActive()` gate
A malformed call throws even when the recorder is inert (pre-§5). All
content.js call sites are failure-isolated, so this is fail-fast on
programmer error, not a UX risk. The ordering is defensible; noting it
so a future caller isn't surprised.

### NOTE-5 — Validator accepts `from === to` (documented deviation)
The contract's §3.1 ("transitions require from !== to") and §3.2
("no-op when from === to") were ambiguous about where the same-mode
case is rejected. Accepting it in the validator and no-op'ing in
`recordTransition` is the coherent reading, and the test asserts both
halves. A direct `sender.emit` of a from===to payload would pass
validation, but the recorder is the only emitter — theoretical only.

### NOTE-6 — `setPieceSet` assigns/persists before recording
`piece_set = mode; localStorage.setItem(...); applyCurrentPieceSet();`
run before the recorder call. An invalid `mode` would corrupt the
variable and storage while the (caught) validator throw swallows the
event. Pre-existing ordering, single valid caller (the v-key toggle) —
not a 3.3 regression. A future `'api'` caller should validate before
calling.

### NOTE-7 — `recordHelpRequest` returns null when inert (3.4 handoff)
Pre-§5, the recorder returns null (no eventId) for help requests. This
is coherent — there is nothing for 3.4 to link to until §5 activates
emission — but 3.4's utterance-linking must handle null eventIds rather
than assuming the 3.4.1 reference always exists.
