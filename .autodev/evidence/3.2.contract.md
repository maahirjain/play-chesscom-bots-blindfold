# Task 3.2 contract — instrument move input in content.js

PLAN.md §3.2 (human-owned; this contract must not weaken, reinterpret, or
omit any of 3.2.1–3.2.7).

## 1. Scope

Instrument the keyboard move-input flow in `content.js` so every submitted
move attempt is recorded with its exact input, first-edit time, validation
outcome, dispatch result, and — only after the move is observed as accepted
in the move list — its link to the confirmed history move. Rejected mouse
attempts stay outside guaranteed coverage (3.2.7); the limitation is
documented, not worked around by inference.

**In scope:** the `#blindfold-chess-move-input` Enter handler, the `input`
listener (first-edit capture), `makeMoveOnBoard`'s failure reporting,
attempt lifecycle (pending → matched | unconfirmed | terminal-at-birth),
attempt→confirmed matching against the 3.1 tracker's confirmed list.

**Non-goals:** any change to input UX (border colors, sounds, hotkeys stay
exactly as-is); keystroke logging (explicitly forbidden by 3.2.1);
inferring mouse attempts from clicks; speech changes (3.4); visibility /
assistance (3.3); session controls ( §5 owns Start/Stop and game identity).

## 2. Current-state analysis

`content.js` (Enter handler) today:

1. Reads `move_input.value`, normalizes via `normalizeMove(game, value)`,
   clears the field. The exact submitted text is discarded.
2. `isMoveLegal(game, move)` decides green/red border + illegal sound.
   The outcome is not recorded anywhere.
3. `makeMoveOnBoard(game, move)` is called **without await**; its boolean
   result is ignored. Dispatch failures (no board element, bad coords,
   promotion-window timeout, missing promotion choice) are invisible.
4. Nothing is emitted. The 3.1 tracker later emits `move_confirmed` for
   moves that appear in Chess.com's move list, but there is no record of
   what the user typed, when they started typing it, or whether dispatch
   succeeded.

`makeMoveOnBoard` (chess_utils.js) has exactly one caller (content.js:62),
so its return contract can be extended safely.

## 3. Design

### 3.1 Event vocabulary (3.2-owned, per 1.3 §2.2)

All five types live as `BlindfoldSession.*_EVENT_TYPE` constants in
chess_utils.js next to the 3.1 vocabulary. `event_envelope.js` is untouched.

| eventType | when | refs | payload (exact keys) |
|---|---|---|---|
| `move_attempt` | Enter pressed (submit) | null | `{submittedText, firstEditMonotonicMs, validation}` |
| `move_dispatch_started` | `makeMoveOnBoard` invoked | `{attemptEventId}` | `{}` |
| `move_dispatch_failed` | `makeMoveOnBoard` returns failure | `{attemptEventId, dispatchStartedEventId}` | `{failureReason}` |
| `move_attempt_matched` | pending attempt matches a confirmed move | `{attemptEventId, confirmedMoveEventId}` | `{}` |
| `move_attempt_unconfirmed` | timeout / pagehide / game-reset with attempt still pending | `{attemptEventId}` | `{reason}` |

Payload domains:
- `submittedText`: verbatim `move_input.value` at submit (no trim).
- `firstEditMonotonicMs`: `performance.now()` captured at the first
  `input` event since the last submit, else `null` (unknown = unknown).
  Same content-script clock segment as the sender's stamp → wall time is
  derivable via the segment anchor. No per-keystroke data is stored.
- `validation`: `'legal'` or `'illegal'` — the actual `isMoveLegal` outcome.
  The normalized string is **not** stored (derivable from submittedText +
  position via the versioned `normalizeMove`; 3.2.3).
- `failureReason` ∈ `DISPATCH_FAILURE_REASONS` (frozen): `'move_unparsable'`,
  `'board_not_found'`, `'square_coordinates_failed'`,
  `'promotion_window_timeout'`, `'promotion_choice_missing'`.
- `reason` ∈ `{'timeout','pagehide','game_reset'}`.

Empty payloads (`{}`) are legal per `requirePayload` (plain object only).

### 3.2 Attempt tracker (DOM-free state machine)

New `BlindfoldSession.createAttemptTracker(opts)` in chess_utils.js,
following the 3.1 tracker precedent (namespace, Node shim, exact-keys
payload validators, TypeError/RangeError/plain-Error conventions):

```js
createAttemptTracker({
  emitEvent,            // (eventType, payload, refs) => {eventId}|null
  getSessionId,         // () => BlindfoldSession.activeSessionId (thunk)
  getGameId,            // () => BlindfoldSession.activeGameId (thunk)
  unconfirmedTimeoutMs, // default 30000, injectable for tests
  setTimeoutFn, clearTimeoutFn // injectable for tests
})
```

- **Emission gate** (2.7/3.1 §5-seam precedent): every emit path first
  requires `getSessionId()` and `getGameId()` to be non-empty strings;
  otherwise the tracker is inert (no events, no timers). Rationale: 3.2.5
  linking is meaningless without emitted `move_confirmed` events, which
  are themselves game-scoped (3.1 `emitGameEvent` gates on gameId); emitting
  half a lifecycle pre-§5 would create dangling records.
- `submitAttempt({submittedText, firstEditMonotonicMs, validation, from, to,
  promotion})` → emits `move_attempt`, returns `{attemptEventId}` or null
  when dormant. If `validation==='legal'` and from/to are non-null, the
  attempt enters `pending` with an `unconfirmedTimeoutMs` timer. Illegal
  attempts and unparsable attempts are terminal at birth (known outcomes).
- `noteDispatchStarted(attemptEventId)` → emits `move_dispatch_started`,
  returns `{dispatchEventId}`.
- `noteDispatchFailed(attemptEventId, dispatchEventId, failureReason)` →
  emits `move_dispatch_failed`; attempt leaves `pending` (terminal).
- `noteConfirmedMoves(confirmedEntries)` → for each entry **in order**,
  skips entries with null `eventId` (cannot link honestly); finds the first
  pending attempt with equal `(from, to, promotion)`; on match clears the
  timer, removes from pending, emits `move_attempt_matched`. FIFO keeps
  repeated identical attempts ordered.
- Timeout → emits `move_attempt_unconfirmed` `{reason:'timeout'}`.
- `handleGameReset()` → all pending become unconfirmed
  `{reason:'game_reset'}` (a reset orphans in-flight attempts).
- `handlePageHide()` → best-effort unconfirmed `{reason:'pagehide'}` for
  all pending; clears timers (2.7 best-effort philosophy).

Thunks (not construction-time values) for session/game IDs so §5 can set
them later without recreating the tracker.

### 3.3 content.js wiring

- `input` listener: in addition to clearing the border, capture
  `firstEditMonotonicMs = performance.now()` on the first `input` event
  since the last submit (a module-level `let`, reset on submit).
- Enter handler becomes `async`:
  1. `rawText = move_input.value` — **before** normalize/clear (3.2.2).
  2. `firstEdit` snapshot; reset the module-level tracker.
  3. Existing normalize → clear → `isMoveLegal` → border/sound UX unchanged.
  4. `parsed = legal ? parseMoveSquares(game, normalized) : null`.
  5. `attempt = attemptTracker.submitAttempt({...})`.
  6. If legal and attempt non-null: `dispatch = attemptTracker.noteDispatchStarted(attempt.attemptEventId)`; `outcome = await makeMoveOnBoard(game, normalized)`; if `outcome !== true`, `attemptTracker.noteDispatchFailed(...)`.
- `observeMoves` callback: after `historyTracker.observe(half_moves)`,
  call `attemptTracker.noteConfirmedMoves(result.confirmed)`.
- `onGameReset` stub: also call `attemptTracker.handleGameReset()`.
- `pagehide`: call `attemptTracker.handlePageHide()` (best-effort; shares
  the 2.7 hook philosophy — register alongside, never throws, never flush).

### 3.4 makeMoveOnBoard failure reasons

Return contract becomes `true` on success, otherwise one of
`BlindfoldSession.DISPATCH_FAILURE_REASONS` (frozen string constants).
Each existing `return false` is replaced with its specific reason; no
other behavior changes. Single caller (content.js) is updated.

### 3.5 First-edit timing (3.2.1)

Programmatic `move_input.value = ""` does not fire `input`, so the
first-edit variable cannot be polluted by the submit clear. The variable
resets only on submit. No keystroke contents, counts, or inter-key timings
are recorded — one monotonic timestamp per attempt.

### 3.6 Mouse attempts (3.2.7)

Mouse input goes directly to Chess.com's own event handlers; the extension
observes only the resulting move list (3.1.3 covers confirmed mouse moves).
There is no reliable DOM signal for a *rejected* mouse attempt (no error
element or state change the extension can observe without speculating from
click coordinates, which would be fabrication). The builder must audit the
live DOM in the V3 environment and document the findings; the guaranteed
coverage stays: keyboard attempts only. Documented in DECISIONS.md and a
code comment at the (non-)integration point.

## 4. Acceptance criteria

### V1 — static / unit (Node, DOM-free)

- [ ] **AC1.** First-edit capture: simulated `input` events set the
  timestamp once; subsequent inputs before submit do not overwrite it;
  submit resets it. Only the timestamp is retained (assert no keystroke
  content/count anywhere).
- [ ] **AC2.** Submit path captures `move_input.value` verbatim before
  `normalizeMove`/clear (test via the wiring order; payload
  `submittedText` has no trim applied).
- [ ] **AC3.** `move_attempt` payload has exactly
  `{submittedText, firstEditMonotonicMs, validation}`; the normalized
  string appears nowhere in any 3.2 payload.
- [ ] **AC4.** `makeMoveOnBoard` returns `true` or a member of
  `DISPATCH_FAILURE_REASONS`; each of the five failure sites is unit
  reachable (parse/board/coords/promotion-window/promotion-choice);
  `move_dispatch_started` precedes every dispatch; `move_dispatch_failed`
  carries the exact reason with both refs.
- [ ] **AC5.** Matching: pending attempt + confirmed entry with equal
  from/to/promotion → exactly one `move_attempt_matched` with
  `{attemptEventId, confirmedMoveEventId}`; confirmed entries with null
  eventId never produce links; FIFO order for duplicate attempts; no
  match on from/to mismatch.
- [ ] **AC6.** Lifecycle: illegal-at-submit and dispatch-failed attempts
  are terminal (no timer, no unconfirmed event); a pending attempt with
  no match inside `unconfirmedTimeoutMs` → `move_attempt_unconfirmed`
  `{reason:'timeout'}`; `handleGameReset`/`handlePageHide` mark pending
  with their reasons. Absence of confirmation is never recorded as
  illegal.
- [ ] **AC7.** Dormancy: with null/empty sessionId or gameId, all tracker
  methods are inert (no events, no timers scheduled).
- [ ] **AC8.** Payload validators: exact keys, `validation`/`reason`/
  `failureReason` enums, `firstEditMonotonicMs` number|null; wrong
  types → TypeError, bad enum → RangeError.
- [ ] **AC9.** Diff discipline: only `chess_utils.js` (tracker +
  makeMoveOnBoard reasons), `content.js` (wiring), tests, evidence,
  DECISIONS.md. No other product files.
- [ ] **AC10.** No 3.3/3.4/3.5 scope; PLAN.md unmodified; existing UX
  (borders, sounds, hotkeys) byte-identical in behavior.

### V2 — integration / runtime (real Chrome, repo-path argv)

- [ ] **AC11.** Harness drives the real input element: type → Enter →
  `move_attempt` in IDB with verbatim text and first-edit stamp;
  legal move → `move_dispatch_started`; forced dispatch failure (board
  hidden) → `move_dispatch_failed` with the exact reason; short-timeout
  pending attempt → `move_attempt_unconfirmed`.
- [ ] **AC12.** All existing harnesses still PASS.

### V3 — real browser behavior (deferred, §7 / owner device)

- [ ] **AC13.** End-to-end on a live Chess.com bot game: typed attempt →
  dispatch → observed confirmation → `move_attempt_matched`; plus the
  3.2.7 DOM audit for rejected-mouse signals with documented findings.

## 5. Explicit non-goals

- Changing what the input UI does (it keeps working exactly as today).
- Recording keystrokes, counts, or inter-key timings.
- Inferring mouse attempts from click coordinates.
- Touching speech (3.4), visibility (3.3), lifecycle (3.5), or §5 seams
  beyond reading the two ID thunks.
- Any analysis of attempt data (no success rates, no metrics).
