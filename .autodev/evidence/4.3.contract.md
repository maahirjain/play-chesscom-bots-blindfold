# Task 4.3 contract — screen/tab capture selection and permission handling

PLAN.md §4.3: "Add screen/tab capture selection and permission handling."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope boundary — what 4.3 is and is not

**4.3 delivers a selected, permitted screen/tab capture configuration — not a
recording.** Concretely: a persisted capture-mode preference (`'tab'` vs
`'screen'`), game-tab targeting for tab mode, a permission-probe flow
(acquire-then-stop, mirroring 4.2's probe-then-stop), queryable permission
state, and durable events for selection/permission changes. 4.3 ends with
**no open capture stream**: every probe stream's tracks are stopped before
`capture-request-permission` resolves. 4.6 re-acquires at Start and owns
stream lifetime; the revoked-between-probe-and-Start race is 4.6's failure
case (4.2 §6 seam precedent).

**Divergence from 4.2 (deliberate, per 4.2 §1):** `getDisplayMedia` has no
stable deviceId, so 4.3 does not reuse `createDeviceSelector`. It gets its
own module (`capture_selection.js`) with a parallel shape (persisted
preference, probe, queryable state, events) so reviewers can compare the
two designs side by side.

**Not 4.3:**
- No UI of any kind (§5 owns it; 5.3 reads the persisted capture mode).
- No `MediaRecorder`, no chunks (4.5/4.6/4.8), no track monitoring (4.9),
  no per-stream status UI (4.14 — but 4.3 provides the queryable state it
  reads).
- No invocation of the `getDisplayMedia` picker (screen mode's picker
  happens at Start; that is 4.6's call).
- No audio routing/mixing decisions (4.7 owns them; 4.3 only records
  whether tab audio was included in the probe).
- No changes to the 1.2 session-conditions schema.

## 2. Architecture

### Surface choice

| Candidate | Verdict |
|---|---|
| `chrome.tabCapture` (programmatic capture of the chess.com game tab) | **Chosen as the primary surface.** Deterministic (no per-session picker → reproducible, scriptable Start for 5.1/5.6); install-time manifest permission → permission state is *queryable* (`granted`/`revoked`), not per-prompt; supports tab **audio** capture, which is 4.7's game-audio feed; scoped exactly to the tab the mission records. `chrome.desktopCapture` is Chrome-Apps-only — excluded explicitly. |
| `getDisplayMedia` (browser picker: screen/window/tab) | **Supported as the user-driven fallback mode** (`captureMode:'screen'`). No manifest permission; permission is per-prompt so state is inherently `'prompt'` until Start; the picker *is* the selection, so nothing persistent is selectable beyond the mode itself. 4.3 persists the mode preference and defines its permission semantics; 4.6 invokes the picker at Start. |

Rationale: the mission's games always happen on the chess.com tab; tab
capture is the reproducible, permission-queryable surface. The task title
says "screen/tab" — the persisted mode preference *is* the "selection"
between screen and tab, and tab-mode additionally selects *which* tab.

### The chrome.* split (driven by 4.2's empirical finding)

4.2's V2 proved offscreen documents expose only `chrome.runtime`
(`chrome.storage` undefined even with the manifest permission; selection
persists in document `localStorage`). The builder must assume
`chrome.tabCapture` / `chrome.tabs` / `chrome.permissions` are likewise
absent in the offscreen document and verify empirically. Therefore:

- **SW side** (a small addition to `recording_host.js` or a new
  `capture_broker.js` — builder's choice, documented): owns all
  `chrome.*` calls — `chrome.tabs.query` (find the game tab),
  `chrome.permissions.contains` (permission state),
  `chrome.tabCapture.getMediaStreamId({ targetTabId })` (the probe's
  streamId). The SW never touches a `MediaStream`.
- **Offscreen document** (`capture_selection.js`, loaded by
  `recorder.html`): owns all `navigator.mediaDevices` calls — consumes
  the SW-supplied `streamId` via
  `getUserMedia({ video: { mandatory: { chromeMediaSource: 'tab',
  chromeMediaSourceId: streamId } }, audio: { mandatory: {
  chromeMediaSource: 'tab', chromeMediaSourceId: streamId } } })`,
  then stops every track (probe-then-stop, no retention).
- The streamId travels SW → recorder on the existing
  `{kind:'recorder', msg, v:1}` channel as a request field (never
  persisted; single-use).

If empirical probing shows `chrome.tabCapture` *is* available in the
offscreen document, the builder may collapse the split — but must document
the finding and keep the SW-broker path as the tested fallback. If
`getUserMedia`-with-`chromeMediaSource` fails in the offscreen document,
that is a BLOCKER for tab mode: document it, do not fabricate a
workaround.

### Manifest changes (deliberate difference from 4.2)

4.2 needed none; 4.3 needs two:

- `"permissions": [..., "tabCapture"]`
- `"host_permissions": ["https://www.chess.com/*"]` — required to capture
  the game tab (and lets `chrome.tabs.query({ url })` return tab metadata
  without the `"tabs"` permission).

The builder verifies empirically which of the two is actually required
for `getMediaStreamId({ targetTabId })` and documents the result; both are
declared regardless (defense in depth, honest justification in the
permission rationale).

### Selection model

- `captureMode`: `'tab' | 'screen' | null`, persisted at
  `blindfold.captureMode.v1` in document `localStorage` (4.2 precedent).
  Starts `null` on every recorder boot; 4.3 never silently defaults
  (4.2 precedent) — the *absence* of a mode is honest state until §5's UI
  or a test sets it.
- **Tab mode targeting:** the game tab is found via
  `chrome.tabs.query({ url: 'https://www.chess.com/play/computer*' })`;
  most-recently-active match wins. If no tab matches → selection state
  reports `tabId: null` with reason `'no-target-tab'`; no silent fallback
  to the active tab (that would risk recording the wrong tab).
- **Boot restore:** a stored `'tab'` mode re-validates the target tab on
  boot (tab ids are not stable across browser restarts); a stored
  `'screen'` mode restores as-is (no target to validate). Restoration
  source is `'restored'`; explicit user choice is `'user'`; a target tab
  that vanished yields `source:'invalidated'`.

### Permission flow

1. **Tab mode — queryable.** `chrome.permissions.contains({
   permissions: ['tabCapture'], origins: ['https://www.chess.com/*'] })`
   → `'granted'` / `'denied'`(=revoked). Ground truth for *capture
   capability*; the probe (below) is ground truth for *stream
   acquisition*.
2. **Tab mode — probe.** `capture-request-permission { captureMode:'tab' }`:
   SW obtains `streamId` for the target tab → recorder calls
   `getUserMedia` with the `chromeMediaSource` constraints (video + audio;
   audio presence recorded for 4.7) → **stop every track immediately** →
   respond `{ ok:true, permissionState:'granted', audioIncluded:true }`.
   Failure maps honestly: `NotAllowedError` → `'denied'`;
   `NotFoundError`/`InvalidStateError` (tab gone mid-probe) → target
   invalidated; anything else → `'unknown'` with raw `errorName`.
3. **Screen mode — inherently prompt.** `getDisplayMedia` permission
   cannot be queried or probed without showing the picker, so
   `capture-request-permission { captureMode:'screen' }` reports
   `{ ok:true, permissionState:'prompt', note:'picker-at-start' }` and
   performs NO media call. This is honest, not a gap: the picker is the
   permission, and it happens at Start (4.6).
4. **Denial is a state, not an exception** (4.2 precedent): `'denied'`
   persists as queryable state until a later probe succeeds. No recovery
   UX in 4.3 (§5/§7 territory).

### Message channel additions

On 4.1's envelope `{ kind:'recorder', msg, v:1, ... }`, SW/§5 → recorder.
(The SW-broker leg uses SW→recorder messages carrying the `streamId`; the
external API below is what §5 drives.)

| msg | Request fields | Response |
|---|---|---|
| `capture-list-modes` | — | `{ ok, modes: [{ mode:'tab', available, permissionState, targetTab }, { mode:'screen', available, permissionState }] }`. `available:false` with a reason when the platform lacks the API. |
| `capture-select` | `{ captureMode: 'tab'\|'screen' }` | `{ ok, selection }` or `{ ok:false, error }`. Unknown mode → RangeError surfaced as `{ ok:false, error:'unknown-mode' }`; never throws across the channel. Persists the mode, emits `screen_capture_selected`. |
| `capture-request-permission` | `{ captureMode }` | `{ ok:true, permissionState, audioIncluded, errorName }` or `{ ok:false, ... }`. Emits `screen_capture_permission_changed`. Probe tracks always stopped before responding (tab mode). |
| `capture-get-state` | — | `{ ok, captureMode, tabId, tabTitle, permissionState }`. The queryable state 4.14 and 5.6 read. `tabTitle` is `null` when unavailable — never fabricated. |

`recorder-set-session` (4.2) is reused for session scoping; until set,
4.3's events are **inert** (2.x/3.x/4.2 precedent).

### Events (4.3-owned event types)

Task-owned types per repo convention (`event_envelope.js` untouched),
via the existing writer intake (`sourceContext:'recording_context'`):

- `screen_capture_permission_changed`
  `{ captureMode: 'tab'|'screen', permissionState:
  'granted'|'denied'|'prompt'|'unknown'|'unavailable', source:
  'query'|'request', errorName: string|null }`
- `screen_capture_selected`
  `{ captureMode: 'tab'|'screen'|null, tabId: number|null, tabTitle:
  string|null, source: 'user'|'restored'|'invalidated' }`

Exact-keys payload validators (house convention). `unavailable` covers
"platform lacks the API" (very old Chrome / API removed).

### Failure isolation

Every channel handler is failure-isolated (3.2 SF-1 precedent): a throwing
selector never breaks the recorder's message listener and never drops a
liveness pong. Absent `chrome.tabCapture` (very old Chrome) is the plain-
`Error` unavailable-capability convention on the SW side.

## 3. Testability

- **V1 (Node):** inject fakes for `mediaDevices` (scripted
  `getUserMedia` outcomes incl. `chromeMediaSource` constraint capture),
  `localStorage`-shaped storage, a fake SW broker
  (`getMediaStreamId`, `tabs.query`, `permissions.contains`), and an
  `emitEvent` spy. All AC1–AC8 DOM-free. The SW-broker logic is unit-
  tested separately with an injected `chrome` mock (4.1 precedent).
- **V2 (real headless Chrome 154):** the honest scope is narrower than
  4.2's — headless Chrome may not offer a capturable tab and there is no
  CDP fake for tabCapture. V2 proves: manifest permissions present;
  `capture-list-modes` / `capture-select` / `capture-get-state` through
  the real channel; mode persistence across document kill+recreate
  (`source:'restored'`); both events in IDB via the writer intake
  (gapless appendSeq); the tab-mode probe attempted against the real
  `chrome.tabCapture` — whatever the outcome (success / honest
  unavailable), it is recorded as observed, never fabricated. If the
  probe cannot run headless, the probe path is V1-only and the limitation
  is documented.
- **/tmp hygiene:** repo path to every harness (2.x/3.x precedent).

## 4. Acceptance criteria

- AC1 (V1): `capture_selection.js` loads in Node via the shim; factory
  constructs with injected fakes; `chrome.*` split documented
  (SW-broker vs recorder).
- AC2 (V1): `capture-list-modes` reports both modes with honest
  `available`/`permissionState`; tab mode without a matching game tab
  reports `tabId:null, reason:'no-target-tab'`.
- AC3 (V1): `capture-select` unknown mode → `{ ok:false,
  error:'unknown-mode' }` (RangeError internally); known mode persists to
  `blindfold.captureMode.v1` and emits `screen_capture_selected` with
  `source:'user'`. Persist-before-live (4.2 SF-1 precedent): storage
  failure leaves no phantom selection and emits nothing.
- AC4 (V1): tab-mode probe success → `'granted'`, every probe track's
  `stop()` called (spy), no stream retained; `audioIncluded` recorded.
- AC5 (V1): scripted `NotAllowedError` → denied state + raw error name;
  vanished target tab → `source:'invalidated'`, selection cleared.
- AC6 (V1): boot with stored `'tab'` + matching game tab →
  `source:'restored'`; stored mode with no matching tab → `tabId:null`,
  no silent fallback to the active tab.
- AC7 (V1): screen mode `capture-request-permission` performs NO media
  call and reports `permissionState:'prompt'` with the picker-at-start
  note.
- AC8 (V1): changed files only: `capture_selection.js`,
  `recorder.js`/`recorder.html` (wiring), `recording_host.js` or new
  broker module, `manifest.json` (tabCapture + host_permissions), tests,
  evidence, DECISIONS.md entry. Content scripts byte-identical. No
  `MediaRecorder` token in product code.
- AC9 (V2): real Chrome: mode list/select/state through the real
  channel; both events land in extension IDB via the writer intake
  (appendSeq gapless).
- AC10 (V2): kill+recreate of the offscreen document restores the
  persisted mode (`source:'restored'`) without user action.
- AC11 (V2): the tab-mode probe is attempted against real
  `chrome.tabCapture`; the observed outcome (success or honest
  unavailable/failure) is recorded as observed. No fabricated green.
- AC12 (V3, deferred to §7/owner device): real game tab capture on the
  owner's machine — tab video+audio probe succeeds; picker flow for
  screen mode verified by a human; denial via browser UI yields explicit

## 6. Known seams and honest limitations

1. **Probe-then-start race** (4.2 §6 seam precedent): tab capture granted
   at probe time can fail at Start (tab closed/navigated). 4.6 must treat
   stream-start failure as its own case.
2. **Tab ids are unstable** across browser restarts; the target tab is
   re-resolved (not persisted) on every boot and every Start.
3. **`chrome.tabCapture` in the offscreen document** is assumed absent
   (4.2's empirical finding); the SW-broker split is the design. The
   builder verifies and documents the actual availability.
4. **Screen-mode permission is unknowable pre-Start** by platform design;
   `'prompt'` is the honest state, not a defect.
5. **One active mode** per recorder; concurrent `capture-request-
   permission` calls serialize on a guard (builder's choice, documented).
6. **4.7 dependency:** 4.3's probe records `audioIncluded:true/false`;
   4.7 decides what to do with tab audio (mix/exclude/document bleed).
