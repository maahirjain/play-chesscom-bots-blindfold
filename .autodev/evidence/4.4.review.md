## Findings

### Probe kind-branch — VERIFIED sound (no finding)

The contract's one genuine factory gap is fixed correctly.
`runPermissionProbe` (`device_selection.js`, ~line 438) builds
`constraints.video = { deviceId: { exact: selection } }` (or `true`
with no selection) for `kind: 'videoinput'`, and `constraints.audio`
only for `audioinput`. Empirically probed in Node with a `getUserMedia`
spy: the video probe produces exactly
`{"video":{"deviceId":{"exact":"cam-1"}}}`, `'audio' in constraints`
is `false`. The `kind` is validated at factory construction
(`RangeError` for anything but `audioinput`/`videoinput`), so no code
path can produce a probe carrying both keys. No resolution/framerate/
facingMode policy is added — 4.6's decision per the contract, and the
absence is documented, not an omission. There is no 4.7 violation
vector: the camera probe never requests audio, so the microphone
stream's intentional mix cannot be contaminated by this path.

### Validator parameterization — VERIFIED backward compatible (no finding)

`requireValidPermissionChangedPayload` /
`requireValidDeviceSelectedPayload` take an optional second argument
(the event-type name), defaulting to the `microphone_*` pair.
Empirically: the default signature validates with mic names (all 44
pre-existing 4.2 tests pass unchanged), and passing
`'camera_device_selected'` produces camera-named error messages. The
factory's internal emit calls (`emitDeviceSelected`,
`emitPermissionChanged`) pass the instance's `eventTypes`, so 4.4
camera failures blame `camera_*`, never `microphone_*`. The 4.2 mic
paths are untouched.

### restoreDevices() Promise.all repair — VERIFIED sound (no finding)

The old implementation returned only the first selector's restore
promise — a real race the builder caught with a failing test (camera
restore still in flight when the caller proceeded). The repair
(`recorder.js` ~line 690) awaits `Promise.all` over all three
selectors' best-effort restores, each rejection swallowed to `null`,
each construction failure caught per-selector; the function still never
throws. Pre-existing mic/capture restore semantics are preserved, not
weakened. See NOTE-1 for the residual observability caveat.

### Selector independence — VERIFIED, no cross-contamination (no finding)

Mic and camera are independent factory instances with fully separate
closures (`selection`, `selectionSource`, `devices`, `permissionState`,
`restoredAnnounced`). Storage: each selector gets its own
localStorage-adapter instance; the underlying document localStorage is
shared but key-partitioned (`blindfold.micDeviceId.v1` vs
`blindfold.cameraDeviceId.v1` — verified distinct in Node). Shared
surfaces are intentional and read-only or sink-only: the writer-intake
emitter (`emitRecorderEvent`), the platform `mediaDevices`, and the
session thunks. No mutable state is shared between the selectors.

### "Saved separately from the screen" — boundary is honest (no finding)

4.4 delivers a selected, permitted camera and stops: no retained
streams, no `MediaRecorder`, no chunks, no stream wiring. Separateness
is a property of 4.6's stream wiring ("Start separate microphone,
screen, and webcam recording streams"), which does not exist yet.
Nothing in 4.4 merges streams, retains a stream, or preempts 4.6's
design. The contract (§1, §5) and DECISIONS.md (§4.4) document this
explicitly. Deferring is the correct call, not a scope dodge.

### Events — VERIFIED (no finding)

`camera_permission_changed` / `camera_device_selected` use exact-keys
validators (parameterized, see above), travel the existing
transactional writer intake with `sourceContext: 'recording_context'`,
and are session-gated by the kind-agnostic `isActive()`
(sessionId+gameId thunks shared with the mic selector — the 3.x
precedent). Labels are `null` pre-grant (never fabricated).

## NOTEs

- **NOTE-1 (observability):** `restoreDevices()` swallows each
  selector's restore rejection to `null`. A storage failure at boot is
  therefore silent: the selector keeps `selection = null`, which is
  honest (no phantom selection), but `cam-get-state` cannot
  distinguish "no stored selection" from "storage failed". §5's 5.6
  readiness checks should be aware of this; no 4.4 change required.
- **NOTE-2 (dead-code fallback):** `announceSelectionForSession` falls
  back to `selectionSource || 'restored'`. All live paths set
  `selection` and `selectionSource` together (`select()` after
  persist per 4.2 SF-1; `restoreOnBoot()`), so the fallback is
  unreachable in practice. Defensive; fine as-is.
- **NOTE-3 (§5 awareness):** `cam-request-permission` with no selection
  probes `{ video: true }` — the system-default camera. This mirrors
  the 4.2 mic precedent, but §5 should know a permission grant can
  precede any user selection.
- **NOTE-4 (test-only):** the `o.cameraSelector` injection path
  bypasses factory kind validation; a test could inject a misconfigured
  selector. Same pattern as 4.2's `o.deviceSelector`; acceptable.
- **NOTE-5 (future callers):** the exported validators' defaults are
  the `microphone_*` names, so a future external caller validating a
  camera payload without the second argument gets mic-named errors.
  The code comment documents this; acceptable.
- **NOTE-6 (coordinator):** the evolved pin allowlists reference
  `4.4.contract.md`/`4.4.build.md` (present). This file
  (`4.4.review.md`) and the forthcoming `4.4.behavior.md` will trip the
  git-status pins — standard workflow-ordering mechanical repair per
  the 2.x/3.x/4.x precedent.
