## 1. The new event type — exactly one, correctly specified

No other event-type strings, no new channel messages (recorder.js byte-identical, 0 diff lines; MSG_ identifier count unchanged at 26 before/after — the contract's "24" counts the actual message vocabulary, my broader grep is stable), no new stores, no new permissions (manifest.json 0 diff lines), PLAN.md 0 diff lines.

**Validator is strict and honest.** I ran 22 adversarial cases directly against `requireValidMomentMarkerPayload`:
- Accepts: `{note: null}`, `{note: 'text'}`, `{note: ''}`, exactly-500-char note. Returns the payload (identity).
- TypeError: `null`, `'x'`, `[]`, extra keys, missing `note` key, wrong key name, `note: undefined`, `note: 42`, `note: {}`, `new String('x')` (object, not primitive — correctly rejected).
- RangeError: 501 chars, 10000 chars. **Never silent truncation** — over-length throws, and the UI preserves the text.
- Error messages carry the event type name (default `moment_marker`, custom override respected).
- 21/22 passed; the single "failure" was my own test's fault (a throwing getter propagates its own `Error`, not a validator TypeError — correct behavior; no validator in the repo wraps property access, and none should).

**Justification holds.** 5.7's contract explicitly reserved marker ownership to 5.8 ("no new event type (5.8 owns the timestamped marker — adding one here would duplicate it)"). One new type is the specified deliverable.

## 2. Emission honesty — guarded, isolated, never dangling

**Idle cannot emit.** Double-guarded: the button/input are `disabled` unless ACTIVE (DOM-level), AND `onMarkerClick` re-checks `phase !== CONTROL_PHASE_ACTIVE` before doing anything (logic-level). The STOPPING window (phase neither ACTIVE nor IDLE) is covered by the re-check — a click during stop returns early, no emit. I verified every `phase = CONTROL_PHASE_IDLE` assignment (7 sites: abortStart, localAbortStart, 4 inline Start-chain aborts, Stop complete) has a preceding `setMarkerEnabled(false)`, and every `phase = CONTROL_PHASE_ACTIVE` (Start success, boot adoption) has `setMarkerEnabled(true)`. The initial DOM state is disabled. No dangling marker is possible.

**Correct identity.** Emits via `opts.sender.emit({eventType, sessionId: activeSessionId, gameId: activeGameId, payload})` — the live slots, same pattern as `emitPageStart`. `opts.sender` is validated at install (`options.sender must expose emit()`), so the emit target cannot be undefined at click time.

**Failure isolation (3.2 SF-1).** Validation failure → `marker-failed:<ErrorName>` title, text preserved, return. Emit throw → same title path, text preserved, return. The click listener itself is wrapped in try/catch ("unreachable by construction; fail-safe"). The V1 AC4 test pins this (throwing sender → text preserved, honest title, control survives). No silent drops, no throws into page code.

**No XSS/sanitization issue.** Input is read via `.value` (not innerHTML), trimmed, passed as data. The failure title is set via `setAttribute` (not HTML parsing). Note text is stored as a validated string ≤500 chars.

## Notes (non-blocking)

**N1 — Observation, not a defect.** The `setMarkerEnabled(false)` calls clear the input on every abort path. If a user types a note and then their Start fails for an unrelated reason (e.g., `ensure-failed`), the note text is lost. This is the specified behavior ("Disabling clears the input (no stale text carries into the next session)") and the failure title still records that a marker failed — but a user who typed a long note before a Start failure loses it. Given the input only enables on ACTIVE (after Start succeeds), the realistic window for this is narrow (type during ACTIVE → abort is rare). The contract's choice is defensible; noting it for awareness, not requesting a change.
