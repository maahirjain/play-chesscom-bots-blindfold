## What was built

**New module `chunk_writer.js`** (DOM-free, repo module pattern:
dependency-free classic script → guarded `BlindfoldSession` global →
IIFE `'use strict'` → Node `module.exports` shim). `createChunkWriter({
db, nowUtcIso, performanceNow, setInterval, clearInterval, setTimeout,
clearTimeout, random })` — fully injected platform surface for V1; the
offscreen document relies on the real globals, and the DB is read lazily
from the shared namespace (`format_support.js` precedent) so chunk
writes go direct to the extension-owned IDB (4.1's direct-IDB path).

API: `startForStream({streamKind, segmentId, recorder})`,
`stopForStream(streamKind)`, `stopAll()`, `getChunkState(streamKind)`
→ `{status, lastChunkIndex, lastWriteAtUtc, consecutiveMisses,
emptyPolls, lastErrorName, lastErrorMessage}` (in-memory; the durable
trace is the chunks themselves), `hasActivePoll(streamKind)`.
Statuses: `active` | `chunk-stalled` | `chunk-quota-exceeded` |
`chunk-write-error` | `stopped`; `getChunkState` returns `null` for a
never-chunked streamKind (unknown is null).

**Extraction design (contract §3):** one `setInterval` poll loop per
stream at `CHUNK_POLL_MS = 5000` ± 10% jitter (named, V1-pinned
constants `CHUNK_WRITER_POLL_MS` / `CHUNK_WRITER_REQUEST_TIMEOUT_MS` /
`CHUNK_WRITER_MAX_MISSES` exported on the namespace). Tick: skip (and
stop the loop, status `stopped`) when `recorder.state !== 'recording'`;
`requestData()` throw → missed tick; await `ondataavailable` up to
2000 ms — non-empty Blob → chunk record written, miss counter reset;
0-byte Blob → dropped (not stored, index not consumed, `emptyPolls`
counted, not a miss); timeout → miss; 3 consecutive misses →
`chunk-stalled`, loop stopped, fail-loud. `QuotaExceededError` on write
→ loop stopped, `chunk-quota-exceeded`, no retry spin; other rejections
→ `chunk-write-error` with name/message preserved. The recorder is never
touched by any failure path — polling never fails the stream. No new
event type (4.9 decides the log shape).

**Chunk record** (exactly the contract §2 shape, key
`[segmentId, chunkIndex]`):
`{segmentId, chunkIndex, receivedAtUtc, receivedAtMonotonicMs,
timecodeMs, data}` — `timecodeMs` stored raw from the event (null when
absent), never analyzed; no `streamKind`/`sessionId`/`byteLength`
(derivable rule).

**Wiring:** `recorder.js` gains a lazy `getChunkWriter()` (same pattern
as `getFormatSupport()`/`getStreamStarter()`/`getAudioPolicy()`),
exposed on the recorder surface for tests; the
`recorder-start-streams` handler starts chunking automatically for every
successfully started stream (via `starter.getActiveStreams()` —
Start implies record; no new channel message). The kickoff is
best-effort and wrapped in try/catch: chunking can never fail the
streams or the channel response. `recorder.js` references no
media-capture APIs (4.1 boundary, V1-pinned). `recorder.html` loads
`chunk_writer.js`. `.autodev/DECISIONS.md` gains `## 4.8`.

**4.13 seam:** `stopForStream()`/`stopAll()` stop the poll loops but the
`ondataavailable` handler stays attached — the final `dataavailable`
from `recorder.stop()` is stored as a chunk like any other; 4.13 must
await it before declaring a segment finalized. `stopAll()` is
idempotent; terminal failure states survive `stopForStream` (the honest
record for 4.9/4.14).

## Deviations

1. **Real bug found by V1 and fixed: chunkIndex was assigned in the
   write's `.then`, allowing two rapidly accepted chunks to share a key**
   (IDB `put` with a duplicate compound key silently overwrites — data
   loss). The index is now reserved synchronously at chunk acceptance.
   Consequence, documented in code and here: a failed write leaves a
   gap in the sequence, never a duplicate key (4.13 reads in key order;
   gaps are honest, duplicates would be data loss). This refines the
   contract §2 phrasing "incremented per stored chunk": in the normal
   case (writes succeed) the observable behavior is identical; under
   write failure the reservation is the only correct choice. 0-byte
   drops still never consume an index (rejected before acceptance).
2. **Injected `setTimeout`/`clearTimeout`/`random` added** to the
   `createChunkWriter` surface beyond the contract's listed
   `{db, nowUtcIso, performanceNow, setInterval, clearInterval}` — the
   2 s dataavailable wait needs a timer and the ±10% jitter needs a
   random source; both are injected for V1 determinism and default to
   the real globals in the document. No contract behavior changed.
3. **Cumulative pin evolutions with justification comments** in all 17
   suites' diff-discipline allowlists (the 4.8 block: `chunk_writer.js`,
   `tests/chunk_writer.test.js`, 4.8 evidence ×4).

No product-code deviation from the contract's behavior. No schema
change, no `DB_VERSION` bump, no manifest widening, no new event types,
no new channel messages, no new permissions. Content scripts
byte-identical; no gameplay change.
