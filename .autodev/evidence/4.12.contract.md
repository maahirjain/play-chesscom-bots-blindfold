# Task 4.12 contract — calculate and store recording timecode/offsets for multi-stream synchronization

PLAN.md §4.12: "Save timecode/offset information needed to align each media
segment with event time; do not use chunk-arrival time as exact frame time."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.12 is (one paragraph)

4.6 saved per-stream start times (`streamStartedAtUtc` +
`streamStartedAtMonotonicMs`, which differ per stream); 4.8 saved raw
per-chunk `timecodeMs` (media time, never analyzed); 4.10 saved the
`clockSegmentId` link from each recording segment to its clock anchor;
4.11 saved `sync_marker` events whose envelope `monotonicMs` /
`clockSegmentId` are the markers' source timestamps. **4.12 is the first
task allowed to do timestamp arithmetic**: it defines the single
canonical set of pure conversion functions (media time → document
clock → wall clock), the ruling on what `event.timecode` means and what
it does not, the played-vs-failed marker disambiguation rule the 4.11
review required, and the discontinuity-continuity rule for interpreting
media timelines across 4.9's gaps. 4.12 computes offsets; it stores no
new fields (§0.1).

## 0.1 PLAN reading note — why 4.12 stores nothing new (for the section-4 auditor)

PLAN.md §4.12 says "**Save** timecode/offset information needed to align
each media segment with event time". Read against the mission's standing
rule — **do not persist derivable values** (repo AGENTS.md; the
`requireValidManifestRecord` exact-keys discipline exists to enforce
it) — the "save" half of this requirement is already satisfied in
aggregate:

| Information | Saved by | Where |
|---|---|---|
| per-stream start (mono + UTC) | 4.6 | manifest `streamStartedAtUtc`, `streamStartedAtMonotonicMs` |
| per-chunk media timecode | 4.8 | `media_chunks.timecodeMs` (raw, never analyzed) |
| segment → clock-anchor link | 4.10 | manifest `clockSegmentId` |
| marker source timestamps | 4.11 | `sync_marker` event envelopes (`monotonicMs` + `clockSegmentId`) |

Every offset 4.12 defines (§2) is a pure function of already-stored
values on already-identified clocks. Persisting computed offsets would
be textbook derivable-value persistence — the exact thing the mission
forbids. 4.12's distinctive, non-duplicated contribution is therefore
the **calculation** half: the canonical functions, the semantics
ruling (§3), and the alignment rules (§§4–5), V1-pinned and in one
module. `MANIFEST_KEYS` stays at exactly 16; `DB_VERSION` stays 2; no
new store, no new index. (PLAN.md itself is never modified; this note
is the durable record of the reading. If the auditor disagrees, the
remedy is a deliberate, documented widening — not silent drift.)

## 1. The ingredients (as they exist — no new machinery)

All monotonic timestamps below are `performance.now()` readings on a
single document's clock within one document generation (4.10's
contract: same document ⇒ same clock; document restart ⇒ new clock,
new anchor, new generation). Wall time for any monotonic reading is
`anchor.utcEpochMs + (monotonicMs − anchor.monotonicMs)`
(`deriveWallUtcMs`, event_envelope.js) — 4.12's `wallUtcMs` is the
canonical home of this formula for recording-alignment use (V1-pinned
equal to `deriveWallUtcMs` on fixtures).

Per recording segment (one manifest record, one `MediaRecorder`):

- `streamStartedAtMonotonicMs` — the document-clock reading taken when
  `recorder.start()` was called (4.6). Media time `0` is treated as
  this instant (§3.1).
- `clockSegmentId` — the recording-context anchor active at stream
  start (4.10). The anchor row `{segmentId, utcEpochMs, monotonicMs}`
  lives in the event log as the `clock_anchor` event.

Per chunk (`media_chunks` record, 4.8):

- `timecodeMs` — `event.timecode` from the `dataavailable` event,
  stored raw; `null` when the platform did not supply a number.
- `receivedAtMonotonicMs` — arrival time at the IDB write. **Not**
  frame time (PLAN's explicit prohibition, §3.2).

Per marker (`sync_marker` events, 4.11):

- envelope `monotonicMs` + `clockSegmentId` — the source timestamp.
  Audible emissions carry the offscreen (`recording_context`) clock;
  **visible emissions carry the content-script (page) clock** (4.11
  contract §5: "4.12 aligns each against its own anchor — no
  cross-context clock confusion"). Every 4.12 conversion therefore
  takes the anchor as an explicit parameter, resolved by the event's
  own `clockSegmentId` — the recording-context anchor is never
  assumed.

Per discontinuity (`stream_discontinuity` events, 4.9):

- envelope `monotonicMs` — the observation time of the gap. The
  media timeline is discontinuous around it (§5).

## 2. The canonical offset set (new module `timecode.js`)

DOM-free, dependency-free, repo module pattern (`BlindfoldSession`
guarded global, IIFE, `'use strict'`, Node shim). **Pure math only**:
no IDB, no `chrome.*`, no DOM, no `Date.now()` / `performance.now()`
calls — every timestamp is a parameter (V1 code-scan pin). This is the
single home for recording-alignment arithmetic; 4.13, 4.14, and §6.3
call these functions instead of scattering ad-hoc math.

All functions: `null`/`undefined` input → `null` output (unknown is
null); non-finite numbers (`NaN`, `±Infinity`) → `null` (platform
gave garbage — unknown, not a guess); wrong-type non-null input →
`TypeError` (repo convention); negative `timecodeMs` → `null`
(treated as unusable platform data, not a domain error thrown into
bulk export loops — deliberate, documented here).

- `mediaToMonotonicMs(streamStartedAtMonotonicMs, timecodeMs)` →
  `number|null` — `streamStartedAtMonotonicMs + timecodeMs`. Converts
  a media-timeline position to the document clock. Encodes the §3.1
  assumption (timecode `0` ≈ `start()` call time).
- `wallUtcMs(anchor, monotonicMs)` → `number|null` —
  `anchor.utcEpochMs + (monotonicMs − anchor.monotonicMs)`. The
  canonical wall-clock derivation for alignment use; V1-pinned equal
  to `event_envelope.deriveWallUtcMs` on fixtures. `anchor` must be a
  well-formed `{segmentId (uuid-v4), utcEpochMs, monotonicMs}` triple
  (else `TypeError` — an anchor is never "unknown null" here; the
  caller resolves it or does not call).
- `chunkWallUtcMs(anchor, streamStartedAtMonotonicMs, timecodeMs)` →
  `number|null` — composition of the two above: the wall-clock time
  of a chunk's media position. `null` when `timecodeMs` is null
  (unknown, never arrival-time-backed — §3.2).
- `streamStartWallUtcMs(anchor, streamStartedAtMonotonicMs)` →
  `number|null` — wall-clock time the stream's recording began.
- `markerMediaOffsetMs(markerMonotonicMs, streamStartedAtMonotonicMs)`
  → `number|null` — `markerMonotonicMs − streamStartedAtMonotonicMs`:
  the marker's predicted position in the stream's media timeline, in
  ms. **May be negative** (the marker is per-generation; streams
  start at different times — a negative offset honestly means the
  marker precedes this stream's media). Callers pass only usable
  markers (§4).
- `markerWallUtcMs(anchor, markerMonotonicMs)` → `number|null` —
  wall-clock time of the marker event (anchor = the anchor named by
  the marker event's own `clockSegmentId`).
- `streamStartOffsetMs(refStartMono, otherStartMono)` →
  `number|null` — `otherStartMono − refStartMono`: the canonical
  per-stream start offset against a caller-chosen reference (e.g.
  the earliest stream start). Trivial arithmetic, named so
  multi-stream sync never re-derives it ad hoc.
- `isUsableSyncMarker(payload)` → `boolean` — §4.
- `mediaRangeIsContinuous(discontinuityMonos, fromMono, toMono)` →
  `boolean` — §5.

No other arithmetic lives in 4.12. In particular: no duration
computation (chunk durations require decoding — content analysis,
forbidden), no averaging, no smoothing.

## 3. The timecode semantics ruling

### 3.1 What `event.timecode` is

Per the MediaStream Recording spec, the `BlobEvent.timecode`
attribute on `dataavailable` is a `DOMHighResTimeStamp`: **the
difference between the timestamp of the Blob's first frame and the
timestamp of the first frame of the first Blob** — i.e. media time
elapsed since recording began. 4.12 treats `timecodeMs` as
**milliseconds of media time since `recorder.start()`**, i.e. as the
offset from `streamStartedAtMonotonicMs` (§2,
`mediaToMonotonicMs`).

Assumptions, stated honestly:

1. **Timecode `0` ≈ `start()` call time.** There may be encoder
   start latency between the `start()` call (when 4.6 stamps
   `streamStartedAtMonotonicMs`) and the first encoded frame. That
   latency is unobservable to us (no frame inspection — content
   analysis is forbidden) and is folded into alignment tolerance,
   not corrected.
2. **Reliability is implementation-defined.** The spec defines the
   attribute's meaning, not its accuracy; implementations may
   quantize, delay, or (pathologically) not advance it. 4.8 stores
   it raw precisely so 4.12+ can observe rather than assume.
3. **V2 characterizes, not proves.** AC9 requires the harness to
   report the observed `timecodeMs` series from real headless
   Chrome (advancing? zeros? nulls?) — whatever it is. One
   implementation's behavior is not a spec guarantee; the ruling
   above holds regardless, and §7/AC11 re-characterizes on the
   owner's device.

### 3.2 What chunk-arrival time is not

PLAN: "do not use chunk-arrival time as exact frame time."
`receivedAtMonotonicMs` is stamped at the IDB write inside the
`dataavailable` handler — downstream of the 5-second `requestData()`
poll loop (4.8), event-loop scheduling, and the write itself. It is
**ordering evidence** (with `chunkIndex`, it corroborates sequence)
and a **liveness signal**, never frame time. 4.12's conversions never
take it as input.

**Fallback rule** (when `timecodeMs` is null or unusable): the chunk
keeps its sequence position (`chunkIndex` order); its exact media
time is **unknown** (`chunkWallUtcMs` → `null`). Consumers must
render "time unknown", never substitute arrival time. This is the
honest degradation — arrival-time-as-truth would be fabrication.

## 4. Marker disambiguation rule (required by the 4.11 review)

Only `sync_marker` events that actually anchored a modality
participate in alignment:

- `isUsableSyncMarker(payload)` returns `true` iff
  `payload.status === 'played'` (audible) or `payload.status ===
  'shown'` (visible). Malformed payload (non-object, missing/non-string
  status) → `false` (defensive predicate, never throws).
- `'failed'` = the modality produced no acoustic/optical anchor —
  the event remains in the log as the honest attempt record (4.11),
  but it is excluded from alignment. A failed audible marker means
  **no beep exists in any recording to align against**; downstream
  must not treat its timestamp as a media landmark.
- `'skipped'` = the modality was not attempted (e.g. `no-target-tab`)
  — excluded likewise.
- **Stop-phase double-beep:** the two beeps share one `markerId`
  (4.11); each beep has its own `'played'` event. For alignment, use
  the **earliest** `'played'` audible event per `markerId`, ordered
  by the event log's `appendSeq` (onset of the first beep is the
  landmark; the 150 ms gap is a disambiguator for human ears, not a
  second landmark).
- The usable marker's wall time comes from **its own**
  `clockSegmentId`'s anchor (§1 — audible ⇒ recording-context
  anchor; visible ⇒ content-script anchor). Cross-context confusion
  is a correctness bug; the anchor parameter makes it impossible by
  construction.

## 5. Discontinuity / continuity rule

4.10's contract: the clock continues across media gaps; 4.12
interprets gaps using 4.9's discontinuity events plus verbatim
monotonic timestamps. The rule:

- Within one `segmentId`, the media-time → clock mapping
  (`mediaToMonotonicMs`) is valid **only where no discontinuity
  intervenes**. A `stream_discontinuity` event's envelope
  `monotonicMs` marks the observation of the gap; media on either
  side of it must not be interpolated across.
- `mediaRangeIsContinuous(discontinuityMonos, fromMono, toMono)`:
  `discontinuityMonos` is the array of envelope `monotonicMs` values
  of that segment's `stream_discontinuity` events (any order —
  interval membership needs no sorting); returns `true` iff no
  value lies within the closed interval `[fromMono, toMono]`.
  `fromMono > toMono` → `RangeError`. Discontinuity timestamps are
  observation times with inherent fuzz — consumers treat boundaries
  conservatively (this predicate already does: closed interval).
- The `'restart'` discontinuity is **not** handled here: a restart
  mints new `segmentId`s with new manifest records, new
  `streamStartedAtMonotonicMs`, and new clock links (4.9/4.10). Each
  generation aligns independently via its own anchor; cross-generation
  comparison happens in wall-clock space, never by comparing
  monotonic readings across clocks.
- **4.13 seam:** 4.13's re-segmented pieces call these same
  functions per piece, passing the piece's own
  `(anchor, pieceStartMonotonicMs, timecodeMs)`. Whether a piece's
  `timecodeMs` restarts at 0 (new `MediaRecorder` per piece) or
  continues (slicing the existing chunk series) is 4.13's contract
  to decide — these functions accept either, because they are
  parameterized by start time, not by recorder identity. 4.12 does
  not model 4.13's pieces itself.

## 7. Runtime design

### 7.1 New module: `timecode.js`

DOM-free, dependency-free, repo module pattern. Nine pure functions
(§2). Zero platform surface: no `chrome.*`, no IDB, no DOM, no clock
calls — fully parameter-driven (V1 code-scan pin). Loadable in any
context (offscreen document for 4.13's use, SW for §6.3's export);
**4.12 does not wire it into `recorder.html`** — 4.13's contract
decides whether the offscreen document loads it (minimal-change
principle; the module is a library, not a pipeline stage).

### 7.2 Consumers (none modified by 4.12)

- **4.13** (finalization): per-piece wall times, marker placement in
  the finalized timeline; calls the 4.13 seam functions per piece.
- **4.14** (per-stream status): "recording for X (wall)" style
  status — `streamStartWallUtcMs` against now.
- **§6.3** (`media-sync.json` export): the alignment timeline —
  per-segment start wall times, per-chunk wall times (where
  knowable), usable marker landmarks with media offsets,
  discontinuity boundaries. The primary consumer; §6.3 owns the
  join logic (manifest × anchor × events × chunks), 4.12 owns the
  math.

4.12 modifies no consumer and no producer (4.6/4.8/4.10/4.11
untouched).

## 8. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — media→clock conversion.** `mediaToMonotonicMs(s, t) ===
  s + t` on fixtures; `null` in → `null` out; non-finite →
  `null`; wrong-type → `TypeError`. The §3.1 assumption (timecode
  0 ≈ `start()` call) is documented on the function.
- **AC2 — canonical wall derivation.** `wallUtcMs(anchor, m)`
  equals `event_envelope.deriveWallUtcMs(anchor, m)` on a fixture
  battery (V1: import both, compare) — one formula, one home for
  alignment use. Malformed anchor → `TypeError`.
- **AC3 — compositions.** `chunkWallUtcMs`,
  `streamStartWallUtcMs`, `markerWallUtcMs`, `markerMediaOffsetMs`,
  `streamStartOffsetMs` pinned on fixtures, including a negative
  `markerMediaOffsetMs` (marker before stream start — honest, not
  clamped) and a two-stream offset table.
- **AC4 — marker disambiguation.** `isUsableSyncMarker` truth
  table: `'played'`→true, `'shown'`→true, `'failed'`→false,
  `'skipped'`→false, malformed→false. Stop double-beep rule
  (earliest `'played'` per `markerId` by `appendSeq`) documented
  and V1-pinned as a selector example.
- **AC5 — continuity predicate.** `mediaRangeIsContinuous`
  truth table: no discontinuities → true; discontinuity inside
  `[from, to]` → false; on the boundary → false (closed
  interval); `from > to` → `RangeError`.
- **AC6 — purity and no persistence.** Code-scan pin:
  `timecode.js` executable code contains no `indexedDB`,
  `chrome.`, `document.`, `Date.now(`, `performance.now(`;
  `MANIFEST_KEYS` is still exactly the 16-key shape (a test asserting
  4.12 changed nothing about the manifest); `media_chunks` shape
  unchanged; `DB_VERSION` 2.
- **AC7 — validation discipline.** Wrong-type non-null input →
  `TypeError`; `null`/`undefined`/non-finite/negative-`timecodeMs`
  → `null` (unknown, never a guess); malformed anchor →
  `TypeError`; `fromMono > toMono` → `RangeError`; malformed
  marker payload → `isUsableSyncMarker` returns `false` (never
  throws).
- **AC8 — changed-files discipline.** Working-tree diff touches
  only: `timecode.js` (new), `tests/timecode.test.js` (new),
  cumulative pin evolutions with justification comments,
  `.autodev/evidence/4.12.*`, `.autodev/DECISIONS.md`. No producer
  or consumer modified (4.6/4.8/4.10/4.11 untouched); `recorder.html`
  untouched (no new script tag — §7.1); content scripts
  byte-identical; no gameplay change; PLAN.md unmodified; no
  4.13/4.14/§6 bleed.

### V3 — deferred (AC11)

- **AC11 — real-device alignment reality (§7 / owner device).**
  On the owner's device: (a) start a recording and confirm
  reconstructed chunk/marker wall times match observed reality
  within clock-skew tolerance; (b) confirm the start beep's actual
  audible position in the mic recording matches the predicted

## 9. Explicit non-goals

- No manifest widening, no new IDB store/index, no `DB_VERSION`
  bump (the §0.1 decision).
- No re-segmentation or post-discontinuity piece modeling (4.13;
  4.12's functions are piece-parameterized for 4.13 to call).
- No per-stream status reporting (4.14) and no export assembly
  (§6.3) — 4.12 provides the math, consumers own the joins.
- No content analysis of any kind: no beep detection in audio, no
  flash detection in video, no chunk-duration decoding, no
  averaging/smoothing of timestamps.
- No arrival-time-based alignment, ever (PLAN's prohibition, §3.2)
  — arrival time is ordering evidence only.
- No changes to 4.6/4.8/4.10/4.11 modules, no new event types, no
  new channel messages, no new permissions, no `recorder.html`
  wiring.
- No cross-context clock confusion: the anchor is always an
  explicit parameter resolved by the event's own `clockSegmentId`.
