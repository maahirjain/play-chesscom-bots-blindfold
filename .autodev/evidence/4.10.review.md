## NOTEs (informational)

1. **Anchor-ordering subtlety (for the section-4 auditor).** AC1's
   `streamStartedAtMonotonicMs >= anchor.monotonicMs` sanity holds in
   every realistic flow because `handleSetSession`
   (`recorder.js:336+`) emits selector announcements through
   `emitRecorderEvent` → `ensureAnchor()`, capturing the anchor
   *before* any stream starts. The pure forced-at-write-stage case
   (anchor captured at `stream_starter.js:688`, after
   `recorder.start()`) is reachable only via the degenerate
   announcement-failure path or direct starter use in tests, and
   would reverse the inequality. Product correctness is unaffected
   either way: `deriveWallUtcMs` is order-independent (the anchor is
   a fixed linear mapping for the document's clock lifetime; forcing
   capture earlier shifts `utcEpochMs` and `monotonicMs` by the same
   delta). The V1 `>=` test uses injected clocks where the property
   holds; no test asserts it where it cannot.
2. **4.13 seam completeness.** `getClockLink()` is exposed, but
   `linkClockSegment` also needs the `getAnchor` thunk, and
   `ensureAnchor` is not on the test seam. This is usable as
   documented because 4.13's Stop handler will live in `recorder.js`
   itself, where `ensureAnchor` is in closure scope — but 4.13's
   planner should note the thunk is not seam-exposed.
3. **Screen link path V2 gap.** Honestly reported (harness header +
   build report); the kind-agnostic call site justifies the
   per-stream-identical claim. No action.
4. **PLAN reading note.** Contract §0.1 correctly records that 4.10's
   "give every recording segment an ID" half was already satisfied by
   the 4.5 §2 amendment (4.6 mints); PLAN.md itself untouched. The
   section-4 auditor should confirm this reading stands.
5. **No `getAnchor` staleness hazard.** `ensureAnchor` memoizes per
   document generation (`anchor` closure var, `recorder.js:393-403`);
   the linker always reads the memoized value, so repeated links
   within a generation are consistent by construction.
