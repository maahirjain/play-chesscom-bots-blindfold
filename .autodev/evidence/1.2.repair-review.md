## SF1 — playerColor error model (was: TypeError for non-strings)

**Repair implemented:** `normalizePlayerColor` no longer routes through
`normalizeConditionString`. It now: null/undefined → null;
whitespace-only/empty string → null; trimmed 'white'/'black' pass;
EVERYTHING else (misspellings, 'White', 'w', non-strings including
`1`, `true`, `{}`, `[]`, `NaN`) → RangeError.

**Check 1 — contract bounds (AC6):** AC6 reads "playerColor accepts only
'white'/'black'/null; anything else (incl. 'White', 'w') → RangeError".
The test asserts RangeError for 'White', 'w', 'WHITE' and now for
[1, true, {}, []]. Runtime probe confirms. 'White'/'w' → RangeError
preserved. ✓

**Check 2 — consistency with 1.1 precedent and the convention table:**
`session_identity.js` line 97–98 and 115–118 throw RangeError for
out-of-domain `sessionCategory` (membership predicate returns false for
non-strings, so `sessionCategory: 1` → RangeError). Contract §3.1's own
table says RangeError = "value outside an allowed domain (bad source, bad
color, unknown field name — consistent with 1.1's sessionCategory →
RangeError)". The repair adopts exactly the reading the contract cites,
resolving the review's ambiguity in favor of the documented precedent.
`normalizeBotRating`'s TypeError for floats/negatives/numeric strings is
untouched, matching AC7's explicit mandate. ✓

**Check 3 — AC13 untouched:** AC13 constrains only
`normalizeConditionString`/`normalizeBotRating`/
`normalizeAssistanceSettings` ("they throw TypeError only on wrong-typed
non-null input") — playerColor is deliberately absent from that list, and
the convention table assigns "bad color" to RangeError. No AC13
violation, no contract amendment needed. ✓

**Check 4 — whitespace→null consistency:** whitespace-only/empty strings
mean "not supplied" → null, matching the module's universal unknown
handling (normalizeConditionString, contract §2.5) and PLAN §1.2.3
("unavailable conditions as unknown rather than guessing"). An empty
string is never a color observation, so mapping it to null rather than
rejecting it is within the unknown-representation rule, not a dodge.
Verified at runtime: `'   \t'` → null, `''` → null, `' white '` →
'white'. ✓

**Note N1 (test strength, not a defect):** the AC6 test asserts the
whitespace-only → null and '' → null playerColor behaviors' existence only
indirectly — null passes, ' white ' trims, but neither `' '` → null nor
`''` → null is an explicit assertion (the analogous paths ARE asserted for
normalizeConditionString). Behavior confirmed correct by independent
probe; suggest adding one assertion to close the coverage gap for the new
sub-behavior.

## SF2 — `__proto__` assistance-setting key (was: silently dropped)

**Repair implemented:** `normalizeAssistanceSettings` throws TypeError on
an own `'__proto__'` key instead of assigning through the inherited
setter.

**Check 1 — hole closed:** realistic vector `JSON.parse('{"__proto__":true,
"legit":1}')` → TypeError (asserted in-suite, re-verified at runtime with
a second probe including `{"__proto__":false}` alone). The throw discards
the partial accumulator — no half-record escapes. ✓

**Check 2 — legitimate maps unaffected:** near-miss key `'proto'`
round-trips (in-suite). Runtime probe: proto-adjacent `'constructor'` and
`'toString'` keys assign as own properties and survive JSON round-trip
(they shadow, not invoke, inherited members — no silent loss, no throw),
and a normal map's JSON round-trip is unchanged. ✓

**Check 3 — documented limitation honest:** object literals cannot carry
`'__proto__'` as an own key (it sets the prototype — no-op for `true`);
the test's NOTE documents this and constructs the vector via JSON.parse,
which is the genuine ingestion path for Chess.com-side observations.
The reviewer asked for explicit rejection OR a null-prototype accumulator;
the coordinator chose explicit rejection of `__proto__` only. That is the
minimal correct fix: only `__proto__` has setter semantics that silently
drop data; `constructor`/`prototype` keys are benign own properties.
✓

**Check 4 — error class:** TypeError (wrong shape for this container)
aligns with the module's convention that key/value-shape problems are
TypeError, while unknown *field names* are RangeError. ✓
