## 3. Contract behavior — independent code inspection

I read `computeReadiness` (session_controls.js:359), `classifyStorageReadiness` (:304), the badge renderer (:707), and the poll-loop wiring (:800–860) directly rather than trusting the build report.

**(a) Readiness requires all three streams recording-healthy AND a confirmed storage write — CONFIRMED.**
- `STREAM_KINDS` is exactly `['microphone', 'screen', 'webcam']` (:103).
- Each kind must classify as `LIGHT_RECORDING_HEALTHY` via the existing 5.1 `classifyStreamStatus`; anything else sets `allStreamsReady = false` with a named reason.
- `classifyStorageReadiness` returns `ready:true` only when: `pendingCount === 0`, `lastError === null`, AND `initialEmitObserved === true`. The honesty argument holds: the sender dequeues exclusively on positive ack, so a drained queue after an observed emission proves ≥1 durable acknowledgment.

**(b) Degraded streams block readiness with honest reasons — CONFIRMED.**
- `recording-degraded` → `'not-ready'`, reason names the stream and classification (e.g. `microphone: recording-degraded`), `blocked: true`.
- `failed-not-started` → `'not-ready'` with the start error in the reason (e.g. `screen: failed-not-started (start-failed:denied)`), `blocked: true`.
- `off-idle` with no failure facts → `'not-ready'` but `blocked: false` (waiting, not a confirmed failure) — the badge shows "Waiting for recording…", never a premature "ready".
- Malformed stream status → `'not-ready'`, `blocked: true` ("malformed status").
- Missing kind in response → `'not-ready'`, `blocked: true` ("no status in response").
- Null/malformed `streamStatuses` (query failed) → `'unknown'` with reason `'status query failed'` — never defaults to ready.
- Persistent sender errors (`write-failed:*` or unrecognized — fail-closed) → storage not ready, `blocked: true`.
- Transient sender errors → not ready, `blocked: false` ("storage write retrying").
- No observed emission (boot adoption) → "storage write unconfirmed", `blocked: true` — never a premature ready.

**(c) The badge latches (no flapping) — CONFIRMED.**
- `readinessLatched` is set on the first `'ready'` verdict (:845); once latched, the poll always renders the ready state (:847–849), even if a later poll degrades or the query fails (:793, :811, :854 all check `!readinessLatched` before rendering unknown).
- `resetReadiness()` clears the latch on all idle transitions (abort, local abort, Stop).
- The badge is hidden while idle and after Stop.

**(d) Readiness never gates Stop or the session — CONFIRMED.**
- `onStopClick` (:1299) checks only `phase` — it never consults readiness state.
- Session activation (start-streams → slots → ACTIVE) is unchanged; readiness is computed in the poll loop only.
- `renderReadiness` is presentation-only; no code path conditions session behavior on the readiness verdict.

## Notes (non-blocking)

- The builder's 4th parameter (`initialEmitObserved`) is a documented deviation from the contract's 3-param signature. I verified the justification is sound: without it, a drained queue on boot adoption would be indistinguishable from a confirmed write, risking a premature "ready". The deviation serves the contract's honesty requirement.
- Boot adoption can never show "ready" (storage stays unconfirmed) — honest per contract §4.4, though it means an adopted session's badge will read "Not ready: storage write unconfirmed" indefinitely. The user can Stop and Start for a fresh ready signal. This is the contract's specified behavior, not a defect.
