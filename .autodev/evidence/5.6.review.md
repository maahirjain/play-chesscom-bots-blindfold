## 1. `computeReadiness` purity and correctness

**Purity: holds.** The function touches no DOM, creates no timers, references no `chrome.*`. Its only external call is the pre-existing pure `classifyStreamStatus`, plus `isPlainObject`/`isFinite` utilities and `Object.freeze`. It throws `TypeError` only on wrong-typed containers (caller error, per repo convention); a null `streamStatuses` is the honest `'unknown'`, not a throw. Verified by reading the full function body.

**Truth table: fail-closed on every input.** Verified against the code:
- All three `recording-healthy` + storage confirmed → `'ready'`. ✓
- Any `recording-degraded` (adverse facts: muted track, chunk stall, recorder error, or the `finalizedAtUtc`-while-recording inconsistency) → `'not-ready'`, stream named with detail, `blocked=true`. Degraded can never yield ready — the 4.14 anti-masquerade rule is enforced by the strict `!== LIGHT_RECORDING_HEALTHY` check. ✓
- `failed-not-started` → `'not-ready'`, blocked. ✓
- `off-idle` with no failure facts → `'not-ready'`, not blocked ("waiting"). Honest: genuinely pending, and the per-stream lights show the truth. ✓
- `unknown` lifecycle or malformed per-stream status → `'not-ready'` (blocked) or caught-exception → `'not-ready'` with `'malformed status'`. Never throws into the caller; the poll loop additionally wraps the whole call. ✓
- Missing kind in response → `'kind: no status in response'`, blocked. ✓
- Null/malformed `streamStatuses` container → `'unknown'` with `'status query failed'`. Never defaults to ready. ✓
- Unexpected classification states → the `!== LIGHT_RECORDING_HEALTHY` gate catches everything not exactly healthy. ✓

**`classifyStreamStatus` null-safety:** the 5.1 function handles null `startResult` (boot adoption → honest `'off-idle'`), and `computeReadiness` passes `(isPlainObject(startResults) ? startResults[kind] : null) || null`. Safe.

## 2. The storage-ack mechanism — honest

The builder's central claim: `pendingCount===0 && lastError===null` with an observed initial emission proves ≥1 durable writer ack, without modifying `sender.js`. I verified each link:

- **Dequeue exclusively on positive ack:** `sender.js` line 306-307 — `queue.shift()` occurs ONLY inside `if (isPositiveAck(response, head.eventId))`. No other queue-shrink path exists (no `queue.length = 0`, no reassignment; grep confirmed).
- **`isPositiveAck` is strict:** `response.ok === true && response.eventId === headEventId`. A late ack after timeout can't double-dequeue (documented race handling).
- **Emission implies queueing:** `sender.emit()` throws on validation failure *before* queueing; success means the event is in the queue. `emitPageStart` (lifecycle.js) calls `sender.emit()` synchronously; the `pageStartEmitted = true` assignment sits after the try/catch, so a throwing emission never sets the flag.
- **`initialEmitObserved` closes the boot-adoption hole:** without it, an adopted session's empty queue (`pendingCount===0`, `lastError===null`) would be indistinguishable from "all acked." The flag is false at install and on every idle reset; only the Start path's observed emission sets it. Boot adoption therefore degrades to `'not-ready'` with `'storage write unconfirmed'` (blocked) — honest, per contract §4.4.
- **Error taxonomy mirrors 2.8 exactly:** transient (`send-timeout`, `no-ack`, `transport-error:*`) → not-ready, not blocked (retrying); persistent (`write-failed:*` or any unrecognized string — fail-closed) → not-ready, blocked. Verified against `status_indicator.js` lines 18-21, 54-58.
- **Defensive sender read:** a missing or throwing `getStatus()` yields `senderStatus = null` → `'storage status unavailable'`, blocked. Never a premature ready.

**The 4th parameter (documented deviation):** the contract specified three params; the builder added `initialEmitObserved`. This is a *strengthening*, not a weakening — the three-param version the contract sketched would have permitted the boot-adoption premature-ready hole. The contract's open question #1 explicitly invited the builder to determine the honest mechanism, and the build report documents the deviation with rationale. Acceptable.

- **Boot adoption:** flags remain false from install; storage can never confirm. Honest.
- **5.9 game change:** same session continues; latch correctly persists (the session didn't end).
