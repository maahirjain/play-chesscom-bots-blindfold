## SHOULD_FIX

### SF-1 — Writer's silent `→ 0` renumbering on a corrupt counter contradicts 2.6's corruption honesty

**Location:** `writer.js:284–288`
```js
seqReq.onsuccess = function () {
  var rec = seqReq.result;
  var next = (rec && typeof rec.nextAppendSeq === 'number')
    ? rec.nextAppendSeq
    : 0;
```

**The problem.** This conflates two cases: (a) *absent* record (legitimate
new session → `0` is correct) and (b) *present-but-malformed* record
(e.g. `nextAppendSeq: "abc"`, negative, fractional, or wrong
`sessionId`) → also `0`, **silently**. Case (b) restarts the append
sequence from zero, producing duplicate `appendSeq` values across the
session's event stream. The `byAppendSeq` index is non-unique so nothing
throws; §6.2's "events.jsonl in persistent append order" would then
contain two events with `appendSeq: 0`, two with `1`, etc. — silently
corrupted ordering.

Meanwhile 2.6's `restoreSessionState`/`getSequenceState` treat case (b)
as corruption and throw `session-store: corrupt sequence_state`. So the
system is incoherent: the writer happily forks the sequence while
restore refuses to read it. The 2.6 contract documents this as a wart
(2.4 review NOTE-2) and explicitly asks the reviewer whether 2.6 should
have fixed it.

**Why not a blocker.** The wart is unreachable through the mission's own
code paths: the writer is the sole writer of `sequence_state` (verified —
`session_store.js` contains only two `DB.put` calls, to
`session_metadata` and `conditions`; `grep` confirms no writes to
`sequence_state`/`events`/`media_chunks`), and the writer always writes
well-formed `{sessionId, nextAppendSeq: integer ≥ 0}` records. Only
external corruption (devtools, foreign code, disk failure) can trigger
case (b). The 2.6 contract made an explicit, documented scoping decision
(AC9: `writer.js` byte-identical), and the restore side — 2.6's actual
responsibility — is honest.

**Recommended repair** (5 lines, surgical; coordinator may apply as a
2.6 follow-up with targeted re-review, or defer explicitly):
```js
var rec = seqReq.result;
var next;
if (rec === undefined || rec === null) {
  next = 0; // new session: legitimate
} else if (typeof rec.nextAppendSeq === 'number' &&
           Number.isInteger(rec.nextAppendSeq) &&
           rec.nextAppendSeq >= 0 &&
           rec.sessionId === sessionId) {
  next = rec.nextAppendSeq;
} else {
  fail(new Error('writer: corrupt sequence_state for session ' + sessionId));
  return;
}
```
This makes the writer fail the write (→ `{ok:false}`, → 2.5 retry →
2.8 status) instead of silently forking the sequence, which is coherent
with 2.6's restore-side honesty. Note the repair also adds the
`rec.sessionId === sessionId` check, which the current code omits.

## What I verified (adversarial conclusions)

### The "no in-memory restore" claim is airtight
- `writer.js` has **no module-level mutable state** (grep for `^  var x =`
  returns nothing; all state is function-local or const). Every
  `writeEvent` reads the counter from IndexedDB inside the single
  `readwrite` transaction and writes back `next + 1` in the same
  transaction. Nothing to restore into memory.
- `db.js`'s `cachedDb` (line 89) is a lazy cache, not durable state: on
  restart the fresh JS context re-opens it. Re-derived, not restored. ✓
- The writer's `onMessage` listener is re-installed synchronously by
  `sw.js` top-level code on every start. ✓
- **In-flight transactions at restart:** IndexedDB transactions are
  atomic — a killed worker means the transaction aborts. The sender sees
  no ack → 2.5 retries → 2.4's eventId dedup absorbs the case where the
  transaction actually committed. Coherent; no 2.6 action needed.

### Deviation 1 (`saveConditions(sessionId, record)`) — ACCEPTED
The contract specified `saveConditions(record)`, but the `conditions`
store's keyPath is `sessionId` and the 1.2 domain record has no such
field — a 7-field record cannot be stored (IDB DataError). Of the
alternatives (out-of-line keys → requires `db.js` changes; 8th field in
1.2 → breaks 1.2's contract; schema keyPath change → breaks 2.2's
contract), the explicit-parameter fix is the least invasive: no
`db.js` change, no 1.2 domain-model change, no schema change. The
stored form `{sessionId, ...sevenFields}` is documented in the module
comment and pinned by the AC4 test
(`assert.deepEqual(triple.conditions, Object.assign({sessionId: SID1},
conditions))`). Honest deviation, correctly documented in
`2.6.build.md`.

### Restore re-validation leniency — SOUND
`requireValidConditions` is whitelist-build (validates the seven fields,
ignores extras like the stuffed `sessionId`); `requireValidMetadata`
is field-validating (checks each expected field, no exact-keys
enforcement). Both 1.1 and 1.2 validators are consistent with each
other in this leniency — the "strict exact-keys" pattern belongs to
1.3/1.4's validators, a later convention. 2.6 correctly reuses the
owning modules' validation rather than inventing stricter rules. A
stored record with garbage extra fields but seven valid fields is not
"corruption" in any meaningful sense (extras are inert for §6.1, which
reads the seven fields). The corruption cases that matter (missing
field, bad `playerColor`, `__proto__`, non-numeric counter) all throw.

### The two export lines — ACCEPTABLE and minimal

### Verdict: APPROVE

### 1. Repair semantics vs. the reviewer's recommended fix

The applied diff matches the recommended fix exactly in semantics:

- absent (`undefined`/`null`) → `next = 0` (legitimate new session);
- valid (`typeof number`, `Number.isInteger`, `>= 0`, `sessionId` matches) → `next = rec.nextAppendSeq`;
- corrupt → `fail(corruptErr); return;`.

**Deviation (strict improvement):** the coordinator added
`corruptErr.name = 'CorruptSequenceState'`, which the reviewer's sketch
did not include. Same fail-fast semantics; strictly better, because it
yields a stable machine-matchable ack code
(`write-failed:CorruptSequenceState`) instead of the generic
`write-failed:Error`, and 2.8 can match on the string per the existing
comment at `writer.js:122–124`. No behavior change beyond the naming.

### 2. Name propagation chain

Verified by code inspection:

- `fail(corruptErr)` → `ack = { ok:false, eventId, error: toWriteFailed(corruptErr) }`;
- `toWriteFailed`: message does not contain `'indexedDB is unavailable'`;
  `err.cause` is absent, so `inner = err`; `errorName(inner)` returns
  `err.name` since it is a non-empty string → `'CorruptSequenceState'`;
- result: `'write-failed:CorruptSequenceState'`.

The two new tests assert this exact ack string (not a regex), so the
chain is covered end-to-end by V1.
