# 5.1 contract — Compact Start/Stop control and recording/saving health indicator

## 1. Scope

PLAN.md §5.1: "Add a compact Start/Stop control and recording/saving
health indicator."

This is the first task of Section 5 ("Add minimal session controls").
Section 4 (recording pipeline) is complete and checkpointed at
`autodev/checkpoint-04-auto-acceptance`; this contract consumes its
seams and the Section 4 audit's §5 carry-forward list
(`.autodev/evidence/section-4.audit.md` §6):

- "Required streams" is §5's policy; 4.14 reports facts (§5.6 consumes).
- `recorder-get-status` is §5.1's health-indicator query surface.
- 4.13's stop response is §5.10's seam; `flushTimedOut` is response-only
  and must be surfaced by the §5 Stop flow.
- 4.6's already-started registry guard is §5.5's duplicate-Start seam.
- §5 must mint UUID-v4 session/game IDs (1.1.1, 1.1.2).
- 3.5.4 seam: `recordStopTermination(reason, result)` — "§5 calls it
  from the Stop control".
- 2.7 seam: `BlindfoldSession.activeSessionId` (null until §5 sets it
  at Start); "§5 owns calling emitPageStart and session continuity".
- 2.7 carry-forward: "§5 should define whether tabs share a session or
  get distinct sessions."

## 2. UI surface decision — in-page control, not a browser-action popup

**Decision: the Start/Stop control and health indicator live in-page,
adjacent to the extension's existing move-input UI** (the same anchor
the 2.8 status indicator uses), installed by content.js. No
browser-action popup, no manifest `action`.

PLAN evidence:

1. PLAN §(c) "Each game", steps 3–4 and 7: "Click Start and approve
   capture prompts if required" → "Wait for the microphone, screen,
   webcam, and saving indicators to show ready" → "Click Stop. ...
   Wait for media finalization". The whole flow happens on the game
   page, mid-play. A popup closes on focus loss and is the wrong home
   for a control the user operates while playing.
2. The 2.8 contract (§3.7) explicitly rejected a browser-action
   popup for the status surface: "the in-page indicator is where the
   user already looks during play". §5.1's control+indicator is the
   same surface, extended.
3. PLAN §(c) step 4 names exactly four indicators: microphone,
   screen, webcam, and saving. The saving indicator already exists
   in-page (2.8's `status_indicator.js`); 5.1 adds the three
   per-stream lights beside it. No new surface is needed.

(DECISIONS.md's 4.2 note — "§5's popup reads the same store" —
concerns device-selection UI, which is not 5.1's scope; see §8
non-goals.)

## 3. What 5.1 builds

### 3.1 New module `session_controls.js` (content-script side)

BlindfoldSession convention (dependency-free classic script → guarded
global → IIFE `'use strict'` → Node shim). Two exports, mirroring
the 2.8 classifier/renderer split:

- `classifyStreamStatus(status)` — **pure**. Input: one per-stream
  status object from 4.14's `recorder-get-status` response (the exact
  17-key shape). Output: frozen `{state, detail}` where `state` is one
  of the closed set in §4 and `detail` is the raw fact string(s)
  (never a smoothed summary). Throws `TypeError` on malformed input.
  No DOM, no timers, no `chrome.*` — independently unit-testable.
- `installSessionControls(options)` — creates the DOM: one compact
  Start/Stop button + three per-stream lights (mic/screen/webcam),
  anchored adjacent to the existing move-input UI / 2.8 indicator
  (fixed-corner fallback, 2.8 precedent). Wires the Start/Stop
  sequences (§5), polls `recorder-get-status` **only while a session
  is active** (injectable interval, 2 s default — the 2.8 precedent;
  no pre-session polling, so no pointless SW wakes), re-renders only
  on state/detail change. Never throws into page code (3.2 SF-1
  precedent: instrumentation/UI never breaks gameplay); invalid
  options → `TypeError` at install time, before any timer starts.

The existing 2.8 saving indicator is **unchanged** (it keeps showing
sender/storage health). 5.1's cluster sits beside it: four lights
total, exactly PLAN §(c) step 4's "microphone, screen, webcam, and
saving indicators".

### 3.2 Session identity

- At Start click, 5.1 mints `sessionId` and `gameId` via
  `session_identity.js` (`newSessionId()` / `newGameId()`, UUID-v4) —
  satisfying 1.1.1 and 1.1.2 ("use one game per recording session in
  the normal workflow").
- `session_identity.js` is added to the manifest `content_scripts`
  js list (additive; it is dependency-free and already
  Node-shimmed). No other manifest change: no `action`, no new
  permissions.
- Session metadata record: 5.1 persists the minimal identity record
  (IDs, schema/extension/protocol versions, startedAtUtc) with
  **category unknown** — 1.2.3 ("Represent unavailable conditions as
  unknown rather than guessing"). Category selection and remembered
  defaults are 5.2/5.3's; they update the record. (Persistence path:
  the existing SW-side session intake — 5.1 must not invent a new
  storage path; if no session-metadata intake message exists, 5.1
  records session start as an event through the existing sender and
  leaves the metadata record to 5.2. The builder must check and
  document which path exists; inventing a new SW storage API is out
  of scope.)
- Sets `BlindfoldSession.activeSessionId` / `activeGameId` (the
  content-script slots content.js already reads for the sender) and
  calls `BlindfoldSession.emitPageStart(sender, sessionId)` (the 2.7
  seam: "§5 owns calling emitPageStart").

### 3.3 Start sequence (button → recording)

1. **Local interlock**: if this tab already has an active session
   (`activeSessionId !== null`), Start is a no-op (button disabled
   while active). This is 5.1's local single-session interlock; the
   cross-tab refusal policy is 5.5's (§7).
2. Mint IDs (§3.2).
3. **Ensure the recording context**: content script sends
   `{kind:'recorder', v:1, msg:'recorder-ensure'}` — a **new SW-side
   message** handled by `recording_host.onRuntimeMessage` →
   `ensureRecordingContext()` → `{ok:true, bootId, created}` or
   `{ok:false, reason}`. Justification (deliberate, recorder-get-status
   precedent): only the SW can call `chrome.offscreen.createDocument`;
   the content script is the Start origin and cannot ensure the
   document itself. Without this, Start messages would go to a
   non-existent listener and fail silently — the exact masquerade
   §4.14 exists to prevent. If ensure fails, Start aborts honestly:
   button back to idle, the failure reason shown as control detail
   (tooltip/text), no session minted into any stream.
4. `recorder-set-session` `{sessionId, gameId}` → `{ok:true}` (this
   also triggers 4.2/4.3/4.4's selection announcements into the
   event stream). **Additive**: recorder.js records `ownerTabId` from
   the message `sender.tab.id` at set-session time (no behavior
   change when no session is active; 5.5's guard consumes it).
5. `recorder-start-streams` → per-stream results. Per-stream
   failures are **not** Start failures (4.6 failure isolation): the
   session is active; the lights show the truth (§4). Only a
   channel-level failure (no response, `{ok:false}` at top level)
   aborts Start.
6. Set `activeSessionId`/`activeGameId`, `emitPageStart`, begin
   status polling, button → "Stop" state.

User-activation caveat (honest, V3): the Start click's transient
activation does not transfer to the offscreen document, so a real
headed `getDisplayMedia` picker may still need its own gesture path;
4.6's `picker-unavailable` degradation already covers the failure
honestly. 5.1 does not invent activation forwarding.

### 3.4 Stop sequence (button → finalized)

1. `recordStopTermination(reason, result)` via
   `BlindfoldSession.gameLifecycleRecorder` (3.5.4 seam): `reason`
   is null (unknown) unless a `game_ended` event was already observed
   for the game, in which case the observed reason/result is passed.
   A manual reason-entry UI is **not** 5.1 (see §8).
2. `recorder-stop-streams` → 4.13's 11-step sequence. Button shows a
   transitional "Stopping…" (disabled) until the response arrives.
3. On response: lights reflect the per-stream `finalized` states;
   the **full stop response — including `flushTimedOut` — is handed
   to 5.10's completion seam** (named callback/store the 5.10
   contract will own; 5.1 defines the handoff point, not the
   presentation). Per the Section 4 audit carry-forward, §5.10
   surfaces `flushTimedOut`; 5.1 must not drop it.
4. Clear `activeSessionId`/`activeGameId`, stop polling, button →
   "Start" (idle).
5. If the stop channel call itself fails (no response / `{ok:false}`
   top-level): the control stays in "Stopping…" with the honest
   failure as detail — it must not silently revert to idle while
   the recorder may still hold the session (that would masquerade).

### 3.5 Boot adoption (4.1 refresh survival)

On content-script load, the control sends one `recorder-get-status`:
- `{ok:true, sessionId}` → a session survived the reload: adopt it
  (`activeSessionId`/`activeGameId` set — gameId from the response?
  Note: get-status returns `sessionId` only; the gameId adoption
  path must be specified by the builder — e.g. the recorder echoes
  the active gameId, or the control reads it from the session
  event stream. The contract requires the builder to close this
  honestly, not assume it). Button → "Stop", polling starts.
- `{ok:false, error:'no-session'}` → idle. Button → "Start".

## 4. Status → indicator mapping (no smoothing)

`classifyStreamStatus` implements the 4.14 no-smoothing discipline:
**failures surface as facts, never as a collapsed lifecycle.** The
lifecycle values come from 4.14 (`idle|recording|stopped|finalized`);
the classifier derives the light state mechanically:

| light state | meaning | condition (mechanical) |
|---|---|---|
| `off-idle` | not started | `lifecycle === 'idle'` and no adverse facts |
| `failed-not-started` | start failed / denied | `lifecycle === 'idle'` and adverse facts present (e.g. `lastRecorderError`, start-failure detail) |
| `recording-healthy` | recording, clean | `lifecycle === 'recording'` and no adverse facts |
| `recording-degraded` | recording, facts present | `lifecycle === 'recording'` and ≥1 adverse fact |
| `stopped-finalizing` | stop in flight | `lifecycle === 'stopped'` |
| `finalized` | finalized | `finalizedAtUtc !== null` |
| `unknown` | status unavailable | query failed / malformed (never green) |

Adverse facts (closed list, from the 17-key shape): `chunk` in a
terminal state (`chunk-stalled`, `chunk-quota-exceeded`,
`chunk-write-error` per 4.8's `getChunkState`), non-null
`lastRecorderError`, non-null `lastDiscontinuity`, any `tracks[]`
entry with `readyState === 'ended'` or `muted === true`.

The critical masquerade case: **chunk-stalled with
`recorderState === 'recording'` stays `recording-degraded`
(amber), never green** — the 4.14 contract's core case, re-pinned
here. `detail` carries the raw fact strings (e.g.
`"chunk:chunk-stalled; discontinuity:track-ended"`); the light's
`title` shows them, exactly like 2.8's raw-code tooltip.

"Ready" is **not** defined here — 5.6 owns the required-set policy
and readiness presentation. 5.1's lights show lifecycle+facts only.

## 6. Boundaries with 5.2–5.10

- **5.2** (category/training selection): 5.1 mints the session with
  category unknown; 5.2 owns the selection UI and updates the
  record. 5.1 builds no selection UI.
- **5.3** (remember selections): untouched.
- **5.4** (conditions completion): untouched.
- **5.5** (duplicate-Start guard): 5.1 provides the local interlock
  + `ownerTabId`; 5.5 owns the cross-tab refusal policy. **Known
  interim gap**: between 5.1 and 5.5, a second tab's set-session
  could overwrite the active session identity — 5.5 closes it;
  the contract records it as 5.5-owned, not a 5.1 defect.
- **5.6** (readiness gating): 5.1's lights are facts-only; 5.6
  defines the required set and the "ready" presentation.
- **5.7** (record through game end): architectural no-op — nothing
  auto-stops; 5.1's Stop is the only stop. 5.1 must not add
  auto-stop on game end.
- **5.8** (note markers): untouched.
- **5.9** (new game before Stop): 5.1's control tolerates a
  `gameId` change mid-session (5.9 drives `recorder-set-session`
  with the same sessionId + new gameId); 5.1 does not implement
  game-boundary detection.
- **5.10** (post-Stop acks/export-complete): 5.1 owns the Stop
  trigger + transitional UI + handing the full stop response
  (incl. `flushTimedOut`) to 5.10's seam; 5.10 owns awaiting
  storage acks and the export-complete presentation.

## 8. Explicit non-goals

- Category/training/evaluation selection UI (5.2); remembered
  defaults (5.3); conditions detection/completion UI (5.4).
- Cross-tab duplicate-Start refusal policy (5.5) — beyond the local
  interlock and `ownerTabId`.
- Readiness definition and required-set policy (5.6).
- Note/moment markers (5.8); game-boundary detection (5.9).
- Export-complete presentation and storage-ack awaiting (5.10).
- Manual termination-reason entry UI: **unassigned by PLAN's task
  list** — 5.1 passes null (unknown) per 3.5.4; the contract
  records this as a §5 follow-up for owner decision, not a 5.1
  defect.
- Device-selection UI (4.2/4.3/4.4 deferred it to §5; it is not
  5.1's "minimal session controls" — the one-time setup flow in
  PLAN §(c) covers selection; a §5 task must own it — flagged for
  the §5 planner sequence, not built here).
- Keyboard shortcuts for Start/Stop (not in PLAN).
- Dashboards, counts, metrics, charts (PLAN forbids).
- Any gameplay/content-script behavior change beyond the install
  line.
