# 7.4 contract — Verify batched DOM updates and same-length history revisions are handled without duplicate moves

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.4. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.4 requires demonstrating two DOM-timing hazards are handled:

1. **Batched DOM updates:** Chess.com may apply multiple move-list mutations
   in one DOM batch (one MutationObserver callback sees several new moves at
   once, e.g. `[e4]` → `[e4, e5, Nf3]` in a single callback). The tracker must
   emit exactly one `move_confirmed` per new move — no drops, no duplicates.

2. **Same-length history revisions:** A takeback followed by a different move
   (`[e4, e5]` → `[e4, d5]`) has the same length but different content. The
   3.1.1 content-comparison (not length-comparison) must detect this and emit
   the correct revision events (`history_revised`, not a duplicate
   `move_confirmed` for `e4`, and a correct `move_confirmed` for `d5`).

"Without duplicate moves" means: in both scenarios, each distinct move in the
final history has exactly one `move_confirmed`, and revisions produce exactly
the contracted revision events.

## 2. What already exists

- `chess_utils.js` `observeMoves`: content comparison via `halfMovesEqual`
  (3.1.1) — same-length substitutions fire the observer.
- `tests/history_tracker.test.js`:
  - AC1 (observeMoves content comparison)
  - AC5 (takeback)
  - AC7 (batch/recovery marking)
  - AC4 (correction revision)
- `tests/game_records.test.js` AC12–AC14 (`history_revised`).

**Gaps identified:**
1. The **batched multi-move** case (3+ moves in one callback) may not be
   pinned — AC7 covers batch/recovery marking but the acceptance criterion
   here is specifically "one confirmed event per new move, no duplicates."
2. The **same-length substitution** end-to-end (takeback + different move →
   exactly the right events, no duplicate `e4`) deserves an explicit
   acceptance test rather than relying on unit-test composition.

## 3. Verification plan

### V1 — static/unit (Node)

- [ ] **AC1.** Batched update: drive the tracker from `[e4]` to `[e4, e5, Nf3]`
  in a single observer callback; assert exactly two `move_confirmed` events
  (`e5`, `Nf3`) in order, no duplicates, no drops.
- [ ] **AC2.** Same-length revision: drive `[e4, e5]` → `[e4, d5]`; assert NO
  second `move_confirmed` for `e4`, exactly one `history_revised` (or the
  contracted revision event) covering the `e5`→`d5` substitution, and one
  `move_confirmed` for `d5`.
- [ ] **AC3.** Rapid alternation: `[e4]` → `[e4, e5]` → `[e4]` (takeback) →
  `[e4, c5]`; assert the final event stream has no duplicate `move_confirmed`
  for any move and the revision events correctly describe each transition.

### V2 — not required (the observer callback is the seam; V1 drives it
directly)

### V3 — deferred to owner device

- [ ] **AC4.** On the real device: play a game with a takeback (bot games
  allow takebacks); confirm the exported `events.jsonl` has no duplicate
  `move_confirmed` entries.
