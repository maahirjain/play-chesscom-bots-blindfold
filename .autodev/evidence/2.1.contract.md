# Task 2.1 Contract — Add the smallest required extension background/service-worker entry to the manifest

## 1. Scope

PLAN.md §2.1 says exactly one sentence (quoted verbatim):

> 2.1. Add the smallest required extension background/service-worker entry to the manifest.

PLAN.md mentions the service worker nowhere else except §2.6
("Restore session metadata and stored sequence state after background-worker
restart"), which confirms the SW will later host persistent storage — but
§2.6 is a different task. Task 2.1 is the manifest entry **plus the minimum
necessary for the entry to load**: a target file must exist, because a
`service_worker` entry pointing at a nonexistent file makes Chrome refuse to
load the extension. Everything else (IndexedDB, message passing, event
writing, retry, restart restoration, lifecycle events, status UI, retention)
belongs to tasks 2.2–2.9 and is an explicit non-goal (§6).

## 2. Design decisions

### 2.1 Manifest entry: `"background": { "service_worker": "sw.js" }`

- MV3's background entry takes exactly one required key: `service_worker`
  (a relative path to the worker script). `"persistent"` is an MV2 key and
  is invalid in MV3; MV3 workers are non-persistent by design. `"type":
  "module"` is not required — a classic service worker script is the
  smallest working form.
- Placement: conventionally directly after `name`/`version`, before
  `content_scripts`, for a deterministic diff. (Cosmetic; the loader does
  not care.)
- File name `sw.js` at the extension root (repo root), matching the entry.
  Conventional minimal name.

### 2.2 The stub must exist but must do nothing

`sw.js` is comments only (plus an optional `'use strict';`). Rationale:

- An empty (comment-only) service worker is valid: Chrome registers it, it
  activates, it goes idle. No load error, no console noise.
- Anything functional is a later task: `onMessage`/`onConnect` listeners are
  2.3/2.4; `onStartup`/`onInstalled` restoration is 2.6/2.7; `importScripts`
  of the Section-1 contract modules is 2.2/2.4's decision, not 2.1's.
- The stub's comment header must state what is intentionally absent (§3.2),
  so a later task doesn't mistake silence for oversight.

### 2.3 No other manifest changes

- **No `permissions`.** Registering a background service worker requires no
  permission. (2.2's extension-owned IndexedDB is also permissionless.)
- **No `host_permissions`.** The SW does not fetch anything in 2.1.
- **No `content_security_policy`.** MV3's default extension-page CSP is
  sufficient for a comment-only worker.
- **No `web_accessible_resources` change.** Service workers are loaded by
  the extension itself, not by web pages.
- **No `content_scripts` change.** The block must be byte-identical
  before/after (regression criterion AC6).
- **No version bump.** Tasks 1.1–1.4 did not bump `version`; 2.1 follows the
  same smallest-change precedent. (Version bumps, if ever needed, belong to
  a release task, not here.)

## 3. Exact deliverables

### 3.1 Modified file: `manifest.json`

Before (current):

```json
{
    "manifest_version": 3,
    "name": "Play Chess.com Bots Blindfold",
    "version": "1.0.0",
    "content_scripts": [
        {
            "matches": ["https://www.chess.com/play/computer*"],
            "js": ["sounds.js", "chess.min.js", "chess_utils.js", "content.js"],
            "css": ["overlay.css"]
        }
    ],
    "web_accessible_resources": [
        {
            "resources": ["illegal_move.wav"],
            "matches": ["https://www.chess.com/*"]
        }
    ]
}
```

After (the only change is the added `background` block):

```json
{
    "manifest_version": 3,
    "name": "Play Chess.com Bots Blindfold",
    "version": "1.0.0",
    "background": {
        "service_worker": "sw.js"
    },
    "content_scripts": [
        {
            "matches": ["https://www.chess.com/play/computer*"],
            "js": ["sounds.js", "chess.min.js", "chess_utils.js", "content.js"],
            "css": ["overlay.css"]
        }
    ],
    "web_accessible_resources": [
        {
            "resources": ["illegal_move.wav"],
            "matches": ["https://www.chess.com/*"]
        }
    ]
}
```

Diff rule: the `content_scripts` and `web_accessible_resources` blocks must
be byte-identical to the pre-change manifest; the only added JSON is the
`background` object with exactly one key.

### 3.2 New file: `sw.js` (repo root)

Full intended contents:

```js
// sw.js — extension service worker (task 2.1: registration stub).
//
// This file exists so the manifest's "background.service_worker" entry
// points at a real file. It intentionally does NOTHING yet. Chrome
// registers an empty service worker without error; it activates and
// goes idle.
//
// Intentionally absent (owned by later PLAN.md tasks):
//   - 2.2: IndexedDB database for metadata, events, and media chunks
//   - 2.3: content-script event sender / message intake
//   - 2.4: transactional event writer, dedup by event ID, write acks
//   - 2.5: retry of unacknowledged events
//   - 2.6: restore session metadata and sequence state after worker restart
//   - 2.7: page/context start and clean-end events, unclean-discontinuity marking
//   - 2.8: write-failure / storage-capacity surfacing in the status indicator
//   - 2.9: retention and export semantics
// Do not add message listeners, storage access, or imports here until the
// owning task's contract says so.
'use strict';
```

The stub must contain no functional code: no `indexedDB`, no
`chrome.runtime.onMessage` / `onConnect` / `onStartup` / `onInstalled`, no
`chrome.storage`, no `fetch`, no `importScripts`.

### 3.3 Verification script

A small `node` script (repo test convention is `node --test`, no
framework) performing the V1 static checks (AC1–AC4, AC6). The V2 load
check (AC5) runs through the existing headless-Chrome harness
(`~/workspace/tools/ext-verify/`, puppeteer `--load-extension`, per
`.autodev/DECISIONS.md` decision 3): assert the extension loads with no
load errors on stderr and that a `service_worker` target for `sw.js`
registers (puppeteer `browser.waitForTarget(t => t.type() ===
'service_worker')`), with no uncaught SW exceptions.

## 4. Acceptance criteria

- [ ] **AC1 (V1).** `manifest.json` parses as JSON; `manifest_version`
      is `3`; `background` deep-equals exactly
      `{"service_worker": "sw.js"}` — no extra keys on `background`.
- [ ] **AC2 (V1).** `sw.js` exists at the extension root and is the file
      named by the manifest entry.
- [ ] **AC3 (V1).** `sw.js` contains no functional code for 2.2–2.9:
      static grep finds no `indexedDB`, `onMessage`, `onConnect`,
      `onStartup`, `onInstalled`, `chrome.storage`, `fetch`,
      `importScripts` (outside the header comment that names them as
      intentionally absent).
- [ ] **AC4 (V1).** Task diff touches exactly two files: `manifest.json`
      (modified — only the `background` block added) and `sw.js` (new).
      No `permissions`, `host_permissions`, `content_security_policy`,
      version bump, or other manifest changes.
- [ ] **AC5 (V2).** The unpacked extension loads in real headless Chrome
      via `--load-extension` with no extension-load errors; a
      `service_worker` target for `sw.js` is registered; no uncaught
      exceptions originate from the worker.
- [ ] **AC6 (V1/V2 regression).** The `content_scripts` block is
      byte-identical before/after the change (verified by diff); the
      existing content-script file list is untouched, so injection
      behavior cannot have changed at the manifest layer.
- [ ] **AC7 (V4, deferred).** Real-device load (owner opens
      `chrome://extensions`, loads unpacked, confirms the service worker
      is listed with no errors) cannot be verified from this environment
      — the managed browser cannot load unpacked extensions (see
      `.autodev/DECISIONS.md` decision 3). Deferred to owner device
      verification.

## 5. Verification summary

| Criterion | Level | Method |
|---|---|---|
| AC1–AC4, AC6 (static) | V1 | `node` script: JSON parse, structural assertions, grep guards, `git diff` file list |
| AC5 (load + SW registration) | V2 | Headless Chrome `--load-extension`; assert no load errors; `waitForTarget` service_worker; capture SW exceptions |
| AC6 (injection unchanged) | V1/V2 | Diff-level guarantee (manifest block byte-identical); no fixture test needed for a comment-only addition |
| AC7 (real device) | V4 | Owner device only — deferred |

V3 (black-box real-site behavior) is not applicable: 2.1 changes no
page-facing behavior; there is nothing on chess.com to observe. The
headless load test is V2, not V3, and is labeled as such.

## 6. Explicit non-goals (builder must NOT)

- Any IndexedDB code or schema (2.2).
- Any content-script changes: no `chrome.runtime.sendMessage` in
  `content.js`/`chess_utils.js`/`sounds.js`, no sender/queue (2.3).
- Any event writer, dedup, or acknowledgment logic (2.4).
- Any retry logic (2.5).
- Any restart-restoration logic (2.6).
- Any lifecycle/start/end event emission (2.7).
- Any status-indicator wiring (2.8).
- Any retention/export logic (2.9).
- `importScripts` of the Section-1 contract modules into the worker —
  that wiring belongs to 2.2/2.4's contracts.
- Permissions, host permissions, CSP, version bump, or any other
  manifest change beyond the `background` block.

## 7. Downstream needs this contract must serve

- 2.2 needs a registered, loadable worker file to attach the IndexedDB
  database to — this task provides the file and the registration.
- 2.6 needs the worker to exist so "background-worker restart" is a
  meaningful event — registration is the precondition.
- The stub's "intentionally absent" header is the guardrail that keeps
  2.2–2.9 from being partially implemented here: each later contract
  amends `sw.js` deliberately, with its own review.

## 8. Reviewer notes

- If a reviewer argues the stub should include an `onInstalled` log or
  similar "just in case": reject. Logging is observable behavior with no
  owning requirement; 2.1's requirement is the entry, and silence is
  correct.
- If a reviewer argues for `"type": "module"`: reject unless they show
  the classic worker fails to load. Classic is the smallest working form.
- The one judgment call a reviewer should stress-test: is a comment-only
  file genuinely loadable as an MV3 service worker in current Chrome?
  AC5 exists precisely to settle this empirically — if it fails, the
  fallback is the smallest functional body that loads, still without
  2.2–2.9 behavior.
