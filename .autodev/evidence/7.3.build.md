### Key design decision (verified in source, pinned by test)

- `chess_utils.js` `observeMoves` watches the Chess.com DOM move list via
  `MutationObserver`. Any move Chess.com accepts — typed, clicked, or dragged
  — appears in that DOM list.
- The history tracker's `observe(halfMoves)` takes SAN string arrays (DOM-free
  in V1). A DOM mutation adding a move IS the faithful simulation of
  "Chess.com accepted a mouse move" — the collection observes the DOM
  consequence, not the input device.
- The attempt tracker is wired only to the keyboard input path (content.js
  move-input submit handler). A mouse move yields `move_confirmed` with NO
  preceding `move_attempt` — an honest record (the move was not attempted via
  keyboard).

### Tests

1. **7.3 AC1** — `observe(['e4'])` with no keyboard submission yields one
   `move_confirmed` (from `e2` to `e4`) and zero `move_attempt` events.
2. **7.3 AC2** — Three DOM-only observations (`e4`, `e5`, `Nf3`) yield 3
   `move_confirmed` events and zero `move_attempt` events.
3. **7.3 AC3** — Mixed sequence with shared emitter (attempt tracker +
   history tracker):
   - Keyboard `d4` (attempt submitted) → DOM observe → `move_confirmed`
   - Mouse `d5` (NO attempt) → DOM observe → `move_confirmed`
   - Keyboard `c4` (attempt submitted) → DOM observe → `move_confirmed`
   - Event stream: `[attempt:d4, history_recovered, confirmed:d2-d4,
     confirmed:d7-d5, attempt:c4, confirmed:c2-c4]`
   - The `history_recovered` event on first observation is the honest
     batch/recovery marker (the tracker adopted an existing history).
   - Provenance is unambiguous: attempts exist only for keyboard moves; all
     moves are confirmed in DOM order.

The `move_confirmed` payload is `{from, to, promotion}` (no SAN — verified in
`game_records.js` `createMovePayload`).
