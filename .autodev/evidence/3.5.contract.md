# Task 3.5 contract — Instrument lifecycle events

## 1. Scope

PLAN.md §3.5:

- **3.5.1.** Record document visibility and focus changes without treating them as proof of a cognitive pause.
- **3.5.2.** Record page reload/reconnect and detected game resets or takebacks.
- **3.5.3.** Observe Chess.com result/termination information where available, including endings not implied by chess rules.
- **3.5.4.** Allow a termination reason at Stop when the ending is unknown, such as abandonment.

This is the **game/session lifecycle layer**. It is explicitly NOT a re-implementation of:

| Already done | Owner | 3.5 relationship |
|---|---|---|
| `page_start` / `page_end_clean` / `page_discontinuity` (page-context lifecycle) | 2.7 (`lifecycle.js`) | NOT duplicated. A page reload IS a new page context; 2.7 already records it. |
| `history_revised` (takeback/correction), `history_recovered` | 3.1 (`chess_utils.js`) | NOT duplicated. 3.5.2's "takebacks" are already covered. |
| `move_confirmed`, `history_sync_failed`, `position_checkpoint` | 3.1 | Untouched. |
| Game-result utterance linking terminal `move_confirmed` | 3.4 (`sounds.js`) | Untouched. 3.4 must not steal 3.5.3's scope and vice versa. |

**Genuinely new in 3.5:**

1. **Document visibility/focus observation** (3.5.1) — nothing records these today. Zero `visibilitychange`/`focus`/`blur` listeners exist in product code.
2. **`game_reset` event** (3.5.2) — 3.1 *detects* genuine resets (`onGameReset` fires from `handleSuspect`), but the content.js stub only marks attempts unconfirmed; **no event is emitted**. The detection exists; the record does not.
3. **Chess.com result/termination observation** (3.5.3) — today only chess-rules-derived results exist (`getResultAnnouncement` on the internal board). Endings not implied by chess rules (resignation, timeout, abandonment) come from Chess.com's UI, which is unobserved.
4. **Termination-reason vocabulary + §5 Stop seam** (3.5.4) — "Stop" is §5's Start/Stop control (PLAN 5.1/5.7/5.10), which does not exist yet. 3.5 designs the vocabulary and the recording API; §5 wires the button.

## 2. Design

### 2.1 New module: `createGameLifecycleRecorder` in `chess_utils.js`

Named `createGameLifecycleRecorder` (not `createLifecycleRecorder`) to avoid collision with 2.7's `lifecycle.js` (page-context lifecycle). This is the **game-level** lifecycle recorder.

Follows the 3.1/3.2/3.3 recorder precedent:

- DOM-free, Node-shim'd, namespace-exported on `BlindfoldSession`.
- Emission gated on non-empty `sessionId` AND `gameId` via thunks (`getSessionId`, `getGameId`) — pre-§5 inert (2.7/3.1/3.2/3.3 precedent).
- Exact-keys payload/refs validators; `TypeError` = wrong type/shape, `RangeError` = bad domain value (AGENTS.md convention).
- All recorder calls from DOM event listeners wrapped in try/catch — failure-isolated per the 3.2 SF-1 precedent. Instrumentation must never break the page.

### 2.2 Event types (3.5-owned constants in `chess_utils.js`)

`event_envelope.js` is **untouched** (open snake_case vocabulary per 2.7/3.x precedent).

| eventType | payload (exact keys) | refs | emitter |
|---|---|---|---|
| `document_visibility_changed` | `{ visibilityState: 'visible' \| 'hidden', focused: boolean }` | `null` | content.js: `visibilitychange` + `focus`/`blur` listeners |
| `game_reset` | `{ detection: 'suspect_threshold', confirmedMoveCount: integer >= 0 }` | `null` | content.js: 3.1 `onGameReset` callback |
| `game_ended` | `{ termination: <enum>, source: 'chess_rules' \| 'chesscom_dialog' \| 'stop', speechLogicVersion: '1' }` | `{ terminalMoveEventId: uuid-v4 } \| null` | content.js: result observation (3.5.3) or §5 Stop (3.5.4) |

**Termination enum** (frozen): `checkmate`, `stalemate`, `threefold_repetition`,
`insufficient_material`, `fifty_move_rule`, `resignation`, `timeout`,
`abandonment`, `draw_agreed`, `unknown`.

- The chess-rules-derived subset (`checkmate`, `stalemate`, `threefold_repetition`,
  `insufficient_material`, `fifty_move_rule`) comes from the internal board —
  the same conditions `getResultAnnouncement` already evaluates.
- `resignation`, `timeout`, `abandonment`, `draw_agreed` are **not** implied by
  chess rules; they come from Chess.com's result dialog (3.5.3) or the Stop
  reason (3.5.4).
- `unknown` is the honest value when the ending cannot be determined (3.5.4).

### 2.3 3.5.1 — visibility/focus semantics

- One event type, emitted on **either** `document.visibilitychange` **or**
  window `focus`/`blur`, capturing **both** values at emit time:
  `{ visibilityState: document.visibilityState, focused: document.hasFocus() }`.
- **Honest naming is the mechanism** for "without treating them as proof of a
  cognitive pause": the event is named `document_visibility_changed`, the
  payload records raw document state, and the documentation states explicitly:
  *these events record document state only; they do not imply, and must not
  be interpreted as, a cognitive pause, attention shift, or player absence.*
- No debouncing, no aggregation — raw observations only (mission scope:
  raw data collection).

### 2.4 3.5.2 — game resets (the 3.1 gap)

- 3.1's `handleSuspect` calls `onGameReset()` with no arguments, **after**
  `confirmed = []` is cleared — the confirmed-move count is lost.
- **Small additive change to `chess_utils.js`**: capture
  `confirmed.length` before clearing and pass `{ confirmedMoveCount }` to
  `onGameReset`. The existing content.js stub signature `() => {...}` keeps
  working (extra argument ignored); the 3.5 wiring uses it.
- content.js `onGameReset` gains: `gameLifecycleRecorder.recordGameReset({ confirmedMoveCount })`
  (failure-isolated), keeping the existing `attemptTracker.handleGameReset()`.
- **Explicitly NOT recorded here** (already owned elsewhere):
  - Takebacks → `history_revised` (3.1.4).
  - Page reload → `page_start` (2.7) — a reload is a new page context.
  - "Reconnect": the builder must survey for a Chess.com reconnection signal;
    if none is reliably observable, document as unsupported (3.3.4 precedent:
    explicit marking, not fabricated observers).

### 2.5 3.5.3 — result/termination observation

Two sources, first-observation-wins per game (deduplicated by the recorder):

1. **`source: 'chess_rules'`** — when the internal board reaches a terminal
   state (`game.game_over()`), emit `game_ended` with the matching termination
   and `refs: { terminalMoveEventId }` (the last confirmed move's eventId,
   same link 3.4.1 uses). This fires from the existing `observeMoves` callback
   region where `announceResultIfOver` is called — the observation point, not
   the speech function.
2. **`source: 'chesscom_dialog'`** — the builder must audit Chess.com's
   game-over dialog DOM (the 3.3 domaudit §6 notes these are outside current
   selectors). If a reliable selector exists, observe it (MutationObserver or
   polling per existing precedent) and map the dialog text to the termination
   enum. If **no** reliable signal exists, the deliverable is the explicit
   unsupported-coverage marking (3.3.4 precedent) — do not fabricate.

The recorder keeps per-game `endedEmitted` state: the second source to fire
for the same game is suppressed (first observation wins). A game that ends
by chess rules and *also* shows a dialog records one `game_ended`.

### 2.6 3.5.4 — termination reason at Stop (§5 seam)

- New recorder method: `recordStopTermination(reason)` → emits `game_ended`
  with `{ termination: reason, source: 'stop', ... }`, subject to the same
  first-observation-wins dedup (if the game already ended by chess rules or
  dialog, the Stop reason is **not** emitted as a second `game_ended` —
  the ending is already known).
- Exposed on `BlindfoldSession` for §5's Stop control (5.1/5.7/5.10).
  §5 owns: the Stop button, prompting for a reason when the ending is unknown
  (PLAN §9 flow: "If the ending is unknown, supply a brief reason such as
  abandoned or resigned"), and calling this method.
- `reason` must be a member of the termination enum; `unknown` is valid and
  honest. `RangeError` otherwise.

### 2.7 What 3.5 does NOT do (non-goals)

- No changes to 2.7's `lifecycle.js`, 3.1's tracker semantics (beyond the
  additive `onGameReset` argument), 3.4's speech code, or `event_envelope.js`.
- No Stop/Start UI (owned by §5).
- No recording/stream logic (owned by §4).
- No interpretation of visibility events as pauses (3.5.1's explicit prohibition).
- No pagehide/unload flush (2.5/2.7 tension — unchanged).

## 3. Acceptance criteria

### V1 (static + unit)

- [ ] **AC1.** `document_visibility_changed` emitted on `visibilitychange` with
  `{ visibilityState, focused }` captured at emit time (both fields).
- [ ] **AC2.** `document_visibility_changed` emitted on window `focus`/`blur`
  with both fields captured.
- [ ] **AC3.** Event/payload naming and documentation explicitly disclaim
  cognitive-pause interpretation (no `pause`, `attention`, `away` tokens in
  3.5 code or docs).
- [ ] **AC4.** `game_reset` emitted from 3.1's `onGameReset` with
  `{ detection: 'suspect_threshold', confirmedMoveCount }`; the 3.1
  `onGameReset` receives the count (additive argument).
- [ ] **AC5.** No duplication: takebacks still emit only `history_revised`;
  reloads still emit only `page_start` (assert by code inspection + tests
  that 3.5 adds no handler for these).
- [ ] **AC6.** `game_ended` with `source: 'chess_rules'` emitted when the
  internal board reaches a terminal state; `refs.terminalMoveEventId` links
  the last confirmed move (null when none).
- [ ] **AC7.** Chess.com result dialog audited; `game_ended` with
  `source: 'chesscom_dialog'` for non-chess-rules endings where a reliable
  signal exists, otherwise explicit unsupported-coverage marking in
  DECISIONS.md (no fabricated observer).
- [ ] **AC8.** `recordStopTermination(reason)` exists on the recorder namespace;
  validates `reason` against the termination enum (`RangeError` otherwise);
  emits `game_ended` with `source: 'stop'`; documented as the §5 seam.
- [ ] **AC9.** First-observation-wins: at most one `game_ended` per game
  across the three sources (unit-tested: chess_rules then dialog → one event;
  dialog then stop → one event).
- [ ] **AC10.** All recorder calls from DOM listeners failure-isolated
  (try/catch; 3.2 SF-1 precedent) — a recorder throw never breaks page behavior.
- [ ] **AC11.** Diff discipline: only `chess_utils.js` + `content.js` among
  product files; `event_envelope.js`, `lifecycle.js`, `sounds.js` untouched;
  PLAN.md unmodified; no §4/§5 implementation.

### V2 (integration / runtime)

- [ ] **AC12.** New `~/workspace/tools/ext-verify/sw-lifecycle-game.js` harness:
  drives visibility changes, a game reset (via the 3.1 suspect path), and a
  chess-rules game end in real headless Chrome; asserts the three event types
  land in IDB with correct payloads/refs and the dedup holds. All existing
  harnesses still PASS.

### V3 (deferred)

- [ ] **AC13.** Live Chess.com result-dialog observation on the real
  `chess.com/play/computer` page (bot game resignation/timeout) — deferred
  to §7 / owner device. The V2 harness uses a synthetic dialog fixture.

Follow the established precedent: 3.5 legitimately touches `chess_utils.js`
and `content.js`; evolve the diff-discipline pins in existing suites honestly
(exact-diff or allowlist additions with justification comments). Never weaken
