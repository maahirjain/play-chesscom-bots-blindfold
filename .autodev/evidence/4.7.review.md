## NOTEs (informational, not defects)

1. **Contract §1.2 nuance:** it says `screenAudioContent` is `null`
   "only when the classification could not run (manifest write path
   never reached)." The code can also produce nulls with the write path
   *reached* — when the policy module is unavailable (`readAudioPolicy`
   → null) or a policy throw is swallowed. The behavior is honest
   (null = not observed, never a guess) and documented in
   `stream_starter.js` comments, but the contract's parenthetical is
   slightly narrower than the code. No AC fails; flagged for precision,
   not repair.
2. **`codeOnly` comment stripping** only handles `//` and full-line
   `*` comments; an inline block comment (`/* AudioContext */`) would
   evade the scan. The 4.6 precedent uses the same function and no
   product code uses that style. Test-hardening note only.
3. **`'system-audio'` is possibility-classification**, and the V2
   observation that the platform yielded an audio track in headless is
   exactly that — a track, not content. Genuine divergence (whether the
   checkbox was ticked, what was audible) awaits AC11/§7.
4. **Tab-mode `'tab-audio'` is V1-pinned only** (truth table + wiring
   test); live tab-audio capture failed honestly in the sandbox
   (`no-stream-id` / `ERR_TUNNEL_CONNECTION_FAILED`) and is correctly
   left to §7.
5. **`audioPolicyValidators()` in `format_support.js` throws plain
   `Error` on a wiring defect** (audio_policy.js unavailable) — per
   repo convention (unavailable platform/capability → plain Error), and
   `recordSegmentFormat` converts it to a rejected promise. Sound.
6. **No `already-started`/recovery semantics were touched** — 4.7 adds
   no state, so 4.6's guards are unchanged. Noted for the section-4
   auditor's convenience.
