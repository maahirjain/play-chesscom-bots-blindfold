## Adversarial focus areas — findings

1. **Stop-clear defect fix: real and correct.** `clearRecorderSession()`
   (session_controls.js:560) sends `recorder-set-session` with
   `{sessionId: null, gameId: null}`; `handleSetSession`
   (recorder.js:1502–1524) clears `sessionId`, `gameId`,
   `ownerTabId`, **and** `sessionCategory` (`sid === null` forces the
   category to `null` regardless of the message payload — the
   "clearing the session clears it" comment is accurate). The call
   sits only on the Stop-*success* path (session_controls.js:904,
   after `stopResp.ok === true` and the final poll); the failure
   path returns early in `Stopping…` with the session kept for
   retry — exactly 5.1's stopping-retry contract. The only residual
   window is a lost best-effort message, which self-heals: the
   finalizer is idempotent (4.13's `nothing-to-finalize`), so a page
   adopting the dead session can Stop again normally and land clean.
   No stale-adoption path survives the fix.
2. **Field-set / `'manual'` honesty: deliberate and documented, not
   a defect.** The 1.2 contract (§2.4) explicitly blesses
   null+`'manual'`: "When a value is `null` (unknown), `source` still
   records *how the unknown was determined* … user left the field
   blank ⇒ `manual`." The closed `{'observed','manual'}` vocabulary
   forces a choice for the five undetected fields; `'observed'`
   would falsely claim a detection attempt, `'manual'` asserts only
   "not DOM-detected" — the smaller untruth — and the placeholder
   comment (session_fields.js:91–96) plus the contract document the
   5.4 correction path (`createConditionChange` →
   `applyConditionChange` → `saveConditions` + `conditions_changed`
   event, per 1.2.4). See NOTE-2.
3. **No per-category enforcement: verified absent.** No code path
   conditions field requirements on the category; session_fields.js:58
   documents the deliberate non-enforcement (PLAN §3(b): "logs
   deviations but does not enforce"). A training approach entered
   for a baseline session is stored truthfully. ✓
4. **`session-save` both-or-neither: verified.**
   `handleSessionSave` (recording_host.js:396–428) calls
   `requireValidMetadata` then `requireValidConditions` **before**
   either `saveSessionMetadata`/`saveConditions`. The only partial
   path is an IDB failure between the two saves — honestly
   documented in the code comment and surfaced as a plain-Error
   `{ok:false}`, not a silent state. The listener never throws;
   every outcome is data. ✓
5. **No-category abort: verified complete.** The abort precedes
   minting (no UUIDs created), persistence (no `session-save`), and
   all recorder messages (`channelCall` comes later); the fields
   were never disabled. No partial state can leak — including no
   orphan offscreen document from `recorder-ensure`. ✓
6. **Write-once/disabled-while-active: fully wired.** Start success
   → `fieldsHandle.setEnabled(false)` (session_controls.js:807);
   Stop success → `setEnabled(true)` (line 894); boot adoption →
   disabled (line 966); `setSelection` while disabled is a no-op
   (session_fields.js). Mid-session category changes cannot reach
   the record — 5.3's guard is intact. ✓
7. **5.4 seam: real, not a stub.**
   `getDetectedConditions()` (session_fields.js:368) invokes the
   `opts.getDetectedConditions()` plug-in at Start, falling back to
   the honest placeholder only on throw/non-object — never a silent
   drop of detected values. ✓
8. **Changed-files discipline: verified** (see AC7). ✓
9. **Boundaries: verified.** No `chrome.storage` in the 5.2 modules
   (5.3's persistence mechanism absent — 5.3 owns it); no
   readiness/`isReady` vocabulary (5.6 owns it); no DOM detection
   in `session_fields.js` (5.4 owns it); no `conditions_changed`
   emission; no 5.6–5.10 functionality. ✓

- **NOTE-4.** `clearRecorderSession()` is best-effort by design
  (failures swallowed); the lost-message window self-heals via the
  idempotent finalizer. Documented contract, not a defect.
- **NOTE-5.** `session-save` has no client-side timeout by design:
  the SW handler is total (every path answers), so a missing answer
  means SW death → rejected `sendMessage` → the honest
  `session-save-failed:no-response` abort. A second timer would add
  a double-handling failure mode. Documented with justification.
