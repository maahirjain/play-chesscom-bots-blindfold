# 5.3 build evidence — Remember previous selections without silently changing a game's recorded conditions

## What was built

Implemented PLAN.md §5.3 per `.autodev/evidence/5.3.contract.md` (11 ACs),
on branch `autodev/logging-instrumentation`. Nothing committed.

**New: `selection_memory.js`** — `createSelectionMemory({storage}) →
{restore, capture, STORAGE_KEY}` + total-function
`validateRememberedSelection` (repo module convention). The remembered
selection is a UI-preference convenience, not experimental data: it lives
in `chrome.storage.local` under the versioned key
`'blindfold.sessionSelection.v1'` (extension-scoped, invisible to page
JS, survives restarts), never in §2's IDB raw-data stores. The module
never touches the `chrome` global directly — the promise-shaped
`{get,set,remove}` adapter is built inline in content.js and injected
(the 4.2/4.3/4.4 pattern). `restore` is safe to call unconditionally at
install (no enabled-check): the 5.2 write-once rule makes `setSelection`
a no-op while the form is disabled, so both orders of the boot-adoption
race are safe — adopted truth always wins. `capture` writes exactly
`{[STORAGE_KEY]: clean}` and swallows write failures (a preference write
must never affect the session that already started).

**Wiring (all additive)**:
- `session_controls.js`: new optional install option `onSessionStarted`
  (5.1/5.2-era callers stay compatible; non-function → TypeError), fired
  exactly once per successful Start at the `phase → 'active'` point with
  the recorded selection, guarded in try/catch (a throwing callback can
  never break Start). Not fired on any abort path; not fired for
  boot-adopted sessions (adoption sets the phase directly — adoption is
  not a Start, so adopted sessions are never captured).
- `content.js`: declares `selectionMemory`, passes
  `onSessionStarted: (sel) => memory.capture(sel)` into the controls
  install, and after the fields install builds the memory (inline
  `chrome.storage.local` adapter; TypeError → degraded no-defaults
  inside the existing install try/catch) and calls `restore(handle)`
  fire-and-forget.
- `manifest.json`: `"storage"` appended to `permissions` (benign,
  standard); `selection_memory.js` added to the content_scripts js
  list (content_scripts only — never SW importScripts, never the
  offscreen document).

**No-silent-change invariant** (four independent mechanisms, all
V1-pinned): (1) write-once (5.2, existing); (2) no record-write path —
comment-stripped scan pins the absence of `session-save`,
`saveSessionMetadata`, `saveConditions`, `indexedDB`,
`chrome.runtime.sendMessage` (and the `chrome` global entirely) in
`selection_memory.js`; (3) capture reads the live form at Start — the
only defaults→record flow is the explicit Start path; (4) no
load-past-session path exists.

**Remembered set**: all three 5.2 fields as one record (PLAN says
"previous selections" unqualified; editability answers the
session-specific-text worry). **Capture timing**: at Start-success only
— aborted Starts capture nothing; no capture on edit or Stop.
**Non-goals**: no clear-defaults UI (one-line `storage.remove` — a §5
follow-up if the owner wants it); no device selections; no
`chrome.storage.sync`; remembered prefs excluded from §6 export
(local-only, never transmitted).
