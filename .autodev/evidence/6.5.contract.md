# 6.5 contract — Use numbered files for interrupted recordings

**Planner:** task planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §6.5. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope

PLAN.md §6.5: "Use numbered files for interrupted recordings and list
every segment in media-sync.json."

**PLAN evidence:** 4.13 numbers segments at finalize (`segmentNumber`,
1-based per streamKind, chronological); §6 consumes them at export
time. The "list every segment in media-sync.json" half is 6.3's job
(already implemented — 6.3 lists all segments including unfinalized
ones with `finalized: false`).

**What 6.5 does:** Add a pure builder function (in the SW-side
`exporter.js` module, per the section architecture and 6.1–6.4's
precedent) that assigns a deterministic export filename to every
manifest segment: `{streamKind}-{NNN}{ext}` (e.g.
`microphone-001.webm`). It consumes 4.13's `segmentNumber` where
present and numbers on the fly where absent (unfinalized sessions),
never colliding. Its `{segmentId: filename}` mapping feeds 6.3's
`segmentFiles` input and 6.6's ZIP entry names.

**What 6.5 does NOT do:** It does not read IndexedDB (6.6's
orchestration reads `recording_manifest` via `bySessionId` and passes
plain records in). It does not assemble chunk bytes (6.4). It does not
build the ZIP (6.6). It does not decide the ZIP's internal directory
path (6.6 owns `<category>/<date>_<id>/`).

## 2. Inputs

The builder function signature (names at the builder's discretion):

```
nameSegmentFiles({ manifestRecords })
```

| Input | Source | Required? |
|-------|--------|-----------|
| `manifestRecords` | `recording_manifest` store rows for the session (via `bySessionId`; 6.6's orchestration reads them) | Yes — may be empty (a session with no segments yields an empty mapping; that is honest data, not an error) |

Each record carries `segmentId`, `streamKind`, `segmentNumber`
(integer or null), `fileExtension` (e.g. `".webm"`, may be null),
`actualMimeType` (may be null), `createdAtUtc`.

All inputs are plain data. The function performs no I/O, reads no
clock, mints no IDs. It is synchronous and pure.

## 3. Behavior (exact)

1. **Validation (TypeError, fail-closed):**
   - `manifestRecords` must be an array; each element must be a plain
     object with a non-empty string `segmentId`.
   - `streamKind` must be a non-empty string.
   - `segmentNumber`, when present (not null/undefined), must be a
     positive integer.
   - Duplicate `segmentId` values → TypeError (the store's keyPath
     prevents this; defensive).
   - **Format honesty:** every segment must resolve to a file
     extension (see §3.3). A record with neither `fileExtension` nor
     `actualMimeType` is corrupt — TypeError naming the segmentId
     (the 2.6 corruption-honesty precedent: surface, never silently
     skip or invent).

2. **Ordering:** sort the records per streamKind by 6.3's deterministic
   order: `segmentNumber` ascending (nulls last) → `createdAtUtc`
   ascending → `segmentId` ascending. This is the same order 6.3 uses
   in media-sync.json, so filenames and the sync file agree.

3. **Numbering (the core rule):**
   - Filenames are `{streamKind}-{NNN}{ext}` where `NNN` is the
     segment's number, zero-padded to a minimum of 3 digits
     (`001`, `010`, `100`; `1000` stays `1000` — no truncation).
   - **Finalized segments** (`segmentNumber` present): use it verbatim.
     4.13 assigns 1-based per-kind chronological numbers; the export
     preserves them exactly.
   - **Unfinalized segments** (`segmentNumber` null): number on the fly.
     Collect the set of used numbers for the kind; assign the smallest
     positive integers not already used, in the §3.2 sort order. This
     single rule handles all three cases uniformly:
     - *All segments unfinalized* (never-finalized session): no used
       numbers → assigns 1..N chronologically. This is exactly the
       order 4.13 would have used (createdAtUtc, segmentId).
     - *All segments finalized*: no nulls → verbatim, no changes.
     - *Mixed* (should not occur per 4.13's all-or-none numbering,
       but defensive): real numbers kept; nulls fill the gaps from the
       smallest unused integer upward. Never collides, never reuses.
   - Numbering is **per streamKind** — `microphone-001.webm` and
     `screen-001.webm` coexist (they are different streams).

4. **Extension resolution:**
   - Prefer the manifest's `fileExtension` (it includes the leading
     dot; validated to start with `.`).
   - If null/missing: derive from `actualMimeType` via the
     format_support mapping (`video/webm*`/`audio/webm*` → `.webm`;
     `video/mp4*` → `.mp4`; `audio/mp4*` → `.m4a`).
   - If both are null/unusable: TypeError (corrupt record — the
     container format is unknowable).

5. **Return value:**
   ```js
   {
     files: [
       { segmentId, filename, streamKind, segmentNumber }
       // segmentNumber: the EFFECTIVE number used in the filename
       // (real or on-the-fly); in §3.2 order, grouped by kind
     ],
     bySegmentId: { [segmentId]: filename }
     // feeds 6.3's segmentFiles input and 6.6's ZIP entry names
   }
   ```

## 4. Worked examples

- Finalized session, microphone split once:
  `microphone-001.webm`, `microphone-002.webm`
- Never-finalized session, screen recorded:
  `screen-001.webm` (on-the-fly; media-sync.json marks `finalized: false`
  with the `unfinalized` gap — 6.3's existing honesty)
- Mixed (defensive): kind has numbers `{1, 3}`, one null →
  null gets `2` (smallest unused)

## 5. Coordination

- **6.3:** `bySegmentId` is passed as 6.3's `segmentFiles` input.
  6.3 already handles `filename: null` (segment not in the mapping);
  with 6.5, every manifest segment gets a filename, so nulls should
  not occur — but 6.3's null-tolerance remains as defense.
- **6.6:** `files` (in order) drives the ZIP entry sequence; each
  entry's file data comes from 6.4's `assembleSegmentChunks` for that
  `segmentId`. The ZIP's internal path prefix
  (`<category>/<date>_<id>/`) is 6.6's concern, prepended to 6.5's
  bare filenames.

## 7. Explicit non-goals

- Reading IndexedDB (6.6's orchestration).
- Chunk assembly (6.4).
- ZIP construction or internal directory paths (6.6).
- Renaming or re-numbering 4.13's finalized `segmentNumber` values.
- Persisting the on-the-fly numbers anywhere (they are export-time
  labels only; the manifest is never written by §6 — readonly rule).
