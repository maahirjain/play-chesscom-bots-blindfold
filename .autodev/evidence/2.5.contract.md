# Task 2.5 Contract — Retry unacknowledged events while the originating context remains available

## 1. Scope

PLAN.md §2.5 says (quoted verbatim):

> 2.5. Retry unacknowledged events while the originating context remains available.

This task adds the **retry policy** to the content-script sender (`sender.js`,
task 2.3). Everything it needs already exists: the unbounded in-memory FIFO
(never silently drops), the stop-and-wait pump, `flush()` as the re-kick
primitive, `lastError` classification, and `getStatus()`. What 2.5 adds is
exactly two mechanisms:

1. **A send timeout** — a transport promise that never settles currently
   stalls the pump for the page lifetime (2.3 review NOTE-2, 2.3 behavior
   Check 1; both explicitly assign this to §2.5). The timeout bounds each
   send attempt; on expiry the attempt is treated as failed, the event stays
   queued, and the retry path takes over.
2. **A retry timer** — after a failed attempt, re-kick the pump after a fixed
   interval instead of waiting for the next `emit()`/`flush()`. Retry
   continues while the context lives; context death (page unload) ends it —
   that *is* the meaning of "while the originating context remains
   available" (§4).

Downstream shape: 2.6 restores sequence state after SW restart (a restarted
SW is one cause of transient send failure — retry covers the gap); 2.8
surfaces persistent failure via `getStatus()` (which gains one field, §3.4).

## 2. Design decisions

### 2.1 What "retry" means here (and what 2.3 already does)

2.3's sender already: keeps every unacknowledged event queued forever,
re-kicks the pump on every `emit()`, and exposes `flush()`. So "retry" in
2.5 does **not** mean "keep events" (done) — it means **autonomous
re-attempt without waiting for new observations**: a failed head-of-queue
send is retried on a timer until it is acknowledged or the context dies.
Fresh `emit()` calls still kick the pump immediately (unchanged); the timer
only matters when the queue is stalled with no new observations.

### 2.2 Send timeout: 10 000 ms per attempt

- **Constant:** `SEND_TIMEOUT_MS = 10000` (default; injectable, §3.1).
- **Rationale:** the transport is local IPC (`chrome.runtime.sendMessage`
  to the SW). The slowest legitimate path is a cold SW start (wake +
  IndexedDB open + one readwrite transaction) — hundreds of milliseconds.
  10 s is 10–100× headroom, so a slow-but-alive writer never trips it
  spuriously; a hung transport (crashed SW mid-handler, never-settling
  promise) is recovered within a bounded window. A spurious timeout is
  harmless: the resend is byte-identical and 2.4's dedup-by-`eventId`
  absorbs it idempotently.
- **Mechanics:** each send attempt races the transport promise against a
  timeout promise (`Promise.race`). Timeout win → `lastError =
  'send-timeout'`, the head stays queued, the pump stops, a retry is
  scheduled (§2.3). The race **discards the loser**: a late ack from the
  timed-out attempt cannot double-dequeue or corrupt pump state. If the
  late ack was `{ok:true}`, the event *was* durably written; the retry's
  resend then receives the idempotent `{ok:true}` from 2.4's dedup — the
  redundancy is correct, not a bug. The losing transport promise already
  has handlers attached (the race subscribes), so no unhandled rejection
  can escape.
- **Timer resolution:** `setTimeout`/`clearTimeout` are read from
  `globalThis` at schedule time (call-time resolution, matching the
  transport-lazy pattern), so `node:test` `mock.timers` works in V1 and no
  timer handle is cached at load.

### 2.3 Retry timer: fixed 5 000 ms interval, at most one pending

- **Constant:** `RETRY_INTERVAL_MS = 5000` (default; injectable, §3.1).
- **Rationale for fixed (not exponential):** there is exactly one sender
  per context — no thundering-herd risk. Failure modes here are binary:
  transient (SW restarting, momentary IPC failure — recovers in seconds)
  or persistent (quota exhaustion — never recovers by waiting; 2.8
  surfaces it). Exponential backoff adds state and test complexity for no
  behavioral benefit in either mode. A fixed, predictable interval is the
  smallest coherent policy.
- **Scheduling rule:** after a *failed send attempt* (transport threw /
  rejected, `undefined`/mismatched ack, `'send-timeout'`, or writer
  `{ok:false}`), if the queue is non-empty and no retry is already
  scheduled, schedule exactly one `setTimeout(kickPump, retryIntervalMs)`.
  At most one retry timer exists at any time (invariant).
- **Consumption rule:** when the timer fires it clears its own handle
  *before* kicking the pump; when any pump run actually starts (not joins
  an in-flight run), any pending retry handle is cleared. A pump that
  drains the queue leaves no retry scheduled. `flush()` and `emit()`
  participate in the same rules — no special cases.
- **No retry when there was no attempt:** if `resolveTransport()` yields
  no transport, the pump finishes immediately and **no** retry is
  scheduled (nothing to retry with; in production `chrome.runtime`
  does not appear/disappear mid-context).

### 2.4 No failure classification in the retry decision (uniform retry)

The sender does **not** parse the writer's error strings to decide whether
to retry. `transport-error:*`, `no-ack`, `send-timeout`, and every writer
`{ok:false}` (`malformed-message`, `invalid-envelope`,
`append-seq-present`, `event-id-content-mismatch`, `write-failed:<name>`)
all schedule a retry identically while the context lives — the plain
reading of PLAN §2.5 ("retry unacknowledged events").

Rationale (considered and rejected the alternative): classifying on error
strings couples the sender to the writer's error vocabulary (a contract
surface that may grow); retrying a deterministic rejection is harmless
(the resend is byte-identical, the writer rejects identically, one
sendMessage per 5 s); and "never give up while the context lives" is the
only rule simple enough to audit. Classification already exists where it
belongs: `lastError` carries the writer's string for 2.8's status
surfacing.

### 2.5 "While the originating context remains available" — interpretation

The retry timer lives in the content-script context. Page unload destroys
the context, the timer, and the in-memory queue together (2.3's
context-scoped design stands). Retry therefore runs until context death —
no cross-context persistence, no resurrection. Loss remains detectable
via `sourceSeq` gaps, not hidden. This is the complete meaning of the
PLAN phrase; no unload-time behavior is added (§5).

### 2.6 Timer throttling in background tabs

Content-script `setTimeout` may be throttled when the tab is backgrounded
(Chrome's intensive throttling). Acceptable: retry is best-effort
recovery; when the tab is backgrounded there are no new observations, and
every `emit()` kicks the pump immediately regardless of throttling. The
SW writer side is unaffected. Documented, not mitigated.

## 3. Exact deliverables

### 3.1 `sender.js` changes (only app file touched)

All changes are inside `createSender`'s closure plus two namespace
constants. Function-level specification:

- **Options:** `createSender({transport?, sendTimeoutMs?, retryIntervalMs?})`.
  `sendTimeoutMs`/`retryIntervalMs`, when provided, must be numbers:
  non-number (incl. `NaN`) → `TypeError`; number but not finite or `<= 0`
  → `RangeError` (AGENTS.md error convention: wrong type → TypeError,
  bad domain value → RangeError; follows the `transport`-must-be-function
  `TypeError` precedent). Defaults are the exported constants.
- **New closure state:** `retryTimerId = null` (at most one pending retry).
- **New helpers:**
  - `scheduleRetry()` — no-op unless `queue.length > 0`,
    `retryTimerId === null`, **and** a transport is currently resolvable
    (mirrors the §2.3 no-retry-without-transport rule). Otherwise sets
    `retryTimerId = setTimeout(onRetryTimer, retryIntervalMs)` with the
    timer resolved from `globalThis` at schedule time.
  - `onRetryTimer()` — sets `retryTimerId = null` first, then `kickPump()`.
  - `clearRetry()` — `clearTimeout` + `retryTimerId = null` if set.
- **`runPump()` modifications:**
  - At the top of a *new* run (not when joining `pumpPromise`):
    `clearRetry()` — an explicit kick supersedes any scheduled retry.
  - In `step()`: race the transport promise against the timeout:
    ```js
    var timeoutId;
    var timeoutPromise = new Promise(function (_, reject) {
      var g = (typeof globalThis !== 'undefined') ? globalThis : null;
      var st = g && g.setTimeout;
      timeoutId = (typeof st === 'function')
        ? st.call(g, function () { reject(new Error('send-timeout')); }, sendTimeoutMs)
        : null;
      if (timeoutId === null) { reject(new Error('send-timeout')); } // no timer: fail fast, still retryable
    });
    Promise.race([settled, timeoutPromise]).then(onSettled, onRejected);
    ```
    (If `setTimeout` is unavailable the attempt fails fast as a timeout —
    honest failure, still queued, still retryable; in production timers
    always exist.)
  - `onSettled(response)`: `clearTimeout(timeoutId)`; existing ack logic
    unchanged (positive matching ack → dequeue, clear `lastError`,
    continue; anything else → `recordAckFailure`, `finish()`).
  - `onRejected(err)`: `clearTimeout(timeoutId)`; if the rejection is the
    timeout's `send-timeout` error → `lastError = 'send-timeout'`, else
    existing `transport-error:<name>`; `finish()`.
  - After `finish()` on any **failed** attempt (not on drain, not on
    no-transport): `scheduleRetry()`. The success-drain and no-transport
    paths must not schedule.
- **`getStatus()`:** adds `retryScheduled: retryTimerId !== null`
  (frozen into the returned object). Rationale: lets 2.8 distinguish
  "stalled with recovery scheduled" (working as designed) from "stalled
  with nothing scheduled" (a bug). The existing three fields are
  unchanged.
- **Exported constants** (frozen numbers on the namespace, following the
  `SENDER_MESSAGE_KIND` precedent):
  `BlindfoldSession.SENDER_SEND_TIMEOUT_MS = 10000`,
  `BlindfoldSession.SENDER_RETRY_INTERVAL_MS = 5000`.
- **No other API changes.** No `destroy()`/`close()` (considered and
  rejected: the sender lives for the context lifetime; a single pending
  5 s timer dies with the context; tests use injected short intervals or
  `mock.timers`). No change to `emit()`'s synchronous
  timestamp-then-queue contract. No change to the wire message shape.

### 3.2 Tests: extend `tests/sender.test.js`

New `describe('2.5 retry policy')` block reusing the existing mocked-
transport harness (real `performance.now()`). Use `mock.timers` from
`node:test` **or** injected short intervals (`sendTimeoutMs: 50,
retryIntervalMs: 50`) — either is acceptable; do not mix styles within
the block. Suggested coverage (maps to AC1–AC9):

- never-settling transport → after the timeout, `lastError ===
  'send-timeout'`, head queued, pump stopped, `retryScheduled === true`;
- late `{ok:true}` after a timeout → no double-dequeue, no corruption;
  the scheduled retry resends and the idempotent ack dequeues exactly
  once;
- rejecting transport → advance past the interval → exactly one
  re-attempt; success dequeues; further time advance → no extra sends
  (queue drained, no timer);
- repeated failures → send-attempt count grows linearly with intervals
  (at most one timer: N intervals ⇒ N re-attempts, not N²);
- `emit()` while a retry is scheduled → immediate pump run (attempt
  happens before the interval elapses); stale timer consumed
  (`retryScheduled === false` afterwards unless the attempt failed);
- no transport at all → failures never schedule a retry
  (`retryScheduled === false` after a failed no-transport pump);
- options validation: `'x'`/`NaN` → `TypeError`; `0`/`-1`/`Infinity` →
  `RangeError`, for both options independently;
- `getStatus()` includes `retryScheduled`; constants exported with the
  specified default values;
- `{ok:false, error:'event-id-content-mismatch'}` schedules a retry
  (pins the §2.4 no-classification decision);
- diff discipline: `git status` shows only `sender.js`,
  `tests/sender.test.js`, and `2.5.*` evidence (plus DECISIONS.md if the
  builder records the pagehide/timeout findings there).

### 3.3 V2 harness: `~/workspace/tools/ext-verify/sw-retry.js` (new, outside repo)

Reuse the 2.3/2.4 `/tmp` test-extension-copy technique (product files
verified byte-identical before launch; `ignoreDefaultArgs:
['--disable-extensions']`). The harness driver creates its own sender
with short injected intervals (e.g. `{sendTimeoutMs: 400,
retryIntervalMs: 400}` — driver-side code may inject; product defaults
stay 10 s / 5 s):

- **Flaky listener:** install a SW `onMessage` listener that ignores the
  first K sends (returns `false`, no response) then acks normally →

- **Never-responding listener:** never calls `sendResponse` → assert the
  send timeout fires (attempts repeat at ~the injected interval),
  `lastError === 'send-timeout'`, events stay queued, no uncaught
  exceptions; then install the acking listener → drain.
- Assert byte-identical product files, zero worker exceptions.

## 4. Acceptance criteria

- [ ] **AC1 (V1).** Never-settling transport: after `sendTimeoutMs`,
  `lastError === 'send-timeout'`, head stays queued, pump stops,
  `getStatus().retryScheduled === true`.
- [ ] **AC2 (V1).** Late `{ok:true}` arriving after its attempt timed
  out: no double-dequeue, queue intact; the retry's resend is acked
  idempotently and dequeues exactly once.
- [ ] **AC3 (V1).** Failing transport (rejects): advancing past
  `retryIntervalMs` re-attempts the send; success dequeues; no further
  sends once drained.
- [ ] **AC4 (V1).** At most one retry timer: repeated failures produce
  linearly many re-attempts (no timer stacking).
- [ ] **AC5 (V1).** `emit()` while a retry is scheduled runs the pump
  immediately; the stale scheduled retry is consumed, not duplicated.
- [ ] **AC6 (V1).** No transport resolvable: no retry is ever scheduled.
- [ ] **AC7 (V1).** `sendTimeoutMs`/`retryIntervalMs` validation:
  non-number/`NaN` → `TypeError`; non-finite/`<= 0` → `RangeError`,
  each option independently.
- [ ] **AC8 (V1).** `getStatus()` includes `retryScheduled`; namespace
  exports `SENDER_SEND_TIMEOUT_MS === 10000` and
  `SENDER_RETRY_INTERVAL_MS === 5000`.
- [ ] **AC9 (V1).** Writer `{ok:false}` (incl. deterministic
  `event-id-content-mismatch`) schedules a retry — no classification.
- [ ] **AC10 (V1).** Diff discipline: only `sender.js`,
  `tests/sender.test.js`, `2.5.*` evidence (and DECISIONS.md if
  touched) differ from HEAD; `content.js`, `manifest.json`, `sw.js`,
  `db.js`, `writer.js`, Section-1 modules byte-identical.
- [ ] **AC11 (V2).** Real content-script world: flaky listener → retries
  drain the queue in order; never-responding listener → timeouts repeat
  at the injected interval with `send-timeout`, then drain once the
  acking listener is installed; zero worker exceptions.
- [ ] **AC12 (V1/V2 regression).** Full accumulated suite passes;
  `sw-load.js`, `sw-db.js`, `sw-sender.js`, `sw-writer.js` still pass.
- [ ] **AC13 (V3, deferred).** Real `https://www.chess.com/play/computer`
  injection: no new page-facing behavior in 2.5; injection correctness

## 6. Explicit non-goals (builder must NOT)

- Any writer/SW change (2.4): ack protocol, dedup, validation untouched.
- Retry with backoff (fixed interval only — §2.3).
- Failure classification in the retry decision (§2.4 — uniform retry).
- `pagehide`/unload best-effort flush (considered and rejected: the ack
  path is dead at unload so durability can't be confirmed; 2.7 owns
  lifecycle honesty via clean-end/unclean-discontinuity marking; the
  queue stays context-scoped per 2.3).
- Queue persistence across page loads (still context-scoped).
- `destroy()`/`close()` on the sender (rejected: single 5 s timer dies
  with the context; tests inject short intervals or mock timers).
- Restore after SW restart (2.6); lifecycle event types/emission (2.7);
  status-indicator UI (2.8 — only `getStatus().retryScheduled`);
  retention/export (2.9, §6).
- Changes to `content.js`, `manifest.json`, `sw.js`, `db.js`,
  `writer.js`, or any Section-1 module.

## 7. Reviewer notes (pre-answered)

- If a reviewer argues for exponential backoff: reject — single sender,
  no herd; failure modes are transient-seconds or persistent-forever;
  fixed interval is the smallest coherent policy (carries §2.3's
  simplicity forward).
- If a reviewer argues the sender should stop retrying deterministic
  writer rejections: reject — uniform retry is the auditable rule;
  resends are byte-identical and idempotent via 2.4 dedup; parsing
  writer error strings would couple the sender to the writer's
  vocabulary.
- If a reviewer argues for a `pagehide` flush: reject — §6 above; the
  honest mechanism for "context died with N pending" is `sourceSeq`
  gaps plus 2.7's discontinuity marking, not an unconfirmable send.
- The one judgment call to stress-test: **the timeout-vs-late-ack race.**
  `Promise.race` discards the loser, so no token/generation guard is
  needed — but the reviewer should verify the implementation actually
  races (rather than, e.g., clearing the timeout on any settle and
  misattributing a late ack to the new attempt) and that the losing
  promise's handlers are attached (no unhandled rejection).
- Also verify: `scheduleRetry` is called **only** on failed attempts
  (never on drain, never on no-transport), and the at-most-one-timer
  invariant holds across `emit()`/`flush()`/timer interleavings.
