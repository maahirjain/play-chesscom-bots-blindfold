# Task 4.10 contract — generate segment IDs and link clock segments to recordings

PLAN.md §4.10: "Give every recording segment an ID and link it to the corresponding clock anchor."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.10 is (one paragraph)

4.6 mints uuid-v4 `segmentId`s at stream start and records per-stream
`streamStartedAtUtc` + `streamStartedAtMonotonicMs`. The event system
(1.3/2.4) timestamps every event with `clockSegmentId` + `monotonicMs`
against a per-context `clock_anchor`. **4.10 is the link between those
two identity systems**: at stream start it writes the active
recording-context clock segment's ID into the recording's manifest
record, so 4.12 can later convert any recording-relative timestamp
(`streamStartedAtMonotonicMs`, chunk `timecodeMs`) to wall clock via the
named anchor. 4.10 mints nothing, computes no offsets, and emits no
events — it writes one nullable field and documents the model.

## 0.1 PLAN reading note (for the section-4 auditor)

PLAN.md §4.10 says "Give every recording segment an ID". That half of
the requirement is already satisfied by the **4.5 §2 amendment,
implemented in 4.6**: segmentIds are minted (uuid-v4) at stream start
because the manifest record is written at stream start and its keyPath
*is* `segmentId`. Re-reading PLAN.md §4.10 after the amendment, 4.10's
remaining work is the **link** half. This contract does not re-mint,
re-assign, or rename any segmentId. (PLAN.md itself is never modified;
this note is the durable record of the reading.)

## 1. The clock-segment model (as it exists — no new machinery)

A "clock segment" in this codebase is exactly one `clock_anchor` event
row: `{segmentId (uuid-v4), utcEpochMs, monotonicMs}` (event_envelope.js,
`createClockAnchor` / `captureClockAnchor`). Every event envelope
carries `clockSegmentId` + `monotonicMs`; wall time for any event is
`anchor.utcEpochMs + (monotonicMs - anchor.monotonicMs)`
(`deriveWallUtcMs`). The anchor defines the segment; the segment is the
monotonic clock's lifetime.

Per-context anchor discipline (verified in code, not assumed):

- `recorder.js` (offscreen document, `sourceContext:
  'recording_context'`): **one anchor per document, captured lazily at
  first emission** (`anchor = null` → `captureClockAnchor()` on first
  `emitEvent`; recorder.js:390-401). All recording_context events from
  one document generation share one `clockSegmentId`.
- `sender.js` (content script): one anchor per sender instance
  (context lifetime).
- `lifecycle.js` (service worker): one anchor per (SW-instance,
  session).

Consequences for 4.10:

1. **The lazy-anchor subtlety.** The offscreen document's anchor may
   not exist when the first stream starts (nothing may have been
   emitted yet). 4.10's linker must *force* anchor capture (via
   recorder.js's existing `getAnchor()`) before writing the link —
   otherwise the link would race the first emission. Forcing capture
   is honest: the anchor describes the document's clock, which already
   runs; capturing it earlier changes nothing about the clock.
2. **One clock segment per document generation.** The anchor is never
   re-captured within a document lifetime. A mid-recording
   discontinuity (4.9: track ended, recorder error, chunk stalled)
   does **not** change the clock segment — the clock continues; only
   the media timeline has a gap. 4.10's link therefore *survives*
   discontinuities; 4.12 interprets gaps using 4.9's discontinuity
   events plus verbatim monotonic timestamps.
3. **Document restart = new clock segment.** New document → new
   `performance.now()` origin → new anchor → new `clockSegmentId`.
   The 4.9 `'restart'` discontinuity mints new segmentIds; 4.10 writes
   new links for them against the new anchor. Old manifest records
   keep their old links (the manifest survives document death in
   extension-owned IDB) — this is exactly why the link belongs in the
   manifest and not in document memory.

## 2. The link: one new manifest field

`MANIFEST_KEYS` widens deliberately **15 → 16** with the `// 4.10-owned:`
comment convention (4.6/4.7 precedent). One field:

- `clockSegmentId`: `string (uuid-v4) | null` — the `segmentId` of the
  recording_context `clock_anchor` active when this recording segment
  started. `null` iff the anchor could not be captured (e.g.
  `performance.now()` unavailable → `captureClockAnchor` throws a
  plain `Error`; malformed anchor → `null`). Unknown is null; never
  guessed, never a placeholder.

Everything else the link needs is already present or derivable — this
is why one field suffices:

- `streamStartedAtMonotonicMs` (4.6) is on the *same* monotonic clock
  as the anchor (same document), so 4.12 computes
  `deriveWallUtcMs(anchor, streamStartedAtMonotonicMs)` with zero new
  stored values.
- The anchor row itself (`utcEpochMs`, `monotonicMs`) lives in the
  event log as the `clock_anchor` event — 4.12 joins on
  `clockSegmentId`.
- Link creation time = `createdAtUtc` (4.5).

The exact-keys discipline holds: this widening is deliberate and
documented here; 4.12/4.13 widenings must be equally deliberate.

## 3. Runtime design

### 3.1 The linker

A small pure-ish function (new module `clock_link.js`, DOM-free, repo
module pattern — or a factory section inside `format_support.js` if
the builder finds the seam cleaner; the contract fixes behavior, not
file layout):

- `linkClockSegment({segmentId, getAnchor})` → `{clockSegmentId}` —
  calls `getAnchor()` (forced capture), validates the result is a
  well-formed anchor (`requireUuidV4(segmentId)`-style), returns the
  id or `null`. **Never throws**: any failure → `{clockSegmentId:
  null}`. Linking can never fail a stream (the 4.6/4.7/4.8/4.9
  "can never fail the pipeline" precedent).
- `stream_starter.js` calls the linker during the manifest-write
  stage (the same stage 4.6/4.7 own) and passes `clockSegmentId`
  into `recordSegmentFormat`'s 4.10-widened write.

### 3.2 The 4.13 seam

4.13 mints post-discontinuity segmentIds. 4.10 owns **all** linking:
4.13 calls the same `linkClockSegment` for each minted segmentId
(the clock segment is unchanged — same document — so the link value
will normally equal the generation's anchor id; it is still written
fresh, never copied, so the record is self-describing). The linker
takes `{segmentId, getAnchor}` as inputs — it is not hardwired to
4.6's pipeline.

### 3.3 Read API (additive, minimal)

One additive read on `format_support.js`:
`getManifestRecord(segmentId)` → the manifest record or `null`.
(Rationale: 4.12/4.14/§6.3 need per-segment link reads; the existing
`getManifestRecordsBySession` is session-scoped. No schema change, no
new index — the store's keyPath *is* `segmentId`.) The manifest
record itself is the link; no separate link store, no separate link
event.

### 3.4 No arithmetic in 4.10

The linker performs **no time arithmetic**: no `deriveWallUtcMs`
calls, no offset computation, no `timecodeMs` interpretation. It
reads one identifier off the anchor. Offset computation is 4.12's;
a code-scan pin asserts the linker module contains no wall-clock
derivation (identity-only).

## 4. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — link written at stream start.** The manifest record for a
  started stream carries `clockSegmentId` equal to the active
  recording_context anchor's `segmentId`; `streamStartedAtMonotonicMs`
  is on the same monotonic clock (V1: injected anchor + injected
  clocks; assert `streamStartedAtMonotonicMs >= anchor.monotonicMs`
  in the success case).
- **AC2 — lazy anchor forced.** When no anchor exists at link time,
  the linker captures it (via the injected `getAnchor`) before the
  write; when capture throws or the anchor is malformed, the record
  carries `clockSegmentId: null` and the stream still starts.
- **AC3 — manifest widening is deliberate.** `MANIFEST_KEYS` is
  exactly the 16-key shape (15 prior + `clockSegmentId`, `//
  4.10-owned:` comment); `requireValidManifestRecord` still rejects
  extra keys; the new field is nullable.
- **AC4 — linking never fails the stream.** Throwing `getAnchor`,
  malformed anchor, throwing manifest write — the stream-start
  pipeline's outcome is unchanged (V1: the 4.6 failure-isolation
  tests still pass; link failure is not a 4.6 failure stage).
- **AC5 — identity-only.** Code-scan pin: the linker's executable
  code performs no wall-clock derivation (no `utcEpochMs`
  arithmetic, no `deriveWallUtcMs` equivalent); it reads the
  anchor's `segmentId` and nothing else.
- **AC6 — 4.13 seam.** The linker is callable standalone with a
  caller-minted `segmentId` (V1: link a synthetic post-discontinuity
  segmentId against an injected anchor; assert the record carries the
  link). 4.13 will own the minting; 4.10 owns the linking.
- **AC7 — discontinuities don't re-link.** A `stream_discontinuity`
  (any of 4.9's six reasons) does not change any manifest link;
  the link written at stream start is untouched by later 4.9 events
  (V1: attach monitor, fire ended/error, assert manifest record
  unchanged). Documented: the clock continues across media gaps.
- **AC8 — changed-files discipline.** Working-tree diff touches
  only: the linker module (new) or `format_support.js` (if the
  builder places it there), `tests/` for 4.10 (new),
  `stream_starter.js` (linker call in the manifest-write stage),
  `format_support.js` (`MANIFEST_KEYS` + `getManifestRecord`),
  cumulative pin evolutions with justification comments,
  `.autodev/evidence/4.10.*`, `.autodev/DECISIONS.md`. No new event
  types, no new channel messages, no gameplay change, PLAN.md
  unmodified, no 4.11/4.12/4.13 bleed (the 4.13 seam is a callable,
  not 4.13 logic).

## 5. Explicit non-goals

- No offset or timecode computation (4.12 owns all of it).
- No segmentId minting (4.6 at stream start; 4.13 post-discontinuity).
- No re-linking on discontinuity (the link survives media gaps).
- No new event types, no new channel messages, no new permissions.
- No schema change beyond the additive 16th manifest key (the store
  and its indexes already exist; `DB_VERSION` stays 2).
- No changes to the anchor model itself (one anchor per document
  generation is 2.3/2.4's design; 4.10 consumes it).
