# 6.7 contract — Provide repeatable export from retained local data if a download is interrupted

## 1. Scope

PLAN.md §6.7: "Provide repeatable export from retained local data if a download is interrupted."

**PLAN evidence:** §(c) "Each game", step 8–9: the user downloads the game ZIP after Stop. If the download is interrupted (browser crash, disk full, user cancels, network drive disconnects), the user must be able to re-export the same session without data loss.

**Current state (verified):** 6.6's `exportSession` is readonly end-to-end (zero `DB.put`/`DB.delete` in exporter.js, proven by AC5's store-changed-during-export test). 6.6's Download button "stays enabled after success for 6.7 re-export" (6.6 contract §7). The stores are retained per 2.9 (export never deletes).

**What 6.7 does:** Formalize and prove the repeatability guarantee. No new product-code paths are expected (architecture: "repeatability-by-discipline"); 6.7 is a verification task that pins the guarantee with tests and documents the exact byte-identity semantics.

**What 6.7 does NOT do:** It does not add retry logic, resume-from-partial-download, or new UI. It does not change the export pipeline.

## 2. Definitions

### 2.1 "Repeatable export"

The user can click Download any number of times after Stop-complete, and each export reads the same retained local data. Specifically:

1. **Export never mutates the stores.** Proven by 6.6's readonly discipline (before/after count snapshot; `store-changed-during-export` on mismatch).
2. **The Download button stays enabled after success.** 6.6's contract §7: "stays enabled after success for 6.7 re-export". Verified by code inspection.
3. **Re-export after an interrupted download produces a complete bundle.** Because the sources are untouched, a second export re-reads the full session data — there is no "partial export" state to resume from; every export is a full, independent build.

### 2.2 Byte-identity semantics (the exportedAtUtc resolution)

Two exports of the same session at different wall-clock times produce ZIPs that are **byte-identical except for the two `exportedAtUtc` fields** (`metadata.json` and `media-sync.json`).

- `exportedAtUtc` is the one labeled clock read in the export pipeline (6.1, 6.3). It honestly records when the export ran. It cannot be derived from stored data without fabrication (there is no stored "export time"), so it must use the wall clock.
- **Everything else is byte-identical:** `events.jsonl` (byte-stable envelope serialization), all media files (byte-concatenated chunks), ZIP structure (deterministic ordering, fixed DOS timestamps from session data, precomputed CRCs), file paths, and central directory.
- With an injected fixed `nowUtcIso` (the test seam), two exports are **fully byte-identical** — pinned by V1.

This resolves the 6.1/6.3 reviewer tension (N4/N3): the timestamp is the documented, labeled exception to byte-identity, not a defect.

### 2.3 What "interrupted download" covers

- User cancels the download → click Download again.
- Browser crash during download → reopen, click Download again (the SW restarts; the stores persist; the verdict may be absent → `stop-verdict-unavailable` degradation, still a complete bundle of stored data).
- Disk full / write error → free space, click Download again.
- In all cases: no cleanup needed, no "resume" needed — every export is a fresh full build from retained data.

## 4. Explicit non-goals

- Download resume (HTTP range requests) — the browser's download manager owns this; the extension re-exports from scratch.
- Automatic re-export on failure — the user clicks Download again.
- Progress UI for long exports.
- Deleting or compacting stores after successful export (2.9 owns retention).
