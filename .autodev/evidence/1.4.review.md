## SHOULD_FIX findings

### SF-1 — `isFen` accepts rank strings the vendored `validate_fen` rejects (consecutive digits)

- **Files/lines:** `game_records.js:152`
  (`FEN_RANK_CHARS_RE = /^[pnbrqkPNBRQK1-8]+$/`); rank loop ~`game_records.js:236-248`.
- **Contract claim:** `.autodev/evidence/1.4.contract.md` §2.2 says the
  validator "mirrors the vendored chess.js `validate_fen` field-1/4 rules".
- **Evidence (independent probe):**
  - `new Chess().validate_fen('rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQK11R w KQkq - 0 1').valid`
    → `false` (vendored error 8: consecutive numbers).
  - `BlindfoldSession.isFen(<same>)` → `true` (accepted).
  - Replaying the accepted FEN: `new Chess(<that FEN>).fen()` →
    `8/8/8/8/8/8/8/8 w - …` — the load **silently fails** and the board is
    left empty. No throw.
- **Why it matters:** the contract's whole reconstruction story (PLAN §1
  context; AC9) is "starting FEN + confirmed moves replays in chess.js".
  A FEN this contract accepts but the replay oracle cannot load breaks
  that story, and it breaks *silently* (empty board, no error). "11" is
  not valid FEN per spec; accepting it is a validator defect, not
  generosity — the validator's stated job is caller-error detection.
- **Blast radius (honest):** canonical `fen()` output from the internal
  chess.js board never contains consecutive digits, so the §3.1 observed
  path is unaffected. The exposure is the manual-entry path
  (`position_checkpoint` with `fenSource: 'manual'`, §5.4 Stop-time
  entry). Narrow, but real.
- **Fix:** add the consecutive-digit rule to the rank loop (reject a
  digit immediately following a digit), matching the vendored validator's
  error-8 behavior; add a regression test. One-line-class change.

### SF-2 — Factories store FENs verbatim without trimming; surrounding whitespace is accepted and silently unreplayable

- **Files/lines:** `game_records.js:286-296` (`requireValidFen` trims only
  for the *check*); `game_records.js:344` (`fen: input.fen` stored raw);
  `game_records.js:473` (same in `createPositionCheckpointPayload`).
- **Evidence (independent probe):**
  - `isFen('  rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1  ')`
    → `true`; `createGameStartedPayload` stores the padded string verbatim.
  - Vendored `validate_fen` on the padded string → `false`
    (`split(/\s+/)` yields 8 tokens). `new Chess(padded).fen()` →
    `8/8/8/8/8/8/8/8 w - …` — again a **silent empty-board misload**.
- **Why it matters:** same silent-replay hazard as SF-1, and the more
  realistic of the two — a user pasting a FEN at Stop (§5.4/3.5.4 manual
  completion) with a trailing newline is plausible. Whitespace is
  container, not evidence; storing it gains nothing ("preserve original
  observations" protects the *position*, not padding).
- **Precedent:** 1.2's `normalizeConditionString` trims at the contract
  boundary (`session_conditions.js`). The 1.4 factories should do the
  same: store `input.fen.trim()` (after `requireValidFen` passes).
  Alternatively reject untrimmed input in `requireValidFen` — but
  trim-and-store is friendlier and matches 1.2.
- **Fix:** trim the FEN in `createGameStartedPayload` and
  `createPositionCheckpointPayload` before storing; add a test asserting
  the stored payload is the trimmed canonical-whitespace string.
  `requireValidFen`/`isFen` behavior (trim-for-check) can stay.

*The reviewer also checked the reverse direction: inputs the vendored
validator accepts but ours rejects (`+1`/`1.5` halfmove clocks). Ours is
strictly narrower there — benign caller-error detection, no replay
hazard. Document the deliberate difference; no change needed.*

## NOTE findings (no change required, recorded for the record)

### NOTE-1 — Extra-input-key inconsistency: 1.4's choice is acceptable; the test comment misstates 1.2

- `tests/game_records.test.js:102` comments that factories ignoring extra
  input keys is "the 1.1/1.2/1.3 convention". That is **factually wrong
  about 1.2**: `session_conditions.js` `createInitialConditions`
  *rejects* unexpected keys (`TypeError: 'unexpected condition field'`,
  a documented 1.2 builder deviation). The true convention is: 1.1
  (`createSessionMetadata`) and 1.3 (`createEvent`, `createClockAnchor`)
  ignore extras on input; 1.2 rejects; all validators enforce exact keys
  on records.
- **Decision (as instructed): 1.4's lenient-on-input / strict-on-record
  is ACCEPTABLE, no change.** Justification: (a) it matches the 2-of-3
  majority convention; (b) the fail-loud boundary is preserved —
  `requireValid*` rejects extra keys on the record itself, so nothing
  malformed reaches storage; (c) the realistic hazard (a typo'd key like
  `promocion` silently dropped) is contained because §3.x emitters are
  written directly against this contract and covered by V3 behavioral
  verification; (d) forcing all-strict would retroactively rewrite the
  locked 1.1/1.3 contracts, and forcing all-lenient would rewrite locked
  1.2 — both out of scope ("do not refactor unrelated"). 1.2's strictness
  has its own rationale (a fixed 7-field schema where a missing *or*
  extra field signals caller/schema mismatch).
- **Action:** fix the inaccurate comment (test line 102 and the echo in
  the build report) to say "the 1.1/1.3 convention" rather than
  "1.1/1.2/1.3". Documentation-only.

### NOTE-2 — Suffix-retraction stress test: rule survives; worst case is conservative over-retraction

I attempted to construct a realistic same-length correction that does
*not* require retracting the full suffix:

- **Case A (SAN change at ply k, later SANs textually identical):**
  fails — plies k+1…N were SAN→coordinate-converted through the *old*
  board state; disambiguation (e.g. `Nd7` resolving to a different
  knight) can change coordinates even when SAN text is unchanged, so the
  old coordinate records are untrustworthy without re-derivation. Full
  suffix retraction is the honest rule.
- **Case B (annotation-only change, e.g. `Nf3` → `Nf3+`):** the rule
  over-retracts (coordinates would re-derive identically), but the
  outcome is conservative, not incorrect — no fabrication, replacements
  carry identical coordinates. Wasteful, not wrong.
- **Case C (change at the final ply):** suffix of length 1; rule
  degenerates correctly.

**Conclusion:** no realistic case was found where the suffix rule
produces *incorrect* data. The contract's escalation path (contract §8:
report with DOM evidence, do not silently switch to in-place rewriting)
is the right call for any genuinely unworkable future case. The
contract-layer honesty about its limits ("validates shape only; the
suffix rule is §3.1's to enforce", contract §2.5.2) is exactly right.

### NOTE-3 — Checkpoint gate: documentary-only is inherent, and the wording cannot be read as routine permission

The gate (`game_records.js:61-78`) is enforceable only in prose — the
contract layer cannot see the event stream, so no code *could* enforce
"replay from game_started FEN and from the last checkpoint both fail".
That is a scope truth, not a defect. The wording is strong
("a checkpoint without a recorded sync failure is a defect, not a
recovery"; "must never paper over a bridgeable gap"; "Frequent
checkpoints indicate an instrumentation bug"). **Recommendation for the
coordinator:** carry the gate explicitly into the §3.1 emitter task's
contract and the §6.1 coverage task (same handoff pattern as AC24's
vocabulary-table note), so the documentary gate is re-checked where
emission and export actually happen.

### NOTE-4 — 1.4 declares obligations on §6.1 (conflict rule; defect-flag surfacing)

The module header pins two §6.1 behaviors: "if metadata.json's FEN ever
disagrees with the `game_started` event, the event wins" and "any export
containing a `position_checkpoint` … MUST surface it in §6.1's
collection coverage/completeness as a defect flag". Both are reasonable
inferences from PLAN §3(a)'s "collection coverage/completeness" row, but
they are decisions *about* §6.1 made by task 1.4. No code impact today;
the §6.1 reviewer must re-confirm them rather than inheriting them
blindly.

### NOTE-5 — "Latest by occurrence time" (game_ended, contract §2.7) is loose phrasing

Multiple `game_ended` events are ordered by "occurrence time", but
`monotonicMs` is only comparable within a clock segment; cross-segment
ordering requires 1.3's `deriveWallUtcMs`. Suggest the §3.5/§6.1
contracts say "latest by envelope time (wall-derived)" to avoid a
future consumer comparing raw `monotonicMs` across segments. No 1.4
code change (1.4 stores no time at all — correctly).

### NOTE-6 — `node --test tests/` (directory mode) fails spuriously; per-file runs pass

All 215 tests pass per-file (47 + 91 + 47 + 30, 0 failures). The bare
directory invocation reports `test at tests:1:1 / 'test failed'` — a
node runner artifact unrelated to 1.4 (it predates this task's files in
behavior; the mission documents per-file invocation). Not a 1.4 defect;
noting so the coordinator doesn't misread it as a regression.

### NOTE-7 — AC9 oracle shares the contract's encoding assumption (residual, accepted)

The chess.js replay oracle genuinely proves the payload *encoding*
(lowercase promotion, king-from/to castling, pawn-from/to en passant)
is consumable for SAN derivation — a wrong convention would fail loudly
(e.g. uppercase promotion, `e1→h1` castling). It does *not* prove the
future §3.1 SAN→coordinate converter is correct; that is §3.1/§7.2's
explicitly deferred V3 job. The test and contract both document this
boundary honestly. No change.
