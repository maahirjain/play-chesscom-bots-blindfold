# 5.6 contract — Show readiness only after required media streams have started and an initial storage write has succeeded

## 1. Scope

PLAN.md §5.6: "Show readiness only after required media streams have started and an initial storage write has succeeded."

This closes the gap the 5.1 contract recorded as 5.6-owned: "5.1's lights
are facts-only; 5.6 owns the required-set policy and readiness
presentation." It also answers the section-4 audit carry-forward:
"'Required streams' policy is §5's, not 4.14's (4.14 reports facts; §5
applies its required-set) — §5.6 readiness gating consumes 4.14's
status."

**PLAN evidence:** §(c) "Each game", step 4: "Wait for the microphone,
screen, webcam, and saving indicators to show ready." The user must be
able to tell when it is safe to start playing — i.e., when the
recording is actually capturing. Currently (5.1–5.5), the button flips
to "Stop" and phase becomes ACTIVE as soon as `recorder-start-streams`
answers, but per-stream failures do not abort Start (4.6 isolation) and
no storage write has been confirmed. The user has no explicit "ready"
signal and may start playing before capture is actually running.

**What 5.6 does NOT do:** it does not gate the session itself. The
session becomes active when start-streams answers (5.1's existing
behavior, preserved). 5.6 adds an explicit, honest readiness
presentation: the UI must not claim "ready" until the conditions below
hold, and must honestly show *why not* when they don't.

## 2. Readiness definition

### 2.1 Required streams (the §5 policy)

The required set is **all three stream kinds**: `microphone`,
`screen`, `webcam`.

Rationale:
- PLAN §(c) step 4 names exactly these three plus saving.
- 4.6 always attempts all three (system default device when no
  selection); there is no "opt out of a stream" in the current
  selection UI.
- 4.14 reports per-stream facts; §5 applies the required-set. This
  contract is where the policy lives.

### 2.2 "Started" (per stream)

A required stream counts as started when **both** hold, derived from
the 4.14 `recorder-get-status` response via the existing 5.1
`classifyStreamStatus`:

- 4.14 `lifecycle` is `'recording'` for the stream, **and**
- 5.1 classification is `'recording-healthy'` (no adverse facts).

A `'recording-degraded'` stream (e.g., muted track, chunk stall,
recorder error) is recording but not healthy — it does not count as
ready. Rationale: a muted microphone or stalled chunk loop will not
capture the game; claiming "ready" would be the masquerade 4.14
exists to prevent. The light already shows the degradation; readiness
additionally withholds the "ready" claim.

`'failed-not-started'`, `'off-idle'`, `'unknown'` never count as
started. `'stopped-finalizing'` / `'finalized'` are post-recording
states and cannot occur before Stop in the normal flow.

### 2.3 "Initial storage write has succeeded"

The event-storage pipeline (2.3 sender → 2.4 SW transactional writer)
has durably acknowledged **at least one event since Start**, with no
persistent write error.

Concretely, observed via the content-script sender's `getStatus()`
(the same surface 2.8's saving indicator uses):

- `lastError` is null or transient-only (no `'write-failed:*'`
  persistent family), **and**
- at least one event emitted since Start has been acknowledged by the
  writer (queue drained the initial events).

The builder determines the exact mechanism (e.g., tracking the
page-start event's ack, or observing pendingCount drain to zero after
Start with no error). The mechanism must be honest: it must reflect
an actual writer acknowledgment, not the mere act of sending. A
missing or ambiguous signal degrades to "not ready (storage
unknown)", never to a premature "ready".

Note: 5.2's `session-save` `{ok:true}` is a confirmed metadata write,
but it is not the "initial storage write" for 5.6's purpose — 5.6
concerns the ongoing event/media pipeline the user depends on during
play, which the 2.8 saving indicator monitors.

### 2.4 Readiness verdict

Readiness is a pure function of (stream statuses, sender status,
start observations). The verdict is one of:

- `'ready'` — all three required streams are `recording-healthy`
  AND the initial storage write has succeeded.
- `'not-ready'` — with the specific reasons (which streams are not
  started/healthy, whether storage is unconfirmed). Reasons are raw
  facts, not smoothed.
- `'unknown'` — the status query itself failed or returned malformed
  data. Unknown is unknown; never default to ready.

## 3. Where readiness lives

**`session_controls.js` owns the readiness policy** (audit
carry-forward). Concretely:

- A pure, unit-testable `computeReadiness(streamStatuses,
  senderStatus, startResults)` function (new; follows the
  `classifyStreamStatus` precedent: no DOM, no timers, no chrome.*).
  Inputs are the already-available shapes: the 4.14 per-stream status
  objects (17-key), the sender's `getStatus()` object, and the
  per-stream start results 5.1 already remembers (`lastStartResults`).
- The existing poll loop (`pollOnce`) feeds it: after applying the
  per-stream statuses, compute readiness and update the readiness
  presentation. No new poll cadence; no new channel messages.
- 4.14's `stream_status.js` is untouched (it reports facts; §5
  applies policy). 2.8's `status_indicator.js` is untouched (it keeps
  showing sender health; 5.6 reads the same sender surface).

## 4. UI presentation

### 4.1 Before readiness (starting → waiting)

After Start succeeds (phase ACTIVE under 5.1's definition), the
readiness presentation shows **"Waiting for recording…"** (builder
chooses exact wording; it must not say "ready") until the verdict is
`'ready'`. The per-stream lights continue to show their truthful
states (5.1 behavior unchanged).

### 4.2 When ready

When the verdict becomes `'ready'`, the presentation shows **"Ready —
recording"** (or equivalent). This is the signal PLAN §(c) step 4
tells the user to wait for. The transition is latched per session:
once ready, it stays "ready" for the session (a later degradation
still shows on the per-stream lights via the existing poll; the
readiness badge does not flap — the "initial" conditions were met).

Rationale for latching: 5.6 gates the *initial* readiness claim
("only after ... has succeeded"). Ongoing health remains the lights'
job (5.1) and the saving indicator's job (2.8).

### 4.3 When not ready (honest reasons)

If a stream fails to start or degrades before readiness is achieved,
the presentation names the blocker honestly, e.g. "Not ready:
webcam failed to start (start-failed:...)". The user may Stop and
retry, or continue knowing the recording is incomplete (4.6
isolation is preserved — 5.6 never aborts or blocks the session).

If the status query fails, show "Recording status unknown" —
never a premature "ready".

### 4.4 What does NOT change

- The Start/Stop button behavior (5.1): "Stop" appears when the
  session is active, regardless of readiness. Readiness is
  informational; it does not gate Stop (the user can always stop).
- The per-stream lights (5.1): unchanged classification and rendering.
- The 2.8 saving indicator: unchanged.
- Boot adoption: an adopted session's readiness is computed the same
  way from the first poll (no start-results memory → a never-started
  stream reads honestly, per 5.1's existing rule).

## 5. Acceptance criteria

### V1 — static/unit

- [ ] **AC1.** `computeReadiness` returns `'ready'` only when all
  three streams classify `recording-healthy` AND sender shows ≥1 ack
  with no persistent write error. Unit pins for each input
  combination.
- [ ] **AC2.** A `recording-degraded` stream (adverse facts present)
  yields `'not-ready'` with the stream named — degraded never counts
  as started.
- [ ] **AC3.** `failed-not-started` / `off-idle` / `unknown` stream
  states yield `'not-ready'` (or `'unknown'` when the query itself
  failed), each with honest reasons.
- [ ] **AC4.** Sender `lastError: 'write-failed:*'` (persistent) or
  zero acknowledged writes yields storage-not-ready; the verdict is
  never `'ready'` on ambiguous storage signal.
- [ ] **AC5.** The readiness presentation transitions waiting →
  ready exactly once per session (latched); it never shows "ready"
  before the verdict is `'ready'`.
- [ ] **AC6.** Diff discipline: changed files exactly the §7 list;
  no new channel messages; no new event types; no new stores; no new
  permissions; PLAN.md unmodified.

## 6. Explicit non-goals

- Gating or blocking the session on readiness (the session is active
  once start-streams answers; 5.6 is presentation-only).
- Auto-retrying failed streams or re-requesting permissions.
- Changing 4.14's status shape or 2.8's indicator.
- A new "I am ready, let me play" confirmation button or any new
  user action.
- Per-stream "required" configurability (the required set is fixed
  at all three by this contract).
- 5.7's post-game reflection, 5.8's note marker, 5.9's game
  boundaries, 5.10's finalization gating.

## 8. Open questions for the builder

1. **Storage-ack mechanism:** the exact way to observe "≥1 event
   acknowledged since Start" from the content-script sender without
   modifying `sender.js`. If no honest mechanism exists without a
   sender change, the builder must say so explicitly rather than
   faking it — a minimal, additive sender affordance (e.g., an ack
   counter in `getStatus()`) is preferable to an inferred signal,
   but it widens the diff and needs reviewer approval.
2. **Presentation surface:** whether readiness is a text badge, a
   fourth light state, or button-adjacent text — builder's choice,
   subject to "must not say ready prematurely" and the existing DOM
   conventions.
