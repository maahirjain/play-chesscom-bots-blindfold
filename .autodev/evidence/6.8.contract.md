# 6.8 contract — Document that the user extracts ZIPs into the experiment directory; do not assume arbitrary filesystem write access

## 1. Scope

PLAN.md §6.8: "Document that the user extracts ZIPs into the experiment directory; do not assume arbitrary filesystem write access."

**PLAN evidence:** §(c) "Each game", step 9 (implied): after downloading the game ZIP, the user extracts it into their experiment directory for analysis. The extension itself never writes to the user's filesystem — it only offers a download via `chrome.downloads` (6.6), and the browser places it in the user's configured download location.

**What 6.8 does:** Write the user-facing export documentation: where the ZIP goes, how to extract it, what the bundle contains, how to re-export after an interrupted download, and what the extension explicitly does NOT do (arbitrary filesystem writes).

**What 6.8 does NOT do:** It does not change the extension's behavior. It does not add filesystem access. It does not modify the README's existing gameplay documentation (7.14 owns the full README update; 6.8 writes the export section that 7.14 will integrate).

## 2. Documentation content

The documentation must cover:

1. **Where the ZIP goes.** The extension triggers a download via the browser's download manager (`chrome.downloads.download` with `saveAs: false`). The ZIP lands in the user's configured download location (usually `~/Downloads`). The extension does not choose the location and does not write anywhere else.
2. **What the user does with it.** The user extracts the ZIP into their experiment directory (the directory where they keep their blindfold-chess experiment data). The ZIP contains a single top-level directory `<category>/<YYYY-MM-DD>_<gameId>/` (or `<category>/<YYYY-MM-DD>_session-<sessionId>/` for multi-game sessions).
3. **What's inside the bundle.**
   - `metadata.json` — session identity, conditions, completion status, media inventory.
   - `events.jsonl` — the full event stream in persistent append order, one JSON object per line.
   - `media-sync.json` — media filenames, formats, clock anchors, segment offsets, known gaps.
   - `microphone-NNN.webm`, `screen-NNN.webm`, `webcam-NNN.webm` — the assembled original-format media files (numbered per 6.5).
4. **Re-export after interruption.** If the download is interrupted, click the Download button again — the export is rebuilt from retained local data (6.7). No cleanup needed.
5. **What the extension does NOT do.**
   - It never writes to arbitrary filesystem paths. It has no filesystem access beyond offering a download.
   - It never deletes or modifies the stored recording data on export (readonly).
   - It never uploads, syncs, or backs up the bundle anywhere. The user copies the ZIP to their backup location.

## 3. Where the documentation lives

**New file `EXPORT.md` in the repo root.** Rationale:

- The existing `README.md` is gameplay-focused (keyboard shortcuts, Chess.com settings, move input). The export workflow is a separate concern for the experiment/recording use case.
