# Task 2.2 Contract — Extension-owned IndexedDB database for metadata, events, and media chunks

## 1. Scope

PLAN.md §2.2 says (quoted verbatim):

> 2.2. Create an extension-owned IndexedDB database for metadata, events, and media chunks; do not use Chess.com's localStorage for experiment records.

This task creates the **database and its schema plus the minimal storage
API** that tasks 2.3–2.9, §4, and §6 will build on. It does **not** write
events (2.4), send them (2.3), retry them (2.5), restore state after restart
(2.6), emit lifecycle events (2.7), surface status (2.8), retain/export (2.9,
§6), or validate records against the Section-1 contracts (validation is the
writer's job, §2.4).

Downstream shape requirements (investigator-verified from PLAN + contracts):

| Consumer | Needs from the DB |
|---|---|
| 2.4 writer | store envelopes keyed by `eventId` (dedup by event ID, PLAN §2.4); durable slot for the per-session `appendSeq` counter it assigns (1.3 §2.8) |
| 2.6 restore | read back session metadata + sequence state after SW restart (PLAN §2.6) |
| 4.8 / 4.10 | save recorder chunks incrementally, keyed by recording-segment ID (§4.8, §4.10: "Give every recording segment an ID") |
| 6.1 metadata.json | session metadata (1.1 shape), initial conditions (1.2 shape), game starting FEN |
| 6.2 events.jsonl | per-session events in persistent `appendSeq` order ("in persistent append order without computed metrics") |
| 6.3 / 6.4 / 6.5 | chunk inventory per segment (mimeType, byteLength) for assembly; numbered segments for interrupted recordings |

"Do not use Chess.com's localStorage for experiment records": the DB lives in
the **extension service worker's origin** (`chrome-extension://<id>`), never
in the page's origin. (Pre-existing `localStorage["blindfold_chess_piece_set"]`
in content.js is gameplay UI state, not an experiment record — out of scope,
untouched.)

## 2. Design decisions

### 2.1 Database identity

- **Name:** `blindfold-experiment`
- **Version:** `1`
- **Owner:** the extension service worker. IndexedDB is origin-scoped, so a
  database opened in the SW is invisible to `https://www.chess.com` pages and
  to content scripts (different origins) — this *is* the "extension-owned"
  guarantee. No manifest permission is required (verified: SW `indexedDB`
  works with zero permissions; probe 2026-10-06).

### 2.2 Module layout: `db.js` + one `importScripts` line in `sw.js`

- New file `db.js` at repo root: plain dependency-free script, guarded
  `BlindfoldSession` global, IIFE `'use strict'`, Node `module.exports`
  shim (Section-1 precedent). It is **IndexedDB-specific** (unlike the pure
  contract modules) and only ever loaded in the SW.
- `sw.js` gains exactly one functional line: `importScripts('db.js');`
  (plus the 2.2 line removed from its "intentionally absent" header). This
  matches the pattern the 1.1 contract anticipated
  ("MV3 service worker: loaded via `importScripts('session_identity.js')`").
- **No `importScripts` of the Section-1 contract modules in 2.2.** `db.js`
  stores plain records and performs no envelope/metadata validation;
  validation at write time is §2.4's design (1.3 §2.8: "the writer owns that
  rule"). This keeps 2.2 load-order independent and minimal. The 2.4 contract
  may add validation imports.
- `db.js` must read `globalThis.indexedDB` **lazily (per call), never cached
  at load time**: (a) V1 tests simulate unavailability by deleting the global;
  (b) the module must load in Node (where `indexedDB` is undefined) without
  throwing.

### 2.3 Schema (declared as data)

The schema is a frozen `SCHEMA` constant — `{dbName, version, stores[]}` —
so V1 tests assert the schema **statically** without IndexedDB, and
`openDatabase()` consumes it (single source of truth, no drift).

Five object stores. Each is justified; none is speculative:

| Store | keyPath | Indexes | Holds | Justification |
|---|---|---|---|---|
| `events` | `eventId` | `bySessionId` → `sessionId` (non-unique); `byAppendSeq` → `appendSeq` (non-unique) | Frozen 11-key envelopes (1.3) | keyPath = PLAN §2.4 dedup key; `bySessionId` = per-session reads/export (§6.2 per-game bundles); `byAppendSeq` = §6.2 "events.jsonl in persistent append order" |
| `session_metadata` | `sessionId` | none | 1.1 `SessionMetadata` record verbatim | PLAN §2.6 restore; §6.1 metadata.json IDs/versions/category. Separate store preserves 1.1's exact-six-keys validation (a merged container would break it). |
| `conditions` | `sessionId` | none | 1.2 `SessionConditions` record verbatim | §6.1 "initial conditions; observed/manual sources". Separate store mirrors the module split. |
| `sequence_state` | `sessionId` | none | `{sessionId, nextAppendSeq}` (integer ≥ 0) | Durable slot for the counter §2.4 assigns and §2.6 restores. 2.2 defines the slot only; assignment protocol is §2.4's. |
| `media_chunks` | `['segmentId','chunkIndex']` (compound) | none | `{segmentId, chunkIndex, mimeType, byteLength, data}` (`data` = Blob) | §4.8 incremental chunk saving; §4.10 segment IDs; §6.4 ordered assembly via compound-key prefix range; §6.5 numbered segments. `mimeType`/`byteLength` support §6.3/§6.4 manifest decisions without reading blobs. No `receivedAt`: §4.12 forbids using chunk-arrival time as frame time. |

Deliberately absent: a `byGameId` index (export filters `gameId` in JS —
§6.x's choice, not §2.2's); a generic kv store (each record type keeps its
contract shape in its own store); per-chunk `chunkId` (compound key already
orders and scopes chunks; no dedup requirement exists for chunks).

### 2.4 Upgrade / migration discipline

- `onupgradeneeded` creates every store/index in `SCHEMA` **idempotently**
  (guard each with `objectStoreNames.contains` / `indexNames.contains`).
- Future schema changes: bump `DB_VERSION`, add guarded creation/migration
  steps keyed on `oldVersion` in the same handler. **Never delete user data
  in an upgrade** (PLAN §2.9: records live until deliberate deletion).
- `onblocked` → the open promise rejects with a plain `Error` (caller
  decides; surfacing is §2.8's).

### 2.5 Minimal public API (`BlindfoldSession.DB`)

All async methods return Promises. Each `put`/`get` uses its own
single-store transaction — §2.4's multi-operation transactions are that
task's design, not this one's.

| Signature | Behavior |
|---|---|
| `DB_NAME`, `DB_VERSION`, `SCHEMA` | Frozen constants (schema-as-data). |
| `openDatabase()` → `Promise<IDBDatabase>` | Opens `DB_NAME` at `DB_VERSION`, runs the idempotent upgrade. Rejects plain `Error` if `indexedDB` unavailable or open fails. |
| `put(storeName, record)` → `Promise<void>` | `readwrite` put of one record. Unknown `storeName` → `RangeError`; non-object `record` → `TypeError`. IDB errors (incl. `QuotaExceededError`) → plain `Error` wrapping the DOMException name. |
| `get(storeName, key)` → `Promise<any\|undefined>` | `readonly` get. Same `storeName` validation. |
| `getAll(storeName, options?)` → `Promise<Array>` | `readonly` read. `options = {index, lower, upper}` opens a key range on the named index (used by §6.2 appendSeq-order reads and §6.4 per-segment chunk reads). Unknown index → `RangeError`. |
| `closeDatabase()` → `void` | Closes the cached handle (test/reload hygiene). |

No `deleteDatabase()` in `db.js` — V2 tests call
`indexedDB.deleteDatabase(DB_NAME)` directly in the harness. No transaction
runner, no `count()`, no validation helpers: not needed yet.

### 2.6 Error conventions (AGENTS.md)

- `indexedDB` undefined / `indexedDB.open` not a function → plain `Error`
  ("unavailable platform capability" — never a fallback store; a silent
  in-memory fallback would violate "preserve original observations" by
  risking silent data loss).
- Unknown store/index names → `RangeError` (value outside the allowed
  domain, per the 1.3 DECISIONS.md ruling).
- Wrong types (non-object record, non-string store name) → `TypeError`.
- IDB request/transaction failures → plain `Error` carrying the underlying
  `DOMException` name/message. Quota errors are *reported* this way; the
  §2.8 status indicator is a later task.

## 3. Exact deliverables

### 3.1 New file: `db.js` (repo root)

Full required contents (builder implements exactly this):

- Header comment: what the module is, the five stores and why (one line
  each), what is intentionally absent (2.3–2.9 list), the lazy-`indexedDB`
  rule, the never-delete-in-upgrade rule.
- `'use strict';`, guarded `BlindfoldSession` global, IIFE, Node shim.
- Frozen `SCHEMA`, `DB_NAME = 'blindfold-experiment'`, `DB_VERSION = 1`.
- `openDatabase`, `put`, `get`, `getAll`, `closeDatabase` per §2.5.
- No `chrome.*` references. No `localStorage` references. No imports of
  Section-1 modules.

### 3.2 Modified file: `sw.js`

Diff: add `importScripts('db.js');` after the header comment (before
`'use strict';` — actually `importScripts` must run in the worker scope;
place it after the header comment block, keep `'use strict';` first line
per the 2.1 stub), and remove the `2.2:` line from the "Intentionally
absent" list. Nothing else.

### 3.3 New test: `tests/db.test.js` (`node --test`, no framework)

V1 only (no IndexedDB in Node — by design):

- `SCHEMA` deep-equals the §2.3 table (db name, version, all five stores,
  keyPaths, index names/keyPaths/unique flags). Any schema drift fails here.
- API surface: `openDatabase`/`put`/`get`/`getAll`/`closeDatabase` are
  functions; `DB_NAME`/`DB_VERSION`/`SCHEMA` frozen.
- Unavailable platform: with `globalThis.indexedDB` deleted,
  `openDatabase()` rejects a plain `Error` (assert `!(e instanceof
  TypeError)` and `!(e instanceof RangeError)`); module still loads.
- `put('nope', {})` → `RangeError`; `put('events', 42)` → `TypeError`;
  `getAll('events', {index: 'nope'})` → `RangeError`. (These run without a
  real IDB by validating arguments before touching `indexedDB` — the
  implementation must order validation first.)
- Static: `db.js` contains no `localStorage`, no `chrome.`; `sw.js` diff
  contains only the `importScripts` line + header update; `manifest.json`
  byte-identical to HEAD (IndexedDB is permissionless — no manifest change).

## 4. Acceptance criteria

- [ ] **AC1 (V1).** `SCHEMA` matches §2.3 exactly: name
      `blindfold-experiment`, version 1, five stores with the specified
      keyPaths; `events` has indexes `bySessionId` and `byAppendSeq`
      (both non-unique); all constants frozen.
- [ ] **AC2 (V1).** Public API per §2.5 exists with the specified
      signatures; `db.js` loads in Node with `indexedDB` undefined (no
      throw at load); no `chrome.*` / `localStorage` references.
- [ ] **AC3 (V1).** Error contract: unavailable `indexedDB` → plain
      `Error`; unknown store/index → `RangeError`; wrong types →
      `TypeError`. Argument validation happens before any IDB access.
- [ ] **AC4 (V1).** `sw.js` diff = `importScripts('db.js');` + 2.2 header
      line removed, nothing else; `manifest.json` byte-identical to HEAD.
- [ ] **AC5 (V2).** In the real extension SW (puppeteer harness,
      `ignoreDefaultArgs: ['--disable-extensions']` per DECISIONS.md #7):
      `openDatabase()` creates all five stores and both indexes (assert via
      `db.objectStoreNames` / `indexNames`); `put`/`get` round-trip in every
      store (events: synthetic envelope; media_chunks: small Blob —
      `byteLength` intact); close + reopen is idempotent and preserves data.
- [ ] **AC6 (V2).** Origin isolation: a page-context
      `indexedDB.databases()` does not list `blindfold-experiment`
      (extension-owned, not page-visible).
- [ ] **AC7 (V1/V2 regression).** All Section-1 + 2.1 suites pass
      unchanged; SW still loads clean (re-run `sw-load.js`).
- [ ] **AC8 (V4, deferred).** Owner-device: database persists across real
      browser restarts; storage-pressure behavior sane. Cannot be verified
      in the ephemeral headless harness.

V3 is not applicable: 2.2 adds no page-facing behavior.

## 6. Explicit non-goals (builder must NOT)

- Event writer, dedup-by-eventId logic, write acknowledgments, `appendSeq`
  assignment (2.4).
- Content-script sender/queue (2.3); any content-script changes.
- Retry logic (2.5); restore-after-restart logic (2.6 — only the stores it
  will read); lifecycle/start/end event emission (2.7); status indicator
  (2.8); retention/export (2.9, §6).
- Envelope/metadata validation in `db.js` (no Section-1 imports).
- `deleteDatabase`, transaction runner, `count()`, or other speculative
  helpers.
- Manifest changes (none needed). Version bump (not needed).
- `localStorage` for anything. In-memory fallback stores.

## 7. Downstream needs this contract must serve

- 2.4: `events.put` keyed by `eventId` (dedup = get-then-put); `put` +
  `get` on `sequence_state` for the counter; assigns `appendSeq` (2.2
  stores whatever record it is given).
- 2.6: `get('session_metadata', sessionId)`, `get('conditions',
  sessionId)`, `get('sequence_state', sessionId)` after restart.
- 4.8: `put('media_chunks', {segmentId, chunkIndex, mimeType, byteLength,
  data})` per chunk.
- 6.2: `getAll('events', {index: 'bySessionId', lower/upper: sessionId})`
  then `appendSeq` ordering (or `byAppendSeq` range + session filter —
  6.x's choice).
- 6.4: `getAll('media_chunks', {lower: [segmentId, 0], upper:
  [segmentId, Infinity]})` — ordered assembly. (IDBKeyRange.bound with
  array keys; the harness probe verified compound keyPaths work.)

## 8. Reviewer notes

- If a reviewer argues for a sixth store, a generic kv store, or a
  `byGameId` index: reject unless they show a §2.2 requirement it serves.
  Every store/index above traces to a quoted PLAN/contract requirement;
  speculative schema is the failure mode here.
- If a reviewer argues `db.js` should validate envelopes: reject — 1.3
  §2.8 assigns validation + `appendSeq` to the §2.4 writer; a validating
  2.2 would need the Section-1 imports and create the load-order coupling
  2.2 was designed to avoid.
- If a reviewer argues for `fake-indexeddb` as a test dependency: reject —
  the repo is dependency-free by decision; schema-as-data gives V1 full
  schema coverage statically, and V2 covers real IDB behavior in the SW.
  A fake would test the fake's fidelity, not our code.
- Empirical risk to stress-test: compound keyPath `['segmentId',
  'chunkIndex']` on `media_chunks` and Blob storage in the SW — AC5
  settles both against real Chrome.
