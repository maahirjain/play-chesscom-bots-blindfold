# Task 2.9 contract — retention: keep saved records until deliberate deletion; export must not delete the originals

PLAN.md §2.9 (human-owned, quoted verbatim): "Keep saved records until deliberate
deletion; export must not delete the originals."

## 1. Scope

This is a **small, primarily negative task**. A codebase survey (2026-10-06)
found **zero deletion paths** in product code:

- No `indexedDB.deleteDatabase` call anywhere.
- No `objectStore.clear()` or `objectStore.delete()` call anywhere.
- No TTL, expiry, pruning, compaction, or retention-window logic.
- `db.js` `closeDatabase()` closes the connection handle only; it does not
  delete data.
- The only `localStorage` uses (`content.js` piece-set key) are pre-existing
  gameplay code, unrelated to experiment data.

There is **no export feature yet** (§6 owns export). There is **no deletion
API**, and PLAN.md mentions deletion nowhere else (single occurrence: §2.9
itself).

## 2. Design decisions

### 2.1 No new deletion API

2.9 does **not** add `deleteSession`/`deleteAll`/prune APIs. Rationale:

- PLAN never requests deletion functionality; "until deliberate deletion"
  is a retention guarantee, not a feature request.
- A deletion API is new footgun surface (accidental invocation destroys the
  raw data this whole mission exists to preserve). The mission's bias is
  toward keeping data.
- "Deliberate deletion" = an explicit owner/developer action **outside the
  extension** (e.g. browser devtools → Application → IndexedDB → delete;
  profile wipe). This is documented, not implemented.

If the owner later wants in-extension deletion, that is a §7/owner decision,
not 2.9 scope.

### 2.2 "Export must not delete the originals" = architectural constraint for §6

With no export code to test, 2.9's contribution is a **binding constraint**
that §6 builders must obey, plus a forward test obligation:

- §6 export must read through **readonly** transactions/cursors only
  (`db.js` `getAll`/`get` with `'readonly'` mode).
- §6 export must never call `delete`, `clear`, or `deleteDatabase`.
- §6.7 ("repeatable export from retained local data") already implies
  non-destructiveness; §6's test suite must assert store record counts are
  **identical before and after export** (the concrete, testable form of
  "export must not delete the originals").

### 2.3 What 2.9 proves

1. **No auto-deletion exists** — static scan over product code (V1 test).
2. **Close ≠ delete** — `closeDatabase` is connection-only (V1 test).
3. **Records survive restarts** — already proven by the 2.6/2.7 harnesses
   (sw-restart two-launch gapless 0–9; sw-lifecycle); 2.9 re-runs sw-restart
   as its V2 rather than re-proving.
4. **The constraint is written down** where §6 builders will find it
   (this contract + a DECISIONS.md entry).

## 3. Changes

- **New:** `tests/retention.test.js` (V1 static-scan tests; no product code
  under test beyond what exists).
- **Modified:** `.autodev/DECISIONS.md` (one entry: the §6 export
  non-destructiveness constraint + no-deletion-API decision).
- **No product code changes.** No new modules, no API additions, no manifest
  changes.

## 4. Acceptance criteria

### V1 (static / Node)

- [ ] **AC1.** Static scan: none of the product files
  (`db.js`, `writer.js`, `session_store.js`, `lifecycle.js`, `sender.js`,
  `status_indicator.js`, `sw.js`, `content.js`) contain
  `deleteDatabase`, `.clear(`, `.delete(`, `TTL`/`ttl`, `expir`, or `prune`
  (case-sensitive token scan; `settled` must not false-positive).
- [ ] **AC2.** `db.js` `closeDatabase` closes the cached handle and nulls it;
  it performs no IDB write/delete (code-shape assertion).
- [ ] **AC3.** The five object stores still exist with the 2.2 schema and no
  store carries retention metadata (no `expiresAt`/`ttl` fields in SCHEMA).
- [ ] **AC4.** Diff discipline: `git status` shows only
  `tests/retention.test.js`, `.autodev/evidence/2.9.*`, `.autodev/DECISIONS.md`,
  and the cumulative test-pin files the new test's allowlist legitimately
  extends. No product file modified.

### V2 (integration / real Chrome)

- [ ] **AC5.** `sw-restart.js` (repo path argv) PASS — records written in
  launch 1 are all present in launch 2 (retention across full browser
  restart, not just SW restart).

### V3 (deferred)

- [ ] **AC6.** Owner-device acceptance (§7): records persist across real
  device restarts; owner confirms no data loss over a multi-day span.

## 5. Non-goals

- §6 export implementation (only the constraint + forward test obligation).
- Any deletion API, UI, or pruning feature.
- TTL/retention-window policy (PLAN does not request one).
- Analysis, metrics, dashboards (standing mission rule).

## 6. Forward obligations for §6 (binding)

When §6 implements export, its contract must include: "Export performs
readonly reads only; store record counts before and after export are
identical (asserted in §6 tests)." This contract is the authority for that
requirement.
