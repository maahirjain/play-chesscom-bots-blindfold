# 5.5 contract — Prevent a duplicate Start from creating overlapping recording sessions

## 1. Scope

PLAN.md §5.5: "Prevent a duplicate Start from creating overlapping recording sessions."

This closes the interim gap the 5.1 contract recorded as 5.5-owned:
"between 5.1 and 5.5, a second tab's set-session could overwrite the
active session identity". 5.1 provides the tab-local interlock and the
`ownerTabId` capture; 5.5 adds the cross-tab refusal policy.

**Architectural correction to the naive reading:** the
`recorder-set-session` handler lives in the **offscreen document**
(`recorder.js` `handleSetSession`, ~line 1502), not in SW-side
`recording_host.js`. The SW host handles `recorder-ensure`,
`session-save`, the capture broker, and the sync-flash relay; it holds
no session identity. The guard therefore lives in the offscreen
document, where `sessionId`/`gameId`/`ownerTabId` already live — this
is also where the authoritative session state survives a SW restart,
so no SW-restart recovery path is needed (see §4).

## 2. The refusal policy

### 2.1 Allow/refuse matrix (the whole policy)

The discriminator is **sessionId equality**, not tab identity. `tabId`
is recorded as forensic evidence (`ownerTabId`); it does not decide.

| Offscreen state | Incoming `sessionId` | Verdict |
|---|---|---|
| No active session (`sessionId` null/empty) | any, incl. `null` | **allow** — normal Start, or Stop-clear |
| Session `S` active | `null` | **allow** — the Stop-clear path (5.2) |
| Session `S` active | `S` (equal) | **allow** — idempotent re-set; 5.9's new-game-before-Stop drives set-session with the same sessionId + new gameId |
| Session `S` active | `S′ ≠ S` | **refuse** — `{ok:false, error:'session-active'}` |

Notes:

- A same-tab second Start with a *new* sessionId is refused exactly
  like a cross-tab one. The 5.1 tab-local interlock should prevent it
  first; the guard is defense in depth.
- On refusal nothing is overwritten: `sessionId`, `gameId`,
  `ownerTabId`, and `sessionCategory` keep their active values. The
  refusal is checked **before** any assignment.
- The refusal response carries no session details — just
  `{ok:false, error:'session-active'}`. Discretion: tab B learns only
  that a session is active, never whose sessionId or which tab.

### 2.2 Atomicity

The check-and-set is one synchronous block in `handleSetSession`:
read `isSessionActive()` and the current `sessionId`, decide, and only
then assign — with no `await`, promise, or callback between the check
and the assignment. JS's single-threaded message dispatch makes this
atomic against two tabs' racing set-session messages. A code-review
pin (V1) asserts no async gap: the guard sits directly above the
existing assignment lines and the function performs no asynchronous
work before them.

### 2.3 Layering (three guards, each with its job)

1. **5.1 tab-local interlock** (existing): Start is a no-op while this
   tab has an active session. First line of defense; unchanged.
2. **5.5 pre-check** (new, content side): after `recorder-ensure`,
   before minting, query `recorder-get-status` — but only when ensure
   reports the document already existed (`created:false`). A fresh
   document (`created:true`) cannot hold a session, so no round-trip
   is needed. If the status is `{ok:true, sessionId}` and this tab
   has no local active session (the interlock already passed), abort
   honestly **before minting, persisting, or messaging** — nothing
   minted, no `session-save`, no `set-session`. Detail:
   `duplicate-start:session-active` (see §5).
3. **5.5 atomic guard** (new, offscreen side): `handleSetSession`
   refuses per §2.1. This is the correctness arbiter that closes the
   pre-check's TOCTOU race. No new channel message; the vocabulary is
   unchanged (offscreen MSG_* stays 24, SW-side envelope stays 7).

4.6's `already-started` registry guard on `recorder-start-streams`
remains as a further backstop (streams can't start twice); 5.5's guard
fires earlier, at session-identity time.

### 2.4 What the pre-check must not break

- **Same-tab re-entrant flows:** the local interlock runs first; a tab
  with a local active session never reaches the pre-check.
- **Boot adoption:** adoption sets the local slots at install, so an
  adopted session is covered by the local interlock.
- **5.9's re-set:** 5.9 calls set-session directly with the *same*
  sessionId — it never goes through the Start sequence's minting path,
  so the pre-check doesn't see it; the atomic guard allows it per the
  matrix.
- **Stop-clear:** `set-session{null,null}` is allowed per the matrix.
- **get-status no-response in the pre-check:** if the document died
  between ensure and the query, it holds no session — proceed; the
  atomic guard remains the arbiter. (A dead document cannot have an
  active session by construction: session state is offscreen-local.)

## 3. What 5.5 builds

### 3.1 Offscreen guard (`recorder.js`, additive)

In `handleSetSession`, immediately after the existing request-shape
validation and before the `sessionId = sid` assignment:

```js
// 5.5: duplicate-Start guard. Refuse a *new* session while one is
// active; allow idempotent re-set (same sessionId, 5.9's game
// change) and the Stop-clear (null). Synchronous check-and-set —
// no async work between the check and the assignment below.
if (isSessionActive() && sid !== null && sid !== sessionId) {
  try {
    sendResponse({ ok: false, error: 'session-active' });
  } catch (e) { /* ignore */ }
  return false;
}
```

Everything else in the handler is unchanged, including the
`ownerTabId` capture (which now only runs on allowed sets — a refused
tab never becomes the owner) and the selection announcements.

### 3.2 Content-side pre-check (`session_controls.js`, additive)

In the Start sequence, between `recorder-ensure` and minting:

- If `ensureResp.created === true`: skip the pre-check (fresh
  document, no session possible).
- Else query `recorder-get-status`. If `{ok:true}` with a string
  `sessionId`: this tab passed the local interlock yet a session is
  active ⇒ duplicate Start. Abort honestly **before minting**:
  button back to idle Start, detail `duplicate-start:session-active`,
  fields stay enabled, nothing persisted, no further messages.
- `{ok:false}` or no-response: proceed to minting.

This requires moving ID minting after `recorder-ensure` in the Start
sequence (currently minting precedes ensure). The reorder is
5.5-scoped: interlock → validate selection → recorder-ensure →
pre-check → mint → build records → session-save → set-session →
start-streams → slots + emitPageStart + poll.

### 3.3 Refusal handling on the set-session leg

The existing set-session response handling already aborts honestly on
`{ok:false}` (`abortStart('set-session-failed:' + err)`). 5.5 maps the
`session-active` error to the user-facing detail
`duplicate-start:session-active` (same button/tooltip surface as other
aborts — raw codes, the 5.1 pattern). No new UI beyond the refusal
message.

## 4. SW-restart and document-restart analysis (no recovery path needed)

- **SW restarts, offscreen document survives:** the guard consults
  offscreen-local `sessionId`, which is intact. The pre-check's
  `recorder-get-status` is answered by the offscreen document, not
  the SW. No recovery logic required — this is *why* the guard lives
  offscreen rather than SW-side.
- **Offscreen document restarts (session state lost):** the guard
  correctly sees no active session and allows the new Start. The
  previous session's orphans are 4.13's crash-recovery territory
  (`finalized-orphans`), not 5.5's.
- **Race loser persisting metadata:** if two tabs race past the
  pre-check simultaneously, the loser's `session-save` may persist a
  metadata/conditions record before the atomic guard refuses its
  set-session. That record is kept as honest raw data — a refused
  Start attempt is an actual observed outcome (the mission's
  "preserve actual observations" principle; deletion would destroy
  evidence). §6 export must already tolerate sessions without media
  (4.6 isolation allows Start with all streams failed), so no new
  export burden.

## 5. B's UX (the refused tab)

- Start click → refusal (via pre-check or set-session) → button
  returns to idle "Start", detail text names the cause honestly:
  the user-facing form of `duplicate-start:session-active` (builder
  chooses the exact wording; it must say a recording is already
  active, not which tab or session).
- B mints nothing, persists nothing, sends no further recorder
  messages. B's fields stay enabled and editable.
- No polling for the other session's end (minimal — the user retries
  Start). No cross-tab session info displayed.

## 6. Boundaries

- 5.5 owns the refusal policy + pre-check + atomic guard. It does not
  change the local interlock, the Start/Stop sequences' other steps,
  or any record shape.
- 5.9 owns game-boundary detection and the same-session re-set call;
  5.5 only guarantees the re-set is allowed.
- No new channel messages, no new event types, no new stores, no new
  permissions.
- Changed files (exact): `recorder.js` (guard block only),
  `session_controls.js` (pre-check + mint reorder + refusal detail
  mapping only), tests, evidence, DECISIONS.md. Everything else
  byte-identical.

## 8. Explicit non-goals

- Cross-tab session *takeover* or handoff (no UI or protocol for
  moving a session between tabs).
- Showing tab B any details of tab A's session (title, sessionId).
- Polling/waiting for the active session to end.
- Deleting the race-loser's persisted metadata (kept as honest raw
  data; see §4).
- Any change to the local interlock, the 4.6 stream guard, or 4.13's
  crash recovery.
- 5.9's game-boundary logic itself.
