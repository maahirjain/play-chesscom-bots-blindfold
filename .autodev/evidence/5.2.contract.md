# 5.2 contract — Baseline/training/evaluation selection, with training approach and verbal scaffolding fields

## 1. Scope

PLAN.md §5.2: "Add baseline/training/evaluation selection, with training
approach and verbal scaffolding fields."

This is the second task of Section 5 ("Add minimal session controls").
5.1 built the in-page Start/Stop control + per-stream health lights;
sessions are currently minted with **category unknown** — 5.1 writes no
`session_metadata` record (5.1 build evidence, open question #1: no
SW-side session intake exists, content scripts cannot reach extension
IDB, and `createSessionMetadata` requires a category in
`{baseline,training,evaluation}` — no `'unknown'` exists, and
fabricating one would violate 1.2.3). **The metadata record (with
category) is 5.2's**, as is the initial conditions record for the two
fields PLAN §1.2.1 assigns to session start.

### 1.1 Field ownership — the eight-field form

The "stored eight-field form" (§2/§6 carry-forwards) is the seven
1.2 condition fields **plus the sessionId keyPath** under which the
record is stored (`{sessionId, ...sevenFields}` — session_store.js;
requireValidConditions tolerates the key). It is **not** seven fields
plus category: `sessionCategory` is 1.1 **metadata**, not a condition.

| # | Field | Owner | PLAN source |
|---|---|---|---|
| 1 | `sessionCategory` (metadata: baseline/training/evaluation) | **5.2** | 1.1.3, 5.2 |
| 2 | `trainingApproach` (conditions, user-selected) | **5.2** | 1.2.1, 5.2 |
| 3 | `verbalScaffolding` (conditions, user-selected) | **5.2** | 1.2.1, 5.2 |
| 4 | `botName` | 5.4 (detected / manual completion) | 1.2.2, 5.4 |
| 5 | `botDisplayedRating` | 5.4 | 1.2.2, 5.4 |
| 6 | `playerColor` | 5.4 | 1.2.2, 5.4 |
| 7 | `timeControl` | 5.4 | 1.2.2, 5.4 |
| 8 | `assistanceSettings` | 5.4 | 1.2.2, 5.4 |

PLAN evidence for the split: 1.2.1 ("Store the **selected** training
approach and verbal scaffolding level **once at session start**") vs
1.2.2 ("Store bot identity/displayed rating, player color, time
control, and assistance settings, with their source marked **observed
or manually supplied**") vs 5.4 ("Show **detected** game conditions
and allow **manual completion of unavailable fields** before
recording"). 5.2 owns exactly the three selected fields; 5.4 owns
detection + manual completion of the other five.

## 2. UI surface decision — in-page fields beside 5.1's control

**Decision: the selection UI lives in-page, adjacent to 5.1's
Start/Stop control cluster** (the same anchor), installed by
content.js. No popup, no new surface — the 5.1 contract §2 reasoning
applies unchanged: PLAN §(c) per-game step 2 ("Select Baseline,
Training, or Evaluation and confirm remembered conditions") happens
on the game page immediately before step 3 ("Click Start").

The UI is minimal — one `<select>` (Baseline / Training /
Evaluation) + two compact text inputs (training approach, verbal
scaffolding). No per-category hiding or disabling of the two text
fields: PLAN §3(b) step 2 states "The recorder **logs deviations but
does not enforce** these rules", so the UI records what the user
selects; a training approach entered for a baseline session is stored
truthfully (1.2.1: "Store the **selected** ... once at session
start"). Inapplicability stays derivable: per the 1.2 contract §2.5, a
blank field is `null`, and its inapplicability (e.g. training approach
for a baseline session) is derivable from `sessionCategory` — no
third state, no UI enforcement.

## 3. What 5.2 builds

### 3.1 New module `session_fields.js` (content-script side)

BlindfoldSession convention (dependency-free classic script → guarded
global → IIFE `'use strict'` → Node shim). Exports:

- `buildInitialConditions(selection, detectedFields)` — **pure**.
  `selection`: `{sessionCategory, trainingApproach, verbalScaffolding}`
  (raw UI values; strings or null/undefined). `detectedFields`: the
  five 5.4-owned fields as `{value, source}` wrappers — **required,
  no silent default** (the caller passes the explicit placeholder,
  below). Returns the frozen seven-field record via
  `createInitialConditions`: the two 5.2 fields as
  `{value: trimmed-or-null, source: 'manual'}` (1.2 contract §2.4:
  1.2.1's "selected" ⇒ `'manual'`; blank ⇒ `null`, never `""`),
  the five 5.4 fields passed through untouched. `TypeError` on
  malformed input (per the 1.2 error contract).
- `UNDETECTED_CONDITION_FIELDS` — frozen placeholder for the five
  5.4-owned fields: each `{value: null, source: 'manual'}`,
  documented as **"no detection attempted at 5.2; 5.4 owns detection
  and corrects provenance via the 1.2.4 path"**. Rationale for
  `'manual'` over `'observed'` (§7): the closed source vocabulary
  admits no "not yet attempted" value; `'observed'` would falsely
  claim a detection attempt ("detection attempted and found nothing"),
  actively misleading a downstream reader into believing the DOM was
  probed. `'manual'` asserts only "not DOM-detected" — the smaller
  untruth — and 5.4 corrects both values and sources through the
  designed mechanism (`createConditionChange` →
  `applyConditionChange` → `saveConditions` + a `conditions_changed`
  event, per 1.2.4 and the session_store.js merge contract).
- `installSessionFields(options)` — renders the select + two inputs
  beside 5.1's control cluster (fixed-corner fallback, 2.8 precedent);
  returns a handle `{getSelection, setSelection, setEnabled}` (the
  **5.3 seam**, §6). `options.getDetectedConditions` (optional) is
  the **5.4 plug-in seam**: `() =>` the five fields as `{value,
  source}` wrappers; default returns `UNDETECTED_CONDITION_FIELDS`.
  `options.extensionVersion` (required, injected — the 1.1 header:
  "call sites inject the extension version"). Invalid options →
  `TypeError` at install time. Never throws into page code (3.2
  SF-1 precedent).

### 3.2 Selection timing and locking rule

- **Selection happens before Start** (PLAN §(c) step 2 → step 3).
  The category is **required at Start**: a Start click with no
  category selected aborts honestly — button back to idle, the
  reason surfaced as control detail, **nothing minted, nothing
  persisted, no recorder message sent** (the 5.1 ensure-failure
  honesty pattern). Rationale: `createSessionMetadata`/`requireValidMetadata`
  admit no unknown category (RangeError by 1.1 contract); 1.2.3's
  "represent unavailable as unknown" applies to **conditions**, not
  to the 1.1 metadata category. The select starts blank ("Select…")
  until 5.3 supplies remembered defaults — the blank default is the
  forcing function for PLAN §(c) step 2.
- **Write-once at Start** (PLAN 1.2.1 "once at session start" +
  5.3 "without silently changing a game's recorded conditions"):
  the fields are **disabled while a session is active** (mirrors
  5.1's interlock); mid-session `setSelection` is a no-op. Stop
  re-enables the form for the next game. 5.2 emits **no**
  `conditions_changed` events — the initial record is stored, not
  emitted (1.2.4 governs *later* changes; 5.4 owns that path).
- **No per-category enforcement** (§2, PLAN §3(b): "logs deviations
  but does not enforce").

### 3.3 Session-metadata persistence path (open question, decided)

There is no SW-side session intake message (5.1 build evidence), and
content scripts cannot reach extension IDB (2.2) — so 5.2 adds **one
new SW-side message** (below). The storage primitives already exist
and are unwritten: `saveSessionMetadata(record)` and
`saveConditions(sessionId, record)` (session_store.js, 2.6). 5.2
invents no new storage API.

**Metadata-first minting** (no 1.1 contract change): at Start, 5.2
replaces 5.1's `newSessionId()` call with:

```text
metadata = createSessionMetadata({extensionVersion, protocolVersion: null, sessionCategory})
gameId   = newGameId()
metadata = addGameToSession(metadata, gameId)   // gameIds: [gameId]
```

`protocolVersion` is `null` (unknown): the user maintains
`protocol.md` outside the extension; the extension cannot know its
version (1.1 `normalizeProtocolVersion`). Identity stays
single-sourced in 1.1 — the `sessionId` sent to `recorder-set-session`
and used for events **is `metadata.sessionId`**; no new factory, no
adopted-ID variant. Rejected alternative: a
`createSessionMetadataWithId` factory — duplicates 1.1 validation
for no benefit.

**New SW-side message `session-save`** in the existing
`{kind:'recorder', v:1}` envelope, handled by
`recording_host.onRuntimeMessage` (the SW's established message hub —
the 4.3 capture-broker and 5.1 `recorder-ensure` precedent; SW-side
recorder-envelope vocabulary 6→7, pinned). Payload:
`{metadata, conditions}`. The handler **validates both records
before saving either** (`requireValidMetadata`,
`requireValidConditions` — no orphan metadata on a bad conditions
record), then `saveSessionMetadata` → `saveConditions`, responding
`{ok:true}` or `{ok:false, error}`. Never throws into the listener
(3.2 SF-1 precedent). Only an IDB failure mid-save can orphan
metadata without conditions — a plain-Error honest failure surfaced
by 2.8's storage health, not a silent state.

**Start order** (5.1's §3.3, amended): interlock → read + validate
selection (no category → honest abort) → build metadata + conditions
→ `recorder-ensure` → **`session-save`** → `recorder-set-session`
`{sessionId, gameId, sessionCategory}` → `recorder-start-streams` →
slots + `emitPageStart` + poll. `session-save` sits **after**
`recorder-ensure` and **before** `recorder-set-session`: an
ensure-failure persists nothing (extends 5.1's "no session minted
into any stream" to persistence), and a save-failure aborts before
the recorder ever sees the session — persisted state and recorder
state stay consistent: a saved metadata record implies the recording
pipeline was entered. `session-save` failure → honest abort
(button idle, reason surfaced).

`emitPageStart` keeps its empty payload — the category and conditions
live in the stores (§6.1 reads them); duplicating them into the event
payload would persist derivable-by-join values.

### 3.4 Boot adoption — category echo

`recorder-set-session` gains an **optional additive**
`sessionCategory`; recorder.js stores it with the session and the
`recorder-get-status` response echoes it (5.1's gameId-echo
precedent). On boot adoption, the (disabled) select shows the adopted
session's true category; a missing echo → honest `"unknown
(adopted session)"` disabled state — never the remembered default
masquerading as the active session's category.

## 5. Boundaries

- **5.1** (control surface): 5.2 amends its Start sequence
  (metadata-first minting, session-save, category echo) and installs
  the fields beside it; the lights, interlock, Stop flow, and 5.10
  seam are untouched.
- **5.3** (remember selections): owns the `chrome.storage.local`
  persistence of defaults and restore timing. 5.2's seam is the
  install handle `{getSelection, setSelection, setEnabled}` plus the
  write-once/disabled-while-active rule — restoring defaults can
  never rewrite an active session's record. 5.3 does not change
  record origin: per the 1.2 contract §2.4, remembered defaults are
  still source `'manual'`.
- **5.4** (detected conditions): owns detection + manual-completion
  UI for the five fields and plugs `options.getDetectedConditions`;
  corrects placeholder values/sources via the 1.2.4 change path.
  5.2 builds no detection and no completion UI.
- **5.5** (duplicate-Start guard): the known interim gap persists —
  a second tab's Start would save a second metadata record and
  overwrite the recorder session; 5.5 closes it. Recorded as
  5.5-owned, not a 5.2 defect (5.1 contract §6 precedent).
- **5.6–5.10**: untouched (readiness, game-end recording, notes,
  game boundaries, export-complete).

## 7. Explicit non-goals

- Remembered-defaults persistence (5.3) — beyond the
  getSelection/setSelection seam.
- Condition detection and manual-completion UI (5.4) — beyond the
  `getDetectedConditions` seam and the documented placeholder.
- Per-category field enforcement of any kind (PLAN §3(b): the
  recorder logs deviations, it does not enforce protocol rules).
- `protocolVersion` collection UI (stays `null`/unknown).
- Emitting condition events at Start (no new event types; 1.2.4
  changes are 5.4's path).
- Cross-tab duplicate-Start refusal (5.5); readiness (5.6);
  note markers (5.8); game boundaries (5.9); export-complete (5.10).
- Device-selection UI (flagged for the §5 planner sequence).
- Keyboard shortcuts, dashboards, metrics, charts (PLAN forbids).
- Any gameplay/content-script behavior change beyond the install
  lines and the Start-sequence amendment.
