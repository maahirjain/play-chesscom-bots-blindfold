# 7.1 contract — Verify legal, rejected, ambiguous, and repeated submissions produce distinct correct event records

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.1. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.1 requires an acceptance-level demonstration that the move-submission
pipeline records four distinct submission outcomes as distinct, correct event
records:

| Submission kind | Meaning | Expected record |
|---|---|---|
| **legal** | The submitted text normalizes to a legal move in the current position | `move_attempt` with `validation: 'legal'`, followed by `move_confirmed` when the move appears in the DOM history |
| **rejected** | The submitted text is illegal in the current position (or malformed) | `move_attempt` with `validation: 'illegal'` (or the specific rejection reason); NO `move_confirmed` follows for this attempt |
| **ambiguous** | The submitted text is syntactically valid but matches multiple legal moves (e.g. `Nd7` when both knights can reach d7) | `move_attempt` with a validation outcome that distinguishes ambiguity from legality — the attempt must NOT be recorded as `legal` when the move cannot be uniquely resolved |
| **repeated** | The same text is submitted twice (e.g. user presses Enter twice) | Two distinct `move_attempt` events (each submission is an observation), each with its own `attemptEventId`; the second must not overwrite or suppress the first |

"Distinct correct" means: an analyst reading `events.jsonl` can tell, for each
submission, which of the four kinds it was, from the event records alone —
without guessing.

## 2. What already exists

- `tests/attempt_tracker.test.js` (AC1–AC8): covers `move_attempt` payload shape
  (`submittedText` verbatim, `firstEditMonotonicMs`, `validation`), dispatch
  failure reasons (5 members), attempt→confirmed matching, attempt lifecycle,
  dormancy, payload validators.
- `chess_utils.js` `normalizeMove` + validation: produces the `validation`
  outcome (`legal` / `illegal` / specific reasons).
- `tests/history_tracker.test.js` AC2 (validate before advancing): the history
  tracker does not advance on unvalidated moves.

**Gaps identified:**
1. **Ambiguity is not covered.** No test pins what happens when submitted text
   matches multiple legal moves. The `validation` vocabulary in the tracker
   needs checking: does it have an `ambiguous` outcome, or does ambiguity
   surface elsewhere (e.g. as `illegal`, or as a dispatch failure)?
2. **Repeated submission is not covered.** No test submits the same text twice
   and asserts two distinct `move_attempt` events with distinct IDs.
3. **The four-way distinction is not demonstrated end-to-end.** The existing
   tests cover each piece; 7.1 requires one acceptance test that exercises all
   four in sequence and asserts the resulting event stream is unambiguous.

## 3. Verification plan

### V1 — static/unit (Node)

- [ ] **AC1.** Ambiguity: construct a position where two knights can reach the
  same square (e.g. knights on b1/f1, empty d2 — `Nd2` is ambiguous). Submit
  the ambiguous text through the validation path; assert the recorded
  `validation` outcome is NOT `legal` (it must be `ambiguous`, `illegal`, or
  another non-legal value — the contract pins the exact vocabulary after
  reading the code).
- [ ] **AC2.** Repeated submission: submit identical text twice; assert two
  `move_attempt` events with distinct `attemptEventId`s, identical
  `submittedText`, and monotonically increasing `appendSeq`.
- [ ] **AC3.** Four-way acceptance: drive legal → rejected → ambiguous →
  repeated submissions in one tracker session; assert the emitted event
  sequence contains exactly the expected records in order, each
  distinguishable by its `validation` / identity fields.
- [ ] **AC4.** No fabrication: assert the tracker never invents a
  `move_confirmed` for a rejected or ambiguous attempt (the confirmed event
  comes only from DOM observation, never from the submission path).

### V2 — integration (headless Chrome, optional)

- [ ] **AC5.** If the V1 path uses fakes for DOM observation, a V2 harness
  drives the real `observeMoves` against a synthetic Chess.com move-list DOM
  and confirms `move_confirmed` fires only for DOM-observed moves.

### V3 — deferred to owner device (§7.9/7.13 context)

- [ ] **AC6.** On the real device: submit each kind against a live bot game;
  confirm the exported `events.jsonl` shows the four-way distinction.

## 4. Non-goals

- Changing the validation vocabulary (if `ambiguous` doesn't exist, the
  contract documents what exists; changing it would be a new feature).
- Engine analysis or move-quality judgment (raw data only).
- V3 real-device execution (deferred).
