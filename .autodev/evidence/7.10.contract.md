# 7.10 contract — Verify a page refresh does not stop the independent recording context

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.10. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.10 requires demonstrating that refreshing the Chess.com page
mid-recording does not terminate the media capture or the event pipeline.

The architecture provides this by construction:

- **Media capture** runs in the **offscreen document** (`recorder.js` /
  `recorder.html`), which is owned by the service worker, not the page. A
  page refresh destroys content scripts but does not touch the offscreen
  document.
- **Event storage** runs in the **service worker** (`writer.js`, IndexedDB).
  The SW persists across page navigations (it may sleep, but the DB is
  durable).
- **Content scripts** (`content.js`, `session_controls.js`, trackers) DO die
  on refresh. They must re-attach on page load (late attachment — covered by
  7.5 AC3/AC5) and re-bind to the still-running session.

"Verified" means:
1. (Static/architectural) No recording-state lives in page-bound contexts
   (content script variables, DOM) that would be lost on refresh. The session
   ID, stream handles, and media chunks all live in SW/offscreen/IndexedDB.
2. (Behavioral) After a simulated refresh (content-script teardown +
   re-initialization), the session resumes: the re-attached tracker binds to
   the existing session ID, new events flow to the same session, and the
   offscreen recorder never stopped.

## 2. What already exists

- The offscreen + SW architecture (Sections 2, 4).
- 7.5's late-attachment coverage (history_recovered on re-attach).
- `session_controls.js` recorder-ensure / set-session (5.1): the content
  script re-establishes its binding on load.

**Gaps identified:**
1. No explicit test asserts the **separation**: that `recorder.js` (offscreen)
   holds no page-bound references, and that a content-script reload doesn't
   send a stop/teardown to the recorder.
2. The **re-binding** path (content script reload → `recorder-ensure` →
   existing session found → re-attach, not new session) deserves an explicit
   test — 5.5's duplicate-Start guard is the mechanism, but 7.10 is the
   acceptance scenario.

## 3. Verification plan

### V1 — static/unit (Node)

- [ ] **AC1.** Separation: source-scan `recorder.js` / `recorder.html` for
  page-bound references (`document.querySelector` on chess.com DOM,
  `chrome.tabs` page-specific calls in the capture path); assert none exist
  in the recording lifecycle (setup/teardown may reference the offscreen
  document itself, which is fine).
- [ ] **AC2.** No teardown on content-script unload: assert the content
  script's unload path (if any) does NOT send `MSG_STOP_STREAMS` or
  `recorder-teardown` — the recorder keeps running when the page goes away.
- [ ] **AC3.** Re-binding: simulate content-script reload (fresh
  `session_controls` install with the same session ID in the recorder);
  assert the 5.5 guard allows re-set with the same session ID (idempotent)
  and does NOT mint a new session or stop the streams.

### V2 — integration (headless Chrome)

- [ ] **AC4.** Load the extension, start a session (synthetic streams),
  navigate the page away and back (real reload); assert the SW/offscreen
  session persists (streams still `recording-healthy` via `stream_status`)
  and post-reload events land in the same session.

### V3 — deferred to owner device

- [ ] **AC5.** On the real device: refresh mid-game during a real recording;
  confirm media files contain no gap at the refresh point and events resume
  under the same session ID.

## 4. Non-goals

- Testing Chrome's offscreen-document lifetime policy itself (platform
  behavior; the extension follows the documented pattern).
- Changing the reload/re-attach logic (verification-only).

## 5. Diff discipline

Expected: new tests (acceptance file — builder's choice), evidence files,
DECISIONS.md entry. No product-code changes (verification-only). If the
source scan finds page-bound references in the recorder, that's a defect to
report, not to fix silently.
