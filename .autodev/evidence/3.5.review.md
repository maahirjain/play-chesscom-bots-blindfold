# Task 3.5 adversarial review — Instrument lifecycle events

**Verdict: APPROVE_WITH_DEFECTS** — 0 BLOCKER, 1 SHOULD_FIX, 7 NOTEs.
The 3.5 mechanics are sound and independently verified, but 3.5 ships a
second, incompatible schema for the PLAN-§1.4.5-defined `game_ended` event
and silently replaces 1.4's checkpointed validator on the shared namespace.
That must be repaired (not merely noted) before commit.

## Findings

### SHOULD_FIX-1 — `game_ended` schema fork and validator shadowing vs 1.4's checkpointed contract

**Severity: SHOULD_FIX** (latent today — the recorder is inert pre-§5 and
`createEvent` does not per-type-validate payloads — but it forks a
PLAN-defined event schema and corrupts the shared namespace; §5/§6 will
build on whichever half they find).

1.4 (`game_records.js`) already owns `game_ended`:
- `GAME_ENDED_EVENT_TYPE = 'game_ended'` (game_records.js:116),
  payload exactly `{result, terminationReason, evidenceSource, observedText}`
  (game_records.js:503-510; factory `createGameEndedPayload` :534,
  validator `requireValidGameEndedPayload` :552, exported :607),
  `TERMINATION_REASONS` 9-member vocabulary (:125-134).
- The 1.4 header (:79-84) documents consumer semantics: *"Multiple
  game_ended events per game are permitted (observed auto-detection +
  later manual Stop completion); consumers take the latest by occurrence
  time."* And 1.4's test file explicitly defers *"game-end detection from
  Chess.com UI (→ §3.5.3); manual completion UI (→ §5.4/§3.5.4)"* — i.e.,
  1.4 designed `game_ended` **for this task to consume**.

3.5 (`chess_utils.js`) redefines the same event type with an incompatible
schema and never reconciles:
- Same event-type string `'game_ended'` (chess_utils.js:70), but payload
  `{termination, source, speechLogicVersion}` (validator :1535) —
  no `result` (PGN), no `evidenceSource`, no `observedText`, despite PLAN
  1.4.5 requiring *"observed game-end fields for result, termination
  reason, and evidence source"*.
- A **different function under the same name**:
  `BlindfoldSession.requireValidGameEndedPayload` is assigned at
  chess_utils.js:1563, overwriting 1.4's assignment (game_records.js:607)
  on the shared namespace (manifest load order: game_records.js before
  chess_utils.js). Empirically reproduced: in the load-order-merged
  namespace, a 1.4-shaped payload
  `{result:'1-0', terminationReason:'checkmate', evidenceSource:'observed',
  observedText:null}` is **rejected** (`TypeError: game_ended payload must
  have exactly the keys: source, speechLogicVersion, termination`) while
  the 3.5-shaped payload is accepted. `createGameEndedPayload` (1.4's
  factory) survives only because it closes over its IIFE-local validator;
  any future §5/§6 caller using the *namespace* validator gets 3.5
  semantics under 1.4's documented name.
- A **second termination vocabulary**: 3.5's `TERMINATIONS` (10 members,
  chess_utils.js:77) vs 1.4's `TERMINATION_REASONS` (9 members) with
  renamed members (`draw_threefold` vs `threefold_repetition`,
  `draw_insufficient_material` vs `insufficient_material`,
  `draw_fifty_move` vs `fifty_move_rule`, `abandoned` vs `abandonment`).
- A **contradicted consumer contract**: 1.4 says multiple `game_ended`
  permitted, latest-wins; 3.5 implements first-observation-wins, at most
  one per game (chess_utils.js:1673-1693). Concrete divergence: 1.4's
  model lets a manual Stop completion supersede an earlier `unknown`
  auto-detection; 3.5's dedup suppresses it.
- The 3.5 contract's "Already done / 3.5 relationship" table
  (3.5.contract.md §1) **omits 1.4's `game_ended` entirely** — planner and
  builder never saw the collision. The "each task owns its vocabulary"
  claim (contract §2.2) is wrong here: the vocabulary was already 1.4's.
- Tests dodge the collision rather than catching it:
  game_records.test.js uses the unmerged module; game_lifecycle.test.js
  merges with ChessUtils winning but only exercises 3.5's names.

**Recommended repair (coordinator repair loop):** reconcile, don't fork.
Cleanest direction honoring PLAN 1.4.5: adopt 1.4's
`{result, terminationReason, evidenceSource, observedText}` shape in the
3.5 recorder — chess_rules → `result` from the board (`1-0`/`0-1` via
`game.turn()` as `getResultAnnouncement` already computes,
`1/2-1/2` for draws), `terminationReason` mapped onto
`TERMINATION_REASONS`, `evidenceSource: 'observed'`; dialog →
`'observed'` + raw `observedText` (exactly what 1.4 designed it for);
stop → `'manual'`. Then resolve the dedup contradiction explicitly
(1.4's latest-wins vs 3.5's first-wins) and eliminate the validator
shadowing (one `requireValidGameEndedPayload`, or a clearly renamed
3.5-specific one). If 3.5's schema is kept instead, that is a
supersession of a checkpointed contract and needs an explicit documented
decision plus a discriminator for §6 — do not silently dual-schema
`events.jsonl`.

### NOTE-1 — `confirmedMoveCount` granularity is ambiguous

`handleSuspect` captures `confirmed.length` (chess_utils.js:839) where
`confirmed` holds one entry per observed half-move SAN (:428). So
`game_reset.confirmedMoveCount` counts **plies**, not full moves — the key
name doesn't say so (the unit test asserts 4 for `['e4','e5','Nf3','Nc6']`).
Recommend documenting the unit in the validator comment / DECISIONS.md so
a later analyst doesn't read "4" as four full moves. Not a schema break
(the count is internally consistent with `move_confirmed` granularity).

### NOTE-2 — 3.5.3 dialog audit basis is thin; "unsupported" means "unverified"

The audit is 3.3 domaudit §6 [code-analysis] + claimed public research
(unverified third-party selectors `.game-over-modal`,
`.board-modal-container`); the live authenticated session was **not** used
to inspect the actual game-over dialog DOM. The DECISIONS.md marking is
honest (tagged `[code-analysis]`, "Revisit in §7 with live-page
verification") and the contract's allowed deliverable, so this is not a
defect — but §7 must drive a real resignation/timeout on the live page
and inspect the dialog DOM before treating "unsupported" as settled, and
the research itself left no recorded trail (no notes artifact).

### NOTE-3 — `const game` staleness hazard for the §5 handoff

content.js:32 captures `const game = historyTracker.getGame()` once, and
the chess_rules wiring (content.js:190) reads it on every move-list
change. The `onGameReset` comment anticipates §5 will "install new
tracker"; if §5 replaces the tracker *object*, the termination wiring
keeps reading the dead board. Either switch the wiring to a thunk
(`() => historyTracker.getGame()`) now, or make re-capture an explicit
§5 acceptance item. Pre-§5 behavior is correct.

### NOTE-4 — `speechLogicVersion` on non-chess_rules sources

The validator comment (chess_utils.js:1532-1534) says the field "versions
the chess-rules derivation", but it is a required exact key on
`stop`- and `chesscom_dialog`-sourced events too, where no chess-rules
derivation occurred. Harmless (schema uniformity), but the documented
rationale doesn't cover two of the three sources.

### NOTE-5 — `prerender` visibilityState edge

The validator (chess_utils.js:1507-1518) accepts only
`'visible'`/`'hidden'`; the spec allows `'prerender'`. A prerender
`visibilitychange` would throw `RangeError`, be swallowed by
`recordVisibilitySafe` (content.js:151-155), and the observation silently
dropped. Negligible in practice (content scripts don't run prerendered),
noted for completeness.

### NOTE-6 — stop-then-chess_rules priority

First-observation-wins means a user's Stop reason (e.g. `'abandonment'`)
suppresses a *later* board-derived terminal state (unit-tested,
game_lifecycle.test.js AC9). Defensible (the user's stated reason is
primary), but §5's UX copy should reflect that Stop's reason wins over
anything observed after the click.

### NOTE-7 — `onGameReset` fallback `0` (content.js:23-25)

If `info.confirmedMoveCount` is absent/non-integer the wiring records `0`
rather than failing. Dead in practice (the sole caller at
chess_utils.js:843 always passes the arg), but it trades "unknown means
unknown" for a convenient zero. Prefer letting the validator throw (the
call site is already try/catch-isolated) over recording an unobserved
count.

## Adversarial checks that passed

- **3.5.1 honesty:** the disclaimer exists in chess_utils.js (:1610-1612),
  content.js (:140-143), and DECISIONS.md; the event/payload names are
  document-state terms. The `pause`/`attention` tokens in the diff occur
  only inside explicit negations ("cognitive pause", "attention shift",
  "player absence"); the AC3 test strips those lines and asserts no
  standalone tokens — verified by reading the test. No interpretation as
  pause/attention/away anywhere.
- **3.5.2 additive change:** single call site (chess_utils.js:843), count
  captured before `confirmed = []` is cleared; nullary stubs keep working
  (history_tracker.test.js). No duplication: takebacks stay
  `history_revised`, reloads stay `page_start` (2.7); `game_reset` records
  the previously-unrecorded 3.1 detection.
- **`chessRulesTermination` mirroring:** condition order matches
  `getResultAnnouncement` (sounds.js:85-97) exactly, including the
  unreachable-fallback (`"Game over."` ↔ `'unknown'`). Fifty-move by
  elimination is sound against the vendored chess.js:
  `in_draw() = halfmoves>=100 || stalemate || insufficient || threefold`
  and `game_over()` enumerates the same four causes, so excluding the
  three named draws leaves only the fifty-move rule. All predicates are
  read-only (no board mutation). `'unknown'` is unreachable-defensive.
- **First-observation-wins mechanics:** sound by construction — the
  `chess_rules` source fires only from the validated move-list board, so
  it can only "win" when the board is genuinely terminal; it cannot
  suppress a legitimate dialog/stop result for a *different* ending. The
  dedup engages correctly: `sender.emit` returns the envelope carrying a
  uuid-v4 `eventId` (event_envelope.js:306), so `endedEmitted` is set
  (chess_utils.js:1687-1690). Unit permutations + V2 Stop-after-end
  suppression verified.
- **§5 seam:** `recordStopTermination` exposed via
  `BlindfoldSession.gameLifecycleRecorder` (content.js:132,144-145),
  validates `reason` against the enum (`RangeError` otherwise), subject
  to the documented dedup; `resetEnded()` re-arms per game. Adequate for
  §5 to wire the button + unknown-reason prompt.
- **Validate-before-dedup fail-fast:** sound; matches the 3.3 NOTE-4
  precedent; all content.js call sites are try/catch-isolated (3.2 SF-1),
  so no page breakage.
- **V2 null-refs limitation:** honest and mechanism-verified — pre-§5 the
  history tracker is inert (`emitGameEvent` returns null when gameId is
  null, chess_utils.js:442-447 → confirmed entries get `eventId: null`,
  :578), so `lastConfirmed.eventId` is genuinely null; the harness
  asserts the null case and V1 covers populated refs with uuid-v4
  fixtures.
- **Scope:** only `chess_utils.js` + `content.js` among product files;
  `event_envelope.js`, `lifecycle.js`, `sounds.js` byte-identical to HEAD
  (test-asserted); PLAN.md unmodified; no `MediaRecorder`/`getUserMedia`/
  `getDisplayMedia` tokens (§4 clean); no Start/Stop UI built (§5 clean);
  no gameplay behavior change (listeners passive, termination predicates
  read-only, 3.1 semantics preserved — full suite green).
- **Test pins:** honest. Pin evolution in earlier suites carries
  justification comments (spot-checked tests/speech.test.js); the AC11
  allowlist pre-includes 3.5.review.md/3.5.behavior.md per the 2.x/3.x
  precedent. Several ACs are verified by source inspection (labeled as
