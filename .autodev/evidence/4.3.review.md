## SHOULD_FIX

### SF-1 (mechanical, non-blocking): `tabPermissionState` is write-only dead state

`capture_selection.js` declares `tabPermissionState` (line 218) and
assigns it in four places — `queryTabPermission` (lines 343, 346),
`onProbeOutcome` (line 452), `runTabProbe` success (line 508) — but **no
code path ever reads it**. Every consumer (`permissionStateFor`,
`getState`) re-derives the state via the broker instead. The design
(re-derive, don't cache) is the honest one; the leftover variable is a
trap for a future reader or for §5, who might trust it as a cache and
reintroduce the stale-state bug 4.2's deviation #4 deliberately avoided.
Fix: delete the variable and its four assignments (the re-derive design
already carries the behavior), or keep it with a comment stating it is
intentionally unused. Either is mechanical; the current shape is
neither.

## Verified sound

- **Surface choice.** `chrome.tabCapture` primary + `getDisplayMedia`
  fallback is the right call for this mission: deterministic,
  permission-queryable, tab-audio-capable, scoped to the game tab.
  `chrome.desktopCapture` is correctly excluded (Chrome-Apps-only).
  The persisted `captureMode ∈ {'tab','screen'}` is a legitimate
  "selection" for a task titled "screen/tab capture" — with
  `getDisplayMedia` there is no stable deviceId to select, and the
  contract is explicit about this. Tab-id re-resolution per boot is
  sound (ids are unstable; the contract and code never persist them).
- **chrome.\* split.** Required, not precautionary — the builder's
  CDP probe (`chrome.runtime` present; `chrome.tabs`,
  `chrome.tabCapture`, `chrome.permissions` absent in the offscreen
  document) is the same empirical method 4.2 used, and the split is
  minimal: the SW broker owns exactly the three chrome.\* calls, the SW
  never touches a MediaStream, the streamId travels as a single-use
  request field and is never persisted (verified: no `set`/`localStorage`
  writes of streamId anywhere in `capture_selection.js`).
- **Message contract.** The SW-leg messages
  (`capture-resolve-tab`/`capture-query-permission`/`capture-get-stream-id`)
  ride the existing `{kind:'recorder', msg, v:1}` envelope; the broker
  validates `tabId` (TypeError on bad shape); failures become
  `{ok:false}` data, never listener throws (3.2 SF-1 precedent held on
  both legs).
- **Manifest.** Both additions are justified and neither is
  over-request: `permissions.contains(['tabCapture'])` empirically
  reports `'granted'` (install-time grant effective), and the SW leg
  resolved a real game-tab tabId, which is exactly what
  `host_permissions: ["https://www.chess.com/*"]` enables for
  `tabs.query({url})` without the broader `"tabs"` permission. The 4.2-era
  "no manifest change" pin was evolved honestly with a justification
  comment (spot-checked in `tests/recording_host.test.js`).
- **Probe-then-stop.** `runTabProbe` stops every track before resolving
  (the success path calls `stopAllTracks` before any return; the
  rejection path has no stream). V1 pins this with spies. The
  headless `{ok:true, permissionState:'unknown', errorName:'Error'}`
  outcome is **honest, not a weasel word**: it follows the contract's
  documented mapping (non-NotAllowed/non-stale errors → `'unknown'` with
  the raw name), and the build doc transparently attributes it to
  headless Chrome refusing tab capture without a toolbar invocation.
- **Bogus-streamId AbortError proof.** Valid: an invalid constraint
  *format* would fail with TypeError/OverconstrainedError before any
  capture attempt; `AbortError: "Error starting tab capture"` means the
  constraint was accepted and the pipeline attempted acquisition. This
  is legitimate evidence for the doc-leg API surface, and the builder
  correctly did **not** claim it as proof of the full probe path.
- **Permission honesty.** Screen mode `'prompt'` is the honest inherent
  state (the picker is unqueryable by platform design); tab mode
  `'granted'`/`'denied'` is genuinely queryable; denial is a state, not
  an exception (4.2 precedent). `no-target-tab` → `tabId:null` with no
  active-tab fallback is the right call (recording the wrong tab is the
  failure this avoids).
- **Events.** Both 4.3-owned types have exact-keys validators;
  `event_envelope.js` untouched (verified: `git diff HEAD` shows no
  4.3 change to it); emission is session-gated (4.2's
  `recorder-set-session` reused, including the once-per-session
  announcement with the actual source); `tabTitle` is null when
  unavailable, never fabricated. `audioIncluded` is exposed on the probe
  response for 4.7.
- **4.2 SF-1 precedent honored.** `select()` persists
  `blindfold.captureMode.v1` *before* the in-memory selection goes live
  (dedicated regression test at
  `tests/capture_selection.test.js:301`).
- **Scope.** No 4.4/4.6/4.7 bleed (no `MediaRecorder`, no
  `getDisplayMedia(` invocation in product code — verified with comments
  stripped; no retained streams; no UI; no audio-routing decisions).
  Content scripts byte-identical; only the contract-listed files changed.
  Full suite independently re-run: **719/719 pass**.

## NOTEs

1. `screen_capture_permission_changed` is never emitted for screen mode
   (the `'prompt'` report is response-only). Defensible — `'prompt'` is
   the stable inherent state, not a change — but §5 should know the
   event stream will never contain a screen-mode permission record.
2. The `'query'` member of the permission-event `source` vocabulary is
   never produced in 4.3 (only `'request'`). Reserved, not a defect;
   document it as reserved for §5/4.14 or drop it.
3. `restoreOnBoot` does not refresh the (now write-only — see SF-1)
   permission state; `getState()` re-derives per call, so the queryable
   surface stays fresh. Fine as-is once SF-1 is resolved.
4. Concurrent `select()` calls have no in-flight guard (unlike the
   permission probe): last-writer-wins on storage and in memory. Benign
   for a user-driven setting; §5 should serialize if it drives selects
   programmatically.
5. `select('screen')` performs a wasted broker round-trip to resolve the
   target tab, then discards it. Harmless (degrades to `broker-error`
   honestly) but unnecessary.
6. The headed-machine proof of the full grant path (valid streamId →
   `getUserMedia` success → `audioIncluded`) remains outstanding; it is
   correctly deferred to AC12/§7, and the behavioral verifier should
   treat the headless `'unknown'` outcome as the expected V2 result, not
   a failure.
7. `capture_broker.js` hardcodes
   `GAME_TAB_URL_PATTERN = 'https://www.chess.com/play/computer*'`; the
   comment says future §5/§7 surfaces should agree on it — flagging so
   the §5 planner picks this constant up rather than re-deriving the
   pattern.
