## 1. Scope

Task 1.3 defines the **event envelope and time model only**: the common
envelope shape (1.3.1), the clock-anchor record and context-segment model
(1.3.2), source timestamping via elapsed monotonic time (1.3.3), the
persistent append-sequence field and its storage-time assignment rule
(1.3.4), and the cross-reference mechanism (1.3.5). It defines *factories,
validators, constants, and the wall-clock derivation formula*; it does **not**
send events (§2.3), write them to storage or assign append sequences (§2.4),
emit segment lifecycle events (§2.7), define any §3.x event type or payload,
define recording-segment IDs (§4.10), align media (§4.12), or export anything
(§6).

## 2. Design decisions (investigator-verified)

### 2.1 Event ID: UUID v4, consistent with 1.1

`newEventId()` uses `crypto.randomUUID()`; unavailable → throw, no fallback
(1.1 precedent: fabricating weak IDs silently weakens the contract).
Justification beyond consistency:

- PLAN §2.4 requires the writer to **deduplicate by event ID**. A UUID v4 is
  the dedup key.
- PLAN §2.5 retries unacknowledged events **while the originating context
  remains available**. A retried event is re-sent with the *same* eventId, so
  the writer distinguishes "retry of a known event" from "new event" without
  any cross-context coordination.
- Content script, service worker, and recording context generate IDs
  independently with no shared counter — 122-bit entropy makes coordination
  unnecessary.

### 2.2 Event types: flat snake_case, domain-prefixed — NO namespacing, NO 1.2 amendment

The 1.2 contract explicitly flagged: "If 1.3 namespaces event types,
`CONDITION_CHANGE_EVENT_TYPE` needs an amendment." Decision: **do not
namespace**. Event types are flat `snake_case` strings matching
`/^[a-z][a-z0-9_]{0,63}$/`, by convention prefixed with the originating
domain (`conditions_`, and later `move_`, `game_`, `speech_`, …).

Rationale:

- `'conditions_changed'` is already delivered, frozen, and covered by 47
  passing tests. It already follows the domain-prefix convention.
  Namespacing now (e.g. `'conditions.changed'`) would force a 1.2 contract
  amendment, a `session_conditions.js` change, test churn, and
  re-verification of a DONE task — for zero functional gain. Prefix
  filtering (`type.startsWith('move_')`) works identically on flat strings.
- PLAN.md never requires hierarchical types. "Smallest coherent change"
  and "do not weaken requirements to make implementation easier" both argue
  against churning a verified contract for aesthetics.
- Hierarchy remains derivable at analysis time from the prefix; it is not
  persisted as structure (cf. "do not persist derivable values").

**Registry mechanism** (this is the deliverable the task asks for):

1. `event_envelope.js` owns the *syntax* contract: `EVENT_TYPE_RE` and
   `isEventType()`. Every envelope validates its type against it, so the
   convention is enforced in code, not just docs.
2. Each task defines its own `*_EVENT_TYPE` constant(s) **in its own module**
   (1.2 precedent: `CONDITION_CHANGE_EVENT_TYPE` lives in
   `session_conditions.js`). No load-order coupling, no duplicated string
   constants, no central frozen object that would be incomplete by
   construction.
3. The authoritative human-readable **vocabulary table** lives in this
   contract (§2.2.1) and is extended by each future task's contract. Code
   stays decentralized; the table stays complete.

`EVENT_TYPES` in `event_envelope.js` is seeded with **only the types 1.3
itself defines** (`CLOCK_ANCHOR`). It is not a global registry and must not
be treated as one.

#### 2.2.1 Vocabulary table (complete as of task 1.3)

| eventType | defined by | payload shape |
|---|---|---|
| `conditions_changed` | 1.2 — `session_conditions.js` (`CONDITION_CHANGE_EVENT_TYPE`) | `ConditionChangePayload` (`{changes}`) |
| `clock_anchor` | 1.3 — `event_envelope.js` (`EVENT_TYPES.CLOCK_ANCHOR`) | `ClockAnchor` (§3.2) |

Future §3.x/§4 tasks add rows via their own contracts. Anticipated

of the convention, **not** a pre-definition of the §3.x vocabulary — each
task defines its own types.

### 2.3 Session/game reference: `sessionId` required, `gameId` nullable

- `sessionId`: required UUID v4. Every event belongs to a recording session;
  session-scoped diagnostics outside a session are out of scope (PLAN's data
  model starts at Start). The sender (§2.3) emits only within an active
  session. *Flagged design input for §2.3/§2.7:* they must decide when a
  segment/anchor is created relative to session start (e.g. lazily at the
  first session event); the envelope itself always carries a sessionId.
- `gameId`: UUID v4 or **explicit `null`** — never omitted (`undefined` →
  `TypeError`, mirroring 1.2's "missing field" rule). `null` means
  *session-scoped, not game-scoped*. Honest per PLAN: clock anchors are
  captured at context startup, before any game is detected (§3.5); session
  notes (§5.8) and lifecycle events (§2.7) may fall between games. A `null`
  gameId is a positive statement ("this event is not about a game"), not
  missing data.

### 2.4 Source context: closed 3-value vocabulary, no invented granularity

`SOURCE_CONTEXTS = ['content_script', 'service_worker', 'recording_context']`
(frozen), validated by `isSourceContext()`.

- `content_script` — the Chess.com page content-script world (gameplay
  instrumentation, §3). One segment per page load.
- `service_worker` — the MV3 background service worker (§2). One segment per
  worker instance (see §2.6: a restart is a new segment with a new anchor).
- `recording_context` — the dedicated recording context (§4.1). One segment
  per context lifetime.

Deliberately **not** included: a popup/controls value. The §5.1 control
surface's hosting is not yet designed; inventing `'popup'` now would be
unneeded granularity. If §5's control surface emits events and is none of
the three, §5 amends this vocabulary explicitly (documented extension
point, not a silent stretch). MV3 `MAIN` vs `ISOLATED` world distinction is
also excluded — one `content_script` value covers the instrumentation
context.

### 2.5 Source sequence: per-segment counter, distinct from append sequence

`sourceSeq`: required non-negative integer. Semantics:

- Scoped to **(`sourceContext`, `clockSegmentId`)** — i.e. one counter per
  context segment, not per context lifetime across reloads (a reload starts
  a new segment, and the new `clockSegmentId` disambiguates).
- First event of a segment has `sourceSeq` 0; each subsequent event
  increments by exactly 1. By convention the segment's `clock_anchor` event
  is the first event (sourceSeq 0); the contract validates the integer but
  does not hard-enforce the convention (§2.7 owns emission order).
- The counter is **stateful and owned by the emitting context** (§2.3
  sender); the contract layer is pure — `createEvent` takes `sourceSeq` as a
  validated parameter so tests can use synthetic values deterministically.

How it differs from `appendSeq` (1.3.4): `sourceSeq` records **occurrence
order at the source** (assigned at observation, per segment); `appendSeq`
records **durable storage order** (assigned once by the §2.4 writer, global
across segments). Uses: gap detection within a segment (observing sourceSeq
5 then 7 ⇒ 6 was lost before storage — preserved as evidence, §3(a)
"errors/gaps"); tie-breaking events with equal/coarse `monotonicMs`; the
writer can detect duplicates by (`clockSegmentId`, `sourceSeq`) in addition
to the `eventId` dedup.

### 2.6 Clock anchors (1.3.2): exact record shape

A **context segment** is one continuous lifetime of one event-producing
execution context (one content-script instance per page load, one
service-worker instance, one recording-context instance). Each segment gets:

- `segmentId`: UUID v4 (`newClockSegmentId()`; independent function like
  1.1's `newSessionId`/`newGameId` so the streams stay separable in review).
- Exactly one anchor captured at segment startup, emitted as a `clock_anchor`
  **event row** in `events.jsonl` (PLAN §3(a) lists clock anchors as event
  rows; §6.3 references them from `media-sync.json` rather than duplicating
  them).

`ClockAnchor` — exactly three keys, no more, no fewer:

```json
{
  "segmentId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "utcEpochMs": 1728096000123,
  "monotonicMs": 1234.567
}
```

- `segmentId`: UUID v4 — the segment this anchor belongs to.
- `utcEpochMs`: integer ms since Unix epoch (`Date.now()` at capture).
  **Epoch ms, not ISO-8601 string**: unambiguous, sortable, arithmetic-ready
  for the alignment formula (§4.12/§6.3 need arithmetic, not parsing), and
  JSON-safe. No timezone-format risk.
- `monotonicMs`: the `performance.now()` reading captured **immediately
  before** `utcEpochMs` (monotonic first, then wall). Stored **unrounded** —
  the raw `DOMHighResTimeStamp`; rounding at the contract layer would
  fabricate precision loss.

**No `timeOrigin` persisted.** The (`utcEpochMs`, `monotonicMs`) pair
captured adjacently is the minimal sufficient wall↔monotonic mapping;
`timeOrigin` is a navigation/worker-start constant that adds no mapping
information for events occurring later in the segment, and a third field
would only create consistency questions for reviewers.

**Capture procedure** (documented for §2.3/§4 implementers; `captureClockAnchor`
implements it):

```js
var monotonicMs = performance.now();  // monotonic clock, read first
var utcEpochMs = Date.now();          // wall clock, read immediately after
```

The inter-call skew is microseconds — below the timer resolution available
to the page — hence unobservable at experiment resolution. If
`performance.now` is unavailable the capture **throws** (1.1 precedent: no
silent fallback to `Date.now`, which would silently substitute a
non-monotonic clock).

**Multiple anchors per segment are permitted** (validator does not forbid
them): if a future task (§2/§4) finds monotonic-vs-wall drift material over
multi-hour sessions, it may emit additional `clock_anchor` events for the
same `segmentId`; consumers then use the latest anchor with
`monotonicMs <= event.monotonicMs`. Not required now — documented extension
point, no code.

**Platform facts grounding this design** (verified 2026-10-06):

- `performance.now()` returns ms since `performance.timeOrigin` on a
  **monotonic clock**: "its current time never decreases and isn't subject
  to adjustments" ([MDN `Performance.now()`](https://developer.mozilla.org/en-US/docs/Web/API/Performance)).
- `timeOrigin` is navigation start in window contexts and **worker creation
  in Worker/ServiceWorker contexts** ([MDN `Performance.timeOrigin`](https://developer.Mozilla.org/en-US/docs/Web/API/Performance/timeOrigin)).
  Consequence: every service-worker restart gets a **new** time origin, so a
  single session-wide anchor is impossible — anchors must be per segment,
  and §2.6/§2.7 must re-anchor after restart.
- `Date.now()` is relative to the Unix epoch and **may be impacted by system
  and user clock adjustments, clock skew** (same MDN page) — hence never
  the per-event source of truth.
- Per W3C HR-Time, the UA may reset its monotonic clock across restarts or
  isolated sessions; monotonicity holds only within contexts sharing a time
  origin — hence anchors are never treated as global.

### 2.7 Event timestamp (1.3.3): monotonic at source, wall derivable

Each event carries, flat on the envelope:

- `clockSegmentId`: UUID v4 — which segment's clock this event is stamped on.
- `monotonicMs`: finite number ≥ 0 — `performance.now()` elapsed ms within
  that segment, stored verbatim (never rounded, never rewritten).

**Why NOT a wall-clock field per event** (three reasons):

1. `Date.now()` is not monotonic — NTP/user adjustments can move it
   backward, silently breaking ordering and duration math. The experiment's
   timing questions (durations, ordering, media alignment) require a
   monotonic source.
2. Per-event wall time is **derivable** from the anchor:
   `wallUtcMs = anchor.utcEpochMs + (event.monotonicMs - anchor.monotonicMs)`
   (provided as pure, V1-testable `deriveWallUtcMs(anchor, monotonicMs)`).
   Persisting both would violate "do not persist derivable values" and risk
   the two clocks disagreeing on the same row.
3. Cross-context wall clocks are incomparable without a shared reference —
   the anchor **is** that shared reference. One wall tie-point per segment
   is the honest model.

The anchor event is self-consistent by construction: `createAnchorEvent`
sets the envelope's `clockSegmentId`/`monotonicMs` from the anchor's own
`segmentId`/`monotonicMs`, so `deriveWallUtcMs(anchor, anchor.monotonicMs)
=== anchor.utcEpochMs` exactly.

Note for §2.3 (non-blocking): whether a content script's isolated world
shares the page document's time origin affects only cross-context
interpretation, never 1.3's design — anchors are captured in-context and
monotonic values are never arithmetically mixed across segments.

### 2.8 Persistent append sequence (1.3.4): field + invariant, assignment deferred

- Envelope field **`appendSeq`**: `null` at creation (not yet stored) or a
  non-negative integer once durably stored. `createEvent` always sets `null`.
- **Assignment is §2.4's**: the transactional writer assigns it at durable-
  write time. 1.3 defines the field, the type, and the invariant — not the
  starting value or the write protocol (those are §2.4's design).
- **Invariant: source times are never rewritten on delivery.** `clockSegmentId`
  and `monotonicMs` are fixed at observation. Delivery order may differ from
  occurrence order (async send, §2.5 retries); `events.jsonl` (§6.2) is in
  `appendSeq` order, and consumers **must** use `monotonicMs` (+ segment
  anchor) for occurrence ordering, never file position.
- Storage pattern for §2.4 (documented, not implemented): setting `appendSeq`
  creates a **new frozen record** with the field set — never in-place
  mutation of the frozen envelope (mirrors 1.1's `addGameToSession` pure
  pattern). Design input for §2.4: an event arriving with non-null
  `appendSeq` indicates double-processing; the writer owns that rule.

### 2.9 References (1.3.5): mechanism only, no role inventory

`refs`: `null` (no references — the common case) or a flat frozen object
mapping **reference role → event ID**:

```json
{ "attemptId": "1b2c3d4e-5f6a-4b7c-8d9e-0f1a2b3c4d5e" }
```

- Keys must match `/^[a-z][a-zA-Z0-9]*Id$/` (camelCase, `Id` suffix —
  documents that values are IDs); values must be UUID v4.
- The mechanism is **ID-kind-agnostic**: it carries event IDs (attempts,
  confirmed moves, help requests, speech utterances are all events) and can
  equally carry recording-segment IDs (§4.10) — the role name
  disambiguates (e.g. `recordingSegmentId`).
- **No reference roles are enumerated here.** Concrete roles and their
  linking semantics belong to the tasks that emit them (attempt→move
  linkage is §3.2/§3.4's; utterance links are §3.4's; segment links are
  §4.10's). Defining the graph now would preempt those tasks and invent
  requirements. Illustrative examples only: `attemptId`, `moveId`,
  `helpRequestId`, `utteranceId`, `recordingSegmentId`.
- References never repeat contents — the referenced event carries the data;
  `refs` carries only the ID (PLAN 1.3.5, "without repeating their
  contents").

### 2.10 Module placement: new file `event_envelope.js`, same pattern

New file `event_envelope.js` at repo root: dependency-free plain script,
guarded `BlindfoldSession` global, IIFE `'use strict'`, Node
`module.exports` shim, chrome\*-independent, frozen records, plain-JSON
values, `node --test`-testable. Justification: one file per contract task
(1.1/1.2 precedent); shares the namespace without modifying existing
modules.

**Load-order independence** (1.2 contract §2.2 celebrated this; 1.3
preserves it): `event_envelope.js` reads **no** other module's exports at
load time. Its UUID check is a *private* internal function (same pattern as
1.1's `UUID_V4_RE`) — it does **not** re-export `isUuidV4` (that name is
taken) and does not depend on `session_identity.js` being loaded first. The
documented duplication is deliberate and preferable to load-order coupling.

Error conventions mirror 1.1/1.2: `TypeError` = wrong type/shape (including
missing required fields and malformed IDs — e.g. a non-uuid `sessionId`,
consistent with 1.1's `requireValidMetadata` and AC5/AC15); `RangeError` =
value outside the allowed domain (bad event-type syntax, bad sourceContext,
negative/non-integer sequences, malformed `refs` role names); plain `Error` =
unavailable platform capability (`crypto.randomUUID` / `performance.now`
missing — honest failure, no fallback).

## 7. Downstream needs this contract must serve

- **§2.3 (sender):** calls `captureClockAnchor()` at context startup and
  emits the `clock_anchor` event first (`createAnchorEvent`, conventionally
  `sourceSeq: 0`); owns the per-segment `sourceSeq` counter (starts 0,
  +1/event); captures `performance.now()` at the observation point and
  passes it as `monotonicMs` (contract never captures event times itself —
  keeps factories pure and deterministically testable); never rewrites
  source times on retry. *Design input:* decide segment/anchor creation
  when no session is active (envelope requires `sessionId`).
- **§2.4 (writer):** assigns `appendSeq` by creating a new frozen record
  (never mutating the frozen envelope); deduplicates by `eventId`; owns
  the rule for events arriving with non-null `appendSeq`
  (double-processing signal); uses `isValidEvent` for intake validation.
- **§2.6/§2.7:** SW restart ⇒ new segment ⇒ new `captureClockAnchor()`;
  owns `context_segment_started/ended` event *types* and emission order
  (not defined here — do not preempt).
- **§3.x (instrumentation):** build every event with `createEvent`;
  define each task's `*_EVENT_TYPE` constants in its own module following
  the flat `snake_case` domain-prefix convention and `isEventType`
  validity; define concrete `refs` roles with linking semantics; extend
  the vocabulary table (§2.2.1) in their contracts. Producers needing
  `'conditions_changed'` use `BlindfoldSession.CONDITION_CHANGE_EVENT_TYPE`
  from `session_conditions.js`.
- **§4.10/§4.12:** recording-segment IDs are §4.10's; each segment links
  to its clock anchor (via `refs`, e.g. a `clockAnchorEventId` role, or by
  referencing the anchor event — §4.10 decides); `deriveWallUtcMs` +
  anchor events provide the event-time side of media alignment. Per
  §4.12, chunk-arrival time must never substitute for anchored event time.
- **§5.x:** if the Start/Stop control surface emits events and is none of
  `SOURCE_CONTEXTS`, §5 amends the vocabulary explicitly.
- **§6.2:** `events.jsonl` written in `appendSeq` order; occurrence order
  recovered via (`clockSegmentId`, `monotonicMs`) + anchors — never file
  position.
- **§6.3:** `media-sync.json` references `clock_anchor` events (by
  `eventId`) rather than duplicating anchor payloads.
- Reviewer attention: envelope creep (timestamps/IDs smuggled into
  payloads), invented `refs` roles, wall-clock-per-event proposals,
  `timeOrigin` persistence, and any weakening of the flat-type convention
  are the likeliest failure modes.
