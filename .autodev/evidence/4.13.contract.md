# Task 4.13 contract — finalize recordings at Stop; keep discontinuous or restarted recordings as separate numbered segments

PLAN.md §4.13: "Finalize available chunks on Stop; keep discontinuous or
restarted recordings as separate numbered segments."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 0. What 4.13 is (one paragraph)

4.6 starts the streams, 4.8 extracts chunks incrementally into
`media_chunks`, 4.9 flags discontinuities, 4.10 links clock segments,
4.11 defines the stop-marker seam, and 4.12 provides the (pure, stored-
nowhere) timecode arithmetic. **4.13 is the Stop half of the recording
lifecycle**: on `recorder-stop-streams` it emits the stop sync marker,
waits for the double-beep to be captured, stops every recorder, awaits
the final `dataavailable` flush (boundedly and honestly — see §5),
releases devices, then closes each segment's chunk set: it splits
segments that contain a mid-stream discontinuity with media on both
sides into separate pieces (minting new segmentIds, the 4.6/4.10
anticipation), numbers every piece per `(sessionId, streamKind)` in
chronological order, and marks the manifest `finalizedAtUtc`. 4.13 does
**not** assemble files — §6.4 owns chunk-to-file assembly and §6.5 owns
numbered filenames (consuming 4.13's `segmentNumber`). "Finalize" means
closing the segment's chunk set and declaring it complete, not producing
a file.

## 0.1 PLAN reading notes (flagged for the section-4 auditor)

1. **"Finalize available chunks" — not "all chunks".** PLAN's wording is
   deliberate: 4.13 finalizes *what is available* in `media_chunks` at
   Stop (plus the bounded final-flush wait of §5). A late flush that
   lands after finalization is still in `media_chunks` and §6 exports
   it — the chunk set is append-only; finalization closes the segment,
   it does not freeze the store.
2. **"Numbered segments" vs "numbered files".** 4.13 assigns
   `segmentNumber` on the manifest (per `(sessionId, streamKind)`,
   chronological). §6.5's "numbered files for interrupted recordings"
   consumes these numbers at export time (`microphone-001.webm`, …).
   4.13 defines the numbering; §6.5 defines the filenames.
3. **4.13 mints segmentIds only for post-discontinuity splits.**
   Restart generations are minted by 4.6's start path (the 4.5 §2
   amendment); 4.13 mints solely when a single segment's chunk timeline
   spans a discontinuity with media on both sides (§4). Every segment
   has exactly one uuid-v4 ID (the 4.6 invariant).

## 1. The stop/finalize sequence

New channel message `recorder-stop-streams` (`MSG_STOP_STREAMS`), owned
by a new DOM-free module `finalizer.js` (repo module pattern, fully
injected platform surface). `recorder.js` gains a lazy `getFinalizer()`
(the `getChunkWriter()` precedent); `recorder.html` loads
`finalizer.js`. The `MSG_*` vocabulary grows by exactly one (22→23).

**Guards** (before any device/media action):
- No session → `{ok:false, error:'no-session'}` (the 4.6 precedent).
- Start in progress → `{ok:false, error:'start-in-progress'}` — never
  interleave Stop with a Start.

**Sequence** (all steps best-effort per stream; one stream's failure
never blocks the others — the 4.6/4.8 failure-isolation precedent):

1. Snapshot active streams from `starter.getActiveStreams()`.
2. If any stream is active: `markerId =
   getSyncMarker().emitStopMarker()` inside try/catch (marker failure →
   `markerId:null`, recorded honestly; the marker is auxiliary and can
   never fail Stop). If no stream is active, skip the marker entirely
   (no recorder exists to capture it) and go to step 7 for orphan
   finalization.
3. Wait `STOP_MARKER_WAIT_MS = 1000` for the double-beep capture (§6).
   (Once, globally — not per stream.)
4. For each active stream: `chunkWriter.stopForStream(streamKind)`
   (stops the poll loop; `ondataavailable` stays attached — the 4.8
   seam; idempotent).
5. For each active stream: if `recorder.state === 'recording'`,
   `recorder.stop()` inside try/catch (already-`'inactive'` →
   `InvalidStateError` → skip; no final flush is expected from a dead
   recorder).
6. Final-flush wait (§5): poll until every stopped recorder reports
   `state === 'inactive'` or `FINALIZE_FLUSH_TIMEOUT_MS = 5000`
   elapses; then wait `FINALIZE_WRITE_GRACE_MS = 1000` for the async
   IDB writes to land.
7. For each active stream: `trackMonitor.detachStream(streamKind)` —
   **before** stopping tracks, so the intentional stop does not emit
   spurious `recorder_track_state_changed{ended:true}` /
   `stream_discontinuity{reason:'track-ended'}` events (4.9 logs
   mid-session ends; a clean Stop is not a discontinuity).
8. For each active stream: `stream.getTracks().forEach(track =>
   track.stop())` inside per-track try/catch (release devices).
9. Clear the starter registry for the stopped kinds (new additive seam
   `discardActiveStream(streamKind)` on the starter — name at the
   builder's discretion, behavior fixed here), so a later
   `recorder-start-streams` passes the `already-started` guard.
10. Finalize pass (§§2–4): splits → numbering → `finalizedAtUtc`.
11. Response (see §8).

**Crash-recovery path:** with no active streams but unfinalized
manifest records for the session (a previous generation died without
Stop), steps 2–9 are skipped and step 10 finalizes the orphans. This is
also what makes 4.9's restart pre-check correct going forward:
finalized orphans are excluded from future restart detection.

## 2. The finalized marker

**Field name: `finalizedAtUtc`** — ISO-8601 UTC string, `null` until
finalized. This *is* 4.9's reserved `MANIFEST_FINALIZED_FIELD`: 4.13's
builder sets `recorder.js`'s `MANIFEST_FINALIZED_FIELD = 'finalizedAtUtc'`
(replacing the `null` reservation), and 4.9's existing
`isManifestRecordFinalized()` exclusion then works as designed — no
other 4.9 code change. Written per manifest record (per segmentId).

Manifest widening, deliberate, exact-keys discipline: `MANIFEST_KEYS`
16 → 18, appended with `// 4.13-owned:` comments:
- `segmentNumber`: integer|null — 1-based ordinal per
  `(sessionId, streamKind)`, chronological by `createdAtUtc`
  (tie-break: lexicographic `segmentId`, for determinism). `null`
  until the finalize pass.
- `finalizedAtUtc`: string|null — when the finalize pass marked this
  record. `null` until finalized.

`DB_VERSION` stays 2. No new store, no new index.

## 3. Segment numbering

At finalize, per `(sessionId, streamKind)`: collect all unfinalized
records **plus** any pieces minted by the split pass (§4), sort by
`(createdAtUtc, segmentId)`, assign `segmentNumber` 1..N. The ordering
is chronological across restart generations (old generation =
earlier `createdAtUtc` = lower numbers) and across split pieces
(pre-gap piece keeps the original `createdAtUtc`; post-gap pieces get
finalize-time `createdAtUtc`, so they sort after — §4).

Numbering is deterministic and idempotent: a re-finalize keeps existing
numbers on already-finalized records (they are skipped, not
renumbered). A session that never finalizes (crash before Stop) keeps
`segmentNumber:null`; §6.5 numbers on the fly for such sessions.

## 4. Re-segmentation (the split procedure)

**When:** at finalize, for each unfinalized segment, 4.13 reads that
segment's `stream_discontinuity` events from the events store (query by
the `bySessionId` index, filter `eventType === 'stream_discontinuity'`
and `refs.segmentId === segmentId` in memory — session-scoped volume).
For each event with `reason !== 'restart'` and `lastChunkIndex != null`:

- Let `maxIdx` = the segment's maximum stored `chunkIndex`.
- If `maxIdx > lastChunkIndex` (media exists on **both** sides of the
  gap): split. Otherwise: no split (the gap is terminal — the common
  case for `track-ended`, `chunk-stalled`, `chunk-quota-exceeded`,
  `chunk-write-error`, where the poll loop stopped or the recorder
  died).
- Multiple gaps in one segment: sort by `lastChunkIndex` ascending and
  split into N+1 pieces.

**How (per split):**
1. Mint a fresh uuid-v4 `segmentId` for the post-gap piece (the 4.6
   invariant: exactly one ID per segment).
2. Re-key the post-gap chunks: in a **single IDB transaction**
   (atomic — a mid-split document death leaves either the old keys or
   the new keys, never a mixture), delete `(oldSegmentId, idx)` and
   put `(newSegmentId, idx - (lastChunkIndex + 1))` for every
   `idx > lastChunkIndex`. Post-gap chunks are re-indexed 0-based per
   the 4.8 "chunkIndex is 0-based per segment" rule (the original index
   is derivable: `newIdx + lastChunkIndex + 1`).
3. Write the new piece's manifest record: clone the original's
   4.5/4.6/4.7 fields (`sessionId`, `gameId`, `streamKind`,
   `requestedMimeType`, `actualMimeType`, `fileExtension`,
   `streamStartedAtUtc`, `streamStartedAtMonotonicMs`,
   `effectiveDeviceId`, `audioTrackPresent`, `videoTrackPresent`,
   `screenAudioContent`, `micAudioContent` — the piece is the same
   stream, so the stream's identity fields are unchanged), with fresh
   `segmentId`, fresh `createdAtUtc` (now), and a fresh
   `clockSegmentId` via 4.10's `linkClockSegment({segmentId,
   getAnchor})` (written fresh per the 4.10 contract §3.2 — never
   copied — even though the value will normally equal the generation's
   anchor id). `segmentNumber`/`finalizedAtUtc` are assigned in the
   numbering/finalize pass (§3), not here.
4. Linking can never fail the finalize: a linker failure → the piece
   record carries `clockSegmentId:null` (the 4.10 precedent).

**`'restart'` discontinuities never trigger splits** — restart
generations already have separate segmentIds from 4.6's start path;
they are numbered as separate pieces by §3.

## 5. The final-flush await

4.8 exposes no promise for the final `stop()` flush (its forward note).
4.13's design:

- **Primary signal:** `recorder.state`. After `recorder.stop()`, poll
  (100 ms interval) until every stopped recorder reports
  `'inactive'` or `FINALIZE_FLUSH_TIMEOUT_MS = 5000` elapses. Per
  spec, `stop()` queues the final `dataavailable` before the
  `state` transition, so `'inactive'` means the encoder has handed
  off its last Blob.
- **Write grace:** then wait `FINALIZE_WRITE_GRACE_MS = 1000` for
  4.8's async IDB `put` to land.
- **Honesty on timeout:** if the timeout elapses with recorders still
  not `'inactive'`, finalize with the available chunks and set
  per-stream `flushTimedOut:true` in the response. A late chunk that
  lands afterwards is still in `media_chunks` (append-only) and §6
  exports it — finalization closes the segment, it does not freeze
  the store (§0.1.1).
- **No final flush expected** when `recorder.stop()` was skipped
  (already inactive): the wait still runs (it returns immediately —
  all recorders already `'inactive'`) for uniformity.

4.13 does **not** poll `lastChunkIndex` for advancement: a 0-byte final
flush is legitimately dropped by 4.8 (no index consumed), so index
advancement is not a reliable completion signal. Recorder state is.

## 6. Stop-marker timing

`emitStopMarker()` (4.11) returns the `markerId` synchronously; the
second beep is scheduled 150 ms later (best-effort `setTimeout`); each
beep is 250 ms. Audio timeline: beep 1 ≈ t+0–250 ms, beep 2 ≈
t+150–400 ms, plus `HTMLAudioElement` output latency and acoustic
propagation.

`STOP_MARKER_WAIT_MS = 1000`: covers the full 400 ms double-beep plus
output/encoder latency with margin. The cost is ~1 s of trailing audio
per recording — acceptable for a research record, and tunable in §7
(the value is a named, V1-pinned constant).

4.11's contract establishes that alignment uses the marker **onset**;
a truncated tail does not invalidate the marker. The wait is about
AC11 human-distinguishability of the double-beep, per the 4.11 review.

The wait is once, globally (the stop marker is per-generation, one
`markerId`), before any `recorder.stop()`.

## 7. Idempotency

- **Double Stop:** the second `recorder-stop-streams` finds no active
  streams and no unfinalized records → `{ok:true, streams:{},
  note:'nothing-to-finalize'}`. Already-finalized records are never
  renumbered or re-marked.
- **Stop with no streams and no orphans:** same no-op response.
- **Stop during `start-in-progress`:** `{ok:false,
  error:'start-in-progress'}` (guard, §1).
- **Partial failure:** per-stream `{ok:false, error, stage}` entries;
  other streams still finalize. A later `recorder-stop-streams`
  retries only the still-unfinalized records.

## 8. Module, wiring, and response

- **New module `finalizer.js`**, DOM-free, repo module pattern,
  `createFinalizer({...})` with fully injected platform surface
  (`setTimeout`/`setInterval`/`clearInterval`, db chunk + manifest
  access, event-log read, `crypto.randomUUID` via the existing
  uuid helper, `performanceNow`, `nowUtcIso`). Never throws into the
  channel handler: per-stream try/catch, top-level guard.
- `recorder.js`: `MSG_STOP_STREAMS = 'recorder-stop-streams'`, lazy
  `getFinalizer()`, handler wiring; sets
  `MANIFEST_FINALIZED_FIELD = 'finalizedAtUtc'`. `recorder.html`
  loads `finalizer.js`.
- The finalizer consumes (never modifies): `starter.getActiveStreams()`
  + `discardActiveStream()`, `chunkWriter.stopForStream()` +
  `getChunkState()`, `trackMonitor.detachStream()`,
  `clockLink.linkClockSegment`, `syncMarker.emitStopMarker()`,
  `format_support` manifest reads/writes, the events store.
- 4.13 does **not** use 4.12's `timecode.js`: no timestamp arithmetic
  is needed (splits key off `lastChunkIndex`; numbering off
  `createdAtUtc`). The 4.12 library remains for §6.3/4.14.

**Response shape:**
```
{
  ok: true,
  markerId: '<uuid>' | null,
  finalizedAtUtc: '<iso>',
  streams: {
    microphone: { ok: true,
      segments: [{ segmentId, segmentNumber, chunkCount }] },
    screen:     { ok: false, error: '<name>', stage: '<step>',
      segments: [] },
    webcam:     { ok: true, segments: [...] }
  }
}
```
`chunkCount` is counted at finalize time (not persisted — derivable).
`flushTimedOut:true` added per stream when §5's timeout elapses.

## 10. Acceptance criteria

### V1 — static (AC1–AC8)

- **AC1 — stop sequence.** `finalizer.js` implements the §1 11-step
  sequence in order: guards → snapshot → stop marker (iff active
  streams) → `STOP_MARKER_WAIT_MS` → `stopForStream` per stream →
  `recorder.stop()` per stream (skipped when not `'recording'`) →
  flush wait → monitor detach → track stop → registry discard →
  finalize pass → response. Marker failure can never fail Stop
  (V1-pinned: throwing `emitStopMarker` → `markerId:null`, sequence
  continues).
- **AC2 — finalized marker.** `MANIFEST_KEYS` is exactly the 18-key
  shape (16 prior + `segmentNumber` + `finalizedAtUtc`, `//
  4.13-owned:` comments); `finalizedAtUtc` is null-or-ISO-string;
  `segmentNumber` is null-or-positive-integer; exact-keys validator
  still rejects a 19th key. `recorder.js` sets
  `MANIFEST_FINALIZED_FIELD = 'finalizedAtUtc'`, and 4.9's restart
  pre-check excludes finalized records (V1-pinned: pre-check with a
  finalized record present → no spurious `'restart'`).
- **AC3 — numbering.** Per `(sessionId, streamKind)`, chronological
  by `(createdAtUtc, segmentId)`, 1-based, deterministic; restart
  generations number as separate pieces (old=1, new=2); re-finalize
  keeps existing numbers.
- **AC4 — splits.** A segment with a non-`'restart'` discontinuity
  and `maxIdx > lastChunkIndex` splits: new uuid-v4 ID, post-gap
  chunks re-keyed 0-based in a single IDB transaction, new manifest
  record cloned with fresh `segmentId`/`createdAtUtc`/`clockSegmentId`
  (via 4.10's linker); no post-gap chunks → no split; `'restart'`
  never splits. Multiple gaps → N+1 pieces.
- **AC5 — final-flush await.** Bounded wait per §5
  (`FINALIZE_FLUSH_TIMEOUT_MS`, `FINALIZE_WRITE_GRACE_MS`, named
  V1-pinned constants); timeout → finalize-with-available +
  `flushTimedOut:true` (honest, not silent); no `lastChunkIndex`
  polling (0-byte flushes are legitimately index-less).
- **AC6 — idempotency + failure isolation.** Double Stop →
  `nothing-to-finalize` no-op; `start-in-progress` → guarded
  rejection; one stream's finalize failure → per-stream
  `{ok:false, error, stage}`, others proceed; later Stop retries
  only unfinalized records.
- **AC7 — vocabulary and file discipline.** Exactly one new channel
  message (`recorder-stop-streams`; `MSG_*` 22→23); no new event
  types (the manifest mark + stop `sync_marker` events are the
  durable trace); `DB_VERSION` stays 2; no new store/index;
  `finalizer.js` references no media-capture APIs beyond the
  injected recorder/stream handles (the 4.1 boundary — recorder.js
  already owns the orchestration); content scripts byte-identical;
  no gameplay change; PLAN.md unmodified; no §6 bleed (no file
  assembly, no ZIP, no downloads).
- **AC8 — changed-files discipline.** Working-tree diff touches only:
  `finalizer.js` (new), `tests/finalizer.test.js` (new),
  `recorder.js` (wiring + `MANIFEST_FINALIZED_FIELD`),
  `recorder.html` (script tag), `stream_starter.js` (additive
  `discardActiveStream` seam), `format_support.js` (16→18 widening per
  AC2), cumulative pin evolutions with
  justification comments, `.autodev/evidence/4.13.*`,
  `.autodev/DECISIONS.md`. No 4.14/§5/§6 bleed.

## 11. Explicit non-goals

- No chunk-to-file assembly (that's §6.4 — 4.13 never builds a
  media file, never transcodes, never writes to downloads/OPFS).
- No ZIP packaging (§6.6).
- No playback UI.
- No chunk or segment deletion (§2.9 retention owns deletion;
  finalized data stays until retention runs).
- No timestamp arithmetic (4.12's library is not needed here).
- No new event types (the manifest mark + 4.11's stop marker events
  are the durable trace; 4.14 reads the manifest).
- No auto-recovery or stream restart (4.9/§5 territory).
- No changes to 4.6/4.8/4.9/4.10/4.11/4.12 producer behavior beyond
  the additive seams named in §8.

## 12. Honest limitations

- The stop marker's audibility/visibility *in the recordings* needs
  human ears/eyes (AC11/§7); V2 proves the emission, the wait, and
  the capture window, not the perception.
- A final flush that lands after `FINALIZE_WRITE_GRACE_MS` is not in
  the finalize tally but remains exportable (§6 reads the store, not
  the tally).
- `STOP_MARKER_WAIT_MS` (1 s) delays the visible Stop by ~1 s plus
  the flush wait; the constants are named and tunable in §7.
- The split transaction is atomic per segment, but a document death
  *between* segments' splits leaves some segments split and others
  not — a re-finalize completes the remainder (idempotent, §7).
- Orphan finalization (no active streams) emits no stop marker: with
  no recorders running there is no media to align the marker to.
