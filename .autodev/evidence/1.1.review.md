## SHOULD_FIX

### SF1. Duplicate explicit gameId is silently appended, corrupting the uniqueness invariant

- **Location:** `session_identity.js` `addGameToSession`, lines ~128–145.
- **Evidence:** Independent probe — `addGameToSession(addGameToSession(m, gid), gid)`
  yields `gameIds.length === 2` with the same UUID twice.
- **Reasoning:** PLAN's export section states "unique IDs establish identity".
  Two identical entries in `gameIds` are not two identities; they are one
  identity recorded twice, which misrepresents evidence. The contract's AC6
  ("appends a new game ID… rejects non-uuid game IDs") is satisfied as written,
  and the normal path (`newGameId()` per call) cannot collide, so this is not
  a BLOCKER for 1.1. But the semantic choice is unmade: dedupe silently
  (hides a detection bug), throw loudly (preserves evidence of the bug), or
  allow (corrupts identity). Throwing also interacts with §2.4's event-level
  dedup-by-ID (later task) — the game-level policy should be decided once.
- **Recommendation:** Record the decision in `.autodev/DECISIONS.md` and
  revisit at §3.5 (game detection), where the double-detection scenario
  actually arises. My recommendation: detection-time dedup (§3.5) plus a
  loud `Error` on duplicate explicit gameId here, so a detection bug is
  evidence rather than silent identity corruption. Do not silently dedupe
  here — "preserve actual failures… where PLAN.md requires them".

### SF2. Returned records are caller-mutable; the append-only invariant is only conventional

- **Location:** `session_identity.js` `createSessionMetadata` (~lines 100–125),
  `addGameToSession` (~lines 128–145).
- **Evidence:** Independent probe — `r.gameIds.push('tampered')` succeeds on
  a record returned by `createSessionMetadata`. The pipeline is pure (never
  mutates *inputs*), but nothing stops a future §5/§2 call site from mutating
  a record it holds and then storing or appending from it.
- **Reasoning:** This is a raw-data-integrity mission; `gameIds` order and
  content are evidence. The test suite itself proves `addGameToSession`
  tolerates deep-frozen inputs ("never mutates the input record (deep-frozen
  input)"), so freezing outputs is safe: `structuredClone`, `JSON.stringify`,
  `Object.keys`, and IndexedDB storage are all unaffected by frozen records.
- **Recommendation:** `Object.freeze` the returned record and its `gameIds`
  array (and document it). This is within the contract — AC9's exact-key test
  still passes — and hardens AC6/AC7 for downstream §2.2 storage and §5.9
  shared-session handling. Low risk, real benefit.

## NOTE

### N1. `null` gameId treated as omitted — documented, acceptable

- **Location:** `session_identity.js` line ~132; build report "Deviations".
- The contract §3.1 says "generates one if omitted"; the builder extended
  "omitted" to `undefined`/`null` and recorded the interpretation in
  `1.1.build.md`. `null` is never a valid gameId, so generation (vs. throw)
  is the only sensible non-throwing behavior. No change requested; keep the
  documentation.

### N2. `addGameToSession` silently strips extra keys the validator accepts

- **Location:** `requireValidMetadata` (~lines 74–98) enforces the six required
  fields but does not reject extra keys; `addGameToSession` then rebuilds
  exactly six keys, dropping extras. Probe confirmed: an input record with
  `createdAt` passes validation but the output loses it.
- Consistent with the contract's "exactly six keys — no more, no fewer"
  (§3.2). Flagged for the coordinator because **§1.2 (session conditions)**
  may want to extend this record: if initial conditions / observed-manual
  sources live in the same metadata object, this factory's six-key rebuild
  will need a contract amendment. Do not let a later task silently widen or
  narrow the record without updating §3.2.

### N3. `requireValidMetadata` uses strict `schemaVersion` equality

- **Location:** `session_identity.js` lines ~85–87. A record stamped
  `"2.0.0"` throws `TypeError`.
- Correct for 1.1 (single schema version exists). When the schema is bumped
  per contract §2.5 ("Bump when the stored format changes"), a migration path
  — not just rejection — must be designed; rejection alone would strand
  §2.6 restores across an upgrade. Future work, not a 1.1 defect.

### N4. Frozen `UUID_V4_RE` is safe; structuredClone concern does not apply

- `UUID_V4_RE` is `Object.freeze`d. Verified: as a non-global regex,
  `.test()` ignores `lastIndex`, and repeated calls work after freezing.
- RegExp indeed does not structuredClone — but the regex is never part of
  the stored record (only the six plain-JSON keys), so AC16 is unaffected.
  Confirmed by the passing `structuredClone` + JSON round-trip test.

### N5. `crypto.randomUUID` availability assumption is honest, V3 deferred

- The contract §2.1 claims availability in content-script isolated world,
  MV3 service worker, and Node; the implementation throws (no weak fallback)
  when unavailable, which is the honest failure mode and matches AC3.
- Actual extension-context loading (`importScripts` in the §2.1 service
  worker, content-script registration in `manifest.json`) is explicitly
  deferred in the contract §5 and test-file header. The builder did not
  wire `manifest.json` (verified: no existing files modified). This is per
  contract, but the coordinator should ensure the deferred AC17-SW-loading
  and AC4/AC8/AC11-wiring items are actually revisited when §2.1/§3.1/§3.5/§5.1
  land — they are the likeliest place for this task's assumptions to break.

### N6. No test-mirroring, no scope creep, no privacy issues found

- Tests assert real behavior (1,000-sample UUID shape/bit positions, 100k
  uniqueness, stubbed-crypto throw, deep-frozen-input immutability, banned
  key-set for AC14, clone round-trips), not implementation text — except the
  AC17 static source checks, which are legitimately contract-derived.
- No Start wiring, detection, persistence, export, analysis, or gameplay
  changes. Exports match the contract's table exactly (test-enforced).
- IDs are random UUIDs only; no PII, no timestamps-as-identity, no derived
  fields (no sequence numbers, dates, SAN/PGN/FEN, durations, counts).
