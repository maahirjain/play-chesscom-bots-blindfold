# 6.4 contract — Assemble stored chunks into original-format media files without unnecessary transcoding

**Planner:** task planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §6.4. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope

PLAN.md §6.4: "Assemble stored chunks into original-format microphone,
screen, and webcam files without unnecessary transcoding."

**PLAN evidence:** the §(a) export table defines the media files' raw
data: "Original-format media files (assembled from stored chunks, no
transcoding)." The 4.13 finalizer numbers segments; §6 consumes
`segmentNumber` + chunks at export time (finalizer.js:24).

**What 6.4 does:** Add a pure builder function (in the SW-side
`exporter.js` module, per the section architecture and 6.1–6.3's
precedent) that takes one segment's stored chunk records (already read
from IndexedDB in key order by 6.6's orchestration) and returns the
assembled media as Blob parts plus integrity metadata: byte-concatenation
in `chunkIndex` order, incremental CRC-32, byte length, chunk count.
Zero transcoding — the output bytes are exactly the stored chunk bytes.

**What 6.4 does NOT do:** It does not read IndexedDB itself (6.6's
orchestration reads `media_chunks` via the compound-key range
`[segmentId, -1]` → `[segmentId, MAX_SAFE_INTEGER]` per the 4.13
`readSegmentChunks` precedent, and passes plain records in). It does
not name files (6.5). It does not build the ZIP (6.6). It does not
decide which segments to export (6.6 iterates the manifest).

## 2. Inputs

The builder function signature (names at the builder's discretion):

```
assembleSegmentChunks({ chunks })
```

| Input | Source | Required? |
|-------|--------|-----------|
| `chunks` | `media_chunks` store rows for ONE segment, in `[segmentId, chunkIndex]` key order (6.6's orchestration reads them) | Yes — may be empty (a segment with zero stored chunks assembles to a zero-byte file with CRC 0; that is honest data, not an error) |

Each chunk is the stored record: `{segmentId, chunkIndex,
receivedAtUtc, receivedAtMonotonicMs, timecodeMs, data: Blob}` (chunk_writer.js).
Only `chunkIndex` and `data` are consumed by the assembly; the rest are
ignored (not validated, not copied).

All inputs are plain data. The function performs no IndexedDB I/O, reads
no clock, mints no IDs. It is `async` only because reading Blob bytes
(`arrayBuffer()`) is asynchronous — this is data access, not I/O in the
architectural sense.

## 3. Behavior (exact)

1. **Validation (TypeError, fail-closed):**
   - `chunks` must be an array; each element must be a plain object.
   - Each chunk's `data` must be a Blob (or Blob-like with
     `arrayBuffer()` and `size`); missing/non-Blob `data` → TypeError
     naming the chunkIndex.
   - Each chunk's `chunkIndex` must be a non-negative integer;
     duplicate `chunkIndex` values → TypeError (the compound key
     prevents this in practice; the check is defensive).
   - **Gaps are honest, not errors.** The 4.8 writer reserves
     `chunkIndex` synchronously; a failed write leaves a gap (never a
     duplicate). Gaps in the sequence are preserved as-is — the
     assembly concatenates what exists, in key order. It does not
     invent, interpolate, or re-index chunks.

2. **Assembly (byte-concatenation, zero transcoding):**
   - Process chunks in the input order (which 6.6 guarantees is
     `chunkIndex` ascending via the key-range read).
   - For each chunk: read `data` as an ArrayBuffer, append its bytes
     to the output sequence.
   - **No bytes are added, removed, or transformed.** No container
     headers are synthesized, no codec data is re-encoded, no
     initialization segment is injected. The output is exactly the
     concatenation of the stored chunk payloads.
   - **Rationale (why concatenation is correct):** MediaRecorder emits
     chunks where the first chunk of a recording carries the container
     initialization segment and subsequent chunks carry media data.
     Concatenating one recorder's chunks in emission order reproduces
     the original media file byte-for-byte. This is the "original
     format" PLAN requires.

3. **Integrity metadata (computed incrementally):**
   - `byteLength`: total bytes across all chunks (sum of chunk sizes).
   - `crc32`: CRC-32 (ISO 3309, the ZIP/ZIP-Stored checksum) computed
     incrementally as each chunk's bytes are read. The running CRC is
     updated per chunk; at no point is the entire file's bytes held
     as a single buffer for checksumming.
   - `chunkCount`: number of chunks assembled.

4. **Streaming (the 6.6 memory requirement):**
   - The function returns `parts`: an array of Blobs (one per input
     chunk, in order), NOT a single concatenated Blob or ArrayBuffer.
   - JS-heap memory during assembly is O(largest single chunk), not
     O(file). Each chunk's ArrayBuffer is released after its CRC is
     updated and its Blob is pushed to `parts`; the bytes live in the
     browser's blob storage (disk-backed in Chrome).
   - 6.6's ZIP writer consumes `parts` directly as the file-data
     section (with data descriptors carrying the precomputed CRC —
     see §5).

5. **Return value:**
   ```js
   {
     parts: Blob[],       // one per chunk, in chunkIndex order
     byteLength: number,  // total bytes
     crc32: number,       // unsigned 32-bit CRC-32 of the concatenated bytes
     chunkCount: number   // chunks.length
   }
   ```

## 4. Honest limitations (documented, not defects)

1. **Split pieces may lack initialization data.** 4.13's split pass
   re-keys post-gap chunks to a new segmentId without modifying the
   chunk bytes. Those chunks are mid-stream MediaRecorder output —
   they do not begin with a container initialization segment. The
   assembled file is the honest byte-concatenation of what was stored,
   but it may not play standalone in a media player. This is a
   property of the stored data (the split is 4.13's honest
   discontinuity bookkeeping), not a defect in the assembly. 6.6's
   orchestration sees the manifest records and may surface this; 6.4
   does not fabricate init data to "fix" it.

2. **Gaps in chunkIndex produce a file with missing media.** The
   assembly does not invent data for gaps. The resulting file's
   timeline will have a hole where the failed write occurred. This is
   honest — the data was never captured.

3. **Zero-chunk segments** produce a zero-byte file (CRC 0). This is
   honest data (a segment was created but no chunks were stored).

## 5. Coordination with 6.6 (ZIP writer)

6.4's outputs feed 6.6's ZIP assembly directly:

- `parts` → the file-data section of the ZIP entry (local header →
  parts → data descriptor).
- `crc32` and `byteLength` → the data descriptor (general-purpose flag
  bit 3 set in the local header; real values in the descriptor and
  central directory). This is the standard streaming-ZIP technique —
  it avoids buffering the whole file to compute the CRC before
  writing the header.
- `chunkCount` → 6.6's `chunkStats` for 6.3's media-sync.json
  (alongside `chunksAfterFinalize`, which 6.6 computes by comparing
  chunk `receivedAtUtc` to the manifest's `finalizedAtUtc`).

## 6. Acceptance criteria

### V1 — static/unit (Node, no IndexedDB)

- [ ] **AC1.** Byte-concatenation: N chunk Blobs with known bytes
  assemble to a `parts` array whose concatenated bytes equal the
  expected byte sequence in chunkIndex order. Out-of-order input
  (if 6.6 ever mis-ordered) is assembled in input order — the
  function trusts 6.6's key-order guarantee and documents it.
- [ ] **AC2.** Zero transcoding: output bytes are byte-identical to
  the input chunk bytes (no headers added, no bytes transformed).
  Pinned by a test with a synthetic WebM-like byte pattern
  (init segment + clusters).
- [ ] **AC3.** CRC-32 correctness: pinned against known vectors
  (empty input → 0; `"123456789"` → `0xCBF43926`; multi-chunk
  incremental equals single-buffer).
- [ ] **AC4.** Streaming shape: `parts.length === chunks.length`
  (one Blob per chunk, not one merged Blob); the function never
  allocates a single buffer of `byteLength`.
- [ ] **AC5.** Malformed input fails closed: non-array → TypeError;
  missing `data` → TypeError naming the chunkIndex; duplicate
  `chunkIndex` → TypeError; non-Blob `data` → TypeError.
- [ ] **AC6.** Gaps are honest: chunks with indexes `[0, 2, 5]`
  assemble without error; `chunkCount` is 3; no re-indexing.
- [ ] **AC7.** Empty input → `{parts: [], byteLength: 0, crc32: 0,
  chunkCount: 0}` (no throw).
- [ ] **AC8.** Diff discipline: `exporter.js` + `tests/exporter.test.js`
  only (product); no new messages/event types/stores/permissions;
  PLAN.md unmodified (pinned by test).

### V2 — integration (real headless Chrome, repo-path argv)

- [ ] **AC9.** Seed `media_chunks` via the real chunk-writer paths
  (or direct validated puts), read via the compound-key range,
  run `assembleSegmentChunks` in the SW context: assert the
  concatenated `parts` bytes equal the original chunk bytes and
  `crc32` matches an independent computation.
- [ ] **AC10.** Split-piece case: chunks re-keyed per 4.13's split
  procedure assemble to the honest concatenation (no init injection).
- [ ] **AC11.** Regressions: `sw-exporter.js` (6.1–6.3) still 17/17;
  V1 suite green.

### V3 — deferred to §7 / owner device
