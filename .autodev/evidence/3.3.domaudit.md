# 3.3.5 DOM audit — other visual-aid surfaces (2026-10-06)

PLAN.md 3.3.5: "Audit what the current DOM can expose for other visual aids;
document that extension visibility events do not prove complete absence of
visual information."

**Method:** code analysis of the extension's known DOM surfaces (selectors in
`content.js` / `chess_utils.js` / `sounds.js`) plus the documented Chess.com
bot-game page structure. **Live-page verification is V3-deferred (§7 / owner
device)** — every per-surface verdict below is marked [code-analysis] or
[live-verified] accordingly. All verdicts below are [code-analysis] unless a
V3 pass updates them.

**Epistemic disclaimer (also in DECISIONS.md):** extension visibility events
(`piece_visibility_changed`) record what the extension did to the board's
piece rendering. They do **not** prove the player had no other visual
information: Chess.com's own highlights, eval bar, arrows, a second monitor,
screen-reader output, or anything else outside the extension's observation
is invisible to these events. Any analysis that treats "pieces hidden" as
"player saw nothing" is unsound.

## Candidate surfaces

### 1. Last-move highlight squares
- **What:** Chess.com highlights the from/to squares of the last move.
- **Observable:** likely yes — rendered inside `wc-chess-board` (the element
  `getBoardElement()` already reads). [code-analysis]
- **Recorded today:** no. Not in 3.3 scope; a 3.5-or-later decision whether
  highlight presence is worth recording.

### 2. Check highlight
- **What:** the king's square is highlighted when in check.
- **Observable:** likely yes — same board element as above. [code-analysis]
- **Recorded today:** no.

### 3. Premove indicators
- **What:** Chess.com shows a premove arrow/indicator when a premove is queued.
- **Observable:** likely yes inside `wc-chess-board`, if the bot-game page
  renders premoves at all. [code-analysis]
- **Recorded today:** no.

### 4. Legal-move dots / hover highlights
- **What:** dots on legal destination squares when a piece is selected/dragged.
- **Observable:** likely yes inside `wc-chess-board` during mouse interaction.
- **Recorded today:** no. Note the 3.2.7 limitation: mouse *attempts* have no
  reliable signal; the dots' presence is a separate (unrecorded) observation.

### 5. Engine evaluation bar / suggested-move arrows
- **What:** an eval bar and/or best-move arrows, if Chess.com shows them.
- **Observable in bot games:** **unknown, probably absent** — bot games on
  chess.com/play/computer are not known to render an eval bar or engine
  arrows the way analysis boards do. The extension has never observed these
  selectors (no code references them). [code-analysis]
- **Recorded today:** no. If a V3 live pass finds them, 3.3.4's unsupported
  marking must be revisited.

### 6. Takeback / new-game buttons and result dialogs
- **What:** UI controls for takebacks, new games, resign; end-of-game dialogs.
- **Observable:** the move list (`.play-controller-moveList`) is already
  observed (3.1); buttons/dialogs are outside the current selectors.
  [code-analysis]
- **Recorded today:** partially — 3.1 detects takebacks via move-list
  revision; 3.5.2 owns game resets; 3.5.3 owns result/termination info.
  Not duplicated here.

### 7. Chess.com "hints" / assistance toggles in settings UI
- **What:** any first-party hint button or assistance setting reachable from
  the page.
- **Observable:** **none found.** Codebase survey (3.3.4): zero references
  to hints, assistance settings, or engine-evaluation DOM in product code.
  The 1.2 `assistanceSettings` conditions field is a session-level record,
  not a DOM observation. [code-analysis]
- **Recorded today:** no. **Explicitly unsupported coverage** (3.3.4):
  the extension does not observe Chess.com hints or assistance-setting
  changes. If a V3 live pass finds a reliable DOM signal, this marking is
  revisited; until then, recording unreliably-observed "hints" would
  manufacture evidence.
