## Findings

### SHOULD_FIX

**SF-1 — `select()` sets in-memory state before persistence succeeds**
(`device_selection.js`, `select()`, ~line 380): `selection`/`selectionSource`
are assigned *before* `storage.set()` resolves. If the persist fails
(localStorage quota/disabled — rare but real), the channel returns
`{ok:false, error:'internal-error'}` while the in-memory selection is
already `'user'` — and would be announced at the next session activation
as if the selection had succeeded. Fix: move the assignment (and the
`'user'` source) into the `.then()` after `storage.set()` resolves, so a
failed persist leaves no trace. Mechanical, non-blocking (failure mode is
rare), but it is a genuine state/response inconsistency.

### NOTEs

**N-1 — Deviation #1 (localStorage) verified TRUE and sound.** The official
Chrome offscreen docs state the `runtime` API is the *only* extension API
available in offscreen documents, so `chrome.storage` is unreachable there
regardless of manifest permissions — the builder's V2 finding is correct
and the contract's chrome.storage plan could not have worked. Document
localStorage is origin-scoped (`chrome-extension://<id>`), survives
browser restarts, extension updates, and document kill/recreate, and is
shared with §5's popup on the same origin — adequate for 5.3's
"remember previous selections". Caveats (not defects): split-incognito
gets a separate document/profile (selection won't carry); no cross-device
sync (correct for a per-machine setting). A SW-relay persistence design
was possible but strictly more complex for zero gain.

**N-2 — Deviation #4 (probe-denied persistence) is contract-mandated and
the right trade-off.** Contract §2.3 pins it: a probe-observed `'denied'`
persists until a later probe succeeds; the advisory `permissions.query`
never clears it. Answering the brief's question directly: yes, the state
stays `'denied'` even if the user later grants in browser settings —
*until the next `mic-request-permission` probe*. This is deliberate (the
query signal is known-quirky; the probe is ground truth) and the user is
never stuck: §5 drives `mic-request-permission` on user action, which
re-probes. Carry-forward for 4.6/§5 (see N-3).

**N-3 — 4.6 must reconcile its own stream-start outcome with the selector
state.** If 4.6 acquires the mic stream directly (not via
`requestPermission`), a selector stuck at probe-observed `'denied'` will
disagree with reality (`mic-get-state` says denied while recording
works). 4.6 should report its stream-start outcome back through the
selector (or §5 should re-probe at Start) so 4.14/5.6 read a coherent
state. The probe→start revocation race the contract documents (§6.1) is
the same seam.

**N-4 — `invalidateSelection()` has the mirror-image ordering of SF-1.**
In-memory selection is nulled before `storage.remove()` resolves; if the
remove fails, a reboot restores a selection the events said was
`'invalidated'`. Same fix family as SF-1 (clear in-memory only after the
remove resolves, or tolerate-and-document). Rare path; NOTE only.

**N-5 — Dead enum surface.** `SELECTION_SOURCES` includes `'default'`
(`device_selection.js:75`) which nothing in 4.2 ever emits (4.2 "never
silently defaults" — correct), and the validator error strings say
`'microphone_*'` even for the camera kind. Harmless; 4.4 should either use
`'default'` or drop it, and the messages should name the kind.

**N-6 — Test pins honest.** 13 suites evolved with justification comments
following the 2.x/3.x precedent; the stale 4.1-era "vs parent commit"
manifest pin was replaced with a strictly stronger assertion
(`permissions` exactly `['offscreen']`, `git diff HEAD -- manifest.json`
empty) — a justified strengthening, not a weakening.

## Adversarial checks that resolved in the build's favor

- **Event design**: both 4.2 event types have exact-keys validators;
  events travel the existing writer intake (`{kind:'event', event}`,
  `sourceContext:'recording_context'`, lazy per-session clock anchor)
  with sessionId/gameId from the recorder's session seam — no new
  pipeline. Pre-session inertness holds (`isActive()` gates both emitters;
  selection works pre-session as a setting while events stay silent).
- **Channel validation**: `mic-select` rejects non-string/empty deviceId
  at the channel (`invalid-request`); unknown ids → `RangeError` →
  `unknown-device`; absent mediaDevices → `internal-error`. All five
  messages failure-isolated (3.2 SF-1); unknown `msg` still ignored.
- **Label honesty**: empty pre-grant labels map to `null`; no fabrication
  path exists. `OverconstrainedError`/`NotFoundError` correctly invalidate
  stale selections (cleared, stored key dropped, `'invalidated'` event).
- **No retained stream**: every probe track is stopped before
  `requestPermission` resolves (V1-pinned with spies; honestly documented
  as unobservable from outside the document). The probe→start race is
  documented as 4.6's case.
- **Denial V2**: the CDP-`setPermission` attempt was correctly abandoned
  (fake-UI flag bypasses the content setting); the second-browser
  auto-dismiss → genuine `NotAllowedError` is an honest substitution.
- **`recorder-set-session`**: accepts non-empty-string-or-null ids;
  non-uuid ids fail loudly at envelope build (converted to `{ok:false}`)
  — §5's uuid obligation is documented, and failure is observable, never
  silent.
