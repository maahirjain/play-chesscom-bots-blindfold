# 6.2 contract — Export events.jsonl in persistent append order without computed metrics or per-move position duplication

**Planner:** task planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §6.2. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope

PLAN.md §6.2: "Export events.jsonl in persistent append order without
computed metrics or per-move position duplication."

**PLAN evidence:** the §(a) export table defines events.jsonl's raw
data: "Confirmed coordinate moves; raw submitted attempts and actual
validation outcomes; first-edit/submission/confirmation events;
dispatch failures; initial visibility and transitions; help requests;
speech lifecycle; observed assistance changes; history revisions; game
endings; focus/visibility and page lifecycle events; clock anchors;
errors/gaps; optional notes."

**What 6.2 does:** Add a pure builder function (in the SW-side
`exporter.js` module, per the section architecture and 6.1's
precedent) that takes the session's stored event records and returns
the exact `events.jsonl` string for the bundle: one JSON object per
line, in persistent append order, verbatim.

**What 6.2 does NOT do:** It does not read IndexedDB itself (6.6's
orchestration reads the `events` store via the `bySessionId` index
and passes plain records in — the builder is pure and Node-testable).
It does not filter, transform, enrich, or summarize events. It does
not compute anything. It does not touch metadata.json (6.1),
media-sync.json (6.3), or media files (6.4/6.5).

## 2. Inputs

The builder function signature (names at the builder's discretion):

```
buildEventsJsonl({ events })
```

| Input | Source | Required? |
|-------|--------|-----------|
| `events` | `events` store rows for the session (via `bySessionId`; 6.6's orchestration reads them) | Yes — may be empty (a session with zero stored events exports an empty file; that is honest data, not an error) |

All inputs are plain data. The function performs no I/O, reads no
clock, mints no IDs.

Each event is the stored 11-key envelope (`eventId`, `eventType`,
`sessionId`, `gameId`, `sourceContext`, `sourceSeq`, `clockSegmentId`,
`monotonicMs`, `appendSeq`, `refs`, `payload`) with `appendSeq`
assigned by the 2.4 writer (non-null non-negative integer on every
stored row).

## 3. Behavior (exact)

1. **Order:** sort the events by `appendSeq` ascending (numeric).
   This is the persistent append order (PLAN §1.3.4: "Assign a
   persistent append sequence when storing events; preserve source
   times because delivery order may differ from occurrence order").
   The sort must be stable; `appendSeq` values are unique per the
   2.4 sequence counter, so ties indicate corrupt data (see §5).
2. **Serialization:** emit one line per event: `JSON.stringify(event)`,
   lines joined by `'\n'`, with a trailing `'\n'` after the last
   line (standard JSONL). The envelope objects are frozen with
   stable key insertion order (event_envelope.js `EVENT_KEYS`), so
   `JSON.stringify` output is deterministic — byte-stable for 6.7's
   repeatability.
3. **Verbatim passthrough:** every key and value is copied exactly as
   stored. The builder adds no keys, removes no keys, and reorders
   no keys.
4. **No computed metrics:** the builder computes nothing — no
   durations (from `monotonicMs`), no counts, no rates, no
   per-event wall-clock derivation (that is `deriveWallUtcMs`'s job
   at analysis time, not export time). The output contains exactly
   what the store contains.
5. **No per-move position duplication:** the builder does not add
   FEN, SAN, PGN, move numbers, or positions to any event — in
   particular, not to `move_confirmed` events. (The collection
   pipeline already enforces this per 1.4/3.1: "No move numbers, no
   SAN, no per-move FEN, no durations: all derivable.") Conversely,
   the builder does not strip anything either: legitimate stored
   payloads that contain positions — the `game_started` event's
   starting FEN (1.4.1) and 1.4.4 recovery checkpoints — pass
   through verbatim. "No duplication" is a property the builder
   preserves, not a filter it applies.
6. **Empty input:** `events: []` → the empty string (zero lines).
   Not an error.

## 4. Multi-game sessions (5.9)

Events already carry their `gameId`; the stream partitions by game
naturally (the architecture notes `events.jsonl` "partitions by
`gameId` with `game_reset` boundaries (already in the stream)").
6.2 does not regroup, re-partition, or annotate — the boundary
events are in the stream and export verbatim in append order.

## 5. Malformed input (fail-closed, never silent)

- `events` not an array → `TypeError`.
- Any element not a plain object → `TypeError` naming the index.
- Any event with `appendSeq` null, non-integer, or negative →
  `TypeError` naming the `eventId` (when available) and index.
  Rationale: the 2.4 writer assigns `appendSeq` transactionally on
  every stored row; a null/negative value is corrupt data. Per the
  section architecture's corruption-honesty rule, the builder
  surfaces it — never silently skips the event, never silently
  misorders it, never invents a sequence number. 6.6's
  orchestration catches this and answers an honest export error
  naming the store and key.
- Duplicate `appendSeq` values → `TypeError` (the sequence counter
  guarantees uniqueness; a duplicate is corrupt data).

The builder does not re-validate the full 11-key envelope (the 2.4
writer owns intake validation); it validates exactly what its
contract depends on: array shape and `appendSeq` integrity.

## 6. Acceptance criteria

### V1 — static/unit (Node, no IndexedDB)

- [ ] **AC1.** Ordering: fixture events deliberately out of
  `appendSeq` order (including interleaved `sourceSeq`/`monotonicMs`
  that would misorder a naive sort) export in strict `appendSeq`
  ascending order.
- [ ] **AC2.** Verbatim passthrough: every output line parses
  (`JSON.parse`) to a deep-equal of the corresponding input event
  — no added keys, no removed keys, no reordered keys, no
  reformatted values.
- [ ] **AC3.** No metrics, no positions: a fixture containing
  `move_confirmed` events asserts the output lines contain no
  `fen`/`san`/`pgn`/`moveNumber`/`durationMs` keys beyond what the
  inputs carried; a fixture with a `game_started` FEN and a 1.4.4
  recovery checkpoint asserts those payloads survive verbatim
  (not stripped).
- [ ] **AC4.** Malformed inputs: `appendSeq: null`, negative,
  non-integer, and duplicate values each throw `TypeError`
  naming the event; non-array input throws `TypeError`.
- [ ] **AC5.** Byte-stability: the same fixture serialized twice
  yields byte-identical output (for 6.7's repeatability proof).
  Empty array → empty string.
- [ ] **AC6.** Diff discipline: new code lives only in
  `exporter.js` (+ its test file); no changes to stores, writer,
  or content scripts; no new event types/messages/stores/
  permissions (6.6 owns the permission + message); PLAN.md
  unmodified.

### V2 — integration (real headless Chrome, repo-path argv)

- [ ] **AC7.** Seed events via the real 2.4 writer path (out of
  delivery order), read them via `bySessionId` as 6.6 will, run
  the builder: assert the output order matches the store's
  `byAppendSeq` order and every line round-trips to the stored
  record.
- [ ] **AC8.** Regression: full V1 suite green.

### V3 — deferred to §7 / owner device

- [ ] **AC9.** Real session export: events.jsonl opens as valid
  JSONL after ZIP extraction; a game reconstructs from the
  starting FEN + confirmed moves (7.13's collection-correctness
  check consumes this file).

## 7. Explicit non-goals

- Reading IndexedDB (6.6's orchestration does that; 6.2 is pure).
- Filtering or redacting events (export is whole-session).
- Computing wall-clock times, durations, or any metric.
- Adding per-move positions or stripping legitimate ones.
- metadata.json / media-sync.json / media assembly / ZIP (6.1,
  6.3, 6.4–6.6).
- Interpreting the events (no "the user played badly" — raw only).
