## 1. computeCompletion purity/truth table — PASS

**Purity: holds.** The function uses only `isPlainObject`, the module constant `STREAM_KINDS`, and `Object.freeze`. No DOM, no timers, no chrome.*. The result object and warnings array are frozen.

**'complete' is reachable only when everything is truly ok.** Verified by reading and by direct adversarial probing (node -e against the built module):
- Requires: `stopResp.streams` is a plain object; every kind in `STREAM_KINDS` (`microphone`, `screen`, `webcam`) is a plain object with `ok === true` and `flushTimedOut !== true`; AND `flushResult.pending` is a number `=== 0`.
- **flushTimedOut cannot slip through:** the check is strict `=== true`. I verified 4.13's finalizer sets it as a boolean literal (`finalizer.js:820`: `perStream[kind].flushTimedOut = true`), and the 5.10 contract AC1 specifies `flushTimedOut: true` — the implementation matches the contract exactly. A truthy non-boolean would slip through, but that value cannot occur from the real finalizer (out-of-contract input).
- **Undelivered events cannot slip through:** `pending > 0` → `'<N>-events-undelivered'`. Non-numeric, negative, NaN, or string `pending` → `-1` → `'flush-result-unknown'` warning (probed directly: NaN, `'0'`, and missing pending all fail closed).
- **Malformed input fail-closed:** `null`/`undefined` stopResp → `'stop-response-malformed'`; `null` flushResult → `'flush-result-unknown'`; both malformed → two warnings. Never a silent `'complete'` (probed directly).
- Extra stream kinds in `streams` are ignored (contract only requires the three); `ok: true` with a stale `error` field does not warn (correct — the ok flag is authoritative).

## 2. Stop-sequence ordering — PASS

**`onStopComplete` cannot fire before the flush settles.** It is called only inside `finalizeStop`, which is invoked exclusively from the `.then` fulfillment/rejection callbacks of the flush promise chain (`Promise.resolve(flushPromise).then(fr => finalizeStop(...), () => finalizeStop(...))`). There is no other call site.

**The button never shows clean idle during the flush.** Between stop-response arrival and flush resolution, the button shows `"Finalizing…"` (enabled, null detail) — distinct from clean idle (`"Start"`, null detail). Phase stays `STOPPING` throughout; `IDLE` is assigned only in `finalizeStop`. The AC5 V1 test pins this with a gated flush (asserts phase `stopping`, label `Finalizing…`, zero `onStopComplete` calls before release).

**Retry during "Finalizing…"** (user clicks Stop while phase is STOPPING): re-runs the stop sequence per the pre-existing 5.1 retry philosophy. Two `finalizeStop` invocations are possible; last-write-wins on `lastStopResponse`, `onStopComplete` fires twice. This mirrors 5.1's existing retry-during-Stopping semantics — 5.10 did not introduce it, and both verdicts are honest. Not a defect (see N1).

## 3. Failure isolation — PASS

**Stop-channel failure: no flush attempted.** On `{ok:false}` or non-object/no-response, the chain returns early after setting `"Stopping…"` + `stop-failed:<err>` — the flush block is inside the `{ok:true}` path only. Verified in code and by the AC6 V1 test (`flushCalls === 0`, phase stays `stopping`, session retained for retry).

**Flush failure modes all resolve honestly:**
- `sender.flush` throws synchronously → caught → `Promise.resolve(null)` → `'flush-result-unknown'` warning.
- `flush()` rejects → rejection handler → `finalizeStop(stopResp, null)` → warning. (Contract notes flush never rejects; this is defense-in-depth.)
- `sender.flush` missing/non-function → `Promise.resolve(null)` → warning, Stop completes (AC6 V1 test: missing flush → idle with `flush-result-unknown`, no hang/crash).
- **Never-settling flush:** the contract §2.1 explicitly accepts this ("inherently bounded... 5.10 adds no extra timeout"); the button stays enabled during "Finalizing…" so the user can retry Stop. Contract-sanctioned, not a defect.

## 4. flushTimedOut surfacing — PASS (audit carry-forward satisfied)

## 5. The onStopComplete handoff change — PASS (honest, contract-sanctioned evolution)

The handoff changed from `opts.onStopComplete(stopResp)` to `opts.onStopComplete({stopResp, flushResult, verdict, warnings})`.

- The 5.10 contract §3 step 8 **explicitly required and sanctioned this** ("called with the enriched verdict object... the 5.1 test pins the handoff, which 5.10 extends, not breaks"), and open question §7.2 listed it as a builder decision.
- **No production code depends on the raw shape.** The only production consumer (`content.js:370`) forwards to `BlindfoldSession.onSessionStopComplete`, which is undefined — it is §6's future seam. §6 will be designed against the enriched shape.
- **The evolved tests are honest, not weakened:** they assert `opts._stopCalls[0].stopResp === STOP_OK` (same reference, not a copy or subset) — the 5.1 "full stop response" guarantee is preserved — plus the new `verdict`/`warnings`/`flushResult` fields. The STOP_OK fixture was updated to the realistic 4.13 `streams` shape (the old top-level `flushTimedOut: false` fixture did not match the real 4.13 response; the new fixture is more faithful, not less).
- This is transparent, documented evolution (build report §"5.1 test evolutions", DECISIONS.md entry), not a silent break.
