# Task 3.3 contract — Instrument visibility and assistance

## 1. Scope

PLAN.md §3.3, quoted verbatim (human-owned; never modified):

- 3.3. Instrument visibility and assistance.
- 3.3.1. Record the initial extension piece-visibility state.
- 3.3.2. Record each reveal/hide transition at setPieceSet, with its source.
- 3.3.3. Record each existing help shortcut and whether the request had usable content.
- 3.3.4. Record reliably observable Chess.com hints and assistance-setting changes; mark unsupported coverage explicitly.
- 3.3.5. Audit what the current DOM can expose for other visual aids; document that extension visibility events do not prove complete absence of visual information.

## 2. Current-state analysis

### 2.1 Piece visibility (3.3.1/3.3.2)

- `content.js:64-65`: `piece_set` initializes from `localStorage["blindfold_chess_piece_set"]`, default `"neo"`.
- `content.js:254-258`: `setPieceSet(mode)` sets the variable, persists to localStorage, calls `applyCurrentPieceSet()`.
- Exactly one caller: `content.js:196`, the `v`-key handler, toggling blindfold↔neo.
- `content.js:84-85`: `observePieceRenders` re-applies the current piece set on every board re-render — **not a transition** (no state change); must not emit.
- `applyCurrentPieceSet` / `applyPieceSet` (chess_utils.js:292) only rewrite piece `backgroundImage` URLs; no state machine, no events today.

"Source" vocabulary: `'init'` (page-load read from localStorage), `'keyboard'` (v key), `'session_start'` (§5 session-start re-record), `'api'` (any future programmatic caller; the new default for bare `setPieceSet(mode)` calls).

### 2.2 Help shortcuts (3.3.3)

Existing keydown handlers in content.js; the spoken-assistance ("help") requests are:

| Key | Handler | Spoken content | "Usable content" test |
|-----|---------|----------------|----------------------|
| `w` | content.js:200-207 | "White's turn" / "Black's turn" | always true (turn always known) |
| `m` | content.js:209-216 | `getResultAnnouncement(game)` or "Game not over." | `getResultAnnouncement(game)` non-empty (game actually over with a result) |
| `z` | content.js:218-226 | "Last move: …" **only if** `last_spoken_move_text` | `last_spoken_move_text` non-null |
| `i` | content.js:228-233 | `speakFullMoveList(latest_half_moves)` ("No moves yet." if empty) | `latest_half_moves.length > 0` |
| `s` | content.js:242-247 | `speakPosition()` → board DOM read ("Board not found." on failure) | board element readable (`getBoardElement()` non-null) |

Explicitly NOT help requests:
- `j` (focus move input) — UI navigation, not assistance.
- `v` (piece-set toggle) — visibility, covered by 3.3.2.
- `Escape` (`stopAllSpeech()`) — speech cancellation; 3.4.3 owns cancellation requests.

A request with no usable content (e.g. `z` with nothing spoken yet, `m` mid-game) is still a **request**: it is recorded with `hadUsableContent: false`. The request happened; the absence of content is the honest record (3.2.6 precedent: absence is never mislabeled).

### 2.3 Chess.com hints / assistance settings (3.3.4)

Codebase survey (planner, 2026-10-06): **zero** references to hints, assistance settings, or engine-evaluation DOM anywhere in product code (`grep -rni "hint"` and `"settings"|"assist"` return nothing outside tests/.autodev). The extension currently observes no Chess.com hint surface at all.

Honest scoping for 3.3.4: the null hypothesis is that nothing is reliably observable. The builder must attempt the audit and report findings; if nothing reliable is found, the deliverable is the **explicit unsupported-coverage marking** (DECISIONS.md + audit doc), not fabricated observers. Recording unreliably-observed "hints" would be worse than recording nothing — it would manufacture evidence.

### 2.4 Other visual aids (3.3.5)

The DOM audit must cover, at minimum, these candidate visual-aid surfaces and report for each whether the extension's content-script world can reliably observe it:
- last-move highlight squares, check highlight, premove indicators;
- legal-move dots / hover highlights;
- engine evaluation bar / suggested-move arrows (bot games may not show these; report what the bot-game DOM actually contains);
- takeback/new-game buttons and result dialogs (overlap with 3.5 noted, not duplicated);
- any Chess.com "hints" or "assistance" toggles in settings UI reachable from the page.

The audit is a **documentation deliverable** (`.autodev/evidence/3.3.domaudit.md`), written from code analysis; live-page verification is V3-deferred (§7/owner device) and the doc must say so where applicable.

Epistemic disclaimer (must appear in DECISIONS.md and the audit doc): **extension visibility events record what the extension did to the board's piece rendering; they do not prove the player had no other visual information** (Chess.com highlights, eval bar, a second monitor, etc. are outside the extension's observation).

## 3. Design

### 3.1 New event types (3.3-owned constants in chess_utils.js; event_envelope.js untouched — EVENT_TYPE_RE accepts any snake_case)

- `BlindfoldSession.PIECE_VISIBILITY_CHANGED_EVENT_TYPE = 'piece_visibility_changed'`
  - payload (exact keys): `{ from: 'blindfold'|'neo'|null, to: 'blindfold'|'neo', source: 'init'|'keyboard'|'session_start'|'api' }`
  - refs: `null`
  - `from: null` marks the initial-state record (3.3.1). Every transition has non-null `from`/`to` with `from !== to`.
- `BlindfoldSession.HELP_REQUESTED_EVENT_TYPE = 'help_requested'`
  - payload (exact keys): `{ shortcut: 'w'|'m'|'z'|'i'|'s', hadUsableContent: boolean }`
  - refs: `null`
  - The emitted event's `eventId` is the stable reference 3.4.1 will link utterances to. No spoken text in 3.3 (3.4.4 governs that).

Validators follow the 3.1/3.2 precedent: exact-keys payload/refs validators on `BlindfoldSession`, `TypeError` on wrong types, `RangeError` on bad enum values.

### 3.2 `createVisibilityRecorder` (chess_utils.js, 3.1/3.2 precedent: namespace export, Node shim, DOM-free)

```js
BlindfoldSession.createVisibilityRecorder = function ({ getSessionId, getGameId, getPieceSet, emitEvent }) {
  // isActive(): non-empty sessionId AND gameId (2.7/3.1/3.2 §5-seam precedent — pre-§5 inert).
  // recordTransition(from, to, source): validates; no-op (returns null) when from === to;
  //   emits when active, returns the eventId; returns null without emitting when inert.
  // recordInitial(source): recordTransition(null, getPieceSet(), source).
  // recordHelpRequest(shortcut, hadUsableContent): validates; emits when active; returns eventId or null.
};
```

`emitEvent` is the same thunk shape as 3.1/3.2 (`(eventType, payload, refs) => sender.emit({...})`), so `eventIdOf` linkage works for 3.4.

### 3.3 content.js wiring (surgical)

- `setPieceSet(mode, source)` gains an optional `source` param (default `'api'`); after applying, calls `visibilityRecorder.recordTransition(oldMode, mode, source)`. The `v`-key handler passes `'keyboard'`.
- Init path: after recorder creation, `visibilityRecorder.recordInitial('init')` (inert pre-§5; §5's session-start path must call `recordInitial('session_start')` — documented seam, not implemented here).
- Each help-shortcut handler computes `hadUsableContent` from values already in hand (table in §2.2) and calls `visibilityRecorder.recordHelpRequest(key, hadUsableContent)` **before** speaking (request-first ordering; speech itself is 3.4's scope).
- `observePieceRenders` re-application path unchanged and event-free.
- 3.2 review SF-1 precedent applies: recorder calls in keydown handlers must be failure-isolated (try/catch) so instrumentation can never break the shortcut's speech behavior.

### 3.4 What 3.3 does NOT do

- No Chess.com hint observers unless the audit finds a **reliable** DOM signal (default: mark unsupported).
- No changes to help behavior/UX (keys do exactly what they do today).
- No utterance recording (3.4), no lifecycle events (3.5), no new permissions, no manifest changes expected (verify; chess_utils.js already loaded).
