# 5.4 contract — Show detected game conditions; manual completion of unavailable fields

## 1. Scope

PLAN.md §5.4 (line 191): "Show detected game conditions and allow manual
completion of unavailable fields before recording."

PLAN §(c) "Each game", step 2: "Select Baseline, Training, or Evaluation
and confirm remembered conditions; **fill in any unavailable bot/settings
fields**." Step 1: "Set up the Chess.com bot game and ensure intended
blindfold/assistance settings are in place."

This task completes the conditions form that 5.2 started. 5.2 owns three
fields (sessionCategory, trainingApproach, verbalScaffolding) and stores
the other five 1.2 condition fields — botName, botDisplayedRating,
playerColor, timeControl, assistanceSettings — as documented
`UNDETECTED_CONDITION_FIELDS` placeholders ("no detection attempted at
5.2; 5.4 owns detection and corrects provenance via the 1.2.4 path").
5.2 exposed the seam: `options.getDetectedConditions()` on
`installSessionFields`, consumed at Start by
`buildInitialConditions(selection, fieldsHandle.getDetectedConditions())`
(session_controls.js). 5.4 implements that plug-in, renders the
pre-Start conditions panel, and defines honest detection for exactly
what is detectable.

## 2. Per-field detection verdicts

The governing precedent is 3.3.4: "recording unreliably-observed 'hints'
would manufacture evidence." A detector built on an unverified selector
that silently matches the wrong element fabricates a condition — the
worst failure mode in this mission. 5.4 therefore distinguishes
**verified** detection (selector with in-repo precedent) from
**deferred** detection (no verified selector; manual completion is the
honest path; a V3 probe populates the selector table later).

| Field | Verdict | Mechanism |
|---|---|---|
| `playerColor` | **Detected (verified)** | `document.querySelector('wc-chess-board')` (selector already used at chess_utils.js:353) + `classList.contains('flipped')` (logic already used at chess_utils.js:248). Not flipped → `'white'`; flipped → `'black'`. Board element absent → `{value:null, source:'observed'}` (detection attempted, found nothing — the 1.2 contract's own meaning of observed+null). Documented assumption: in Chess.com bot games the player sits at the bottom of the board. |
| `botName` | **Manual-only (deferred)** | No verified in-game selector exists in the repo. The public `/play/computer` picker page shows names exist (e.g. "Martinfoot 250"), but no in-game player-tag selector has been verified. Inventing one would risk matching the wrong element. |
| `botDisplayedRating` | **Manual-only (deferred)** | Same as botName. |
| `timeControl` | **Manual-only (deferred)** | No verified selector; the setup-panel control is not probed. |
| `assistanceSettings` | **Manual-only (by design)** | 3.3.4 explicitly marks Chess.com hints/assistance-setting changes as unsupported coverage ("zero references to hints, assistance settings, or engine-evaluation DOM in product code"); the 1.2 contract states the key inventory comes from the §3.3 DOM audit, which found none. No detection is attempted, ever, in 5.4. |

### 2.1 The probe table (extension mechanism, not speculation)

The new module exposes a frozen `CONDITION_PROBES` table, one entry per
field: `{ field, verified: bool, selectors: [...], note }`. In 5.4 only
the `playerColor` entry is populated and `verified:true`; the other four
entries are present with `verified:false` and empty selector lists, each
noting why (no verified selector / 3.3.4 unsupported). A future V3 probe
task populates entries without new architecture. The contract **forbids**
the builder from adding speculative selectors: an entry may only be
marked `verified:true` with a cited verification (test or V3 evidence).

### 2.2 Source-transition table (placeholder → 5.4 record)

The 5.2 placeholder for all five fields is `{value:null,
source:'manual'}` ("not DOM-detected" — the smaller untruth). At Start,
`getDetectedConditions()` returns the 5.4 record; the initial
`session-save` persists it. Transitions:

| Field | 5.2 placeholder | 5.4 at Start | Rule |
|---|---|---|---|
| playerColor | `{null,'manual'}` | `{value,'observed'}` or `{null,'observed'}` | Detection is attempted; success → value, failure → null with `'observed'` (the 1.2 contract: "detection attempted ⇒ 'observed'"). This **corrects** the placeholder's provenance through the initial record. |
| botName, botDisplayedRating, timeControl | `{null,'manual'}` | `{null,'manual'}` unchanged, or `{typed,'manual'}` | No detection attempted in 5.4 (deferred); user-typed values are `'manual'`. No correction needed — the placeholder was already the honest encoding. |
| assistanceSettings | `{null,'manual'}` | `{null,'manual'}` unchanged, or `{pairs,'manual'}` | No detection attempted by design (3.3.4). |

Disambiguation of the 1.2 contract (recorded here as the 5.4 reading):
when detection was attempted AND the user left the manual input blank,
`'observed'` wins for the null — the probe is the stronger epistemic
claim ("we looked, found nothing") over the blank ("user said nothing").
`'manual'`-sourced nulls therefore mean exactly "no detection attempted
for this field in 5.4".

### 2.3 No 1.2.4 events in 5.4

5.4's flow is pre-Start: the initial record built at Start already
carries detected + manual values, so no correction event is needed for
the common case. 5.4 **emits no `conditions_changed` events** (5.2's
contract: "5.2 emits no conditions_changed events — the initial record
is stored, not emitted (1.2.4 governs *later* changes; 5.4 owns that
path)" — 5.4 now declines the path too: its scope is "before
recording"). The 1.2.4 change path (`createConditionChange` +
`sender.emit({eventType:'conditions_changed',...})`) remains available
for future tasks (e.g. 5.9 game-boundary corrections); 5.4 must not
break it and must not invent a parallel write path.

## 3. The panel UI

New in-page conditions panel, rendered adjacent to 5.2's fields in the
same cluster (DOM order: 5.2 fields → conditions panel → Start →
lights, preserving "select then Start" reading order; overlay.css
additive classes only, 2.8/5.1 precedent).

Per-field rows:

- **playerColor**: install-time detection shown read-only ("White" /
  "Black") with an `observed` tag; detection failure ("board not
  found") shows a White/Black select (manual completion) with a
  `manual` tag. No override affordance on successful detection
  (PLAN: manual completion is for *unavailable* fields; a wrong
  detection is a V3 refinement, not a 5.4 control).
- **botName**: text input. Trimmed; blank ⇒ null.
- **botDisplayedRating**: text input, live-validated as a non-negative
  integer (`/^\d+$/`). Invalid non-blank ⇒ inline error message; the
  raw string is still passed through (see §5 — never silently coerced
  to null; the 1.2 normalizer throws → honest Start abort).
- **timeControl**: text input. Trimmed; blank ⇒ null.
- **assistanceSettings**: key/value row editor — rows of (name input,
  value input, remove button); an empty trailing row is always present
  so filling it adds a pair (no separate Add button). Name: trimmed
  non-empty. Value parsing (contract-defined, strict): `'true'` →
  `true`, `'false'` → `false`, finite numeric string → number,
  otherwise trimmed string; empty ⇒ `null` (the 1.2 "known setting
  with an unreadable value" case). A row with a blank name is ignored
  (not a pair). Any ≥1 pair ⇒ manual-dirty.

Each row shows a live source tag: `observed`, `manual`, or `not set`.
The panel is **disabled while a session is active** (write-once,
mirroring 5.2's rule — the panel feeds the initial record; there is no
5.4 mid-session editing UI). `setEnabled(true)` after Stop re-enables.

### 3.1 Boot adoption

On adoption the panel disables and shows the note: "Session adopted
after reload — conditions were recorded at its start." The install-time
detected values stay visible but are labeled as current-page detection,
never as the adopted session's record (the adopted conditions live in
IDB, unreachable from the content script; implying otherwise would be
the 5.2-category-echo masquerade repeated).

## 4. Timing and merge

- **Install**: `detectGameConditions(document)` runs once; the panel
  renders from it.
- **Re-detect affordance**: one small "Re-detect" button re-runs
  detection and re-renders (covers "user changed bot between install
  and Start" without continuous observation).
- **Start**: `getDetectedConditions()` (the 5.2 plug-in, called by
  `buildInitialConditions` at Start) performs a **fresh**
  `detectGameConditions(document)` and merges with manual overrides:
  for each field, manual-dirty ⇒ `{manualValue,'manual'}` (manual
  wins over fresh detection — explicit user input beats a probe);
  else ⇒ fresh detection result. A manual input cleared back to blank
  is not dirty ⇒ falls back to detection.
- Manual entries are **not** remembered by 5.3 (5.3's contract remembers
  exactly the three 5.2 fields; the panel starts blank each session —
  do not silently expand 5.3's scope).

## 5. The invalid-input path (no silent fallback)

`installSessionFields`'s `getDetectedConditions` wrapper try/catches the
plug-in and falls back to `UNDETECTED_CONDITION_FIELDS` on throw —
"a throwing plug-in must not break Start". The panel must therefore
**never throw for invalid manual input and never silently coerce it to
null** (coercion would drop user data; the fallback would then persist
placeholders as if the user typed nothing). Instead:

- Manual values pass through **un-coerced** to `buildInitialConditions`
  (blank ⇒ null per 1.2; non-blank invalid ⇒ the 1.2 normalizer throws
  `TypeError`/`RangeError` inside `createInitialConditions` ⇒ the
  existing session_controls try/catch aborts Start honestly as
  `record-build-failed`, nothing minted/persisted).
- Live inline validation messages tell the user which field is bad
  *before* they click Start (UX); the 1.2 normalizers are the backstop
  (honesty).
- `detectGameConditions` itself never throws on DOM weirdness: each
  field probe is individually guarded; a probe failure ⇒
  `{value:null, source:'observed'}`. Only a non-document argument ⇒
  `TypeError` (AGENTS.md convention).
