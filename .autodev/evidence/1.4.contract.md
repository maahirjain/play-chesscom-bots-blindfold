## 1. Scope

Task 1.4 defines the **game reconstruction record shapes only**: the
starting-FEN record (1.4.1), the confirmed-move record (1.4.2), the
history-recovery / history-revision event types and payloads (1.4.3), the
recovery-position checkpoint with its strict gate (1.4.4), and the
observed game-end fields (1.4.5). It delivers **factories, validators,
constants, and exact JSON shapes** in a new dependency-free module
`game_records.js`, following the 1.1/1.2/1.3 module pattern. It does **not**
observe the DOM (§3.1), detect game starts/ends (§3.5), assemble envelopes
(§3.x emitters own that), store anything (§2), or export anything (§6).

## 2. Design decisions (investigator-verified)

### 2.1 Where the starting FEN lives: `game_started` event, not identity

1.4.1 "store the starting FEN once per game" is defined as a
`game_started` **event** whose payload is `{fen}` — not as a field on the
1.1 game identity (which is deliberately just a UUID; 1.1's contract locked
the metadata shape). Rationale:

- The FEN is an **observation with an occurrence time** (when the game was
  detected/started). The 1.3 envelope already carries `gameId` +
  (`clockSegmentId`, `monotonicMs`): the exact container 1.4.2's "observation
  timestamp" needs.
- PLAN §3(a) lists the starting FEN in the **metadata.json row** ("game
  starting FEN"). That is §6.1's export-time **denormalization** of the
  canonical `game_started` event — sanctioned because PLAN explicitly lists
  it, not because the event is insufficient. **Conflict rule: if
  metadata.json's FEN ever disagrees with the `game_started` event, the
  event wins** — events.jsonl is the raw store.
- Payload is exactly `{fen}`. Player color, bot, time control are 1.2
  conditions; move numbers are derivable. Nothing else is smuggled in.

### 2.2 FEN validation: structural, local, no chess.js dependency

`isFen(s)` validates **structure, not chess-legality**:

- non-empty string; exactly six space-delimited fields;
- field 1: eight `/`-delimited ranks, each summing to 8, valid piece chars
  (`pnbrqkPNBRQK`) and digits only, with **no two consecutive digits**
  (mirrors the vendored chess.js `validate_fen` field-1 rules — `new Chess()`
  silently misloads consecutive-digit ranks as an empty board);
- field 2: `w`|`b`; field 3: castling availability
  `^(KQ?k?q?|Qk?q?|kq?|q|-)$`; field 4: `-`|`[a-h][36]`, with the
  ep-square-vs-side-to-move consistency check the vendored validator
  performs; field 5: non-negative integer; field 6: positive integer.
- **Deliberately NOT checked**: king counts, check status, or any other
  legality rule. An illegal-but-parseable position from Chess.com is still
  the observed evidence; rejecting it would destroy data ("preserve
  original observations").

Why a local validator instead of the vendored `chess.min.js`
`validate_fen` (verified present and working in Node): the 1.3 precedent
(§2.10) prefers a small private validator over cross-module/load-order
coupling. `game_records.js` stays dependency-free, Node-testable, and
`importScripts`-order-independent. The validator's job is **caller-error
detection** (malformed input → throw), not data cleaning — real observed
FENs come from the internal chess.js board's canonical `fen()` (§3.1), so
structural validation is the honest, sufficient gate. Malformed →
`TypeError` (wrong shape); structurally invalid fields → `RangeError`
(value outside the FEN domain). **Trim-and-store**: the two FEN factories
(`createGameStartedPayload`, `createPositionCheckpointPayload`) trim
whitespace-padded input before storing, so stored records are always
canonical (a padded FEN is rejected by the vendored validator).

### 2.3 Confirmed-move record: `{from, to, promotion}`, time from the envelope

1.4.2's "observation timestamp" is **the 1.3 envelope's
(`clockSegmentId`, `monotonicMs`)** — the payload carries **no time
fields**. Duplicating time in the payload would violate "no duplicated
persisted data" and create the two-clocks-disagree hazard 1.3 rejected.

`MovePayload` — exactly three keys:

```json
{ "from": "e2", "to": "e4", "promotion": null }
```

- `from`/`to`: square strings validated against `/^[a-h][1-8]$/`;
  `from === to` → `RangeError` (a move cannot start and end on one square).
- `promotion`: `null` (not a promotion) or one of `'q'|'r'|'b'|'n'`
  (**lowercase**, matching the vendored chess.js verbose-move encoding —
  verified: `g.move({from:'c7',to:'c8',promotion:'q'}).promotion === 'q'`;
  non-promotion verbose moves carry **no** `promotion` key, which this
  contract normalizes to explicit `null`). Anything else → `RangeError`.
  `undefined` → `TypeError` (explicit-null convention, cf. 1.3 `gameId`).
- **Encoding facts grounding this** (verified 2026-10-06 against the
  vendored chess.js): castling is stored as the king's from/to
  (`e1→g1`); en passant as the pawn's from/to (`e5→d6`); flags/SAN are
  derivable and are NOT stored.
- **A promotion whose piece is unobservable is NOT a confirmed move.**
  There is no third "unknown piece" state: emitting `promotion: null`
  would falsely record a non-promotion. The emitter (§3.1) must treat it
  as a synchronization failure (3.1.7), never as a `move_confirmed`.

### 2.4 No move numbers, no SAN — confirmed as non-goals

PLAN §3(a) forbids persisting move numbers and SAN ("Starting FEN plus
confirmed coordinate moves is sufficient to derive SAN, PGN, subsequent
positions, and move numbers"). Both are derivable from event order +
chess.js replay. The contract layer provides no `moveNumber`/`san`
fields, and the V1 suite includes a chess.js replay check proving the
derivation works (see §5).

### 2.5 Recovery vs revision: marker-first, uniform move stream

This is the subtlest part of 1.4.3. Decision: **recovered and replacement
moves are ordinary `move_confirmed` events**; `history_recovered` and
`history_revised` are **structural marker events emitted FIRST**, and the
moves they cover link back via 1.3 `refs`. The original stream is never
rewritten or deleted.

Ordering within a segment: marker at `sourceSeq` k, its moves at
k+1…k+N (occurrence order = `sourceSeq` order).

**Why not embed moves in the marker payload?** A dual schema (moves
sometimes in `move_confirmed` payloads, sometimes in marker payloads)
would force every consumer — including the §7.2 reconstruction check
("replay correctly from starting FEN and confirmed moves") — to fold two
shapes. One uniform move stream keeps reconstruction a single fold:
starting FEN + `move_confirmed` in occurrence order, minus retractions.

**Why marker-first rather than marker-last?** Forward-scan consumers meet
the explanation before the data it explains; the marker's
`expectedMoveCount` lets consumers detect a truncated batch (context died
mid-batch) — a count that is **not derivable** after interruption, hence
legitimately persisted.

#### 2.5.1 `history_recovered` — reloads and late attachment

Emitted when the observed move list contains confirmed moves the event
stream does not (page reload killed the originating context so §2.5
retries could not save them; or the extension attached mid-game).

```json
{ "recoveryReason": "page_reload", "expectedMoveCount": 3 }
```

- `recoveryReason`: closed vocabulary `['page_reload',
  'late_attachment']` — the two PLAN-grounded triggers (§2.7 page
  reload/reconnect; §7.5 late attachment). Anything else → `RangeError`.
  If §3.1 discovers a third trigger, it escalates for a contract
  amendment (1.2 precedent: no invented taxonomy).
- `expectedMoveCount`: integer ≥ 0 — how many `move_confirmed` events the
  emitter intends to emit in this batch. `0` is legal: the marker then
  records "recovery observed, stream verified complete" (evidence, like
  §2.7's discontinuity marking).
- Each batch move is a `move_confirmed` event with
  `refs: { recoveryEventId: "<marker eventId>" }`. Its envelope timestamp
  is the **discovery** time — honest per 3.1.6 ("do not invent their
  original occurrence times"); the ref marks it as recovered.
  Original occurrence order within the batch = `sourceSeq` order.
- `priorConfirmedCount` is deliberately ABSENT: derivable by counting
  prior `move_confirmed` events for the game.

#### 2.5.2 `history_revised` — takebacks and same-length corrections

Emitted when the observed history contradicts previously confirmed moves
(3.1.4). The contradicted `move_confirmed` events **stay in the stream**;
the revision names exactly which ones are superseded.

```json
{
  "revisionKind": "takeback",
  "retractedMoveEventIds": ["<uuid>", "<uuid>"],
  "observedHistoryLength": 13,
  "expectedMoveCount": 0
}
```

- `revisionKind`: `'takeback'` (observed list shrank / moves retracted)
  | `'correction'` (same-length history changed, 3.1.4). Anything else →
  `RangeError`.
- `retractedMoveEventIds`: non-empty array of UUID v4 event IDs of
  `move_confirmed` events now superseded. **Must be a suffix of the
  game's confirmed-move sequence** (from the first changed ply onward):
  if move 7's SAN changed, moves 8…N were converted through the old
  board state and must be re-derived — §3.1's rule, stated here as the
  semantic contract (the contract layer validates shape only; it cannot
  see the stream).
- `observedHistoryLength`: integer ≥ 0 — the DOM-observed ply count after
  the change. A raw observation, not derivable.
- `expectedMoveCount`: integer ≥ 0 — replacement `move_confirmed` events
  to follow (`0` for a pure takeback). Each replacement carries
  `refs: { revisionEventId: "<marker eventId>" }`.
- **Takeback example**: list shrank 15→13 plies ⇒
  `retractedMoveEventIds: [id14, id15]`, `observedHistoryLength: 13`,
  `expectedMoveCount: 0`. Reconstruction: FEN₀ + moves 1…13.
- **Correction example**: ply 7 changed in a 20-ply list ⇒ retract
  `[id7…id20]`, then 14 replacement `move_confirmed` events
  (`expectedMoveCount: 14`), each ref-linked to the revision.
- **Fold semantics** (declarative, no code — see §2.9): current move
  list = confirmed moves in occurrence order, minus any event ID named
  in any `history_revised.retractedMoveEventIds`, plus replacement moves
  in their occurrence order. Retraction is monotonic: a retracted event
  ID is never un-retracted.

#### 2.5.3 Refs roles defined by this task (fulfills 1.3 AC20, partial)

Per 1.3's deferred role inventory, 1.4 defines exactly two roles (both
satisfy `/^[a-z][a-zA-Z0-9]*Id$/`):

- `recoveryEventId` — on batch-recovered `move_confirmed` events →
  their `history_recovered` marker.
- `revisionEventId` — on replacement `move_confirmed` events →
  their `history_revised` marker.

No other roles are invented here. §3.2/§3.4 own attempt/utterance roles.

### 2.6 `position_checkpoint`: shape, and the strict gate

1.4.4 permits a checkpoint **only** where a logging gap cannot be bridged
with verified moves. Payload — exactly three keys:

```json
{ "fen": "<full FEN>", "reason": "unreconciled_history", "fenSource": "observed" }
```

- `fen`: validated by `isFen` (§2.2).
- `reason`: closed vocabulary `['unreconciled_history']` — the only
  PLAN-grounded case (3.1.7: "Emit synchronization failures when the
  observed history cannot be reconciled with the internal board").
- `fenSource`: `'observed'`|`'manual'` — reuses the 1.2 provenance
  convention (defined locally in `game_records.js` as
  `FEN_SOURCES`, deliberate duplication over load-order coupling, per 1.3
  §2.10 precedent). `'observed'` = derived from page/board state by the
  extension; `'manual'` = supplied by the user (e.g. entered at Stop —
  ties to 1.4.5's manual completion).

**The strict gate** (documented for the §3.1 emitter; a checkpoint is a
data-quality flag, not a routine mechanism):

1. A synchronization failure was observed **and recorded** (3.1.7) —
   a checkpoint without a recorded sync failure is a defect, not a
   recovery.
2. The gap is genuinely unbridgeable: replaying the observed history from
   the `game_started` FEN **and** from the last checkpoint both fail to
   reconcile — a checkpoint must never paper over a bridgeable gap.
3. The emitter can state a current-position FEN (best-effort observed or
   manual); it never invents one.

Consequence: any export containing a `position_checkpoint` with
`reason: 'unreconciled_history'` **must surface it in §6.1's
collection coverage/completeness** as a defect flag. Frequent checkpoints
indicate an instrumentation bug (escalate per the 3-repair rule), not
normal operation.

### 2.7 `game_ended`: result, termination reason, evidence source

1.4.5 — payload exactly four keys:

```json
{
  "result": "1-0",
  "terminationReason": "resignation",
  "evidenceSource": "observed",
  "observedText": "White won by resignation"
}
```

- `result`: closed vocabulary `['1-0', '0-1', '1/2-1/2', '*']` — the PGN
  result vocabulary (the vendored chess.js itself uses this set).
  `'*'` = unknown (covers 1.4.5's "allow unknown"). No `null`: the
  unknown token is part of the vocabulary.
- `terminationReason`: closed vocabulary or `null` (null = unknown, per
  1.2's unknown convention):
  `'checkmate'` | `'stalemate'` | `'resignation'` | `'timeout'` |
  `'draw_agreed'` | `'draw_insufficient_material'` | `'draw_fifty_move'`
  | `'draw_threefold'` | `'abandoned'` | `null`.
  Each value is grounded: chess-rules endings; `'resignation'`/
  `'abandoned'` from 3.5.4; `'timeout'`/draw variants from 3.5.3's
  "endings not implied by chess rules" as shown by Chess.com's result
  text. **No further taxonomy is invented** — anything unclassifiable is
  `null` with the raw text preserved in `observedText`.
- `evidenceSource`: `'observed'`|`'manual'` (1.2 provenance convention,
  defined locally). `'manual'` = user-supplied at Stop (3.5.4: "Allow a
  termination reason at Stop when the ending is unknown, such as
  abandonment").
- `observedText`: the exact result/termination string Chess.com displayed,
  or `null` when there was none (e.g. pure manual completion). This is
  **raw evidence, not analysis** — justified by 3.5.3 ("Observe Chess.com
  result/termination information where available") and the mission rule
  "keep actual observed outcomes". A `null` terminationReason with a
  non-null `observedText` is the honest record of an unclassifiable
  ending.
- **Multiple `game_ended` events per game are permitted**: automatic
  observed detection (3.5.3) and a later manual completion at Stop (3.5.4)
  are both legitimate. Originals are preserved; consumers interpret the
  latest by occurrence time. Recording does not stop at game end (§5.7).

### 2.8 All six types are game-scoped

Every 1.4 event type is emitted with a **non-null `gameId`** (1.3 permits
null for session-scoped events; these six are never session-scoped).
Emitters (§3.x) own envelope assembly via `createEvent`; 1.4 defines
payload factories and type constants only — mirroring 1.2's split
(`CONDITION_CHANGE_EVENT_TYPE` + payload factories, no envelope code).

### 2.9 No fold helper — declarative semantics only

Unlike 1.2's `applyConditionChange`, this task ships **no stream-fold
function**. A reconstructor would be a "reconstruction-test interface",
which PLAN §1 explicitly excludes from the implementation. The revision
semantics are pinned declaratively (§2.5.2); §7.2/§7.4 verify them
behaviorally against real event streams.

### 2.10 Module placement: new file `game_records.js`, same pattern

New file `game_records.js` at repo root: dependency-free plain script,
guarded `BlindfoldSession` global, IIFE `'use strict'`, Node
`module.exports` shim, chrome\*-independent, frozen records, plain-JSON
values, `node --test`-testable. One file per contract task (1.1/1.2/1.3
precedent); shares the namespace without modifying existing modules;
defines its own `*_EVENT_TYPE` constants (1.3 §2.2 decentralized-vocabulary
rule). Error conventions mirror 1.1/1.2/1.3: `TypeError` = wrong
type/shape (including malformed IDs and non-object payloads);
`RangeError` = value outside an allowed domain (bad FEN fields, bad
squares, bad vocabulary values, from===to); plain `Error` = unavailable
platform capability (`crypto.randomUUID` missing — none needed here
beyond the 1.1 precedent, kept for consistency if ID helpers are added).

## 4. Acceptance criteria

### 1.4.1 — starting FEN once per game

- [ ] **AC1** `createGameStartedPayload({fen})` returns exactly `{fen}`
  (one key); `requireValidGameStartedPayload` accepts canonical FENs
  (standard start, mid-game with ep square, Chess960-style castling
  fields are NOT required — standard only). *Verify now (V1).*
- [ ] **AC2** `isFen`/`requireValidFen`: accept valid 6-field FENs;
  reject: non-strings, empty/whitespace, wrong field count, bad rank
  structure (7 rows, row not summing to 8, invalid piece char), bad
  side-to-move, bad castling field, bad ep square, negative halfmove
  clock, zero/negative fullmove number, ep-square/side inconsistency.
  Malformed type → `TypeError`; structurally invalid → `RangeError`.
  *Verify now (V1).*
- [ ] **AC3** No legality check: a structurally valid but
  chess-impossible FEN (e.g. nine queens, missing kings) is ACCEPTED —
  the contract preserves observations, it does not referee them.
  *Verify now (V1): explicit test with a comment citing §2.2.*
- [ ] **AC4** Payload is frozen; JSON round-trip preserves it;
  `GAME_STARTED_EVENT_TYPE === 'game_started'` passes
  `BlindfoldSession.isEventType`. *Verify now (V1).*

### 1.4.2 — confirmed moves as from/to/promotion + observation time

- [ ] **AC5** `createMovePayload` returns exactly `{from, to,
  promotion}`; `promotion` defaults to `null` when omitted; result

- [ ] **AC6** Square validation: `'e2'`/`'a1'`/`'h8'` pass; `'e9'`,
  `'i1'`, `'E2'`, `''`, non-strings rejected; `from === to` →

- [ ] **AC7** Promotion: `null`, `'q'`, `'r'`, `'b'`, `'n'` pass;

- [ ] **AC8** **No timestamp fields exist on the payload** (key-set test
