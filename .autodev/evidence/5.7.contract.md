# 5.7 contract — Keep recording through game end until the user clicks Stop, allowing a spoken reflection

## 1. Scope

PLAN.md §5.7: "Keep recording through game end until the user clicks Stop, allowing a spoken reflection."

**PLAN evidence:** §(c) "Each game", step 6: "After the game, optionally give a short spoken reflection while recording continues." Step 7: "Click Stop. If the ending is unknown, supply a brief reason such as abandoned or resigned." And the closing paragraph: "Neither a detected game ending nor a result announcement stops recording automatically; the explicit Stop action preserves the opportunity for post-game commentary."

**Current state (verified by the planner):** No auto-stop exists. The game lifecycle recorder (3.5, in `chess_utils.js`) observes game endings via `recordGameEnded()` (sources: `chess_rules`, `chesscom_dialog`, `stop`), but no code path connects a `game_ended` observation to the Stop sequence. The only consumers of the lifecycle recorder are:
- `session_controls.js` Start: `resetEnded()` (re-arm per-source idempotency for the new game).
- `session_controls.js` Stop: `getLastObservedEnd()` + `recordStopTermination()` (the 3.5.4 seam — null reason unless a game_ended was observed).

The result announcement (`announceResultIfOver` in `sounds.js`) is speech-only; it does not touch recording state.

**What 5.7 does:** Pin the no-auto-stop invariant as a tested guarantee, and verify the post-game reflection window is genuinely preserved (session stays ACTIVE, all streams keep recording, UI keeps showing "recording"). This is primarily a guarantee to be pinned, not a feature to be built — the behavior is already correct by construction.

**What 5.7 does NOT do:** It does not add UI, event types, or markers for the reflection. The "spoken reflection" is enabled by the continuing microphone stream (already running); the "allowing" is the negative guarantee. The optional timestamped marker is 5.8's work. Game transitions (new game before Stop) are 5.9's work.

## 2. The invariant

### 2.1 No auto-stop on game end

A `game_ended` observation — from ANY source (`chess_rules` terminal board state, `chesscom_dialog` result dialog, or any future source) — MUST NOT:
- trigger `onStopClick()` or any part of the Stop sequence,
- change the control `phase` (stays ACTIVE),
- clear session slots or the recorder session,
- stop any media stream or the chunk writer,
- change the readiness badge (5.6, latched) or per-stream lights.

The ONLY thing that ends the recording session is the explicit user Stop action (clicking Stop), or the failure paths 5.1 already defines (which are honest failures, not game-end reactions).

### 2.2 The reflection window is preserved

After a game_ended observation with no new game started:
- The session remains ACTIVE with the same `sessionId` and `gameId`.
- All three media streams continue recording (mic captures the spoken reflection).
- The event pipeline continues (events recorded under the existing gameId — the reflection is part of the game session).
- The UI continues to show "recording" (5.6 badge stays "Ready — recording", lights show stream health, button stays "Stop", saving indicator keeps showing).
- When the user clicks Stop, the 3.5.4 seam applies: the observed termination reason/result is passed to `recordStopTermination()` (5.1's existing behavior, unchanged).

### 2.3 "Spoken reflection" — what the implementation does vs. what stays manual

| Aspect | Implementation | Manual (user) |
|--------|---------------|---------------|
| Keep mic recording after game end | Already true; pinned by 5.7 | — |
| Capture the reflection audio | Mic stream (4.6) captures it | User speaks |
| Mark the reflection span | NOT 5.7 — no new event type | User may use 5.8's marker |
| Prompt the user to reflect | NOT 5.7 — no new UI | §(c) step 6 is a protocol instruction |
| End the reflection window | Explicit Stop only | User clicks Stop |

Rationale for no marker in 5.7: PLAN's raw-data-collection scope and 5.8's explicit ownership of "optional timestamped note/moment marker." Adding a reflection-specific event type in 5.7 would duplicate 5.8 and exceed the requirement. The reflection is audio in the mic stream; its interpretation belongs to later analysis, not to 5.7.

## 3. The 5.7 / 5.9 boundary

5.7 and 5.9 are adjacent but distinct:

- **5.7 covers:** game ends → NO new game → user reflects (or not) → user clicks Stop. The session (sessionId + gameId) survives unchanged through game end. The game lifecycle recorder's "ended" state persists until Stop or the next Start.
- **5.9 covers:** game ends → NEW game starts before Stop → assign a new gameId, preserve the boundary, flag the shared session. 5.9 will re-arm the lifecycle recorder (`resetEnded()`) when minting the new game identity (the seam 5.1's Start already uses).

**The handoff:** 5.7 guarantees the session is alive and clean after game end, so 5.9 has a well-defined state to transition from. 5.7 MUST NOT reset, clear, or otherwise disturb the game lifecycle recorder's ended-state on game end — that state is 5.9's input (to know a boundary occurred) and the Stop seam's input (for the termination reason). 5.7 leaves `chess_utils.js` untouched.

**Out-of-scope for 5.7 (5.9's):** detecting a new game while the session is active, minting a new gameId mid-session, emitting boundary events, flagging the shared session.

## 5. Explicit non-goals

- Any UI change (no new buttons, badges, prompts, or text for the reflection).
- Any new event type (no `reflection_started`, no game-end marker — 5.8 owns markers).
- Any new channel message, store, or permission.
- Changing the Stop sequence, the 3.5.4 termination-reason seam, or the game lifecycle recorder.
- 5.8's note/moment marker, 5.9's game-boundary handling, 5.10's finalization gating.
- Auto-detection of "reflection complete" or any timeout on the post-game window (the user decides when to Stop; PLAN sets no time limit).
