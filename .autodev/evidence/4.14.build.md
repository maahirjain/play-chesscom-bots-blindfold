## Summary

Implemented the per-stream recording status query surface. The new
`stream_status.js` module reports, per streamKind, whether the stream's
recording is actually happening and what its condition is — so a dead
microphone, failed screen capture, or stalled chunk loop cannot
masquerade as a complete recording (PLAN line 181).

`getStreamStatus(streamKind)` returns the exact 17-key status:
`streamKind, lifecycle, recorderState, segmentId, segmentNumber,
startedAtUtc, startedAtMonotonicMs, clockSegmentId, actualMimeType,
fileExtension, audioContent, chunk{|null}, tracks[], lastRecorderError|null,
lastDiscontinuity|null, finalizedAtUtc, unfinalizedSegments`.
`getAllStreamStatuses()` returns all three kinds.

Reads (offscreen-local only, no event-log dependency):
- `lifecycle`/`recorderState`/live segment+starts — `stream_starter.getStreamRecord()`; lifecycle derived mechanically from the §1.1 truth table (`idle|recording|stopped|finalized`). There is deliberately NO smoothed 'error' lifecycle: failures surface as facts.
- `chunk.*` — `chunk_writer.getChunkState()` (the §1.2 masquerade table: chunk-terminal states with a still-"recording" recorder surface via `chunk.*`, never via lifecycle).
- `tracks[]` — live `muted`/`readyState` per track via `track_monitor.getMonitoredTracks()`, read at query time.
- `lastRecorderError`/`lastDiscontinuity` — the new additive `track_monitor.getStreamHealth(streamKind)` (in-memory, generation-scoped; cleared on detach/attach).
- `segmentNumber`/`finalizedAtUtc`/`clockSegmentId`/mime/ext/`audioContent`/`unfinalizedSegments` — `format_support.getManifestRecordsBySession()` (existing `bySessionId` index; no manifest widening, 18 keys, `DB_VERSION` 2).

`recorder.js` gained the lazy `getStreamStatusReader()` getter (the
`getFinalizer` pattern: shared-namespace-resolved, `o.streamStatus`
test-injectable, wiring defect → plain `Error`) and the single new
channel message `recorder-get-status` (MSG_* 23→24, the
`recorder-get-formats` precedent — the only way SW-side §5/§6.3 can
query offscreen-local live state). The handler is session-gated
(`{ok:false, error:'no-session'}`) and never throws into the channel
(manifest/read failures → `{ok:false}`, the 3.2 SF-1 precedent).

## Design decisions (see DECISIONS.md ## 4.14 for the full list)

- **Masquerade-driven design**: the §1.2 masquerade table maps each failure mode to the exact status field that surfaces it. Smoothing is how failures masquerade, so lifecycle is mechanical and failures are facts.
- **Offscreen-local honesty boundary**: the event log is SW-side; 4.14 reads document-local state only. A document restart empties the health mirror by construction (the manifest tells the cross-generation story).
- **`createdAtUtc` orders generations** for manifest record selection: it is stamped at stream start, so it orders generations including the in-progress one (whose `segmentNumber` is still null). `segmentNumber` is the tiebreak.
- **Injected-read failures degrade; manifest failure rejects**: a throwing registry/chunk/track/health read yields null/[] (a query must never fail because a live read did); a failed manifest read rejects and the channel maps it to `{ok:false}`.
- **Exactly one new channel message** (`recorder-get-status`; MSG_* 23→24). No new event types. No manifest widening. No §5/§6 bleed.

## Deviations from the contract

1. **V2 harness name** (`sw-stream-status.js`, not `sw-status.js`): `~/workspace/tools/ext-verify/sw-status.js` already exists as task 2.8's status-indicator V2 harness. Renamed to avoid clobbering it. No functional impact.
2. **`attachStream` initializes the health generation explicitly** (an early edit for this was silently dropped by the edit tool and re-applied — verified present in the final diff). Without it, `getStreamHealth` after a fresh attach returns `null` instead of the `{lastRecorderError:null, lastDiscontinuity:null}` shape; V1 pins the generation-scoping behavior.
3. **Manifest record ordering** (createdAtUtc-primary, segmentNumber-tiebreak) vs the brief's "(segmentNumber desc, createdAtUtc desc, segmentId)": a finalized segment (number 1) followed by a newer in-progress generation (number null) must select the newer generation. V1-pinned by the mixed finalized/unfinalized test.
