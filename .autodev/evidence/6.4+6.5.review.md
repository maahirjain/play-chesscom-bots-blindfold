## 6.4 — What I attacked

### 1. Zero transcoding — PASS
Probed byte-identity directly: three chunks (`'hello '`, `'world'`,
`'!'`) assemble to parts whose concatenated bytes equal
`'hello world!'` byte-for-byte (P3). Binary payload with `0x00`/`0xFF`
bytes split across a chunk boundary survives exactly (P9). The code
pushes the original chunk Blobs into `parts` and only reads
`arrayBuffer()` for CRC — there is no byte-transforming code path.
`byteLength` (12) and `chunkCount` (3) are exact.

### 2. Streaming (O(largest chunk), not O(file)) — PASS
- `parts.length === chunks.length` (P3d); each part is the *original*
  Blob reference (`r.parts[0] === chunk.data`, P4) — not a copy.
- The promise chain processes chunks sequentially: each chunk's
  ArrayBuffer is allocated, CRC-updated, then released when the
  `.then` callback returns. No single buffer of `byteLength` is ever
  allocated — source scan of the 6.4 section finds no
  `new Uint8Array(byteLength)`, `Buffer.concat`, or whole-file
  `ArrayBuffer` (P8).
- The precomputed `crc32` + `byteLength` are exactly what 6.6 needs
  for ZIP data descriptors (flag bit 3), so the header can be written
  before the file data is streamed — the contract's coordination
  claim (§5) is structurally sound.

### 3. CRC-32 correctness — PASS
- Empty input → `0` (P1a).
- `"123456789"` → `0xCBF43926`, the standard ISO 3309 check vector (P1b).
- Multi-chunk incremental CRC equals Node `zlib.crc32` over the
  concatenated buffer (P2) — independent implementation cross-check.
- Table generation verified by inspection: standard reflected
  polynomial `0xEDB88320`, 8 iterations per byte, `>>> 0` unsigned
  discipline throughout `crc32Update`/`crc32Finalize`.

### 4. Fail-closed — PASS
All eight malformed-input probes throw `TypeError` (P7): non-array
chunks, missing `data`, non-Blob `data`, duplicate `chunkIndex`,
negative `chunkIndex`, fractional `chunkIndex`, non-object chunk,
non-object args. Duplicate detection runs in a pre-validation pass
*before* any Blob is read — a duplicate can never produce a partial
assembly. Note the function returns rejected promises (not sync
throws) for these; this is the honest async-fail-closed shape and the
contract's AC5 does not require sync throws.

### 5. Honest gaps, input-order trust — PASS (as documented)
- Chunk indexes `[0, 5]` assemble without error; `chunkCount` is 2,
  no re-indexing (P6) — matches contract §3.1 ("gaps are honest").
- Out-of-order input `[2, 0, 1]` is assembled in *input* order
  (`'CAB'`, P5). This is the contract's documented trust in 6.6's
  key-order guarantee (AC1 pins it), not a defect — but it means a
  6.6 mis-ordering would silently produce a mis-ordered file rather
  than an error. Flagged for 6.6's orchestration: the key-range read
  must be verified, not assumed.

### 6.4 non-blocking notes
- **N1:** If `chunk.data.arrayBuffer()` rejects (corrupt Blob), the
  rejection propagates as-is (not a `TypeError`). Honest failure, not
  silent corruption — acceptable.
- **N2:** The split-piece init-data limitation (§4.1 of the contract)
  is correctly *not* "fixed" — no init fabrication found in the code.

## 6.5 — What I attacked

### 1. Numbering — PASS (with N1 below)
- Finalized verbatim: `1 → 001`, `12 → 012`, `1000 → 1000` (no
  truncation) (Q1).
- All-null: three segments number `001/002/003` in `createdAtUtc`
  order (Q2).
- Mixed: numbers `{1, 3}` + one null → the null gets `002`
  (smallest-unused gap-fill, no collision) (Q3).
- Per-kind independence: microphone and screen each start at `001` (Q4).
- Duplicate finalized `segmentNumber` within a kind → `TypeError`
  (Q5) — the builder's documented judgment, and the right one: the
  alternative is a silent ZIP filename collision.
- Determinism: reversed input → byte-identical output (Q9).

### 2. Extension resolution — PASS
Full matrix probed (Q6): manifest `.mp4` used verbatim; null
`fileExtension` + `audio/webm;codecs=opus` → `.webm`; `video/mp4` →
`.mp4`; `audio/mp4` → `.m4a`; dotless `"webm"` falls through to mime
derivation (not used verbatim — correct, else `microphone-001webm`);
both null → `TypeError` naming the segmentId; unknown mime
(`video/avi`) → `TypeError`. The mapping mirrors
`format_support.js` as the contract requires.

### 3. Fail-closed — PASS
Seven malformed-input probes throw `TypeError` (Q7): non-array,
missing/empty `segmentId`, duplicate `segmentId` (across kinds —
correct, segmentIds are globally unique), zero/negative/fractional
`segmentNumber`. Empty input → `{files: [], bySegmentId: {}}` (Q8).

### 4. Export-time labels only — PASS
No IndexedDB, `chrome.*`, `DB.put`/`DB.delete`, `sendMessage`, or
`fetch` anywhere in the 6.4/6.5 sections (source scan: 0 hits).
The manifest is never written — readonly rule holds.

### 6.5 non-blocking note
- **N1 (theoretical duplicate-detection defeat):** If two segments
  share an *unknown* `streamKind` (e.g. `'zzz'`) with the same
  finalized `segmentNumber`, `compareSegments` does not group them by
  kind — both unknown kinds sort to `STREAM_KINDS.length` and the
  comparator falls through to `segmentNumber`, so they can interleave
  with other unknown kinds. `nameSegmentFiles`'s `currentKind` reset
  then clears `usedNumbers` between them, the duplicate is *not*
  detected, and both receive the same filename (`zzz-001.webm`
  twice) — a ZIP collision. **This is unreachable in practice:**
  `chunk_writer.js`'s `requireStreamKind` strictly rejects unknown
  kinds at intake, and the finalizer clones `streamKind` from those
  validated templates — no manifest record can carry an unknown kind
  through legitimate write paths. The contract's validation (§3.1:
  "non-empty string") technically permits such input, so this is a
  contract-level gap, not a practical defect. **Recommended fix
  (mechanical, for a future task):** add a kind-name tiebreaker in
  `compareSegments` for unknown kinds, or group explicitly by kind in
  `nameSegmentFiles`. Not a reject.
