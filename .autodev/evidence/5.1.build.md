# 5.1 build evidence — Compact Start/Stop control and recording/saving health indicator

## What was built

Implemented PLAN.md §5.1 ("Add a compact Start/Stop control and
recording/saving health indicator") on branch
`autodev/logging-instrumentation`, per `.autodev/evidence/5.1.contract.md`
(11 ACs: AC1–AC7 V1, AC8–AC10 V2, AC11 V3-deferred to §7).

- **`session_controls.js` (new)** — BlindfoldSession-convention module.
  `classifyStreamStatus(status, startResult)` is pure: 4.14 lifecycle ×
  adverse facts → the closed 7-state set (off-idle, failed-not-started,
  recording-healthy, recording-degraded, stopped-finalizing, finalized,
  unknown). No smoothed 'error' state — the chunk-stalled-with-
  recorderState-'recording' masquerade case stays recording-degraded
  (amber), never green; `detail` carries raw fact strings as the
  tooltip. `installSessionControls(options)` renders the compact
  Start/Stop button + three per-stream lights anchored adjacent to the
  extension's move input (fixed-corner fallback, 2.8 precedent), wires
  the Start/Stop sequences, polls `recorder-get-status` only while a
  session is live (2 s default, injectable), re-renders only on
  state/detail change, and never throws into page code (3.2 SF-1).
- **Start**: local interlock → mint UUID-v4 IDs (session_identity.js,
  added to the manifest content_scripts list) → `recorder-ensure`
  (new SW-side message; only the SW can create offscreen documents) →
  `recorder-set-session` → `recorder-start-streams` (per-stream
  failures do not abort Start — 4.6 isolation, with the abort rule
  refined, see Deviations) → set `activeSessionId`/`activeGameId` +
  `emitPageStart` (2.7 seam) + status polling. `resetEnded()` re-arms
  per-source idempotency for the new game.
- **Stop**: `recordStopTermination(reason, result)` via the 3.5.4 seam
  (null reason unless a `game_ended` was observed — served by the new
  additive `getLastObservedEnd()` getter) → `recorder-stop-streams`
  (transitional "Stopping…", button stays enabled for retry) → the
  FULL stop response, including per-stream `flushTimedOut`, handed
  untouched to the 5.10 seam (`onStopComplete` option +
  `handle.getLastStopResponse()`; content.js forwards to
  `BlindfoldSession.onSessionStopComplete` when present) → slots
  cleared. Stop-channel failure never silently reverts to idle.
- **Boot adoption** (4.1 refresh survival): one `recorder-get-status`
  at install; `{ok:true, sessionId}` adopts (gameId via the new
  additive echo on the get-status response — open question #2), no new
  IDs minted; `{ok:false}` → idle.
- **Additive seams**: `recorder.js` captures `ownerTabId` from
  `sender.tab.id` at set-session (5.5's guard seam; cleared with the
  session) and echoes `gameId` in the get-status response;
  `recording_host.js` handles `recorder-ensure` → the existing
  idempotent `ensureRecordingContext()`; `chess_utils.js` gains the
  read-only `getLastObservedEnd()` getter (documented AC7 deviation);
  `overlay.css` gains additive classes; `manifest.json` gains
  `session_identity.js` + `session_controls.js` in the content_scripts
  list; `content.js` gains the install block only.
- **Channel vocabulary**: exactly one new message, `recorder-ensure`,
  SW-side (SW-side recorder-envelope vocabulary 5→6, pinned). No new
  offscreen-document messages — offscreen MSG_* stays at 24. No new
  event types.
- **`.autodev/DECISIONS.md`** — `## 5.1` section.

## Open questions (contract §9) — closed

1. **Session-metadata persistence path**: there is no SW-side session
   intake message, content scripts cannot reach extension IDB, and
   `createSessionMetadata` requires a category in
   {baseline,training,evaluation} (no 'unknown' exists — fabricating
   one would violate 1.2.3). So 5.1 does NOT write `session_metadata`
   and invents no new storage API; session start is recorded through
   the existing sender event stream (`emitPageStart`, the 2.7 seam).
   The metadata record (with category) is 5.2's.
2. **GameId adoption on boot**: the recorder now echoes `gameId`
   (additive, null when unset) in the `recorder-get-status` response;
   absent → null (honest unknown; instrumentation gates on non-empty
   gameId).
3. **5.10 seam shape**: `onStopComplete(stopResponse)` callback option
   (default no-op, throwing-safe) + `handle.getLastStopResponse()`.
   The full stop response object is passed through untouched.

## Deviations (all deliberate, contract intent preserved)

1. **Start-abort rule refined** (contract §3.3.5/AC4). The contract's
   parenthetical "({ok:false} at top level)" is imprecise against 4.6's
   actual contract: `startStreams()` returns top-level ok =
   all-three-ok, so a failed screen yields top-level `{ok:false}`
   WITH per-stream results. 5.1 aborts Start only when the response
   has no `streams` object (the guard rejections: no-session,
   start-in-progress, already-started, internal-error) or no response
   at all. Per-stream results → the session is active; the lights show
   the truth. V2 proved the refined rule end to end: screen failed
   (no-capture-mode), mic+webcam recording, session active, screen
   light `failed-not-started` — the anti-masquerade case working.
2. **`chess_utils.js` additive getter** (`getLastObservedEnd`) — not in
   the contract's §5 changed-file list. Required by contract §3.4
   ("null reason unless a game_ended was already observed"); the
   observed ending is recorder state, so the getter lives on
   `createGameLifecycleRecorder`. Read-only (set only for the observed
   sources `chess_rules`/`chesscom_dialog`, never manual `stop`),
   re-armed by `resetEnded()`. Pinned in AC7; ~30 earlier suites' pins
   evolved with justification comments.
3. **`classifyStreamStatus` takes an optional second parameter**
   (`startResult`). The contract's §4 table names "start-failure
   detail" as an adverse fact, but the 4.14 status shape carries no
   start-failure detail for never-started streams (no recorder error,
   discontinuity, or tracks exist). The control's own observed
   start-streams result feeds the classifier, so a denied screen reads
   `failed-not-started` (`start-failed:<error>`) instead of
   masquerading as `off-idle`. On boot adoption there is no observed
   start → honestly `off-idle`. V2 proved it against the real
   no-capture-mode failure.
4. **`flushTimedOut` is per-stream, not top-level**, in the real 4.13
   stop response (set only on the kinds that timed out). 5.1 hands the
   untouched response object to the 5.10 seam — V2 proves
   `JSON.stringify(seamArg) === JSON.stringify(rawChannelResponse)`,
   so nothing (including a future per-stream `flushTimedOut`) can be
   dropped. The V1 fixture was adjusted to the faithful shape.
5. **V2 harness origin routing.** A context never receives its own
   sent `chrome.runtime` messages, so the harness sends
   `recorder-ensure` from the offscreen document (the SW answers) and
   the other recorder messages from the SW worker (the offscreen
   answers) — the per-message responding side matches production
   exactly. Documented in the harness header.
6. **Test-only observation**: non-UUID session/game IDs break 4.6's
   manifest write (TypeError) — uuid-v4 (1.1.1/1.1.2) is required, as
   specified. The harness stubs the minters with valid UUIDs.
