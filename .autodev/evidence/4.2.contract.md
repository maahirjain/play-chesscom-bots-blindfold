# Task 4.2 contract — microphone selection and permission handling

PLAN.md §4.2: "Add microphone selection and permission handling."

Status: CONTRACT ONLY. No implementation code written. PLAN.md unmodified.
STATE.json untouched (coordinator-owned).

## 1. Scope boundary — what 4.2 is and is not

**4.2 delivers a selected, permitted microphone — not a recording.**
Concretely: device enumeration, user selection among microphones, a
persisted selection, a permission-probe flow (`getUserMedia` → stop tracks
immediately), queryable permission state, and durable events for
selection/permission changes. 4.2 ends with **no open microphone stream**:
every probe stream's tracks are stopped before `requestPermission`
resolves. 4.6 ("Start separate microphone, screen, and webcam recording
streams") re-acquires the stream at Start and owns stream lifetime; the
permission-revoked-between-4.2-and-4.6 race is 4.6's failure case to
handle, documented here as a known seam.

**Precedent for 4.3/4.4.** 4.2's `device_selection.js` factory covers the
`audioinput`/`videoinput` enumerate-and-persist pattern, which 4.4
(webcam) reuses directly. 4.3 (screen/tab capture) diverges: `getDisplayMedia`
has no stable deviceId to persist (the picker is per-call), so 4.3 gets its
own design; 4.2 must not build screen-specific machinery.

**Not 4.2:**
- No UI of any kind. §5 owns all user-facing controls: 5.1 (Start/Stop),
  5.3 (remember previous selections — 4.2 provides the persisted value it
  reads), 5.4 (manual completion), 5.6 (readiness display). 4.2 exposes a
  message-channel API; §5's UI drives it.
- No `MediaRecorder`, no chunk writing (4.5/4.6/4.8), no track
  mute/end/error monitoring (4.9), no per-stream status UI (4.14 — but 4.2
  provides the queryable state 4.14 reads; the seam is specified in §5).
- No manifest permission changes. Chrome requires no manifest permission
  for `getUserMedia` audio in extensions; the runtime prompt is the
  permission. (4.3 may differ; its planner decides.)
- No changes to the 1.2 session-conditions schema (microphone selection is
  not one of the seven game-condition fields).

## 2. Architecture

### Where the code lives

All microphone platform APIs (`navigator.mediaDevices.enumerateDevices`,
`getUserMedia`) live **only in the offscreen recorder context** (4.1's
rule: recording platform APIs never in content scripts, never in the SW).
New module:

- `device_selection.js` — classic script, house convention
  (dependency-free → guarded `BlindfoldSession` global → IIFE
  `'use strict'` → Node `module.exports` shim). Exports
  `createDeviceSelector(opts)` with injected `mediaDevices`,
  `storage` (chrome.storage.local-shaped), `emitEvent`, and clock.
  `kind: 'audioinput'` for 4.2; 4.4 instantiates `kind: 'videoinput'`.
- `recorder.js` — instantiates the microphone selector and routes the new
  recorder-channel messages to it. `recorder.html` loads
  `device_selection.js` before `recorder.js`.
- `recording_host.js` (SW side) — **no new behavior in 4.2.** It does not
  auto-select or auto-request; there is no 4.2 policy for the supervisor
  to enforce. §5 drives selection through the channel.

### Who initiates

Nobody in 4.2 initiates autonomously. The selector is purely reactive:
§5's future UI (or a test harness) sends channel messages; the recorder
answers. This keeps 4.2 free of UX policy and matches the 4.1 precedent
(the channel exists; tasks add commands).

### Message channel additions

On 4.1's envelope `{ kind: 'recorder', msg, v: 1, ... }`, SW/§5 → recorder:

| msg | Request fields | Response |
|---|---|---|
| `mic-list-devices` | — | `{ ok, devices: [{ deviceId, label, kind:'audioinput' }] }`. Labels are `null` until permission has been granted at least once (Chrome withholds labels pre-permission) — honest null, never fabricated. |
| `mic-select` | `{ deviceId }` | `{ ok, selection }` or `{ ok:false, error }`. Unknown deviceId → `RangeError` surfaced as `{ ok:false, error:'unknown-device' }`; never throws across the channel. Persists the selection and emits `microphone_device_selected`. |
| `mic-request-permission` | — | `{ ok:true, permissionState:'granted' }` or `{ ok:false, permissionState, errorName }`. Emits `microphone_permission_changed`. Probe tracks are always stopped before responding. |
| `mic-get-state` | — | `{ ok, selection, permissionState, devicesEnumeratedAt }`. The queryable state 4.14 and 5.6 read. |
| `recorder-set-session` | `{ sessionId, gameId }` | `{ ok }`. Gives the recorder the active session so the events 4.2 emits are session-scoped through the writer intake. §5 drives it at Start/Stop; until set, 4.2's events are **inert** (the 2.x/3.x pre-§5 precedent — no session, no emission). Clearing (both null) re-arms inertness. |

Unknown `msg` values keep 4.1's behavior: ignored, never throw.

### Permission flow

1. **Advisory query.** `navigator.permissions.query({ name:'microphone' })`
   is a non-invasive check. Chrome extension quirk (documented, not
   solved): the query result is advisory; the `getUserMedia` outcome is
   ground truth. The selector records which source produced each state.
2. **Probe request.** `mic-request-permission` calls
   `getUserMedia({ audio: <constraints> })` where constraints use
   `{ deviceId: { exact: <selection> } }` when a selection exists, else
   `true` (system default). On success: state `'granted'`, **stop every
   track immediately**, emit the event, respond. On failure: map the
   error name — `NotAllowedError`/`SecurityError` → `'denied'`;
   `NotFoundError`/`OverconstrainedError` → selection is stale (clear it
   to null, emit `microphone_device_selected` with `source:'invalidated'`);
   anything else → `'unknown'` with the raw `errorName` preserved on the
   event (4.9 owns error logging; 4.2 records the outcome honestly).
   The response is always data (`{ ok:false, ... }`), never a throw.
3. **Denial is a state, not an exception.** `'denied'` persists as the
   queryable permission state until a later probe succeeds. 7.11's
   "permission denial produces explicit incomplete status" reads this
   state; 4.2 does not invent recovery UX (that's §5/§7 territory).

### Selection state and persistence

- `selection`: a `deviceId` string or `null`. Starts `null` on every
  recorder boot.
- **Restore on boot:** read `storage.local['blindfold.micDeviceId.v1']`.
  If the stored id appears in a fresh enumeration → selection restored,
  emit `microphone_device_selected` with `source:'restored'`. If absent
  from enumeration → selection stays `null`; no fabricated default, no
  event (absence of selection is the honest state). The `mic-select`
  path with an explicit id uses `source:'user'`.
- **Defaulting is 4.6/§5's decision**, not 4.2's: if no selection exists
  at Start, the Start flow may select the system default and that is
  recorded then with `source:'default'`. 4.2 never silently defaults.
- **Permission state is never persisted.** The user can revoke in browser
  UI at any time; 4.2 re-derives it per query/probe. (This is also why
  5.3 "remember previous selections" covers device selection only.)

### Events (4.2-owned event types)

Task-owned types per the repo convention (event_envelope.js untouched):

- `microphone_permission_changed`
  `{ permissionState: 'granted'|'denied'|'prompt'|'unknown', source: 'query'|'request', errorName: string|null }`
  `'prompt'` is recorded when a query returns it; it is a state
  observation, not a user-facing prompt.
- `microphone_device_selected`
  `{ deviceId: string|null, label: string|null, source: 'user'|'restored'|'default'|'invalidated' }`

Both use exact-keys payload validators (house convention). They travel
the **existing writer intake** (`{kind:'event', ...}` direct from the
offscreen document, per 4.1 §3) — no relay, no new pipeline. Session
scoping comes from `recorder-set-session`; pre-session inertness follows
the 3.x precedent.

### Failure isolation

Every channel handler is failure-isolated (3.2 SF-1 precedent): a throwing
selector never breaks the recorder's message listener and never drops a
liveness pong. `getUserMedia` absence (very old Chrome) is the plain-
`Error` unavailable-capability convention.

## 3. Testability

- **V1 (Node):** inject a fake `mediaDevices` (`enumerateDevices`,
  `getUserMedia` with scripted outcomes, track-stop spies), a fake
  storage, and an `emitEvent` spy. All AC1–AC8 are DOM-free.
- **V2 (real headless Chrome 154):** launch with
  `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` so
  enumeration yields fake audio inputs and the permission auto-grants.
  **Denial path:** `--use-fake-ui-for-media-stream` cannot produce a
  denial, so V2 drives denial via CDP `Browser.setPermission` (or
  `grantPermissions`/`resetPermissions`) for origin
  `chrome-extension://<id>` → `microphone: denied`, then
  `mic-request-permission` must return `NotAllowedError` →
  `'denied'` and the event must land in IDB through the writer intake.
  (If CDP permission control proves unavailable for the extension
  origin, the denial path is V1-only and the limitation is documented —
  no fabricated green.)
- **/tmp hygiene:** the 2.x/3.x precedent — pass the repo path to every
  harness; clean stale profiles on tmpfs pressure.

## 4. Acceptance criteria

- AC1 (V1): `device_selection.js` loads in Node via the shim;
  `createDeviceSelector({ kind:'audioinput', ... })` constructs with
  injected fakes.
- AC2 (V1): `mic-list-devices` maps enumeration to
  `[{ deviceId, label, kind }]`; labels are `null` when the fake reports
  empty labels (pre-permission honesty), real strings post-grant.
- AC3 (V1): `mic-select` with an unknown deviceId returns
  `{ ok:false, error:'unknown-device' }` (RangeError internally, never
  thrown across the channel); a known id persists to storage and emits
  `microphone_device_selected` with `source:'user'`.
- AC4 (V1): `mic-request-permission` success → `'granted'`; every probe
  track's `stop()` was called (spy); no stream is retained by the
  selector afterwards.
- AC5 (V1): scripted `NotAllowedError` → `{ ok:false,
  permissionState:'denied', errorName:'NotAllowedError' }` and a
  `microphone_permission_changed` event carrying the raw error name.
- AC6 (V1): boot with a stored deviceId present in enumeration →
  `source:'restored'`; stored id absent → selection `null`, no event, no
  silent default.
- AC7 (V1): recorder channel routes the five new messages with envelope
  validation; unknown `msg` still ignored (4.1 behavior preserved).
- AC8 (V1): changed files only: `device_selection.js`, `recorder.js`,
  `recorder.html` (script tag), tests, evidence, DECISIONS.md entry. No
  manifest changes. Content scripts byte-identical (media-API pins stay
  green). No `MediaRecorder` token in product code (4.6 owns it).
- AC9 (V2): real headless Chrome with fake media devices: list shows
  ≥1 `audioinput`; select + request-permission → granted; tracks stopped
  (no live mic retained — assert via `stream.getTracks()` state or the
  document's retained-stream count).
- AC10 (V2): CDP-denied microphone → `mic-request-permission` returns
  denied; the `microphone_permission_changed` event is present in
  extension IDB via the writer intake (append-sequence gapless).
- AC11 (V2): killing and recreating the offscreen document restores the
  persisted selection (`source:'restored'`) without user action.
- AC12 (V3, deferred to §7/owner device): real microphone on the owner's
  machine — enumeration shows true labels after grant; selection survives
  a browser restart; denying via the browser permission UI yields the
  explicit `'denied'` state (7.8/7.11).

## 5. Non-goals

- No UI (5.1/5.3/5.4/5.6 own it).
- No retained streams, no `MediaRecorder`, no chunks (4.5/4.6/4.8).
- No webcam/screen logic (4.3/4.4), no track monitoring (4.9), no
  per-stream status UI (4.14).
- No manifest changes; no `minimum_chrome_version` change.
- No new event pipeline; the writer intake is reused as-is.
- `recorder-set-session` is the only session-scoping addition, and it is
  the minimal seam §5 needs — §5 owns when it is sent.

## 6. Known seams and honest limitations

1. **Probe-then-start race:** permission granted at 4.2-probe time can be
   revoked before 4.6 starts the stream. 4.6 must treat stream-start
   failure as its own case; 4.2's state is advisory after the probe.
2. **Label availability:** device labels are empty until permission is
   granted (Chrome privacy). Any UI showing device names pre-grant must
   show an honest placeholder — §5's problem, flagged here.
3. **`deviceId: { exact }` staleness:** a stored id can go stale
   (unplugged mic). The `OverconstrainedError` → `'invalidated'` path
   handles it; enumeration should be refreshed before Start (§5/4.6).
4. **GroupId:** not recorded. `groupId` is empty pre-permission and adds
   no analytic value for the mission; omitted deliberately (no
   derivable-value persistence).
5. **One selector per kind:** the factory is instantiated once per kind
   in the recorder; concurrent `mic-request-permission` calls serialize
   on a guard (second call gets the in-flight result or
   `{ ok:false, error:'busy' }` — builder's choice, documented).
