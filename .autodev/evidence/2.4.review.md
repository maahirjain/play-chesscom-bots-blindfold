### SF-2: Module header misattributes the listener handle to "2.6 restart handling"

`writer.js` (`installWriterListener` doc comment) and the build report
justify returning the listener as "(removal in tests; 2.6 restart
handling)". The 2.6 half is factually wrong: an MV3 service-worker
restart destroys the entire JS context; `sw.js` re-executes
`importScripts` + `installWriterListener()` from scratch. There is no
listener to remove on restart, so the handle serves no 2.6 purpose.
Left as-is, this will mislead the 2.6 planner into designing around
listener removal.

Fix (doc-only, no re-review needed): correct the justification to
test-lifecycle management only, and add the guardrail explicitly —
production code must never remove the writer's listener; the handle
exists so tests can construct a genuine no-ack state. Suggested
wording for the `installWriterListener` comment:

```js
// Returns the listener so tests can manage its lifecycle (a genuine
// no-ack state requires removing the writer's listener; see 2.3 AC9).
// Production code must never remove this listener — the writer is the
// sole ack source in the SW. (SW restart needs no removal: restart
// recreates the context and re-installs from scratch.)
```

The same correction applies to `sw.js`'s "The handle lets tests (and
later, 2.6 restart logic) manage the listener lifecycle explicitly."
comment.

## NOTEs

### NOTE-1: The listener handle itself is acceptable

Returning the listener is a small, pragmatic API addition with a real
testing justification: 2.3's AC9 needs a genuine no-ack state, which
is unreachable once the real writer is installed unless the writer's
listener is removable. The integrated test then verifies a meaningful
property — that the writer is the *sole* ack source in the SW (no
other listener would ack these messages). The footgun (deliberate
removal breaking durability) requires action by mission code in the SW
context, where only mission code runs. Acceptable with the SF-2
guardrail.

### NOTE-2: No-lock concurrency argument is sound

The read-modify-write (dedup get → counter get → event put → counter
put) happens inside a single `readwrite` transaction over exactly
`['events', 'sequence_state']`. IndexedDB serializes overlapping
readwrite transactions, and the scopes are identical, so no two
writers can interleave the counter read-modify-write. Code inspection
confirms no non-IDB promises are awaited in the transaction body
(callbacks only) — the auto-commit hazard the contract warns about
cannot trigger. V2 AC13 (4 pages × 6 events → gapless 0..23) is
genuinely concurrent: each page's sender is stop-and-wait, but the
four streams interleave at the SW, which is exactly the contention
the argument must survive.

Binding conditions for the future (already recorded in the module
header): the writer must remain the sole writer of `events` and
`sequence_state`. If 2.6 or §6 ever writes `sequence_state`, the
argument collapses — the 2.6 contract must re-verify.

### NOTE-3: Ack-after-commit verified — no path acks {ok:true} early

Traced every path in `runWriteTransaction`: `{ok:true}` is *constructed*
for the idempotent-duplicate case inside `getReq.onsuccess`, but
`finish()` (the only `resolve`) is called exclusively from
`tx.oncomplete`/`tx.onerror`/`tx.onabort`. The sender therefore never
observes an ack before the commit/abort decision. The new-event path
keeps `ack === null` until `oncomplete` produces `{ok:true}`.
Transaction abort after a successful event put (e.g. counter put
fails) rolls back the event (atomic journal) and delivers
`{ok:false, write-failed:<name>}` — the sender is told the truth,
keeps the event queued, and 2.5's retry re-enters through dedup.

### NOTE-4: Dedup semantics correct; the appendSeq exclusion is not a hole

Same-ID/same-content → idempotent `{ok:true}`, counter untouched
(verified: the duplicate path returns before the counter read).
Same-ID/different-content → `{ok:false, event-id-content-mismatch}`,
stored record never overwritten (verified: `tx.abort()` before any
put). The deep-equal excludes top-level `appendSeq` only — correct,
because a non-null `appendSeq` on intake is rejected by the
`append-seq-present` rule *before* dedup, so the exclusion applies
exactly to the null-vs-assigned-integer retry case. Nested objects
compare fully; key order is irrelevant.

### NOTE-5: Envelope-only validation boundary is faithful to 1.3 §2.8

"the writer owns that rule" in 1.3 §2.8 refers to the appendSeq
double-processing rule — which the writer implements
(`append-seq-present`). The writer additionally enforces the full
envelope shape (`requireValidEvent`: exact 11 keys, uuid IDs, snake_case
type, source context, `payload` is a plain object). Per-type payload
semantics are the emitter's job (factories validate at construction);
a writer-side registry would couple every future emitter task (§3,
§4, 2.7) to this file. A garbage payload (valid envelope, nonsense
payload) *can* be persisted — that is the emitter's bug, and
"preserve original observations" argues for storing what was
observed rather than refereeing it at the durability layer.

### NOTE-6: Hoisting fragility in runWriteTransaction (correct but fragile)

In the `tx.objectStore()` catch path, `ack` is assigned and `finish(ack)`
called *before* the `var ack = null` / `var settled = false` /
`function finish` declarations execute. This works via hoisting
(`var` → undefined; function declarations hoist fully; the `return`
prevents the later `var ack = null` from clobbering), and the
`settled` guard makes the later `tx.onabort` a no-op. Verified correct
by trace, but a future edit could easily break it. Consider moving the
three declarations above the `try { tx = ... }` block.

### NOTE-7: Counter-read defensive default could mask corruption

```js
var next = (rec && typeof rec.nextAppendSeq === 'number') ? rec.nextAppendSeq : 0;
```

On a corrupted `sequence_state` record (non-numeric counter), the
writer silently restarts at 0, which could assign duplicate or
non-integer `appendSeq` values. Unreachable through the writer's own
API (sole writer always writes integers), so this is defense-in-depth
speculation either way — but failing the write would be more honest
than silently renumbering. Not worth changing now; noted for 2.6's
restore design, which should treat a non-numeric counter as corruption.

### NOTE-8: Coarse transaction scope serializes all sessions

Every write takes `['events', 'sequence_state']` readwrite, so a write
for session A blocks a write for session B. Correct, but unnecessarily
coarse — per-session scopes aren't possible (the counter store is
shared). At human-rate event volume this is irrelevant; noted only so
a future throughput-motivated refactor knows the constraint is
deliberate.

### NOTE-9: Test evolutions are honest

The `sw.js`-pinning updates in `tests/db.test.js`,
`tests/manifest_sw.test.js` (exact three functional lines, with
comments tracing 2.1→2.2→2.4) preserve the invariants. The
`tests/sender.test.js` change (git-diff assertion →
occurrence-count for the content.js line) looks like a weakening in
isolation, but the lost coverage (no unrelated content.js additions)
is subsumed by `writer.test.js` AC11's git-status allowlist. Net:
no coverage lost.

### NOTE-10: V1 fake fidelity is adequate for its scope

The hand-rolled fake models per-tx journals, commit/abort, and
read-own-writes — enough for the AC9 atomicity tests to be
meaningful. It does *not* model transaction auto-commit on macrotask
await, but the writer has no awaits in the tx body (verified), so
there is nothing to catch. It does not model overlapping-transaction
serialization — explicitly documented, with V2 AC13 as the backstop.
The fake consumes the real `DB.SCHEMA`, so schema drift breaks loudly.
One gap: the fake's `open()` uses `queueMicrotask` where real IDB is
task-queued; irrelevant here since the writer never depends on that
ordering.
