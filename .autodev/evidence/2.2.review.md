## Findings

### SHOULD_FIX

**SF-1 (doc): `sw.js` header still says "It intentionally does NOTHING yet"**
(`sw.js:4-6`). That was true for the 2.1 stub; after this task's
`importScripts('db.js');` it is false and will mislead the next planner into
treating the worker as still inert. The 2.2 contract §3.2 said "remove the
2.2: line… Nothing else" and the builder obeyed literally — the contract
missed this sentence. Fix: reword the header to state that `sw.js` now loads
the 2.2 storage layer (`db.js`) and remains otherwise behaviorless pending
2.3–2.9. One-line change, no behavior impact.

### NOTEs

**NOTE-1: `withStore` resolves on request success, not on `tx.oncomplete`.**
For `put`, the outer promise settles when the put *request* succeeds, before
the transaction commits. In practice this is safe (`IDBDatabase.close()`
does not abort in-flight transactions; the V2 close/reopen check passed),
and it matches the contract's "single-store transaction" framing. But the
§2.4 transactional writer will need commit-awaiting semantics — carry this
into the 2.4 contract as an explicit requirement rather than inheriting
`withStore`'s settle-early behavior silently.

**NOTE-2: `keyRangeFor` reads `globalThis.IDBKeyRange` without the
availability guard `platformIndexedDB()` applies to `indexedDB`.** In any
real browser the two are inseparable, so this cannot fire in practice; but
the inconsistency means a hypothetical IDBKeyRange-less context would
produce a raw `TypeError` instead of the platform-unavailable plain `Error`.
Harmless; consider routing through the same guard for uniformity in a later
touch.

**NOTE-3: Async validation means argument errors are rejections, never sync
throws.** Consistent with contract §2.5 ("All async methods return
Promises") and documented in the build report; V1 tests use
`assert.rejects`. Callers must `await` to observe errors — inherent to any
promise API, not a weakening of the TypeError/RangeError conventions.

**NOTE-4: Test evolution in `tests/manifest_sw.test.js` is honest.**
AC3's "comment-only stub" → "exactly the db.js import" keeps an
exact-equality assertion on comment-stripped code lines plus the forbidden-
token list (and adds an "exactly one importScripts" check — stronger, not
weaker). AC4's git-relative "only the background block changed" → a
cumulative byte-exact manifest-head assertion; the old form was inherently
transient once 2.1 committed. The dropped "sw.js is new at HEAD" check is
replaced by `db.test.js` owning sw.js's exact code lines. No 2.1 guarantee
was weakened; the evolution is documented in the build report. Future tasks
should continue pinning cumulative invariants rather than resurrecting
git-HEAD-relative assertions.

**NOTE-5: CDP exception listener attaches after SW-target creation**
(`sw-db.js`), so an exception thrown during the earliest startup phase could
be missed — same caveat the 2.1 review noted for `sw-load.js`. The
`waitForTarget` + stderr assertions cover the gap for now; revisit when 2.3+
adds real worker code.

**NOTE-6: `getAll`'s primary-key range path is a harmless superset of the
contract's index-range description** — and it is genuinely required: §6.4's
per-segment chunk reads use the `media_chunks` compound *primary* key, not
an index. No speculative surface.

## Adversarial conclusions on the brief's questions

- **Scope creep: none.** No validation, no dedup, no appendSeq assignment,
  no retry/restore/lifecycle/status/retention, no `deleteDatabase`/`count`/
  transaction-runner. The API surface is exactly the seven contract members.
- **Schema honesty: all five stores and both indexes trace to quoted
  requirements.** `byAppendSeq` serves §6.2's "persistent append order";
  `bySessionId` serves per-session reads/export; `sequence_state` is the
  minimal durable slot §2.4/§2.6 need; the compound chunk keyPath was
  verified empirically in the real SW (prefix range returns the segment in
  order). Nothing speculative; nothing missing that 2.4 will need a breaking
  change for (dedup = get-then-put on the `eventId` keyPath; counter =
  get/put on `sequence_state`).
- **Error conventions hold on every path I probed:** validation runs before
  any platform access (V1 exercises it with `indexedDB` deleted); unknown
  store/index → `RangeError`; wrong types → `TypeError`; unavailable
  platform → plain `Error` with no silent fallback; IDB failures wrapped as
  plain `Error` carrying the DOMException name/message (`cause` attached).
- **Lazy reads verified:** `globalThis.indexedDB` (and `IDBKeyRange`) are
  read per call, never cached; module loads in Node clean.
- **`sw.js`: exactly one functional line added** (`importScripts('db.js');`
  after `'use strict';`); header correctly drops the 2.2 absent-entry and
  retains 2.3–2.9 — except SF-1's stale "does NOTHING yet" sentence.
- **Upgrade discipline:** `applySchema` guards every store/index creation;
  never deletes data (§2.9 honored). Future bumps follow the same guarded
  pattern per the contract.
- **Origin isolation:** a real platform property, not an assertion — the V2
  harness proved `indexedDB.databases()` in a localhost page context does
  not list `blindfold-experiment`. (The `about:blank` SecurityError lesson
  is correctly recorded in DECISIONS.md.)
- **§4.12:** no `receivedAt`/`chunk-arrival` field anywhere in the chunk
  shape or tests; the contract's reasoning (arrival time must not be usable
  as frame time) is honored.
