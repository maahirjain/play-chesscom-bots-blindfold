# 7.5 contract — Verify new games, takebacks, reloads, and late attachment do not create fabricated timings

**Planner:** section-7 planner subagent. **Date:** 2026-10-06.
**Scope:** PLAN.md §7.5. **Branch:** `autodev/logging-instrumentation`.
**Status:** CONTRACT ONLY. No implementation code written. PLAN.md unmodified.

## 1. What "verify" means

PLAN.md §7.5 requires demonstrating that four lifecycle disruptions never
cause the collection pipeline to **invent** occurrence times:

| Disruption | Hazard | Required behavior |
|---|---|---|
| **New game** (mid-session) | The new game's moves could inherit the old game's clock anchor or get `monotonicMs: 0` | 5.9's new gameId + `game_reset` boundary; new moves get fresh monotonic timestamps from the live clock, never copied from the old game |
| **Takeback** | The retracted move's timing could "stick" to the replacement move | The replacement move gets its own observation time; the retracted move's events are revised, not re-timestamped |
| **Reload** (page refresh mid-game) | Moves observed after re-attachment could be backdated to the reload time or forward-dated | Late-observed moves get the observation time (when the tracker saw them), honestly marked as late; never the estimated "actual" play time |
| **Late attachment** (content script loads mid-game) | The existing history could be timestamped as if just played | `history_recovered` captures the pre-existing moves with an explicit "recovered, timings unknown" marking; no per-move `monotonicMs` is invented |

"Do not create fabricated timings" is the core raw-data invariant: every
timestamp in the event stream is either a real clock reading at observation
time or an explicit null/unknown — never an estimate presented as fact.

**Gaps identified:**
1. The **four scenarios together** as an acceptance suite asserting the
   no-fabrication invariant does not exist — the unit tests cover pieces.
2. **Reload/late-attachment** timing honesty: AC8 covers "no invented times"
   generally, but 7.5 wants the specific reload scenario (tracker re-attaches,
   sees existing history, must mark timings unknown rather than stamping
   "now").
3. **New-game clock isolation**: 5.9 verified the gameId boundary; 7.5 adds
   the timing dimension (new game's moves must not reuse the old game's
   monotonic origin).

## 3. Verification plan

### V1 — static/unit (Node)

- [ ] **AC1.** New game: simulate `game_reset` mid-session; emit a move in the
  new game; assert its `monotonicMs` comes from the live clock (greater than
  the reset time), not from the old game's timeline.
- [ ] **AC2.** Takeback: `[e4, e5]` → takeback → `[e4, d5]`; assert the `d5`
  `move_confirmed` has an observation timestamp ≥ the takeback observation,
  and the retracted `e5` events are marked revised (not re-timestamped).
- [ ] **AC3.** Late attachment: tracker starts with pre-existing history
  `[e4, e5, Nf3]`; assert the emitted `history_recovered` marks move timings
  as unknown (null `monotonicMs` or explicit `recovered: true`), never
  stamped with the attachment time.
- [ ] **AC4.** No-fabrication sweep: for every event emitted in AC1–AC3,
  assert each timestamp is either a real clock reading (monotonic, ≥ session
  start) or explicit null — no zeros, no copies from other moves.

### V2 — integration (headless Chrome, optional)

- [ ] **AC5.** Page-reload simulation: load the tracker, observe moves,
  destroy and re-create the tracker (simulating content-script reload),
  assert the recovered history is marked honestly.

### V3 — deferred to owner device

- [ ] **AC6.** On the real device: refresh mid-game; confirm the recording
  continues (7.10) and the post-refresh events have honest timings.
