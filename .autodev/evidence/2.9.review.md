Reviewer: independent adversarial (did not implement). Date: 2026-10-06.
Scope reviewed: `.autodev/evidence/2.9.contract.md`, `.autodev/evidence/2.9.build.md`,
`tests/retention.test.js` (all 8 tests, every line), the DECISIONS.md §2.9 entry,

## Verdict: APPROVE_WITH_DEFECTS — 0 blockers, 1 SHOULD_FIX, 8 NOTEs

The substantive guarantee is TRUE: no deletion path exists in any code the
extension loads (verified independently, not just via the test's scan).
The defects are about the test's future-proofing, not current falsehood.

## SHOULD_FIX

### SF-1 — The AC1 scan list is hand-maintained and omits 5 extension-loaded files

`tests/retention.test.js` `PRODUCT_FILES` covers 8 files, but the extension
actually loads 13 scripts:

- manifest content_scripts js: `event_envelope.js`, `sender.js`, `lifecycle.js`,
  `status_indicator.js`, `sounds.js`, `chess.min.js`, `chess_utils.js`, `content.js`
- sw.js importScripts: `db.js`, `event_envelope.js`, `writer.js`,
  `session_identity.js`, `session_conditions.js`, `session_store.js`, `lifecycle.js`

Unscanned but loaded: `event_envelope.js`, `session_identity.js`,
`session_conditions.js`, `sounds.js`, `chess_utils.js` (+ vendored
`chess.min.js`, explicitly excluded).

**Why not a blocker:** I verified all five contain zero `indexedDB` /
`localStorage` / `sessionStorage` references — they cannot reach the
`blindfold-experiment` database at all (the §1 contract modules are pure
validation/factories; sounds/chess_utils are pre-existing gameplay code).
Among scanned files, only `db.js` and `writer.js` reference `indexedDB`.
The guarantee holds on the current tree.

**Why it must be fixed:** the test's entire purpose is completeness, and a
hand-maintained list silently goes stale — the next task that adds a script
to the manifest or `importScripts` escapes the scan with no failure.
**Recommended repair** (coordinator, mechanical): derive the scan list at
test time from `manifest.json` `content_scripts[*].js` + the `sw.js`
`importScripts(...)` argument list, minus the explicitly documented
`chess.min.js` vendored exclusion — or, minimally, add a meta-assertion
that every manifest/SW-loaded `.js` file is present in `PRODUCT_FILES`,
so a future addition fails loudly. No implementation re-review needed;
re-run `tests/retention.test.js`.

## NOTEs

### NOTE-1 — The scan is a syntactic tripwire, not a semantic proof
Evasions like `IDBObjectStore.prototype.clear.call(store)` (`.clear` not
followed by `(`) or a deletion call built via string concatenation would
pass the regexes. No such code exists today (verified by independent
survey). This review — not the scan — is the actual guarantee for the
current tree. Acceptable as defense-in-depth, but the test must not be
cited as proof against a clever adversary, only against accidental
introduction.

### NOTE-2 — Comment-strip safety verified for the current tree
The strip regex could in principle eat a deletion call if `//` appeared
inside a regex literal or non-URL string. Verified: no regex literals
containing `//` in any product file; the only `//`-in-string occurrences
are `https://` URLs, which the `[^:]` guard protects; no `eval` /
`new Function` anywhere, so a deletion call cannot hide in a string and
execute. If product code ever gains such constructs, the scan needs
revisiting.

### NOTE-3 — `delete` operator correctly excluded
The scan checks `.delete(` method calls only, not the `delete obj.prop`
operator (documented in-test). Correct: the operator cannot remove
IndexedDB records, and by design there is no in-memory record store to
delete from (2.4/2.6). Not a gap.

### NOTE-4 — No-deletion-API decision is honest
"Until deliberate deletion" is a retention guarantee, not a feature
request; PLAN mentions deletion exactly once. Defining deliberate
deletion as explicit owner/developer action outside the extension
(devtools, profile wipe) and deferring any in-extension deletion UI to a
§7/owner decision is the safe default given the mission's
data-preservation bias. If the owner later expects in-app deletion, that
is new scope, not a 2.9 defect.

### NOTE-5 — §6 export constraint is well-placed and sufficient
PLAN §6.7 ("repeatable export from retained local data") already implies
non-destructiveness; the 2.9 constraint (readonly transactions/cursors
only; never `delete`/`clear`/`deleteDatabase`; §6 tests assert identical
store record counts before/after export) makes it concrete and testable,
covering `media_chunks` via record counts. Authority chain
(2.9.contract.md §6 → DECISIONS.md) is where a §6 builder will find it.

### NOTE-6 — Pin conversions lost the removal-half precision (mild)
The three `status_indicator.test.js` conversions (manifest.json,
content.js, overlay.css) changed exact-diff pins into content-existence
pins: they no longer assert that no pre-existing lines were removed or
altered. Mitigations: `tests/lifecycle.test.js` (committed in 2.8) still
pins the full manifest js-list order AND whole-manifest
meaning-identity vs HEAD; `git diff main..HEAD -- content.js overlay.css`
shows 32 insertions / 0 deletions, so the AGENTS.md 0-deletions rule
holds in fact. Forward hardening (coordinator, out of 2.9 scope):
consider a durable automated test asserting `git diff main..HEAD` has no
`-` lines on main-origin files, instead of relying on the manual
coordinator check.

### NOTE-7 — Browser-level eviction is out of scope (correctly)
IndexedDB can be evicted by the browser under storage pressure; that is
platform behavior, not a code deletion path, and 2.8's indicator surfaces
quota failures. The 2.9 guarantee is about code behavior — correctly
scoped.

### NOTE-8 — AC5 (V2) independently confirmed
`sw-restart.js` (repo-path argv) re-run by this reviewer: **SW-RESTART
PASS**; /tmp clean afterward. Records survive full browser restart, not
just SW restart. (AC6 V3 remains deferred to §7 owner-device acceptance.)
