## 6.2 — buildEventsJsonl

### Attack 1: Ordering — genuinely by appendSeq?

**PASS.** Direct probe (P1): input deliberately out of order
`[c(appendSeq:2), a(appendSeq:0), b(appendSeq:1)]` emits lines in
`[a, b, c]` — strict `appendSeq` ascending. The implementation uses
an indirect index sort (`order.sort((a,b) => seqs[a]-seqs[b])`); since
duplicate `appendSeq` values throw (P2), the keys are unique and the
comparator is a strict total order — the output is genuinely sorted
by the persistent append sequence, not by input order, `sourceSeq`,
or `monotonicMs`.

### Attack 2: Any computed metrics added, or any position data stripped?

**PASS.** Direct probe (P4): a `move_confirmed` event with a rich
payload round-trips through `JSON.parse` to a key-identical object —
no keys added, none removed, none reordered. A `game_started` FEN
payload survives verbatim (`fen: 'KEEPME'` preserved). The code path
is `lines[i] = JSON.stringify(events[order[i]])` — pure serialization,
zero computation. "No computed metrics, no per-move position
duplication" holds as the preservation property the contract
specifies: the builder neither adds nor strips anything.

### Attack 3: Fail-closed on corrupt appendSeq?

**PASS.** All probes throw `TypeError`:
- P2: duplicate `appendSeq` → `TypeError` (never silently reordered)
- P3: `-1`, `1.5`, `null`, `"5"` → `TypeError` each
- Non-array input → `TypeError`
- Non-object element → `TypeError` naming the index

### Additional 6.2 probes

- P5: empty array → empty string (not an error). **PASS.**
- P6: same fixture serialized twice → byte-identical. **PASS**
  (required for 6.7's repeatability).

### 6.2 notes (non-blocking)

- **N1:** `JSON.stringify` drops `undefined`-valued keys and coerces
  `NaN` to `null` (probes P7/P8). This is `JSON.stringify` semantics,
  not builder logic. The 2.4 writer strictly validates envelopes at
  intake (`event_envelope.js`: `undefined` gameId throws, refs
  normalized to null, exact 11-key shape enforced), so stored events
  realistically cannot contain `undefined`/`NaN`. Theoretical only —
  not a defect, and the contract explicitly scopes the builder's
  validation to array shape + `appendSeq` integrity.

## 6.3 — buildMediaSyncJson

### Attack 1: Is mediaStartWallUtcMs the ONLY computed value? Is the formula correct? Null-honest?

**PASS.** Probe Q1: with `anchor = {utcEpochMs: 1000000,
monotonicMs: 500}` and `streamStartedAtMonotonicMs: 1000.5`, the
output is exactly `1000500.5` — the timecode.js canonical formula
`anchor.utcEpochMs + (monotonicMs - anchor.monotonicMs)`
(`timecode.js:133-139`, `wallUtcMs`) applied with the segment's start
time. The implementation matches the contract's formula
character-for-character. Not rounded (Q1 pins the `.5`).

Null-honesty verified:
- Q6: missing anchor → `clockAnchor: null`,
  `mediaStartWallUtcMs: null`, gap `missing-clock-anchor`. Never a
  fabricated anchor or offset.
- Q12: null `streamStartedAtMonotonicMs` → null offset + gap
  `missing-stream-start-time`.

The other derived fields are contract-sanctioned, not hidden
computation: `finalized` is the trivial `segmentNumber !== null`
check (contract §3 schema); `gaps` uses the fixed §4.2 vocabulary;
empty-string/unusable-number inputs normalize to `null` per the
repo's "unknown is null" discipline (the same lenient-on-input
pattern the 6.1 review accepted). The clock_anchor payload shape is
exactly `{segmentId, utcEpochMs, monotonicMs}` per `clock_link.js:6`
— the builder copies precisely those three keys, per contract §2.

### Attack 2: Known gaps — verbatim? Absent verdict honest? Deterministic ordering?

**PASS.**
- Q2: absent `stopVerdict` → `knownGaps:
  ['stop-verdict-unavailable']`, `stopVerdict: 'unknown'`. The
  `'complete'` string is never fabricated.
- Q5: warnings echoed verbatim (`.slice()` copy, byte-identical).
- Q8: kind-level `flush-timed-out` applied to every segment of that
  kind (both webcam segments got the gap; the microphone segment did
  not). (My first probe script mis-indexed because the output is
  deterministically sorted — the implementation was correct; the
  probe was wrong. Re-verified by segmentId.)
- Per-segment gap vocabulary matches contract §4.2 exactly:
  `unfinalized`, `flush-timed-out`, `stream-failed`,
  `chunks-after-finalize:<N>`, `missing-clock-anchor`,
  `missing-stream-start-time`. No invented strings.
- Q10: shuffled input → byte-identical output. The comparator
  (kind → segmentNumber nulls-last → createdAtUtc → segmentId) is
  total — `segmentId` is unique — so ordering is fully deterministic
  for 6.7's byte-identity.

### Attack 3: 'failed' verdict → Error (fail-closed)?

**PASS.**
- Q3: `{verdict: 'failed'}` → plain `Error`
  (`session-not-complete`), not `TypeError`. Correct: a real verdict
  the orchestration must refuse, not malformed input.
- Q4: `{verdict: 'bogus'}` → `TypeError`.

### Additional 6.3 probes

- Q7: `segmentNumber: null` → listed with `finalized: false` and
  the `unfinalized` gap — not omitted. **PASS.**
- Q9: `ok: false` + `flushTimedOut: true` on the same kind →
  `['stream-failed']` only (else-if). See N1 below.
- Q11: `chunksAfterFinalize: 2` → gap `chunks-after-finalize:2`
  with `chunkCount: 5` preserved. **PASS.**

### 6.3 notes (non-blocking)

- **N1:** The `ok:false`/`flushTimedOut:true` interaction (Q9) emits
  only `stream-failed`. The contract lists the two gaps as separate
  bullets without specifying their interaction; a failed stream's
  flush timeout is subsumed by the failure, so this is a reasonable
  judgment — not a defect, and not a silent loss (the session-level
  `knownGaps` still carries the verbatim warnings).
- **N2:** Duplicate `clockAnchors` for the same `segmentId` collapse
  to last-wins silently. The contract's malformed-input section does
  not cover this; anchors are unique per clock segment in practice.
  Not a defect.
- **N3:** `exportedAtUtc` (real clock) vs 6.7's byte-identity goal —
  the known tension already documented in the 6.1 review, carried
  forward to 6.7. Not a 6.3 defect.
- **N4:** `for...in` over `segmentFiles`/`chunkStats` is guarded by
  `hasOwnProperty` at both validation and lookup — inherited
  properties cannot leak in. The `seen`/`anchorsBySegment` plain
  objects use system-generated UUID keys, so prototype-key collision
  is not a realistic attack.
